# Chapter 01: Query Optimisation

SQL is declarative. You describe **what** data you want, and the database decides **how** to fetch it. The component that makes this decision is the **optimizer** (called the **planner** in PostgreSQL). Understanding how it thinks is what separates a query that runs in 5 ms from one that runs for 5 minutes.

This chapter covers the small set of concepts that explain most real-world performance problems, with examples for both **Oracle** and **PostgreSQL**.

## 1. How a Query Is Processed

```
  SQL text
     │
     ▼
┌───────────┐  Syntax check; verify tables, columns and permissions.
│  Parse    │
└─────┬─────┘
      ▼
┌───────────┐  Transform into an equivalent, simpler form
│  Rewrite  │  (merge views, unnest subqueries, remove redundant joins).
└─────┬─────┘
      ▼
┌───────────┐  Generate candidate plans, estimate the cost of each,
│ Optimise  │  choose the cheapest.
└─────┬─────┘
      ▼
┌───────────┐  Run the chosen plan and return rows.
│  Execute  │
└───────────┘
```

The central idea of this chapter:

> **The optimizer is only as good as its estimate of how many rows each step will produce.**

Most slow queries trace back to one of four causes:

| Cause | Covered in |
|-------|-----------|
| Inaccurate row estimates due to missing or stale statistics | 12, 13 |
| Query written in a way that prevents optimisation | 7 – 11 |
| Missing index | 4, 5 |
| Wrong join order or join method (usually a result of the first cause) | 6 |

## 2. Sample Schema

All examples use this schema:

```
customers (1) ───< orders (N) ───< order_items (N) >─── (1) products
```

| Table | Rows | Distribution |
|-------|------|--------------|
| `customers` | 100,000 | `country`: 80% UK, 10% FR, 10% DE |
| `orders` | 1,000,000 | `status`: 90% SHIPPED, 9% PENDING, 1% CANCELLED |
| `order_items` | ~3,000,000 | ~3 items per order |
| `products` | 10,000 | |

**PostgreSQL**

```sql
CREATE TABLE customers (
    customer_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL, email TEXT NOT NULL,
    country TEXT NOT NULL, city TEXT NOT NULL
);
CREATE TABLE orders (
    order_id     BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  BIGINT NOT NULL REFERENCES customers,
    status       TEXT NOT NULL,
    order_date   DATE NOT NULL,
    total_amount NUMERIC(12,2) NOT NULL
);

INSERT INTO customers (name, email, country, city)
SELECT 'Customer ' || g, 'c' || g || '@mail.com',
       CASE WHEN g % 10 < 8 THEN 'UK' WHEN g % 10 = 8 THEN 'FR' ELSE 'DE' END,
       CASE WHEN g % 10 < 8 THEN 'London' WHEN g % 10 = 8 THEN 'Paris' ELSE 'Berlin' END
FROM generate_series(1, 100000) g;

INSERT INTO orders (customer_id, status, order_date, total_amount)
SELECT (random() * 99999)::int + 1,
       CASE WHEN g % 100 < 90 THEN 'SHIPPED'
            WHEN g % 100 < 99 THEN 'PENDING' ELSE 'CANCELLED' END,
       DATE '2020-01-01' + (g % 2000),
       (g % 1000) + 10
FROM generate_series(1, 1000000) g;

CREATE INDEX idx_orders_customer ON orders(customer_id);
CREATE INDEX idx_orders_status   ON orders(status);
CREATE INDEX idx_orders_date     ON orders(order_date);
CREATE INDEX idx_customers_email ON customers(email);
ANALYZE;
```

**Oracle** (same structure; only the differences are shown)

```sql
-- Types: NUMBER instead of BIGINT, VARCHAR2 instead of TEXT.
-- Row generation uses CONNECT BY LEVEL instead of generate_series:
INSERT INTO orders (customer_id, status, order_date, total_amount)
SELECT TRUNC(DBMS_RANDOM.VALUE(1, 100001)),
       CASE WHEN MOD(LEVEL,100) < 90 THEN 'SHIPPED'
            WHEN MOD(LEVEL,100) < 99 THEN 'PENDING' ELSE 'CANCELLED' END,
       DATE '2020-01-01' + MOD(LEVEL, 2000),
       MOD(LEVEL, 1000) + 10
FROM dual CONNECT BY LEVEL <= 1000000;
COMMIT;

EXEC DBMS_STATS.GATHER_SCHEMA_STATS(USER);
```

`order_items` and `products` follow the same pattern.

## 3. Cost-Based Optimisation

The **Cost-Based Optimizer (CBO)** works like route planning. It lists the possible ways to execute a query, assigns each an estimated **cost**, and picks the cheapest. Both Oracle and PostgreSQL use it.

**Cost is not time.** It is an abstract unit representing I/O and CPU work, calculated from:

- table size (rows and pages/blocks),
- the estimated number of rows matching each condition,
- available indexes and their properties,
- configuration parameters describing hardware.

### A worked example (PostgreSQL)

| Parameter | Default | Meaning |
|-----------|---------|---------|
| `seq_page_cost` | 1.0 | Read one page sequentially |
| `random_page_cost` | 4.0 | Read one page at a random location |
| `cpu_tuple_cost` | 0.01 | Process one row |
| `cpu_operator_cost` | 0.0025 | Evaluate one operator |

A full scan of `orders` (1,000,000 rows, 8,334 pages) with one filter:

```
  8,334 pages × 1.0      =  8,334
+ 1,000,000 rows × 0.01  = 10,000
+ 1,000,000 ops × 0.0025 =  2,500
                           ------
                           20,834
```

This matches the plan output exactly:

```
Seq Scan on orders  (cost=0.00..20834.00 rows=10000 width=30)
  Filter: (status = 'CANCELLED')
```

On SSD storage, random reads cost almost the same as sequential ones, so many deployments lower `random_page_cost` to about `1.1`. This makes index access look more attractive to the planner.

Oracle's cost model is internal but follows the same principle. In practice you compare cost values between alternative plans rather than calculating them.

### Optimiser goal

Oracle optimises for total throughput by default (`ALL_ROWS`). The hint `FIRST_ROWS(n)` favours plans that return the first *n* rows quickly, which suits paginated screens. PostgreSQL makes the same adjustment automatically when a query has `LIMIT`, preferring plans with a low **startup cost**.

### The chain of dependency

```
Statistics ──► Row estimates ──► Cost ──► Plan choice
```

When a plan is poor, the cost formula is rarely at fault. The row estimate feeding into it almost always is.

## 4. Execution Plans

A plan is a **tree of operations**. Each node receives rows from its children, processes them, and passes the result upward.

```sql
SELECT c.name, o.total_amount
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE c.email = 'c42@mail.com';
```

```
               Nested Loop                 (3) combine
              /           \
   Index Scan              Index Scan
   customers (email)       orders (customer_id)
   (1) find customer       (2) find their orders
```

**Reading order:** start at the most deeply indented node. Data flows toward the root.

### Common operations

**Access paths**

| Operation | PostgreSQL | Oracle | Suitable when |
|-----------|-----------|--------|---------------|
| Full table scan | `Seq Scan` | `TABLE ACCESS FULL` | A large share of rows is needed, or the table is small |
| Index lookup, then table | `Index Scan` | `INDEX RANGE SCAN` + `TABLE ACCESS BY INDEX ROWID` | Few rows are needed |
| Index only, no table access | `Index Only Scan` | Index scan without table access | The index contains every required column |
| Batched index access | `Bitmap Index Scan` + `Bitmap Heap Scan` | `TABLE ACCESS BY INDEX ROWID BATCHED` | A moderate number of rows |

**Other operations**

| Operation | PostgreSQL | Oracle |
|-----------|-----------|--------|
| Joins | `Nested Loop`, `Hash Join`, `Merge Join` | `NESTED LOOPS`, `HASH JOIN`, `MERGE JOIN` |
| Sort | `Sort` | `SORT ORDER BY` |
| Aggregation | `HashAggregate`, `GroupAggregate` | `HASH GROUP BY`, `SORT GROUP BY` |
| Row limit | `Limit` | `COUNT STOPKEY` |
| Per-row subquery | `SubPlan` | `FILTER` |

### Why an index is not always faster

| Query | Matching rows | Best access path |
|-------|---------------|------------------|
| `status = 'CANCELLED'` | 1% (10,000) | Index |
| `status = 'SHIPPED'` | 90% (900,000) | Full scan |

An index lookup performs a random read for each matching row. For a large fraction of the table, one sequential pass is far cheaper:

```
Index, 1% of rows     jump . . . jump . . . jump              few reads
Index, 90% of rows    jump jump jump jump jump jump jump ...  many random reads
Full scan             ────────────────────────────────►       one sequential pass
```

The optimizer can only make this distinction if it knows the data is skewed, which is the purpose of histograms (Section 13).

## 5. EXPLAIN and EXPLAIN ANALYZE

| Plan type | Shows | Executes the query |
|-----------|-------|--------------------|
| Estimated | What the optimizer expects | No |
| Actual | What really happened: row counts, timings, I/O | Yes |

> **The most useful diagnostic habit:** compare estimated rows with actual rows at each step. A difference of 10x or more identifies the problem.

### PostgreSQL

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 42;
```

```
Index Scan using idx_orders_customer on orders
      (cost=0.42..44.61 rows=10 width=30)
      (actual time=0.021..0.045 rows=11 loops=1)
  Index Cond: (customer_id = 42)
  Buffers: shared hit=14
Planning Time: 0.110 ms
Execution Time: 0.068 ms
```

| Field | Meaning |
|-------|---------|
| `cost=0.42..44.61` | Startup cost .. total cost |
| `rows=10` (first bracket) | Estimated rows |
| `rows=11` (actual bracket) | Actual rows **per loop** |
| `loops` | Times the node executed. Total rows = rows × loops |
| `Index Cond` | Condition used to search the index |
| `Filter` | Condition applied after reading rows. Watch for `Rows Removed by Filter` |
| `Buffers: shared hit / read` | Pages found in memory / read from disk |

`EXPLAIN ANALYZE` executes the statement. For data-modifying statements, wrap it in a transaction:

```sql
BEGIN;
EXPLAIN ANALYZE DELETE FROM orders WHERE status = 'CANCELLED';
ROLLBACK;
```

### Oracle

**Estimated plan**

```sql
EXPLAIN PLAN FOR
SELECT * FROM orders WHERE customer_id = 42;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
```

```
-----------------------------------------------------------------------------------
| Id | Operation                           | Name                | Rows | Cost  |
-----------------------------------------------------------------------------------
|  0 | SELECT STATEMENT                    |                     |   10 |   13  |
|  1 |  TABLE ACCESS BY INDEX ROWID BATCHED| ORDERS              |   10 |   13  |
|* 2 |   INDEX RANGE SCAN                  | IDX_ORDERS_CUSTOMER |   10 |    3  |
-----------------------------------------------------------------------------------
Predicate Information:
   2 - access("CUSTOMER_ID"=42)
```

`access(...)` is a condition used to navigate an index. `filter(...)` is applied after rows are read.

**Actual plan**

```sql
SELECT /*+ GATHER_PLAN_STATISTICS */ *
FROM orders WHERE customer_id = 42;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));
```

```
------------------------------------------------------------------------------------------
| Id | Operation                           | Name   | Starts | E-Rows | A-Rows | Buffers |
------------------------------------------------------------------------------------------
|  0 | SELECT STATEMENT                    |        |      1 |        |     11 |      14 |
|  1 |  TABLE ACCESS BY INDEX ROWID BATCHED| ORDERS |      1 |     10 |     11 |      14 |
|* 2 |   INDEX RANGE SCAN                  | IDX_.. |      1 |     10 |     11 |       3 |
------------------------------------------------------------------------------------------
```

Compare `E-Rows × Starts` with `A-Rows`. `EXPLAIN PLAN` can differ from the plan actually used (for example with bind variables), so `DISPLAY_CURSOR` is the more reliable source.

### Diagnosing a misestimate

```
Nested Loop  (rows=5) (actual rows=480000 loops=1)
  -> Seq Scan on customers c  (rows=5) (actual rows=80000 loops=1)
        Filter: (country = 'UK')
  -> Index Scan on orders o   (rows=10) (actual rows=6 loops=80000)
```

The planner expected 5 UK customers and found 80,000. Based on that estimate it chose a nested loop, which then ran the inner index scan 80,000 times. A hash join would have been much faster. Refreshing statistics (`ANALYZE customers`) corrects the estimate, and the planner then chooses the hash join on its own.

## 6. Join Ordering and Join Methods

### Join order

The result of `(A ⋈ B) ⋈ C` equals `(B ⋈ C) ⋈ A`, but the work involved can differ by orders of magnitude. The guiding principle is to **filter early and keep intermediate results small**.

```sql
SELECT *
FROM customers c
JOIN orders o       ON o.customer_id = c.customer_id
JOIN order_items oi ON oi.order_id   = o.order_id
WHERE c.email = 'c42@mail.com';
```

```
Poor order:   orders ⋈ order_items ──► 3,000,000 rows ──► filter ──► 30 rows
Good order:   customers (1) ──► orders (10) ──► order_items (30)
```

With *N* tables there are *N!* possible orders (10 tables give 3.6 million), so optimizers search selectively:

- **PostgreSQL** searches exhaustively for small joins and switches to a genetic algorithm (GEQO) at `geqo_threshold` (default 12). It reorders explicit `JOIN`s freely up to `join_collapse_limit` (default 8).
- **Oracle** uses a bounded permutation search and reorders freely unless hints direct otherwise.

### Join methods

**Nested Loop**

```
for each row in outer:
    look up matching rows in inner (ideally via index)
```

Efficient when the outer input is small and the inner side has an index on the join key. It is the only method that supports arbitrary join conditions (`<`, `BETWEEN`, `LIKE`). It degrades badly when the outer input is large.

**Hash Join**

```
build:  load the smaller input into an in-memory hash table
probe:  stream the larger input, look up each row in the hash table
```

Efficient for large, unsorted inputs joined on equality. Requires memory (`work_mem` in PostgreSQL, PGA in Oracle) and spills to disk if the hash table does not fit. The build side should be the smaller input.

**Merge Join**

```
sort both inputs on the join key (unless already ordered)
walk through both in step
```

Efficient when both inputs are already sorted, for example by an index, or when the output must be sorted anyway.

| Situation | Preferred method |
|-----------|------------------|
| Small outer input, indexed inner join key | Nested Loop |
| Large inputs, equality join | Hash Join |
| Inputs already sorted on the join key | Merge Join |
| Non-equality join condition | Nested Loop |

### Influencing join behaviour

Wrong join orders are usually caused by wrong row estimates, so correct the statistics first. Hints are a last resort.

**Oracle**

```sql
SELECT /*+ LEADING(c o oi) USE_NL(o) USE_HASH(oi) */ ...
```

| Hint | Effect |
|------|--------|
| `LEADING(a b c)` | Join order |
| `USE_NL(t)` / `USE_HASH(t)` / `USE_MERGE(t)` | Join method for table `t` |
| `INDEX(t idx)` / `FULL(t)` | Access path |

An invalid hint is silently ignored, so always verify the resulting plan.

**PostgreSQL** has no native hints. For diagnosis, disable a method in the session to see the alternative plan:

```sql
SET enable_nestloop = off;   -- testing only
EXPLAIN ANALYZE ...;
RESET enable_nestloop;
```

`SET join_collapse_limit = 1` makes the planner keep the written join order. The `pg_hint_plan` extension provides Oracle-style hints.

## 7. Predicate Pushdown

A **predicate** is a filter condition. **Pushdown** moves it as low in the plan as possible, so fewer rows flow through joins, sorts and aggregations.

```sql
CREATE VIEW customer_totals AS
SELECT c.customer_id, c.country, SUM(o.total_amount) AS total_spent
FROM customers c JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.country;

SELECT * FROM customer_totals WHERE country = 'FR';
```

```
Without pushdown:  join + aggregate 100,000 customers ──► keep FR
With pushdown:     keep 10,000 FR customers ──► join + aggregate
```

Both databases push this filter automatically. In the plan, the condition appears on the base table scan (`Filter: (country = 'FR')` in PostgreSQL, `filter("C"."COUNTRY"='FR')` in Oracle).

Oracle can also push **join predicates** into a view, allowing indexed access per outer row (`VIEW PUSHED PREDICATE`, hints `PUSH_PRED` / `NO_PUSH_PRED`).

### What prevents pushdown

The optimizer pushes a filter only when doing so cannot change the result. These constructs commonly block it:

| Construct | Reason |
|-----------|--------|
| `LIMIT`, `FETCH FIRST`, `ROWNUM` in the subquery | Filtering before or after the limit gives different results |
| Window functions, unless the filter is on the `PARTITION BY` columns | Changes the rows each window sees |
| Filters on aggregated values | Can only be evaluated after aggregation |
| Filters on the nullable side of an outer join | Changes which rows are null-extended |
| Materialised CTEs | See Section 10 |

```sql
-- Numbers all 1,000,000 orders, then filters
SELECT * FROM (
    SELECT o.*, ROW_NUMBER() OVER (ORDER BY order_date DESC) AS rn
    FROM orders o
) t
WHERE status = 'CANCELLED' AND rn <= 10;

-- Filters first (10,000 rows), then numbers
SELECT * FROM (
    SELECT o.*, ROW_NUMBER() OVER (ORDER BY order_date DESC) AS rn
    FROM orders o
    WHERE status = 'CANCELLED'
) t
WHERE rn <= 10;
```

The two queries have different meanings, which is exactly why the optimizer cannot convert one into the other. Only the author knows which is intended.

## 8. Correlated vs Non-Correlated Subqueries

A **non-correlated** subquery is independent of the outer query and can be evaluated once:

```sql
SELECT * FROM orders
WHERE customer_id IN (SELECT customer_id FROM customers WHERE country = 'FR');
```

A **correlated** subquery references the outer query, so logically it is evaluated once per outer row:

```sql
SELECT o.*
FROM orders o
WHERE o.total_amount > (
    SELECT AVG(o2.total_amount)
    FROM orders o2
    WHERE o2.customer_id = o.customer_id      -- outer reference
);
```

| | Non-correlated | Correlated |
|---|---|---|
| References outer query | No | Yes |
| Logical evaluation | Once | Per outer row |
| Risk | Low | High if not rewritten by the optimizer |

"Per outer row" describes meaning, not necessarily execution. Optimizers usually transform correlated subqueries into joins. When they cannot, the plan shows a `SubPlan` (PostgreSQL) or `FILTER` (Oracle) node with a high `loops` or `Starts` count, which signals that a manual rewrite may help.

## 9. Subquery Optimisation

### Unnesting

**Unnesting** converts a subquery into a join, making hash joins and join reordering available.

| Written as | Transformed into | Plan (PostgreSQL / Oracle) |
|------------|------------------|----------------------------|
| `IN (subquery)` | Semi-join | `Hash Semi Join` / `HASH JOIN SEMI` |
| `EXISTS (subquery)` | Semi-join | as above |
| `NOT EXISTS (subquery)` | Anti-join | `Hash Anti Join` / `HASH JOIN ANTI` |
| `NOT IN (subquery)` | Anti-join only if NULLs are impossible | `SubPlan` / `HASH JOIN ANTI NA` |

Oracle provides the `UNNEST` and `NO_UNNEST` hints. In modern versions of both databases, `IN` and `EXISTS` usually produce identical plans, so choose whichever reads more clearly.

### The NOT IN problem

```sql
SELECT * FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM some_table);
```

If the subquery returns a single `NULL`, this query returns **no rows**, because `x <> NULL` evaluates to unknown. It also hurts performance. PostgreSQL cannot convert `NOT IN` into an anti-join and falls back to a `SubPlan`, which can be very slow when the subquery result is large. Oracle has a null-aware anti-join but the semantics still apply.

Use `NOT EXISTS`, which handles NULLs correctly and optimises well in both databases:

```sql
SELECT c.*
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
```

```
Hash Anti Join
  Hash Cond: (c.customer_id = o.customer_id)
  -> Seq Scan on customers c
  -> Hash
       -> Seq Scan on orders o
```

### Rewriting a correlated subquery

The "orders above the customer's average" query from Section 8 can be rewritten two ways.

**Join to an aggregate**

```sql
SELECT o.*
FROM orders o
JOIN (SELECT customer_id, AVG(total_amount) AS avg_amt
      FROM orders GROUP BY customer_id) a
  ON a.customer_id = o.customer_id
WHERE o.total_amount > a.avg_amt;
```

**Window function** (a single pass over the table)

```sql
SELECT * FROM (
    SELECT o.*, AVG(total_amount) OVER (PARTITION BY customer_id) AS avg_amt
    FROM orders o
) t
WHERE total_amount > avg_amt;
```

| Version | Work on `orders` |
|---------|------------------|
| Correlated, not unnested | Up to 1,000,000 index lookups |
| Join to aggregate | Two scans |
| Window function | One scan plus a sort |

### Scalar subqueries in the SELECT list

```sql
SELECT c.name,
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS order_count
FROM customers c;
```

This is acceptable for a page of 20 rows and expensive for a full report. For a report, use a join with `GROUP BY`. Oracle's scalar subquery caching helps when outer values repeat, but it should not be relied upon.

## 10. CTEs and Materialisation

A Common Table Expression (`WITH`) names a subquery to improve readability. The database executes it in one of two ways:

```
Inline:        CTE definition is merged into the main query.
               The optimizer sees everything; filters can be pushed in.

Materialise:   CTE is executed once and stored as a temporary result.
               The main query reads that result; outer filters cannot reach inside.
```

| Strategy | Beneficial when | Harmful when |
|----------|-----------------|--------------|
| Inline | Referenced once; the outer query filters heavily | Expensive and referenced many times |
| Materialise | Expensive and referenced multiple times | The outer query needs only a small part of the result |

### PostgreSQL

| Version | Behaviour |
|---------|-----------|
| 11 and earlier | Always materialised. Every CTE acts as an optimisation fence |
| 12 and later | Inlined when non-recursive, free of side effects, and referenced once. Otherwise materialised |

Version 12 added explicit control:

```sql
WITH recent AS NOT MATERIALIZED (
    SELECT * FROM orders WHERE order_date >= DATE '2025-01-01'
)
SELECT * FROM recent WHERE customer_id = 42;   -- can use idx_orders_customer

WITH recent AS MATERIALIZED (
    SELECT * FROM orders WHERE order_date >= DATE '2025-01-01'
)
SELECT * FROM recent WHERE customer_id = 42;   -- builds full set first (CTE Scan)
```

A typical problem on version 11 and earlier:

```sql
WITH all_orders AS (SELECT * FROM orders)      -- materialises 1,000,000 rows
SELECT * FROM all_orders WHERE order_id = 5;   -- then scans them
```

### Oracle

Oracle usually inlines a CTE referenced once and materialises one referenced multiple times. A materialised CTE appears in the plan as `TEMP TABLE TRANSFORMATION` with a `SYS_TEMP_...` object. The widely used (though not formally documented) hints `/*+ MATERIALIZE */` and `/*+ INLINE */` override the default.

### When materialisation helps

```sql
WITH customer_totals AS (
    SELECT customer_id, SUM(total_amount) AS spent
    FROM orders GROUP BY customer_id
)
SELECT * FROM customer_totals
WHERE spent > (SELECT AVG(spent) FROM customer_totals);
```

The CTE is referenced twice. Materialising it aggregates `orders` once instead of twice, and both databases do this by default.

## 11. Query Rewriting

### Automatic rewrites

The optimizer transforms queries into equivalent forms before costing them:

| Transformation | Example | Oracle | PostgreSQL |
|----------------|---------|:------:|:----------:|
| View merging | View definition merged into the outer query | Yes | Yes |
| Subquery unnesting | `IN` / `EXISTS` to semi-join | Yes | Yes |
| Predicate pushdown | Section 7 | Yes | Yes |
| Constant folding | `x = 2 + 3` becomes `x = 5` | Yes | Yes |
| Transitive predicates | `a.id = b.id AND a.id = 5` implies `b.id = 5` | Yes | Yes |
| Join elimination | Removes joins whose tables contribute nothing | Yes | Left joins |
| OR expansion | `a = 1 OR b = 2` as two index accesses | Yes | Via `BitmapOr` |
| Materialized view rewrite | Query on base tables answered from a summary | Yes | No |

Oracle's materialized view rewrite:

```sql
CREATE MATERIALIZED VIEW mv_sales_by_customer
ENABLE QUERY REWRITE AS
SELECT customer_id, SUM(total_amount) AS spent, COUNT(*) AS cnt
FROM orders GROUP BY customer_id;

-- References only ORDERS, but is answered from the materialized view
SELECT customer_id, SUM(total_amount) FROM orders GROUP BY customer_id;
-- Plan: MAT_VIEW REWRITE ACCESS FULL | MV_SALES_BY_CUSTOMER
```

### Manual rewrites

These rewrites resolve the majority of real-world cases.

**1. Keep indexed columns free of functions (sargable predicates)**

A predicate is *sargable* (Search ARGument ABLE) when it can use an index.

| Not sargable | Sargable alternative |
|--------------|----------------------|
| `EXTRACT(YEAR FROM order_date) = 2024` | `order_date >= DATE '2024-01-01' AND order_date < DATE '2025-01-01'` |
| `TRUNC(order_date) = DATE '2024-03-01'` (Oracle) | Range on `order_date` |
| `UPPER(email) = 'A@B.COM'` | Expression index on `UPPER(email)` |
| `total_amount * 1.2 > 120` | `total_amount > 100` |
| `name LIKE '%smith'` | `name LIKE 'smith%'` |
| `phone = 12345` on a `VARCHAR2` column (Oracle) | `phone = '12345'` |

Implicit type conversion is easy to miss. In Oracle it appears as `filter(TO_NUMBER("PHONE")=12345)`. In PostgreSQL look for casts such as `::numeric` applied to the column.

**2. Replace `NOT IN` with `NOT EXISTS`** (Section 9).

**3. Replace correlated subqueries with joins or window functions** (Section 9).

**4. Split `OR` across different columns into `UNION ALL`** when the plan shows a full scan:

```sql
SELECT * FROM orders WHERE customer_id = 42
UNION ALL
SELECT * FROM orders WHERE status = 'CANCELLED' AND customer_id <> 42;
```

**5. Select only required columns.** This allows index-only access:

```sql
CREATE INDEX idx_orders_cust_amt ON orders(customer_id, total_amount);
SELECT customer_id, total_amount FROM orders WHERE customer_id = 42;
```

PostgreSQL also supports covering indexes with `INCLUDE (column)`.

**6. Use `EXISTS` rather than `COUNT(*) > 0`.** `EXISTS` stops at the first match.

**7. Use keyset pagination instead of large offsets:**

```sql
-- Reads and discards 100,000 rows
SELECT * FROM orders ORDER BY order_id
OFFSET 100000 ROWS FETCH NEXT 20 ROWS ONLY;

-- Seeks directly to the next page
SELECT * FROM orders WHERE order_id > :last_id
ORDER BY order_id FETCH FIRST 20 ROWS ONLY;
```

**8. Prefer `UNION ALL` to `UNION`** when duplicates are impossible or acceptable. It avoids a deduplication step.

## 12. Cardinality Estimation

**Cardinality** is the number of rows a plan step produces. **Selectivity** is the fraction of rows that satisfy a condition.

```
estimated rows = input rows × selectivity
```

### Basic selectivity rules

| Predicate | Estimate without a histogram |
|-----------|------------------------------|
| `col = value` | 1 / number of distinct values |
| `col > value` | (max − value) / (max − min) |
| `col IS NULL` | Null fraction |
| `A AND B` | sel(A) × sel(B), assuming independence |
| `A OR B` | sel(A) + sel(B) − sel(A) × sel(B) |
| Unknown (function on column) | Fixed default guess |

### Failure 1: Skewed data

With three distinct values, `status = x` is estimated at 1/3 of rows for every value:

| status | Actual | Estimate | Error |
|--------|--------|----------|-------|
| SHIPPED | 900,000 | 333,333 | 2.7x low |
| PENDING | 90,000 | 333,333 | 3.7x high |
| CANCELLED | 10,000 | 333,333 | 33x high |

For `CANCELLED`, the overestimate can lead the optimizer to reject a suitable index. A histogram (Section 13) records the true frequencies and fixes the estimate.

### Failure 2: Correlated columns

```sql
SELECT * FROM customers WHERE city = 'Paris' AND country = 'FR';
```

Assuming independence gives 0.1 × 0.1 = 0.01, or 1,000 rows. In reality every Paris customer is in France, so the result is 10,000 rows, a 10x underestimate. Each additional correlated condition makes it worse.

Extended statistics tell the optimizer that the columns are related:

```sql
-- PostgreSQL 10+
CREATE STATISTICS st_country_city (dependencies, ndistinct, mcv)
    ON country, city FROM customers;
ANALYZE customers;
```

```sql
-- Oracle 11g+
SELECT DBMS_STATS.CREATE_EXTENDED_STATS(USER, 'CUSTOMERS', '(COUNTRY, CITY)') FROM dual;
EXEC DBMS_STATS.GATHER_TABLE_STATS(USER, 'CUSTOMERS');
```

### Failure 3: Expressions

For `WHERE UPPER(email) = '...'` there are no statistics on the expression, so a fixed default is used. Creating an expression index provides statistics in both databases. PostgreSQL 14+ also supports `CREATE STATISTICS` on expressions.

### Error propagation

Estimation errors multiply as they move up the plan:

```
Scan:     estimate 10     actual 1,000       (100x)
Join:     estimate 50     actual 500,000     (10,000x)
Result:   nested loop chosen for "50 rows", runs for minutes
```

Fix the **lowest** node where estimate and actual diverge. The nodes above it usually correct themselves.

### Oracle's adaptive features

| Feature | Purpose |
|---------|---------|
| Dynamic statistics | Samples data at parse time when statistics are missing or predicates are complex |
| Adaptive plans (12c+) | Switches between nested loop and hash join during execution based on actual row counts |
| Statistics feedback | Reuses actual cardinalities from previous executions |
| SQL Plan Baselines | Fixes a known good plan to prevent regressions |

PostgreSQL has no built-in equivalents and depends on accurate statistics.

## 13. Statistics and Histograms

Statistics are a compact summary of the data that the optimizer reads instead of scanning tables.

| Level | Contents |
|-------|----------|
| Table | Row count, page/block count, average row length |
| Column | Distinct values, null count, min/max, most common values, histogram |
| Index | Depth, leaf blocks, distinct keys, clustering factor (Oracle) or correlation (PostgreSQL) |

Stale statistics, for example collected before a large data load, are among the most common causes of sudden plan regressions.

### Gathering statistics

**PostgreSQL**

```sql
ANALYZE orders;
ANALYZE orders (status);

-- Check freshness
SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables WHERE relname = 'orders';
```

Autovacuum analyzes a table after roughly 10% of its rows change (`autovacuum_analyze_scale_factor = 0.1`). For large tables this can be too infrequent:

```sql
ALTER TABLE orders SET (autovacuum_analyze_scale_factor = 0.02);
```

Run `ANALYZE` manually after bulk loads, and always on temporary tables, which autovacuum does not process.

**Oracle**

```sql
BEGIN
  DBMS_STATS.GATHER_TABLE_STATS(
      ownname          => USER,
      tabname          => 'ORDERS',
      estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,
      method_opt       => 'FOR ALL COLUMNS SIZE AUTO',
      cascade          => TRUE);
END;
/

SELECT table_name, num_rows, last_analyzed, stale_stats
FROM user_tab_statistics WHERE table_name = 'ORDERS';
```

An automatic job refreshes stale statistics (more than 10% of rows changed) during the nightly maintenance window.

### Histograms

Without a histogram the optimizer assumes a uniform distribution. A histogram describes the real one.

```
Assumed (uniform)                    Actual (histogram)

SHIPPED    ██████████                SHIPPED    ██████████████████████████████
PENDING    ██████████                PENDING    ███
CANCELLED  ██████████                CANCELLED  ▌
```

**PostgreSQL** stores, per column:

- a **most common values** list with frequencies,
- **histogram bounds** for the remaining values, in equal-population buckets.

```sql
SELECT attname, null_frac, n_distinct,
       most_common_vals, most_common_freqs, histogram_bounds, correlation
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';
```

| Field | Value for `status` |
|-------|--------------------|
| `n_distinct` | 3 |
| `most_common_vals` | `{SHIPPED,PENDING,CANCELLED}` |
| `most_common_freqs` | `{0.9,0.09,0.01}` |
| `histogram_bounds` | null (all values fit in the MCV list) |

A negative `n_distinct` is a fraction of the row count (`-1` means all values are unique). `correlation` close to ±1 means the table is physically ordered by the column, which makes index range scans cheap.

Resolution is set by `default_statistics_target` (default 100). Raise it for large, skewed columns:

```sql
ALTER TABLE orders ALTER COLUMN customer_id SET STATISTICS 1000;
ANALYZE orders;
```

**Oracle** selects a histogram type automatically with `SIZE AUTO` (default 254 buckets, maximum 2048):

| Type | Used when |
|------|-----------|
| Frequency | Distinct values ≤ buckets. Exact counts per value |
| Top-Frequency (12c+) | A few values account for nearly all rows |
| Hybrid (12c+) | Many distinct values. Equal-height buckets that also record repeat counts |
| Height-Balanced | Legacy, replaced by Hybrid |

```sql
EXEC DBMS_STATS.GATHER_TABLE_STATS(USER, 'ORDERS', method_opt => 'FOR COLUMNS STATUS SIZE 254');

SELECT column_name, num_distinct, histogram, num_buckets
FROM user_tab_col_statistics WHERE table_name = 'ORDERS';
```

With `SIZE AUTO`, Oracle creates histograms only for columns that are skewed **and** used in predicates, based on tracked column usage.

### Histograms and bind variables

```sql
SELECT * FROM orders WHERE status = :s;
```

If the plan is created for `'CANCELLED'` (index) and then reused for `'SHIPPED'` (90% of rows), performance suffers.

| | Handling |
|---|---|
| Oracle | Bind peeking plus Adaptive Cursor Sharing, which keeps separate plans for different selectivity ranges |
| PostgreSQL | Prepared statements use custom plans for the first five executions, then may switch to a generic plan. Controlled by `plan_cache_mode` |

A statement that is sometimes fast and sometimes slow with identical SQL text is a strong indicator of this behaviour.

## 14. A Systematic Approach to Slow Queries

```
1. Capture the actual plan
   PostgreSQL:  EXPLAIN (ANALYZE, BUFFERS)
   Oracle:      GATHER_PLAN_STATISTICS + DISPLAY_CURSOR('ALLSTATS LAST')
        │
        ▼
2. Locate the most expensive node (time, buffers)
        │
        ▼
3. Estimated vs actual rows differ by 10x or more?
        │
        ├── Yes ─► Stale statistics?        → gather statistics
        │          Skewed column?           → histogram / higher target
        │          Correlated columns?      → extended statistics
        │          Function on column?      → rewrite or expression index
        │
        └── No ──► continue
        │
        ▼
4. Full scan or large "Rows Removed by Filter"?    → index
        │
        ▼
5. Nested loop with very high loops / Starts?      → estimates or inner index
        │
        ▼
6. SubPlan / FILTER executing per row?             → NOT EXISTS, join, window function
        │
        ▼
7. Materialised CTE filtered by the outer query?   → inline it
        │
        ▼
8. Sort or hash spilling to disk?                  → work_mem / PGA
        │
        ▼
9. Only then: hints, pg_hint_plan, or plan baselines
```

## 15. Oracle and PostgreSQL Reference

| Task | Oracle | PostgreSQL |
|------|--------|------------|
| Estimated plan | `EXPLAIN PLAN FOR ...` + `DBMS_XPLAN.DISPLAY` | `EXPLAIN` |
| Actual plan | `GATHER_PLAN_STATISTICS` + `DISPLAY_CURSOR(..., 'ALLSTATS LAST')` | `EXPLAIN (ANALYZE, BUFFERS)` |
| Estimated / actual rows | `E-Rows` / `A-Rows` | `rows=` / `actual ... rows=` |
| Executions of a node | `Starts` | `loops` |
| Index condition / filter | `access()` / `filter()` | `Index Cond` / `Filter` |
| Gather statistics | `DBMS_STATS.GATHER_TABLE_STATS` | `ANALYZE` |
| Column statistics | `USER_TAB_COL_STATISTICS`, `USER_HISTOGRAMS` | `pg_stats` |
| Histogram resolution | `method_opt => '... SIZE n'` | `ALTER COLUMN ... SET STATISTICS n` |
| Multi-column statistics | `CREATE_EXTENDED_STATS` | `CREATE STATISTICS` |
| Join order | `LEADING`, `ORDERED` | `join_collapse_limit`, `pg_hint_plan` |
| Join method | `USE_NL`, `USE_HASH`, `USE_MERGE` | `enable_*` settings (testing only) |
| Subquery unnesting | `UNNEST`, `NO_UNNEST` | Rewrite the query |
| CTE control | `MATERIALIZE`, `INLINE` | `MATERIALIZED`, `NOT MATERIALIZED` |
| Plan stability | SQL Plan Baselines, SQL Profiles | `pg_hint_plan` |
| Sort / hash memory | `PGA_AGGREGATE_TARGET` | `work_mem` (per operation) |

## 16. Short Summary

- The optimizer chooses plans by estimated cost, and cost depends on estimated row counts. Accurate statistics come first.
- Diagnose with actual plans. The node where estimated and actual rows first diverge is usually the root cause.
- Histograms handle skewed values. Extended statistics handle correlated columns.
- Write predicates the optimizer can use: no functions on indexed columns, `NOT EXISTS` instead of `NOT IN`, and joins or window functions instead of correlated subqueries.
- CTEs are inlined or materialised depending on the database, version and number of references. Choose deliberately when it matters.
- Use hints only after statistics and query structure have been addressed.
