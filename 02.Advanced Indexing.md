# Chapter 02: Advanced Indexing

An index is a separate, sorted structure that points to table rows. It lets the database find rows without reading the whole table. A well-chosen index can turn a scan of a million rows into three or four page reads. Every index also has costs: storage, extra work on each insert, update and delete, competition for space in the buffer cache, maintenance such as rebuilds and statistics, and more plans for the optimizer to consider. A poorly chosen index pays these costs and may never be used.

This chapter covers how indexes work, the index types available in **Oracle** and **PostgreSQL**, how to design them, and how to maintain them. It assumes you can read execution plans (Chapter 01, Section 5).

## 2. B-tree Indexes

The B-tree (balanced tree) is the default index type in both databases. A plain `CREATE INDEX` builds one.

```sql
CREATE INDEX idx_orders_customer ON orders (customer_id);
```

### Structure

```
Root                            [ 40 | 80 ]
                               /     |     \
                 ┌────────────┘      │      └────────────┐
                 ▼                   ▼                   ▼
Branch       [ 10 | 25 ]         [ 50 | 65 ]         [ 90 | 120 ]
             /    |    \         /    |    \         /    |    \
            ▼     ▼     ▼       ▼     ▼     ▼       ▼     ▼     ▼
Leaf      [1-9][10-24][25-39][40-49][50-64][65-79][80-89][90-119][120+]
            ◄──────────── leaves linked in key order ────────────►

Leaf entry = key + row pointer   (ROWID in Oracle, TID in PostgreSQL)
```

- **Root and branch blocks** hold separator keys that guide the search down the tree.
- **Leaf blocks** hold every key in sorted order and are linked to their neighbours.
- Every leaf is the same distance from the root, which is what *balanced* means.

One block holds hundreds of keys, so the tree stays shallow. An index on 1,000,000 rows is usually 3 levels deep, so finding any key takes about 3 block reads. Oracle reports the number of levels above the leaves as `BLEVEL` in `USER_INDEXES`.

### What a B-tree can do

| Operation | Example | How the tree is used |
|-----------|---------|----------------------|
| Equality | `customer_id = 42` | Descend to one leaf |
| Range | `order_date BETWEEN :a AND :b` | Descend to the start, then walk right along the leaves |
| Prefix match | `email LIKE 'c42%'` | Treated as a range |
| Ordering | `ORDER BY order_date` | Read leaves in order, so no sort is needed |
| Min / max | `MAX(order_date)` | Read only the last leaf |

### Two differences to remember

**NULLs.** Oracle does not store an index entry when **every** indexed column is NULL. PostgreSQL stores NULLs like any other value.

| Consequence | Oracle | PostgreSQL |
|-------------|--------|------------|
| `WHERE col IS NULL` on a single-column index | Cannot use the index | Can use the index |
| `COUNT(*)` answered from an index | Only if an indexed column is `NOT NULL` | Yes |
| Composite unique keys with NULLs | See Section 9 | See Section 9 |
| Excluding rows from an index on purpose | Used to build partial indexes (Section 11) | Not needed; has `WHERE` |

**`LIKE 'prefix%'`.** Oracle uses a normal B-tree. PostgreSQL uses it only under the `C` collation, or when the index is built with `text_pattern_ops`:

```sql
-- PostgreSQL
CREATE INDEX idx_customers_email_pat ON customers (email text_pattern_ops);
```

## 3. Hash Indexes

A hash index runs each key through a hash function and stores the entry in the resulting bucket.

```
B-tree: keys kept in order              Hash: keys scattered by hash value

  a@x.com                                 bucket 0: m@x.com
  b@x.com                                 bucket 1: a@x.com, z@x.com
  c@x.com    ◄─ range a..c is             bucket 2: c@x.com
  ...           one contiguous walk       bucket 3: b@x.com
                                             ◄─ range a..c is spread everywhere
```

Hashing destroys order, so a hash index supports **equality only**: no ranges, no sorting, no prefix matching.

### PostgreSQL

```sql
CREATE INDEX idx_customers_email_hash ON customers USING hash (email);
```

| Property | Detail |
|----------|--------|
| Operators | `=` only |
| Crash-safe | From version 10. Earlier versions were not WAL-logged |
| Unique or multi-column | Not supported |
| Size | Stores a 4-byte hash code rather than the key, so it can be smaller than a B-tree on long values |

For equality lookups a B-tree is usually just as fast and far more flexible. A hash index is a reasonable choice only for long values that are looked up by equality alone, such as URLs or tokens, and only after measuring.

### Oracle

Oracle has no hash index. Two features come close:

- **Hash clusters** store rows at a location computed from the key. They suit static lookup tables accessed only by equality.
- **Hash-partitioned global indexes** spread a normal B-tree over several partitions. This reduces contention when many sessions insert increasing keys, such as sequence values, into the same leaf block.

## 4. Index Selectivity

Selectivity tells you how much a condition narrows the result.

```
column selectivity    = distinct values / total rows       1.0 means every value is unique
predicate selectivity = matching rows / total rows         smaller is better for an index
```

| Column in `orders` | Distinct values | Rows per value | Suitable for an index |
|--------------------|-----------------|----------------|-----------------------|
| `order_id` | 1,000,000 | 1 | Yes |
| `customer_id` | ~100,000 | ~10 | Yes |
| `order_date` | 2,000 | ~500 | For narrow ranges |
| `status` | 3 | ~333,000 on average | Only for rare values |

The average hides skew. Chapter 01 (Sections 12 and 13) explains how histograms let the optimizer tell a rare value from a common one.

### The break-even point

An index scan pays one random read per matching row. A full scan pays a fixed price to read the table once. As the fraction of rows grows, the index eventually costs more:

```
cost
  │                                  index scan
  │                               ╱
  │                            ╱
  │                         ╱
  │  ───────────────────── ✕ ──────────────────  full table scan
  │                    ╱   │
  │                 ╱      │
  │              ╱         break-even point
  │           ╱            (often somewhere between 2% and 20% of rows)
  │        ╱
  └─────────────────────────────────────────────  fraction of rows returned
  0%                                          100%
```

Where the break-even point falls depends mostly on how well the table's physical order matches the index order (Section 13). The better the match, the further to the right it moves.

### Low-cardinality columns

A B-tree on a column with few distinct values rarely helps. Two alternatives exist:

- **Oracle bitmap index**: one bitmap per distinct value. Bitmaps are compact and combine quickly for `AND` and `OR`. They lock many rows per update, so use them only in read-mostly data warehouses.
- **PostgreSQL BRIN index**: stores the minimum and maximum value for each range of table pages. It is tiny and works well when the column follows insertion order, such as a creation timestamp.

## 5. Composite Indexes

A composite index covers several columns. It is sorted by the first column, then by the second within each value of the first, and so on.

```sql
CREATE INDEX idx_orders_cust_date ON orders (customer_id, order_date);
```

```
 customer_id │ order_date
─────────────┼────────────
      41     │ 2024-03-02
      41     │ 2024-07-19
      42     │ 2023-01-05  ┐
      42     │ 2024-02-11  │  all orders of customer 42,
      42     │ 2024-06-30  │  already sorted by date
      42     │ 2025-01-14  ┘
      43     │ 2022-11-20
```

### The leftmost prefix rule

The index can only be searched through its **leading columns**.

| Predicate | Efficient use of the index | Why |
|-----------|----------------------------|-----|
| `customer_id = 42` | Yes | Leading column |
| `customer_id = 42 AND order_date >= DATE '2024-01-01'` | Yes | Both columns, in order |
| `customer_id = 42 ORDER BY order_date` | Yes, and no sort step | Dates are already ordered within the customer |
| `order_date >= DATE '2024-01-01'` | No | Leading column missing |

When the leading column is missing, both databases have a fallback called a **skip scan**. It runs one small search per distinct value of the leading column. Oracle shows it as `INDEX SKIP SCAN`. PostgreSQL has supported it for B-trees since version 18. A skip scan is only efficient when the leading column has few distinct values, so do not design around it.

A composite index also makes a single-column index on its leading column redundant. `(customer_id, order_date)` already serves `WHERE customer_id = 42`.

### Column order: equality first, range last

```sql
SELECT * FROM orders
WHERE status = 'PENDING' AND order_date >= DATE '2025-01-01';
```

```
Index (status, order_date)                 Index (order_date, status)

  PENDING   2024-12-30                       2025-01-01  CANCELLED   read, discard
  PENDING   2025-01-01  ◄ start              2025-01-01  PENDING     match
  PENDING   2025-01-02    match              2025-01-01  SHIPPED     read, discard
  PENDING   ...           match              2025-01-02  CANCELLED   read, discard
  PENDING   2025-06-22  ◄ stop               2025-01-02  PENDING     match
  SHIPPED   2020-01-01                       ...         every date in range is read

  Every entry read is a match.             Most entries read are thrown away.
```

After a range condition, the columns that follow can no longer narrow the search. They can only be checked on each entry (Section 8).

Put columns that every query filters by equality first, even if another column is more selective. Selectivity decides whether an index is worth building. Query usage decides the column order.

## 6. Covering Indexes

A covering index contains every column a query needs, so the query never touches the table.

```sql
SELECT order_date, total_amount FROM orders WHERE customer_id = 42;
```

```
Index on (customer_id)
  index entry ──► row pointer ──► table page ──► order_date, total_amount
                                  one table visit per matching row

Index on (customer_id) covering order_date, total_amount
  index entry ──► order_date, total_amount
                  no table visit
```

**PostgreSQL** (version 11+) has `INCLUDE`:

```sql
CREATE INDEX idx_orders_cust_cov
    ON orders (customer_id) INCLUDE (order_date, total_amount);
```

`INCLUDE` columns are stored only in the leaf entries. They are not part of the key, so they do not change the sort order or uniqueness, and they keep the upper levels of the tree small. Use `INCLUDE` for columns that are returned but not searched or sorted.

**Oracle** has no `INCLUDE`. Add the columns to the key:

```sql
CREATE INDEX idx_orders_cust_cov
    ON orders (customer_id, order_date, total_amount);
```

Covering makes the index larger and more expensive to update. Reserve it for frequent, performance-critical queries, and avoid covering wide columns.

## 7. Index-Only Scans

An index-only scan is the plan operation that makes use of a covering index. How it appears depends on the database.

### PostgreSQL

```
Index Only Scan using idx_orders_cust_cov on orders
      (actual time=0.018..0.024 rows=11 loops=1)
  Index Cond: (customer_id = 42)
  Heap Fetches: 0
```

PostgreSQL index entries carry no information about which transactions can see a row. Before returning a value from the index, the scan checks the **visibility map**, which records which table pages contain only rows that every transaction can see.

```
for each matching index entry:
    is the table page marked all-visible?
        yes ──► return the value from the index
        no  ──► read the table page to check the row   (counted in Heap Fetches)
```

A high `Heap Fetches` count means the scan is barely better than an ordinary index scan. `VACUUM` updates the visibility map, so heavily updated tables need regular vacuuming for index-only scans to pay off.

### Oracle

Oracle keeps read consistency with undo data, so there is no visibility check. A covered query simply has no table access step:

```
| Id | Operation         | Name                |
|  0 | SELECT STATEMENT  |                     |
|* 1 |  INDEX RANGE SCAN | IDX_ORDERS_CUST_COV |
```

When a query needs most of an index but not its order, Oracle may choose `INDEX FAST FULL SCAN`. It reads every index block with multi-block I/O, like a full table scan over a smaller segment.

## 8. Index Condition Pushdown

Index Condition Pushdown is MySQL's name for a technique Oracle and PostgreSQL also use: check as many conditions as possible on the **index entries**, and visit the table only for entries that pass.

```sql
CREATE INDEX idx_orders_cds ON orders (customer_id, order_date, status);

SELECT * FROM orders
WHERE customer_id = 42
  AND order_date >= DATE '2024-01-01'
  AND status = 'CANCELLED'
  AND total_amount > 500;
```

Each condition plays one of three roles:

```
                     INDEX (customer_id, order_date, status)                   TABLE
             ┌───────────────────────────────────────────────┐
 access      │ customer_id = 42 AND order_date >= 2024-01-01 │  where the scan starts and stops
             ├───────────────────────────────────────────────┤
             │ 42 │ 2024-01-03 │ SHIPPED    ── skip          │
 index       │ 42 │ 2024-02-11 │ CANCELLED  ─────────────────┼──► read row ──► total_amount > 500 ?
 filter      │ 42 │ 2024-05-07 │ PENDING    ── skip          │                  table filter
             │ 42 │ 2024-09-15 │ SHIPPED    ── skip          │
             └───────────────────────────────────────────────┘

 4 entries read in the index, 1 table visit
```

| Condition | Role | Reason |
|-----------|------|--------|
| `customer_id = 42` | Access | Leading column, equality |
| `order_date >= ...` | Access | Next column, range |
| `status = 'CANCELLED'` | Index filter | In the index, but after a range column |
| `total_amount > 500` | Table filter | Not in the index |

The table visit is the expensive step, so every entry rejected in the index saves a random read.

### Reading it in plans

**Oracle** lists index filtering in the predicate section of the index step:

```
|* 2 |   INDEX RANGE SCAN  | IDX_ORDERS_CDS |

   2 - access("CUSTOMER_ID"=42 AND "ORDER_DATE">=DATE '2024-01-01' AND "STATUS"='CANCELLED')
       filter("STATUS"='CANCELLED')
```

`STATUS` shows up in both lines. `access` lists every index column the condition touches. `filter` shows that, because it comes after a range, it is only checked entry by entry.

**PostgreSQL** puts every condition that can be checked inside the index under `Index Cond`. The leading ones position the scan and the rest are checked on each entry. Anything else goes under `Filter` and is checked after reading the table row:

```
Index Scan using idx_orders_cds on orders
  Index Cond: ((customer_id = 42) AND (order_date >= '2024-01-01') AND (status = 'CANCELLED'))
  Filter: (total_amount > 500)
  Rows Removed by Filter: 1
```

A large `Rows Removed by Filter` under an index scan suggests adding that column to the index.

## 9. Unique Indexes

A unique index speeds up lookups and also guarantees that no two rows share the same key. Both databases create one automatically for `PRIMARY KEY` and `UNIQUE` constraints, and declaring the constraint is the usual approach:

```sql
ALTER TABLE customers ADD CONSTRAINT uq_customers_email UNIQUE (email);
```

Uniqueness helps the optimizer too. It knows an equality lookup returns at most one row (Oracle shows `INDEX UNIQUE SCAN`), and the guarantee makes rewrites such as join elimination possible (Chapter 01, Section 11).

### NULLs in unique keys

This is where the two databases differ most, and it affects portable schemas:

| Rows inserted | Oracle | PostgreSQL |
|---------------|--------|------------|
| `(NULL)`, `(NULL)` | Allowed | Allowed |
| `(1, NULL)`, `(1, NULL)` | **Rejected as duplicate** | Allowed |
| Treat NULLs as equal | Not configurable | `NULLS NOT DISTINCT` (version 15+) |

```sql
-- PostgreSQL 15+: at most one customer without an email
ALTER TABLE customers
    ADD CONSTRAINT uq_customers_email UNIQUE NULLS NOT DISTINCT (email);
```

### Constraint vs index

- **Oracle** can enforce a unique constraint with a **non-unique** index. This is required for `DEFERRABLE` constraints and allows dropping the constraint while keeping the index.
- **PostgreSQL** always enforces a unique constraint with a unique index. The constraint can be `DEFERRABLE`; a bare `CREATE UNIQUE INDEX` cannot.

## 10. Functional and Expression Indexes

An expression index (Oracle: **function-based index**) stores the result of an expression instead of a raw column value. It makes predicates such as `UPPER(email) = ...` indexable (Chapter 01, Section 11).

```sql
-- PostgreSQL: the extra parentheses are required
CREATE INDEX idx_customers_upper_email ON customers ((UPPER(email)));

-- Oracle
CREATE INDEX idx_customers_upper_email ON customers (UPPER(email));

-- Query that uses it
SELECT * FROM customers WHERE UPPER(email) = 'C42@MAIL.COM';
```

The query must repeat **exactly** the indexed expression. `LOWER(email)` or `UPPER(TRIM(email))` will not match.

| Rule | Oracle | PostgreSQL |
|------|--------|------------|
| User-defined functions must be declared | `DETERMINISTIC` | `IMMUTABLE` |
| Statistics on the expression | Gathered on a hidden virtual column; regather table stats after creating the index | Collected automatically by `ANALYZE` |

Declaring a function deterministic or immutable is a promise. If its result can change for the same input, the index returns wrong results without warning.

Oracle **virtual columns** give the expression a name, so queries do not have to repeat it:

```sql
ALTER TABLE customers ADD (email_upper AS (UPPER(email)));
CREATE INDEX idx_customers_email_upper ON customers (email_upper);
```

Common uses:

| Need | Oracle | PostgreSQL |
|------|--------|------------|
| Case-insensitive search | `UPPER(email)` | `UPPER(email)` |
| Search a timestamp by day | `TRUNC(created_at)` | `(created_at::date)` |
| Search inside JSON | `JSON_VALUE(payload, '$.ref')` | `(payload->>'ref')` |

## 11. Partial and Filtered Indexes

A partial index covers only the rows that meet a condition. When queries always target the same small subset, it is smaller, cheaper to maintain, and faster to scan.

```
Full index on (status, order_date)       ████████████████████████████████  1,000,000 entries
Partial index WHERE status='CANCELLED'   ▌                                    10,000 entries
```

### PostgreSQL

```sql
CREATE INDEX idx_orders_cancelled
    ON orders (order_date)
    WHERE status = 'CANCELLED';

SELECT * FROM orders
WHERE status = 'CANCELLED' AND order_date >= DATE '2025-01-01';
```

The planner uses the index only when it can prove the query's `WHERE` clause implies the index condition. A literal such as `'CANCELLED'` works. A bind parameter works only when the statement is planned with the actual value (a custom plan). A generic plan cannot use the partial index (Chapter 01, Section 13).

A partial unique index enforces a rule on a subset of rows:

```sql
-- At most one PENDING order per customer
CREATE UNIQUE INDEX uq_one_pending_order
    ON orders (customer_id) WHERE status = 'PENDING';
```

### Oracle

Oracle has no `WHERE` clause on indexes. Instead, use an expression that returns NULL for unwanted rows. Rows where every key is NULL are not stored (Section 2):

```sql
CREATE INDEX idx_orders_cancelled
    ON orders (CASE WHEN status = 'CANCELLED' THEN order_date END);

-- Queries must use the same expression
SELECT * FROM orders
WHERE CASE WHEN status = 'CANCELLED' THEN order_date END >= DATE '2025-01-01';

-- At most one PENDING order per customer
CREATE UNIQUE INDEX uq_one_pending_order
    ON orders (CASE WHEN status = 'PENDING' THEN customer_id END);
```

Wrapping the `CASE` in a virtual column keeps application queries readable. For partitioned tables, Oracle 12c+ can also leave selected partitions unindexed (`INDEXING OFF` on the partition, `INDEXING PARTIAL` on the index). This is useful for skipping old archive partitions.

## 12. Prefix Indexes

"Prefix index" can mean three different things.

**1. Indexing only the first N characters.** MySQL supports `INDEX (email(10))`. Oracle and PostgreSQL have no such syntax. Use an expression index and recheck the full value in the query:

```sql
CREATE INDEX idx_email_pfx ON customers (SUBSTR(email, 1, 10));     -- Oracle
CREATE INDEX idx_email_pfx ON customers ((LEFT(email, 10)));         -- PostgreSQL

SELECT * FROM customers
WHERE SUBSTR(email, 1, 10) = SUBSTR(:email, 1, 10)   -- LEFT(...) in PostgreSQL
  AND email = :email;
```

This only pays off for very long values whose first characters are already selective. Otherwise a full-column index is simpler.

**2. Prefix search.** `LIKE 'abc%'` is a range scan on a B-tree (Section 2). A leading wildcard, `LIKE '%abc'`, cannot use a B-tree. For substring search, use PostgreSQL's `pg_trgm` extension with a GIN index, or Oracle Text.

**3. Prefix compression.** Repeated leading key values are stored once:

```
Uncompressed                      Compressed
(UK, London, 1001)                (UK, London) → 1001
(UK, London, 1002)                               1002
(UK, London, 1003)                               1003
```

- **Oracle**: `CREATE INDEX ... COMPRESS n` compresses the first *n* columns. Advanced Index Compression (12c+) is a licensed option.
- **PostgreSQL 13+**: B-tree **deduplication** is automatic. A repeated key is stored once with a list of row pointers.

## 13. Clustered vs Non-Clustered Indexes

The difference is **where the table rows are stored**.

```
Non-clustered: heap table + separate index

   Index (sorted)                Heap (rows in no particular order)
   ┌─────┐                       ┌──────────────────────────┐
   │  1 ─┼──────────────────────►│ page 7   row 1           │
   │  2 ─┼──────────────────────►│ page 9   row 2           │
   │  3 ─┼──────────────────────►│ page 4   row 3           │
   │  4 ─┼──────────────────────►│ page 7   row 4           │
   └─────┘                       └──────────────────────────┘

Clustered: the table is the index

   ┌──────────────────────────────────────────────┐
   │ B-tree whose leaf entries hold the full rows │
   │ [1, row data] [2, row data] [3, row data] …  │
   └──────────────────────────────────────────────┘
```

| | Heap + index | Clustered |
|---|---|---|
| Primary key lookup | Index, then table | One tree descent |
| Primary key range scan | Rows may be on many pages | Rows are adjacent |
| Secondary index points to | Physical row address | Primary key value, which needs a second lookup |
| Insert | Row goes wherever there is space | Row must go to its sorted position |

SQL Server and MySQL InnoDB cluster tables by primary key by default. **Oracle and PostgreSQL use heap tables by default.**

### Oracle: Index-Organized Tables

```sql
CREATE TABLE order_status_history (
    order_id    NUMBER,
    changed_at  TIMESTAMP,
    status      VARCHAR2(20),
    CONSTRAINT pk_osh PRIMARY KEY (order_id, changed_at)
) ORGANIZATION INDEX;
```

An IOT suits tables that are read almost entirely by primary key or key range, such as lookup tables, many-to-many link tables and per-entity history. Secondary indexes on an IOT store a *logical rowid* (the primary key plus a guess at the physical block), which makes them slower than secondary indexes on a heap.

### PostgreSQL: the CLUSTER command

PostgreSQL has no clustered tables. `CLUSTER` rewrites a table in index order **once**:

```sql
CLUSTER orders USING idx_orders_cust_date;
```

The order is not maintained afterwards. `CLUSTER` also holds an `ACCESS EXCLUSIVE` lock for the whole rewrite, which blocks reads and writes. The `pg_repack` extension does the same reorganisation online.

### Physical order still matters on a heap

How closely the table's physical order follows the index order decides how many pages a range scan reads:

```
Well ordered                               Poorly ordered
index:  1  2  3  4  5  6  7  8             index:  1  2  3  4  5  6  7  8
page:   A  A  A  A  B  B  B  B             page:   D  A  C  B  A  D  B  C
        → 2 page reads                             → up to 8 page reads
```

| | Oracle | PostgreSQL |
|---|---|---|
| Metric | `CLUSTERING_FACTOR` (`USER_INDEXES`) | `correlation` (`pg_stats`) |
| Well ordered | Close to the number of table blocks | Close to +1 or −1 |
| Poorly ordered | Close to the number of rows | Close to 0 |

This explains why a range on `order_id`, which is inserted in order, stays cheap over many rows, while a range on `customer_id` becomes more expensive than a full scan much sooner.

## 14. Invisible Indexes

An invisible index is still updated on every write, but the optimizer ignores it. It lets you test adding or removing an index without paying for a rebuild.

```
         create INVISIBLE                      ALTER ... VISIBLE
new ─────────────────────► INVISIBLE ◄──────────────────────────► VISIBLE
                           maintained         ALTER ... INVISIBLE  maintained
                           not used                                used
                               │
                               │ no regressions over a full business cycle
                               ▼
                             DROP
```

### Oracle

```sql
-- Hide an existing index to find out whether anything depends on it
ALTER INDEX idx_orders_cancelled INVISIBLE;

-- Build a new index invisibly and test it in one session only
CREATE INDEX idx_orders_total ON orders (total_amount) INVISIBLE;
ALTER SESSION SET optimizer_use_invisible_indexes = TRUE;
EXPLAIN PLAN FOR SELECT * FROM orders WHERE total_amount > 900;

-- Release it to everyone
ALTER INDEX idx_orders_total VISIBLE;
```

| State | Updated on DML | Used by optimizer |
|-------|----------------|-------------------|
| `VISIBLE` | Yes | Yes |
| `INVISIBLE` | Yes | No, unless the session parameter is set |
| `UNUSABLE` | No | No; must be rebuilt |

### PostgreSQL

PostgreSQL has no invisible indexes. Two workarounds cover the same needs.

**To test removing an index**, drop it inside a transaction and roll back. DDL is transactional in PostgreSQL:

```sql
BEGIN;
DROP INDEX idx_orders_cancelled;
EXPLAIN SELECT * FROM orders WHERE status = 'CANCELLED' AND order_date >= DATE '2025-01-01';
ROLLBACK;
```

`DROP INDEX` holds an `ACCESS EXCLUSIVE` lock on the table until the transaction ends, so keep it short and avoid busy production tables.

**To test adding an index**, use the `hypopg` extension. It creates hypothetical indexes that only the planner can see:

```sql
CREATE EXTENSION hypopg;
SELECT * FROM hypopg_create_index('CREATE INDEX ON orders (total_amount)');
EXPLAIN SELECT * FROM orders WHERE total_amount > 900;
SELECT hypopg_reset();
```

## 15. Index Fragmentation and Maintenance

### Every index has a write cost

```
INSERT into a table with 5 indexes     →  1 table write + 5 index writes
UPDATE of an indexed column            →  1 table write + remove old entry + add new entry
```

PostgreSQL adds a further cost. An update that changes no indexed column can be a **HOT update** (heap-only tuple), which writes no new index entries at all. Indexing a frequently updated column rules out HOT updates for those changes.

### How indexes degrade

```
Page split: inserting 45 into a full leaf
  before   [10 20 30 40 50 60 70 80]
  after    [10 20 30 40 45 __ __ __] [50 60 70 80 __ __ __ __]
           two half-empty pages where there was one full page

After deletes, or old row versions in PostgreSQL
           [10 __ 30 __ __ 60 __ 80]
           space is reusable only by keys in the same range
```

- **Random keys** such as UUIDs split pages all over the index. Increasing keys mostly add to the rightmost leaf.
- **Deletes** free space that only nearby keys can reuse.
- **PostgreSQL MVCC**: every non-HOT update adds new index entries. Old entries stay until `VACUUM` removes them. The wasted space is called **bloat**.

### PostgreSQL

| Task | Command |
|------|---------|
| Measure bloat | `SELECT avg_leaf_density, leaf_fragmentation FROM pgstatindex('idx_orders_cust_date');` (extension `pgstattuple`) |
| Rebuild without blocking writes | `REINDEX INDEX CONCURRENTLY idx_orders_cust_date;` (version 12+) |
| Create without blocking writes | `CREATE INDEX CONCURRENTLY idx_orders_total ON orders (total_amount);` |

- A new B-tree has about 90% leaf density (the default `fillfactor`). Density far below 50% on a large index means significant bloat.
- A failed `CONCURRENTLY` build leaves an `INVALID` index. Drop it and build again.
- `VACUUM` makes dead space reusable but never shrinks the index. Only `REINDEX` returns space.
- Keeping autovacuum effective on busy tables is the best prevention.

Find unused indexes:

```sql
SELECT indexrelid::regclass AS index_name,
       idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

Usage counters are per server. Check read replicas before dropping, because an index unused on the primary may serve queries on a standby.

### Oracle

Oracle B-trees reuse free space well, so routine rebuilds are rarely needed. A rebuild is justified after a large delete, or for an index on increasing keys, such as dates, whose oldest entries are regularly purged.

| Task | Command | Notes |
|------|---------|-------|
| Inspect structure | `ANALYZE INDEX i VALIDATE STRUCTURE;` then query `INDEX_STATS` | Blocks DML while running. Compare `DEL_LF_ROWS` with `LF_ROWS` |
| Rebuild | `ALTER INDEX i REBUILD ONLINE;` | DML allowed during the rebuild |
| Merge sparse leaves | `ALTER INDEX i COALESCE;` | Online; space stays with the index |
| Compact and release space | `ALTER INDEX i SHRINK SPACE;` | Online |
| Create without blocking writes | `CREATE INDEX i ON t (c) ONLINE;` | |

Find unused indexes:

```sql
-- Oracle 12.2+: collected automatically (sampled by default)
SELECT name, total_access_count, last_used
FROM dba_index_usage
WHERE owner = USER;

-- Earlier versions
ALTER INDEX idx_orders_cancelled MONITORING USAGE;
SELECT index_name, used FROM v$object_usage;
```

Before dropping anything, make the index invisible first (Section 14).

## 17. Oracle and PostgreSQL Reference

| Feature | Oracle | PostgreSQL |
|---------|--------|------------|
| Default index | B-tree | B-tree |
| Hash index | None (hash clusters, hash-partitioned indexes) | `USING hash` |
| All-NULL keys | Not stored | Stored |
| Covering columns | Add to key | `INCLUDE (...)` (11+) |
| Index-only access | No table step in plan | `Index Only Scan`, needs visibility map |
| Skip scan | `INDEX SKIP SCAN` | Version 18+ |
| Expression index | Functions must be `DETERMINISTIC` | `((expr))`, functions must be `IMMUTABLE` |
| Partial index | `CASE` expression returning NULL | `WHERE` clause |
| Composite unique with NULLs | `(1, NULL)` twice rejected | Allowed; `NULLS NOT DISTINCT` (15+) |

| Key compression | `COMPRESS n` | Automatic deduplication (13+) |

## 18. Short Summary

- B-trees are shallow and sorted, so one structure serves equality, ranges, prefix matches and ordering. Hash indexes handle equality only.
- An index helps only below a break-even fraction of rows, and physical table order decides where that point lies.
- Composite indexes are searched through their leading columns. Put equality columns first and the range column last.
- A covering index removes table access. In PostgreSQL the benefit also depends on an up-to-date visibility map.
- Expression, partial and unique indexes fit an index to a specific query shape or business rule.
- Oracle's rule of not storing all-NULL keys affects `IS NULL` queries, `COUNT(*)`, composite uniqueness and how partial indexes are built.
- Every index adds write cost. Confirm an index is unused before dropping it, and rebuild only when measurements show bloat.
