# Chapter 03: Join Optimisation

Most slow queries involve joins, and most slow joins come from one wrong decision: the wrong algorithm, the wrong order, or the wrong estimate of how many rows will meet. This chapter explains how **Oracle** and **PostgreSQL** execute joins, when each algorithm wins, and how to recognise and fix a poor choice.

Chapter 01 (Section 6) introduced the three join methods briefly. This chapter goes into how each one works, what it costs, and how data size and distribution change the outcome.

## 2. How a Join Is Planned

A join always combines **two inputs**. A query with four tables is executed as three two-input joins stacked on top of each other.

```
              join
             /    \
          outer   inner
       (driving)  (probed / looked up)
```

For every join the optimizer makes three decisions:

| Decision | Options | Section |
|----------|---------|---------|
| Order | Which tables are joined first, and which input is outer | 10 |
| Method | Nested loop, hash, merge | 3 – 7 |
| Access path for each input | Full scan, index scan, index-only scan | Chapter 02 |

All three depend on the same number: the estimated row count of each input. A join algorithm that is ideal for 10 rows can be disastrous for 10 million, which is why most join problems are estimation problems in disguise.

## 3. Nested Loop Join

The simplest algorithm: for each row of the outer input, search the inner input for matches.

```
for each row r in OUTER:
    for each row s in INNER:
        if r.key = s.key: emit (r, s)
```

```
OUTER             INNER
  r1  ───────────► scan inner ──► matches for r1
  r2  ───────────► scan inner ──► matches for r2
  r3  ───────────► scan inner ──► matches for r3
  ...               (inner is searched once per outer row)
```

```
cost ≈ cost(outer) + rows(outer) × cost(one search of inner)
```

Without an index on the inner side, each search is a full scan, and the cost grows as `outer rows × inner rows`. This plain form is only acceptable when both inputs are tiny, or when the inner input is small and kept in memory:

- PostgreSQL adds a `Materialize` node to keep the inner rows in memory after the first pass.
- PostgreSQL 14+ can add a `Memoize` node, which caches inner results per join key (Section 13).

Nested loop is the **only** method that handles any join condition, including `<`, `BETWEEN`, `LIKE`, and conditions with functions. It also returns its first row immediately, which suits queries with `LIMIT` or `FIRST_ROWS`.

## 4. Index Nested Loop Join

In practice, a good nested loop almost always has an **index on the inner join column**. Each search becomes a short index descent instead of a scan.

```
OUTER (few rows)         INNER index on join key           INNER table
  customer 42  ────────► descend B-tree (3 reads) ────────► 11 order rows
  customer 97  ────────► descend B-tree (3 reads) ────────►  9 order rows
```

```sql
SELECT c.name, o.order_date, o.total_amount
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE c.email = 'c42@mail.com';
```

**PostgreSQL**

```
Nested Loop  (actual rows=11 loops=1)
  -> Index Scan using idx_customers_email on customers c  (actual rows=1 loops=1)
        Index Cond: (email = 'c42@mail.com')
  -> Index Scan using idx_orders_customer on orders o     (actual rows=11 loops=1)
        Index Cond: (customer_id = c.customer_id)
```

The inner `Index Cond` refers to the outer column `c.customer_id`. This is a *parameterised* scan: it runs once per outer row with that row's value. `loops` on the inner node equals the number of outer rows.

**Oracle**

```
| Id | Operation                      | Name                |
|  0 | SELECT STATEMENT               |                     |
|  1 |  NESTED LOOPS                  |                     |
|  2 |   NESTED LOOPS                 |                     |
|  3 |    TABLE ACCESS BY INDEX ROWID | CUSTOMERS           |
|* 4 |     INDEX RANGE SCAN           | IDX_CUSTOMERS_EMAIL |
|* 5 |    INDEX RANGE SCAN            | IDX_ORDERS_CUSTOMER |
|  6 |   TABLE ACCESS BY INDEX ROWID  | ORDERS              |
```

The two `NESTED LOOPS` lines are **NLJ batching** (Oracle 11g+). Oracle first collects row addresses from the inner index for many outer rows, then fetches the table rows in batches, which reduces random I/O. It is one logical nested loop.

### When index nested loop wins

- The outer input is small after filtering: tens to thousands of rows.
- The inner join column is indexed.
- Each outer row matches few inner rows.

### When it loses

```
outer rows      inner index searches      approximate random reads
        10                    10                         ~40
    10,000                10,000                     ~40,000
 1,000,000             1,000,000                 ~4,000,000   ← hash join is far cheaper
```

The cost grows linearly with outer rows, and every search is a random read. If the outer estimate is wrong by 1,000x, this plan is wrong by 1,000x too.

## 5. Hash Join

A hash join works in two phases.

```
Phase 1: BUILD                                Phase 2: PROBE
read the smaller input,                       stream the larger input,
hash each join key into a table in memory     hash each key and look it up

customers (FR, 10,000 rows)                    orders (1,000,000 rows)
   │                                              │
   ▼                                              ▼
 ┌─────────────── hash table ───────────────┐   hash(customer_id)
 │ bucket 0: 17, 4033, ...                  │ ◄──────┘
 │ bucket 1: 8, 902, ...                    │   match? emit joined row
 │ bucket 2: ...                            │
 └──────────────────────────────────────────┘
```

```
cost ≈ read(build) + read(probe) + small CPU per row
```

Each input is read **once**, in any order, with no index needed. That makes hash join the default choice when both inputs are large.

```sql
SELECT c.name, o.total_amount
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE c.country = 'FR';
```

**PostgreSQL**

```
Hash Join  (actual rows=100213 loops=1)
  Hash Cond: (o.customer_id = c.customer_id)
  -> Seq Scan on orders o          (actual rows=1000000 loops=1)
  -> Hash                          (actual rows=10000 loops=1)
        Buckets: 16384  Batches: 1  Memory Usage: 690kB
        -> Seq Scan on customers c (actual rows=10000 loops=1)
              Filter: (country = 'FR')
```

The input under `Hash` is the build side. `Batches: 1` means the hash table fit in memory.

**Oracle**

```
| Id | Operation          | Name      |
|  0 | SELECT STATEMENT   |           |
|* 1 |  HASH JOIN         |           |
|* 2 |   TABLE ACCESS FULL| CUSTOMERS |   ← build (first child)
|  3 |   TABLE ACCESS FULL| ORDERS    |   ← probe (second child)
```

In Oracle the **first child** is the build side. `HASH JOIN RIGHT` (for outer, semi and anti joins) means Oracle swapped the inputs so the smaller one is built. The hint `SWAP_JOIN_INPUTS(t)` forces `t` to be the build side.

### Properties and limits

| Property | Detail |
|----------|--------|
| Join condition | **Equality only** |
| First row | Only after the whole build input is read; high startup cost |
| Output order | None; a later `ORDER BY` needs a sort |
| Memory | PostgreSQL: `work_mem × hash_mem_multiplier` (multiplier default 2.0 from version 15). Oracle: PGA work area, sized from `PGA_AGGREGATE_TARGET` |
| Build side | Should be the smaller input, **after filters** |

### When the hash table does not fit

```
Fits in memory (one pass)
  build ──► [ hash table in memory ] ◄── probe

Does not fit (spill)
  build ──► split into N batches, write N-1 to disk
  probe ──► split into N batches, write N-1 to disk
  then join batch 1, batch 2, ... batch N, reading each pair back from disk
```

Spilling writes and re-reads both inputs, often making the join several times slower.

| | How to detect | How to fix |
|---|---|---|
| PostgreSQL | `Batches` greater than 1 under the `Hash` node | Raise `work_mem` for the session, or reduce the build side's rows or width |
| Oracle | `Used-Tmp` column in `ALLSTATS LAST`; `V$SQL_WORKAREA` shows one-pass or multi-pass executions | Raise the PGA target, or reduce the build side |

```sql
-- PostgreSQL: raise memory for this session only
SET work_mem = '256MB';
```

`work_mem` applies **per operation, per parallel worker**. A query with five hash joins across four workers can use twenty times the setting. Raise it for specific sessions, not globally.

## 6. Merge Join

A merge join reads two **sorted** inputs side by side, like closing a zip.

```
orders (sorted by order_id)          order_items (sorted by order_id)
   1  ◄───────── match ─────────►    1, 1, 1
   2  ◄───────── match ─────────►    2, 2
   3                                 (no row with 3: advance left)
   4  ◄───────── match ─────────►    4, 4, 4
   ...                               ...
   both pointers only move forward
```

```
cost ≈ sort(A) + sort(B) + read(A) + read(B)
       └── zero if already sorted ──┘
```

The merge itself is cheap. The cost is in sorting. A merge join wins when both inputs are **already in order**, usually because they come from indexes on the join key.

`order_items` has primary key `(order_id, product_id)`, so it is naturally sorted by `order_id`:

```sql
SELECT o.order_id, oi.product_id, oi.quantity
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
ORDER BY o.order_id;
```

**PostgreSQL**

```
Merge Join
  Merge Cond: (o.order_id = oi.order_id)
  -> Index Scan using orders_pkey on orders o
  -> Index Scan using order_items_pkey on order_items oi
```

No sort appears anywhere. The result is also already in `ORDER BY` order.

**Oracle**

```
|  0 | SELECT STATEMENT   |             |
|  1 |  MERGE JOIN        |             |
|  2 |   INDEX FULL SCAN  | PK_ORDERS   |
|* 3 |   SORT JOIN        |             |
|  4 |    TABLE ACCESS FULL| ORDER_ITEMS |
```

In Oracle the second input of a merge join always passes through `SORT JOIN`, even when it is already ordered. The first input can skip the sort if it comes from an index.

### Properties

| Property | PostgreSQL | Oracle |
|----------|-----------|--------|
| Join conditions | Equality only | Equality and inequality (`<`, `>`, `<=`, `>=`) |
| Memory | Sorts may spill to disk (`external merge` in the plan) | Same, `Used-Tmp` |
| Output order | Sorted by join key | Sorted by join key |

**Warning sign:** `MERGE JOIN CARTESIAN` in Oracle, or a `Nested Loop` with no join condition in PostgreSQL, is a **Cartesian product**: every row combined with every row. It is usually caused by a missing join condition, or by an estimate of 1 row on one side that turns out to be wrong.

## 7. Choosing Between the Methods

The optimizer compares costs, and costs depend on input sizes. The picture below shows the typical shape for a small outer input joined to a large, indexed inner table:

```
cost
  │                              index nested loop
  │                            ╱   (grows with every outer row)
  │                          ╱
  │                        ╱
  │  ────────────────────x──────────────────────  hash join
  │                    ╱ │                        (reads both inputs once;
  │                  ╱   │                         almost flat in outer rows)
  │                ╱     crossover
  │              ╱
  │            ╱
  │          ╱
  └───────────────────────────────────────────── outer rows
      few                                many
```

Left of the crossover, nested loop wins. Right of it, hash join wins. A wrong row estimate puts the optimizer on the wrong side of the line.

| Situation | Best method |
|-----------|-------------|
| Small outer input, index on inner join key | Index nested loop |
| Query needs the first rows fast (`LIMIT`, pagination) | Index nested loop |
| Both inputs large, equality join | Hash join |
| No useful index, equality join | Hash join |
| Both inputs already sorted on the join key | Merge join |
| Result must be sorted by the join key anyway | Merge join |
| Non-equality join condition | Nested loop (Oracle can also use merge) |
| Build input far too large for memory, inputs sortable | Merge join may beat a multi-pass hash |

### Forcing a method for testing

**Oracle** hints:

```sql
SELECT /*+ LEADING(c o) USE_HASH(o) */ ...     -- hash join, c then o
SELECT /*+ LEADING(c o) USE_NL(o) */ ...       -- nested loop, o as inner
SELECT /*+ USE_MERGE(o) */ ...                 -- merge join
```

**PostgreSQL** session settings (for diagnosis only):

```sql
SET enable_nestloop = off;     -- also enable_hashjoin, enable_mergejoin
EXPLAIN ANALYZE ...;
RESET enable_nestloop;
```

Comparing the actual time of the forced plan with the chosen one tells you whether the optimizer's choice or its estimates are at fault.

## 8. Semi Join

A **semi join** returns each row of the outer input **at most once** if it has at least one match. It is what `EXISTS` and `IN` mean.

```sql
-- Customers who have placed at least one order
SELECT c.*
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
```

```
customers        orders
  1  ──────────► (1, ...)  match: emit customer 1, stop searching
                 (1, ...)  never examined
                 (1, ...)  never examined
  2  ──────────► no match: skip customer 2
  3  ──────────► (3, ...)  match: emit customer 3, stop searching
```

Two properties make it different from an ordinary join:

- **No duplicates.** A customer with 10 orders appears once.
- **Early stop.** The search for a row ends at its first match.

A common mistake is to write an inner join and remove the duplicates afterwards:

```sql
-- Joins 1,000,000 rows, then removes duplicates
SELECT DISTINCT c.* FROM customers c JOIN orders o ON o.customer_id = c.customer_id;
```

`EXISTS` states the intent directly and allows the semi join.

### How it is executed

Each join method has a semi variant:

| Method | PostgreSQL | Oracle |
|--------|-----------|--------|
| Nested loop | `Nested Loop Semi Join` | `NESTED LOOPS SEMI` |
| Hash | `Hash Semi Join` | `HASH JOIN SEMI` / `HASH JOIN RIGHT SEMI` |
| Merge | `Merge Semi Join` | `MERGE JOIN SEMI` |

The optimizer has a second option: remove duplicates from the subquery first, then perform a normal join. This is efficient when the subquery produces few distinct keys:

```
PostgreSQL                               Oracle
Hash Join                                HASH JOIN
  -> Seq Scan on customers c               HASH UNIQUE     (or SORT UNIQUE)
  -> Hash                                    TABLE ACCESS FULL ORDERS
       -> HashAggregate                    TABLE ACCESS FULL CUSTOMERS
            Group Key: o.customer_id
            -> Seq Scan on orders o
```

In modern versions of both databases, `IN` and `EXISTS` are transformed into the same semi join, so choose whichever reads more clearly (Chapter 01, Section 9).

## 9. Anti Join

An **anti join** returns each outer row that has **no** match. It is what `NOT EXISTS` means.

```sql
-- Customers who have never placed an order
SELECT c.*
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
```

```
customers        orders
  1  ──────────► (1, ...)  match found: discard customer 1, stop searching
  2  ──────────► no match: emit customer 2
  3  ──────────► (3, ...)  match found: discard customer 3
```

| Method | PostgreSQL | Oracle |
|--------|-----------|--------|
| Nested loop | `Nested Loop Anti Join` | `NESTED LOOPS ANTI` |
| Hash | `Hash Anti Join`, `Hash Right Anti Join` (16+) | `HASH JOIN ANTI` / `HASH JOIN RIGHT ANTI` |
| Merge | `Merge Anti Join` | `MERGE JOIN ANTI` |

`Hash Right Anti Join` (PostgreSQL 16+) and `HASH JOIN RIGHT ANTI` (Oracle) build the hash table on the **subquery** side instead. This helps when the outer table is the larger one.

### Three ways to write it

| Form | Correct with NULLs | Becomes an anti join |
|------|--------------------|----------------------|
| `NOT EXISTS (...)` | Yes | Yes, in both databases |
| `LEFT JOIN ... WHERE o.customer_id IS NULL` | Yes | PostgreSQL recognises it; in Oracle, check the plan |
| `NOT IN (subquery)` | **No**: one NULL in the subquery returns zero rows | Oracle: null-aware `HASH JOIN ANTI NA`. PostgreSQL: no, it uses a `SubPlan` |

Prefer `NOT EXISTS`. Chapter 01 (Section 9) explains the `NOT IN` NULL problem in detail.

## 10. Join Order Optimisation

Chapter 01 (Section 6) showed that join order can change the work by orders of magnitude and that the principle is to **filter early and keep intermediate results small**. This section covers how the optimizer searches for an order and what limits it.

### Tree shapes

```
Left-deep                           Bushy

            ⋈                              ⋈
           / \                           /   \
          ⋈   D                         ⋈     ⋈
         / \                           / \   / \
        ⋈   C                         A   B C   D
       / \
      A   B

Each join adds one base table.      Two intermediate results are joined.
```

- **Oracle** mainly considers left-deep trees. Each join adds one table to the result so far.
- **PostgreSQL** also considers bushy trees during its dynamic-programming search.

Left-deep trees suit pipelines of index nested loops and chains of hash joins. Bushy trees help when two independent parts of a query each reduce well on their own, for example two filtered dimension tables joined before meeting a large fact table.

### How big the search space is

| Tables | Possible left-deep orders |
|--------|---------------------------|
| 3 | 6 |
| 5 | 120 |
| 8 | 40,320 |
| 12 | 479,001,600 |

Because of this growth, both optimizers limit their search:

| | PostgreSQL | Oracle |
|---|---|---|
| Full search | Dynamic programming up to `geqo_threshold` (default 12) items | Permutation search with an internal cap on the number of orders tried |
| Large joins | Genetic optimizer (GEQO), non-exhaustive | Heuristics; starting order influenced by estimated sizes |
| Written order respected | Beyond `join_collapse_limit` (default 8) explicit `JOIN`s, or `from_collapse_limit` for subqueries | Only with hints (`LEADING`, `ORDERED`) |

For queries joining many tables, the chosen order may be good but not optimal. Breaking such a query into smaller, well-filtered steps often helps both optimizers.

### Outer joins limit reordering

An inner join can be reordered freely. An outer join cannot always be, because moving it can change which rows receive NULLs.

A filter on the nullable side removes the NULL rows anyway, so both optimizers **convert the outer join to an inner join** and regain full freedom of order:

```sql
SELECT *
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'CANCELLED';     -- rejects NULL rows, so this is effectively an inner join
```

If you see an outer join in a plan where you expected an inner one, check whether the query needs to be an outer join at all.

### What a good order looks like in a plan

- The first table read is the one that the filters reduce most.
- Each join produces roughly as many or fewer rows than its input, except where the query genuinely expands (one order to many items).
- No intermediate result is much larger than the final result.

A plan in which an early join produces millions of rows that a later join discards is a join order problem. It is usually caused by a misestimate at the first step (Chapter 01, Section 12).

## 11. Join Elimination

**Join elimination** removes a join from the plan when it cannot affect the result. It matters most for views that join many tables, where a query uses only a few of their columns.

```sql
CREATE VIEW order_details AS
SELECT o.order_id, o.order_date, o.total_amount,
       c.name AS customer_name, c.country
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id;

-- Uses no column from customers
SELECT order_id, total_amount
FROM order_details
WHERE order_date >= DATE '2025-01-01';
```

The join to `customers` can be removed only if it neither **filters** rows nor **duplicates** them:

```
Does not duplicate:  each order matches at most one customer
                     (customers.customer_id is unique)

Does not filter:     each order matches at least one customer
                     inner join: needs a foreign key and NOT NULL on orders.customer_id
                     left join:  never filters, so uniqueness alone is enough
```

| Join type | Oracle | PostgreSQL |
|-----------|--------|------------|
| Inner join, enforced by FK and `NOT NULL` | Eliminated | **Not eliminated** |
| Left join to a unique key, no columns used | Eliminated | Eliminated |

**Oracle** plan: `CUSTOMERS` is absent.

```
|  0 | SELECT STATEMENT  |        |
|* 1 |  TABLE ACCESS FULL| ORDERS |
```

**PostgreSQL** keeps the inner join. Writing the view with `LEFT JOIN` lets it remove the join when no `customers` columns are requested:

```sql
CREATE VIEW order_details AS
SELECT o.order_id, o.order_date, o.total_amount,
       c.name AS customer_name, c.country
FROM orders o
LEFT JOIN customers c ON c.customer_id = o.customer_id;
```

This is safe here only because the foreign key and `NOT NULL` guarantee that every order has a customer, so the left join returns the same rows as the inner join.

### Constraints make elimination possible

Elimination is only as good as the constraints the optimizer can trust. Declare primary keys, unique keys, foreign keys and `NOT NULL` wherever they are true. In Oracle data warehouses, constraints are sometimes declared `RELY DISABLE NOVALIDATE` to inform the optimizer without the cost of enforcement. The optimizer uses them only when `QUERY_REWRITE_INTEGRITY` is set to `TRUSTED`.

## 12. Large-Table Joins

Joining `orders` (1,000,000 rows) to `order_items` (3,000,000 rows) with no selective filter is a typical large join. Index nested loops are out of the question at this size. The work comes down to a hash or merge join, and performance depends on a handful of factors:

```
1. Reduce rows before the join       filters, pre-aggregation
2. Reduce width                      select only the columns needed
3. Fit the join in memory            avoid multi-pass hash joins and disk sorts
4. Split the work                    parallel execution, partition-wise joins
```

### 1. Reduce rows

Aggregate before joining when the query allows it:

```sql
-- Joins 3,000,000 item rows to orders, then aggregates
SELECT o.customer_id, SUM(oi.quantity)
FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
GROUP BY o.customer_id;

-- Aggregates items per order first (1,000,000 rows), then joins
SELECT o.customer_id, SUM(i.qty)
FROM orders o
JOIN (SELECT order_id, SUM(quantity) AS qty
      FROM order_items GROUP BY order_id) i
  ON i.order_id = o.order_id
GROUP BY o.customer_id;
```

Whether this helps depends on how much the pre-aggregation reduces the rows. Check the actual plan.

### 2. Reduce width

A hash table holds every column that later steps need from the build side. `SELECT *` on the build side can make it several times larger and push it over the memory limit.

### 3. Fit in memory

See Section 5. Check for `Batches` greater than 1 (PostgreSQL) or `Used-Tmp` (Oracle).

### 4. Split the work

**Parallel hash join.** Several workers build and probe together.

- **PostgreSQL** (11+): `Parallel Hash Join` with a shared hash table under a `Gather` node. The number of workers is governed by `max_parallel_workers_per_gather` (default 2).
- **Oracle**: parallel execution distributes rows between worker processes. The plan shows the distribution method:

| Distribution | Meaning | Suitable when |
|--------------|---------|---------------|
| `BROADCAST` | Send all rows of the small input to every worker | One input is small |
| `HASH` | Redistribute both inputs by join key | Both inputs are large |
| `PARTITION` / none | Each worker joins matching partitions | Tables are partitioned on the join key |

In parallel plans Oracle also builds a **Bloom filter** from the build side (`JOIN FILTER CREATE` / `JOIN FILTER USE`, named `:BF0000`). It discards non-matching probe rows before they are sent between workers.

**Partition-wise join.** When both tables are partitioned the same way on the join key, the big join splits into many small, independent ones:

```
orders          order_items
hash(order_id)  hash(order_id)

   P1  ⋈  P1        each pair is small enough to fit in memory,
   P2  ⋈  P2        and the pairs can run in parallel
   P3  ⋈  P3
   P4  ⋈  P4
```

| | Oracle | PostgreSQL |
|---|---|---|
| Enabled | Automatic when tables are equi-partitioned on the join key | `enable_partitionwise_join = on` (default off) |
| Requirement | Same partitioning method and boundaries on the join key | Same partitioning scheme, join on the partition key |

## 13. Join Algorithms Under Different Data Distributions

The same query can need a different algorithm depending on the data. This section covers the cases that come up most often.

### Estimating the size of a join

The optimizer estimates an equality join's output as:

```
rows(A ⋈ B) ≈ rows(A) × rows(B) / max(distinct(A.key), distinct(B.key))
```

For `orders ⋈ customers`: `1,000,000 × 100,000 / 100,000 = 1,000,000`. This formula assumes values are spread evenly. When they are not, both databases improve the estimate with column statistics: PostgreSQL compares the most-common-value lists of both join columns, and Oracle uses histograms on the join columns.

### Case 1: Small filtered outer, large indexed inner

```
customers WHERE email = ...   (1 row)   ──► index nested loop into orders
```

This is the classic index nested loop case. It stays correct as long as the outer estimate is correct.

### Case 2: Two large inputs, no order

```
orders (1,000,000)  ⋈  order_items (3,000,000)   ──► hash join
```

Hash join, with memory and parallelism as described in Section 12.

### Case 3: Both inputs already ordered

```
orders by PK  ⋈  order_items by PK (order_id, ...)   ──► merge join, no sorts
```

This also works well for time-series tables joined on time, when both are indexed or clustered on it.

### Case 4: Many repeated join keys on the outer side

```sql
SELECT oi.quantity, p.price
FROM order_items oi
JOIN products p ON p.product_id = oi.product_id;
```

3,000,000 item rows reference only 10,000 products. A nested loop would look up the same product about 300 times.

**PostgreSQL 14+** inserts a `Memoize` node that caches inner results by key:

```
Nested Loop
  -> Seq Scan on order_items oi
  -> Memoize
        Cache Key: oi.product_id
        Hits: 2990000  Misses: 10000  Evictions: 0
        -> Index Scan using products_pkey on products p
              Index Cond: (product_id = oi.product_id)
```

Only 10,000 index lookups happen. A hash join with `products` as the build side is the other natural choice, and it is what Oracle typically uses here.

### Case 5: Skewed join keys

Suppose one customer, a wholesale account, has 200,000 orders and everyone else has about 8.

```
hash table on orders by customer_id

bucket for customer 7      ████████████████████████████████  200,000 rows
bucket for customer 42     █                                       8 rows
bucket for customer 97     █                                      10 rows
```

Effects:

- **Estimates.** The average of 10 rows per customer hides the heavy customer. A nested loop that is fast for normal customers is slow for customer 7. Histograms on `orders.customer_id` let the optimizer tell them apart when the value is a literal. With bind variables this is the plan-reuse problem from Chapter 01 (Section 13).
- **Hash joins.** PostgreSQL uses the most-common-value statistics of the probe side to keep the hottest keys in memory, so they are not spilled to disk with the rest of a batch.
- **Parallel joins.** With `HASH` distribution, every row for one key goes to one worker, which then does most of the work. Oracle 12c+ detects popular values and spreads them across workers (hybrid hash distribution, hint `PQ_SKEW`).

### Case 6: Correlated or multi-column join keys

Consider a `shipments` table that stores both `order_id` and `customer_id`:

```sql
... JOIN shipments s ON s.order_id = o.order_id AND s.customer_id = o.customer_id
```

The optimizer multiplies the selectivities of the two conditions as if they were independent (Chapter 01, Section 12). Because `order_id` already determines `customer_id`, the estimate is far too low, which pushes the plan toward nested loops. Extended statistics on the column pair improve the estimate. So does joining only on the key that determines the other when the query allows it.

### Case 7: The estimate is simply wrong

When estimates cannot be fixed, Oracle can defer the decision to run time. An **adaptive plan** (12c+) includes both a nested loop and a hash join, with a `STATISTICS COLLECTOR` that counts the actual outer rows and switches to the hash join if a threshold is passed:

```sql
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST +ADAPTIVE'));
```

Lines prefixed with `-` are the branch that was not used. PostgreSQL has no equivalent; it relies on accurate estimates.

### Summary by distribution

| Data situation | Likely best method | Risk |
|----------------|--------------------|------|
| Small outer, indexed inner | Index nested loop | Outer underestimated |
| Large and unordered | Hash join | Spill to disk |
| Both sorted on key | Merge join | Hidden sort on unsorted input |
| Few distinct keys on the outer | Hash join, or nested loop with `Memoize` | None significant |
| Skewed keys | Depends on the value | Plan reuse with bind variables; parallel imbalance |
| Correlated multi-column keys | Hash join | Underestimate leads to nested loop |

## 15. Oracle and PostgreSQL Reference

| Item | Oracle | PostgreSQL |
|------|--------|------------|
| Nested loop | `NESTED LOOPS` (two lines when batched) | `Nested Loop` |
| Inner index lookup | `INDEX RANGE SCAN` under the loop | `Index Scan` with `Index Cond` on an outer column |
| Inner result cache | None | `Memoize` (14+) |
| Hash join | `HASH JOIN`; first child is build | `Hash Join`; input under `Hash` is build |
| Swapped build side | `HASH JOIN RIGHT ...`, hint `SWAP_JOIN_INPUTS` | Planner chooses; `Hash Right ...` variants |
| Hash memory | PGA (`PGA_AGGREGATE_TARGET`) | `work_mem × hash_mem_multiplier` |
| Spill indicator | `Used-Tmp`, `V$SQL_WORKAREA` | `Batches` > 1 |
| Merge join | `MERGE JOIN` + `SORT JOIN`; supports inequality | `Merge Join`; equality only |
| Semi join | `... SEMI` | `... Semi Join` |
| Anti join | `... ANTI`, `ANTI NA` for `NOT IN` | `... Anti Join`; `NOT IN` stays `SubPlan` |
| Cartesian product | `MERGE JOIN CARTESIAN` | `Nested Loop` without join condition |
| Join order control | `LEADING`, `ORDERED` | `join_collapse_limit`, `pg_hint_plan` |

## 16. Short Summary

- Every join is a choice of order, method and access path, and all three depend on estimated row counts. Fix estimates before anything else.
- Index nested loop is best for a small outer input and an indexed inner key. Its cost grows with every outer row.
- Hash join reads each input once and is the default for large equality joins. It needs the build side to fit in memory.
- Merge join is cheap when both inputs are already sorted. Otherwise the sorts dominate.
- Semi and anti joins stop at the first match and return no duplicates. Write them as `EXISTS` and `NOT EXISTS`.
- Oracle removes inner joins made redundant by foreign keys. PostgreSQL removes only unused left joins to unique keys.
- Large joins depend on fewer rows, narrower rows, enough memory, and splitting the work through parallelism or partition-wise joins.
- Skewed keys, repeated keys and correlated join columns each change the best algorithm. Recognise them from the actual plan.
