# Chapter 04: Transactions and Concurrency

A database serves many users at once. Two of them may read and change the same rows in the same millisecond, and the result must still be correct. Transactions define what "correct" means. Concurrency control decides who waits, who proceeds, and who gets an error.

This chapter explains how **Oracle** and **PostgreSQL** keep concurrent work correct: MVCC, isolation levels, locks, deadlocks and serializable execution. It also covers how to recognise and reduce contention in production.

    │
    └───< accounts (N)

## 2. Transactions and ACID

A **transaction** is a group of statements that succeed or fail as one unit.

```sql
-- Transfer 100 from account 1 to account 2
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
COMMIT;
```

If the database crashes between the two updates, money must not disappear. ACID names the four guarantees that prevent this.

| Property | Guarantee | Oracle mechanism | PostgreSQL mechanism |
|----------|-----------|------------------|----------------------|
| **Atomicity** | All statements take effect, or none do | Undo records reverse uncommitted changes | Uncommitted row versions are never visible; commit status kept in the commit log (`pg_xact`) |
| **Consistency** | Each transaction moves the database from one valid state to another | Constraints, triggers | Constraints, triggers |
| **Isolation** | Concurrent transactions do not see each other's partial work | MVCC + row locks | MVCC + row locks |
| **Durability** | Committed data survives a crash | Redo log written by LGWR at commit | Write-ahead log (WAL) flushed at commit |

Durability means `COMMIT` does not return until the change is safely in the log on disk. The data files themselves are updated later. After a crash, the log is replayed.

```
COMMIT ──► write log record ──► flush log to disk ──► "commit complete"
                                                        │
               data blocks written later by background processes
```

PostgreSQL can relax this per transaction with `SET synchronous_commit = off`. The commit returns before the WAL flush, so a crash can lose the last fraction of a second of commits, but it never corrupts data. Oracle offers the same trade-off with `COMMIT WRITE BATCH NOWAIT`.

### Transaction boundaries differ

| Behaviour | Oracle | PostgreSQL |
|-----------|--------|------------|
| Start | Implicitly, with the first DML statement | `BEGIN`; without it, each statement commits on its own (autocommit) |
| DDL (`CREATE`, `ALTER`, `DROP`) | Commits the open transaction before and after | Transactional; can be rolled back |
| A statement fails | Only that statement is rolled back; the transaction continues | The whole transaction is marked failed; every further statement errors until `ROLLBACK` |

The last difference catches many developers moving between the two databases. In PostgreSQL, use a savepoint to recover from an expected error inside a transaction:

```sql
BEGIN;
INSERT INTO orders ...;
SAVEPOINT before_optional;
INSERT INTO order_items ...;          -- fails
ROLLBACK TO SAVEPOINT before_optional;
COMMIT;                               -- the first insert is kept
```

Keep savepoints for real error handling. Each one has a cost, and using one per row in a large loop is slow in both databases.

## 3. MVCC

**Multi-Version Concurrency Control** keeps more than one version of a row, so a reader can see the version that was current when its query or transaction began while a writer creates a new one.

The result, in both databases:

```
Readers never block writers.
Writers never block readers.
Only writers block writers, and only on the same row.
```

The two databases implement MVCC in very different ways, and the differences explain many of their operational problems.

### Oracle: update in place, old versions in undo

```
Data block (always the latest version)          Undo segment (before-images)
┌──────────────────────────────┐                ┌──────────────────────────────┐
│ account 1: balance = 400     │ ─── points ──► │ account 1: balance = 500     │
│ (changed at SCN 1050)        │                │ (valid before SCN 1050)      │
└──────────────────────────────┘                └──────────────────────────────┘

A query that started at SCN 1000 reads the block, sees a change newer than 1000,
and rebuilds the old version from undo: balance = 500.
```

- Every change is stamped with a **System Change Number (SCN)**, a counter that orders all changes in the database.
- A query sees data **as of the SCN at which it started**. Oracle calls this *read consistency*.
- If the needed undo has been overwritten, the query fails with **ORA-01555: snapshot too old**. Long queries on busy systems need enough undo space and a suitable `UNDO_RETENTION`.

### PostgreSQL: a new row version for every update

```
Table page
┌──────────────────────────────────────────────────────────┐
│ version 1: account 1, balance 500   xmin=100  xmax=205   │  dead after 205 commits
│ version 2: account 1, balance 400   xmin=205  xmax=0     │  current
└──────────────────────────────────────────────────────────┘

xmin = transaction that created this version
xmax = transaction that deleted or replaced it (0 = still live)
```

- An `UPDATE` writes a complete new row version and marks the old one with `xmax`.
- Each transaction takes a **snapshot**: the list of transactions that had committed when it started. A version is visible if its `xmin` is in the snapshot and its `xmax` is not.
- Old versions stay in the table until **VACUUM** removes them. Until then they take space: this is **bloat** (Chapter 02, Section 15).

You can see this directly:

```sql
SELECT xmin, xmax, account_id, balance FROM accounts;
```

### Consequences

| Topic | Oracle | PostgreSQL |
|-------|--------|------------|
| Where old versions live | Undo tablespace | In the table itself |
| Cleanup | Automatic, as undo expires | `VACUUM` (autovacuum) |
| Long-running query risk | ORA-01555 for that query | Holds back cleanup for **every** table, so bloat grows |
| Update cost | Changes the row in place plus undo | Writes a whole new row, plus index entries unless HOT |
| Transaction ID limits | SCN is effectively unlimited | 32-bit IDs; VACUUM must *freeze* old rows to prevent wraparound |

In PostgreSQL, a session left `idle in transaction` for hours keeps its snapshot open. VACUUM cannot remove any row version newer than that snapshot, anywhere in the database. Set `idle_in_transaction_session_timeout` to protect against this.

## 4. Read Phenomena

The SQL standard defines isolation in terms of anomalies that should or should not be possible. Two more anomalies matter just as much in practice.

### Dirty read

Reading data another transaction has written but not committed.

```
Time  Session A                               Session B
────  ──────────────────────────────────────  ──────────────────────────────────────
t1                                            UPDATE accounts SET balance = 0
                                              WHERE account_id = 1;
t2    SELECT balance FROM accounts
      WHERE account_id = 1;         → 0 ?
t3                                            ROLLBACK;
      A acted on a value that never existed.
```

**Neither Oracle nor PostgreSQL ever allows dirty reads.** MVCC always shows the last committed version. At t2, both return 500.

### Non-repeatable read

The same row, read twice in one transaction, returns different values.

```
Time  Session A                               Session B
────  ──────────────────────────────────────  ──────────────────────────────────────
t1    SELECT balance ... account_id = 1; → 500
t2                                            UPDATE ... SET balance = 400
                                              WHERE account_id = 1;
                                              COMMIT;
t3    SELECT balance ... account_id = 1; → 400
```

### Phantom read

The same query, run twice, returns a different **set** of rows because another transaction inserted or deleted matching rows.

```
Time  Session A                               Session B
────  ──────────────────────────────────────  ──────────────────────────────────────
t1    SELECT COUNT(*) FROM orders
      WHERE customer_id = 7;         → 3
t2                                            INSERT INTO orders (customer_id, ...)
                                              VALUES (7, ...);
                                              COMMIT;
t3    SELECT COUNT(*) FROM orders
      WHERE customer_id = 7;         → 4
```

### Lost update

Two transactions read a value, both compute a new one, and the second write silently overwrites the first.

```
Time  Session A                               Session B
────  ──────────────────────────────────────  ──────────────────────────────────────
t1    SELECT balance ... → 500
t2                                            SELECT balance ... → 500
t3    UPDATE ... SET balance = 400;           (500 − 100, computed in the application)
      COMMIT;
t4                                            UPDATE ... SET balance = 450;
                                              (500 − 50)
                                              COMMIT;
      Final balance 450. The first withdrawal of 100 is lost.
```

This happens whenever an application reads a value, calculates in its own code, and writes the result back. Section 10 covers the fixes.

### Write skew

Two transactions read overlapping data, each makes a decision based on it, and they write to **different** rows. Each write is valid alone. Together they break a rule.

Rule: a customer may have at most 3 `PENDING` orders.

```
Time  Session A                               Session B
────  ──────────────────────────────────────  ──────────────────────────────────────
t1    SELECT COUNT(*) ... status='PENDING'
      AND customer_id = 7;          → 2
t2                                            same query                   → 2
t3    INSERT pending order for 7; COMMIT;
t4                                            INSERT pending order for 7; COMMIT;
      Customer 7 now has 4 pending orders.
```

No row was written by both sessions, so row locks never conflict. Only true serializable execution prevents this (Section 11).

## 5. Isolation Levels

An isolation level declares which anomalies a transaction can tolerate. The standard defines four. Each database implements them differently.

| Level | Dirty read | Non-repeatable read | Phantom | Lost update | Write skew |
|-------|:----------:|:-------------------:|:-------:|:-----------:|:----------:|
| **Oracle** READ COMMITTED (default) | No | Possible | Possible | Possible | Possible |
| **Oracle** SERIALIZABLE | No | No | No | Error (ORA-08177) | **Possible** |
| **PostgreSQL** READ UNCOMMITTED | Behaves as READ COMMITTED | | | | |
| **PostgreSQL** READ COMMITTED (default) | No | Possible | Possible | Possible | Possible |
| **PostgreSQL** REPEATABLE READ | No | No | No | Error (40001) | **Possible** |
| **PostgreSQL** SERIALIZABLE | No | No | No | Error (40001) | Error (40001) |

Oracle has no REPEATABLE READ level. It offers `READ ONLY` transactions, which see a single snapshot and cannot modify data.

### How the levels work

```
READ COMMITTED                     each STATEMENT gets a fresh snapshot
  txn start ──┬── stmt 1 (snapshot 1)
              ├── stmt 2 (snapshot 2)     sees commits made between statements
              └── stmt 3 (snapshot 3)

REPEATABLE READ (PG) /             the whole TRANSACTION uses one snapshot
SERIALIZABLE (Oracle)
  txn start ──┬── stmt 1 ┐
              ├── stmt 2 ├── snapshot taken at the first statement
              └── stmt 3 ┘
```

Oracle's SERIALIZABLE and PostgreSQL's REPEATABLE READ are both **snapshot isolation**. They prevent every anomaly in the standard's table but still allow write skew. Only PostgreSQL's SERIALIZABLE is fully serializable.

### Setting the level

```sql
-- Oracle: first statement of the transaction
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SET TRANSACTION READ ONLY;

-- Oracle: for the session
ALTER SESSION SET ISOLATION_LEVEL = SERIALIZABLE;

-- PostgreSQL
BEGIN ISOLATION LEVEL REPEATABLE READ;
-- or
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- PostgreSQL: session or database default
SET default_transaction_isolation = 'repeatable read';
```

### Updates under READ COMMITTED

When a statement tries to update a row that another transaction changed and committed after the statement's snapshot, both databases avoid applying the change to a stale version:

| | Behaviour |
|---|---|
| Oracle | Restarts the statement with a new snapshot, locking rows as it goes (*write consistency*) |
| PostgreSQL | Waits for the other transaction, then re-checks the `WHERE` clause against the newest version of that row only, and updates it if it still matches |

This is why a single statement such as `UPDATE accounts SET balance = balance - 100 WHERE account_id = 1` never loses an update, even at READ COMMITTED. The lost update in Section 4 happens only because the value was computed **outside** the statement.

### Under snapshot isolation, conflicts become errors

At Oracle SERIALIZABLE or PostgreSQL REPEATABLE READ and above, a transaction cannot update a row that was changed after its snapshot:

```
Oracle:      ORA-08177: can't serialize access for this transaction
PostgreSQL:  ERROR: could not serialize access due to concurrent update  (SQLSTATE 40001)
```

The application must **roll back and retry the whole transaction**. Any code that uses these levels needs a retry loop.

## 6. Locking

MVCC removes conflicts between readers and writers. Conflicts between writers are still resolved with **locks**: a writer that wants a row another uncommitted transaction has changed must wait.

```
Time  Session A                               Session B
────  ──────────────────────────────────────  ──────────────────────────────────────
t1    UPDATE accounts SET balance = 400
      WHERE account_id = 1;       row locked
t2                                            UPDATE accounts SET balance = 300
                                              WHERE account_id = 1;
                                              ... waits ...
t3    COMMIT;                     lock released
t4                                            update proceeds
```

Locks are held **until the end of the transaction**, not the end of the statement. A transaction that updates a row and then waits for user input holds that lock for the entire wait.

### Explicit row locks: SELECT ... FOR UPDATE

`SELECT ... FOR UPDATE` reads rows and locks them as if they were updated. Use it when you must read a value and then write based on it (Section 10).

```sql
SELECT balance FROM accounts WHERE account_id = 1 FOR UPDATE;
-- compute, validate
UPDATE accounts SET balance = :new_balance WHERE account_id = 1;
COMMIT;
```

Options for what happens when the row is already locked:

| Option | Behaviour | Oracle | PostgreSQL |
|--------|-----------|:------:|:----------:|
| (default) | Wait until the lock is released | Yes | Yes |
| `NOWAIT` | Error immediately | Yes | Yes |
| `WAIT n` | Wait up to *n* seconds, then error | Yes | No; use `SET lock_timeout` |
| `SKIP LOCKED` | Return only rows that are not locked | Yes | Yes |

PostgreSQL has weaker row lock modes that allow more concurrency:

| Mode | Blocks | Typical use |
|------|--------|-------------|
| `FOR UPDATE` | All other row locks and updates | Row will be deleted or its key changed |
| `FOR NO KEY UPDATE` | Updates and `FOR UPDATE`, but not `FOR KEY SHARE` | Taken automatically by `UPDATE` that does not change key columns |
| `FOR SHARE` | Any update | Row must not change, but others may also read-lock it |
| `FOR KEY SHARE` | Deletes and key changes only | Taken automatically by foreign key checks on the parent row |

Oracle has only `FOR UPDATE` at row level.

### Lock timeouts

An unbounded wait is rarely what an application wants.

```sql
-- PostgreSQL: fail any lock wait longer than 5 seconds
SET lock_timeout = '5s';

-- Oracle: per statement
SELECT ... FOR UPDATE WAIT 5;

-- Oracle: DDL waiting for a busy table
ALTER SESSION SET DDL_LOCK_TIMEOUT = 5;
```

## 7. Row-Level vs Table-Level Locks

Both databases use two layers of locks:

```
Table-level lock  ── protects the table's structure and permits or blocks whole-table operations
      │
Row-level lock    ── protects individual rows being changed
```

Every DML statement takes a weak table lock **and** row locks. The table lock does not block other DML. It exists so that a conflicting operation, such as `DROP TABLE` or `ALTER TABLE`, waits until the DML is finished.

### Where row locks are stored

Neither database keeps row locks in a central lock table in memory:

- **Oracle** records the lock in the data block. Each block has an **Interested Transaction List (ITL)**, and a locked row points to its ITL slot.
- **PostgreSQL** records the lock in the row version's header (`xmax`, plus *multixact* IDs when several transactions share a lock).

This is why neither database has a limit on the number of row locks, and why neither needs lock escalation (Section 9).

### Oracle table lock modes (TM locks)

| Mode | Abbreviation | Taken by |
|------|--------------|----------|
| Row Share | RS / SS | `LOCK TABLE ... IN ROW SHARE MODE` |
| Row Exclusive | RX / SX | `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `SELECT ... FOR UPDATE` |
| Share | S | `LOCK TABLE ... IN SHARE MODE`; unindexed foreign key checks (see below) |
| Share Row Exclusive | SRX / SSX | `LOCK TABLE ... IN SHARE ROW EXCLUSIVE MODE` |
| Exclusive | X | `LOCK TABLE ... IN EXCLUSIVE MODE`, most DDL |

### PostgreSQL table lock modes

| Mode | Taken by |
|------|----------|
| `ACCESS SHARE` | `SELECT` |
| `ROW SHARE` | `SELECT ... FOR UPDATE / FOR SHARE` |
| `ROW EXCLUSIVE` | `INSERT`, `UPDATE`, `DELETE`, `MERGE` |
| `SHARE UPDATE EXCLUSIVE` | `VACUUM`, `ANALYZE`, `CREATE INDEX CONCURRENTLY` |
| `SHARE` | `CREATE INDEX` (non-concurrent) |
| `SHARE ROW EXCLUSIVE` | `CREATE TRIGGER`, some `ALTER TABLE` forms |
| `EXCLUSIVE` | `REFRESH MATERIALIZED VIEW CONCURRENTLY` |
| `ACCESS EXCLUSIVE` | `DROP`, `TRUNCATE`, `VACUUM FULL`, `CLUSTER`, most `ALTER TABLE` |

### Which common operations block each other

| Running | Blocks `SELECT` | Blocks DML | Oracle | PostgreSQL |
|---------|:---------------:|:----------:|--------|-----------|
| DML | No | Only on the same rows | RX | `ROW EXCLUSIVE` |
| `CREATE INDEX` | No | Yes | Share lock during build | `SHARE` |
| `CREATE INDEX` online | No | No | `ONLINE` | `CONCURRENTLY` |
| Most `ALTER TABLE` / `DROP` / `TRUNCATE` | Oracle: no. PostgreSQL: **yes** | Yes | Exclusive DDL lock | `ACCESS EXCLUSIVE` |

In PostgreSQL, `ACCESS EXCLUSIVE` blocks even plain `SELECT`s. Oracle's DDL does not block queries.

### The lock queue problem (PostgreSQL)

A waiting lock request also blocks everything queued behind it:

```
t1  Session A: long SELECT on orders                    holds ACCESS SHARE
t2  Session B: ALTER TABLE orders ADD COLUMN ...        waits for ACCESS EXCLUSIVE
t3  Session C: SELECT ... FROM orders                   waits behind B
t4  Session D: SELECT ... FROM orders                   waits behind B
    ...  the application stalls on a table no one is actually changing
```

Run schema changes with a short `lock_timeout` and retry, so a waiting `ALTER` gives up instead of stalling all traffic:

```sql
SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN note TEXT;
```

### Unindexed foreign keys

When a parent row is deleted, or its key is updated, the database must check the child table for referencing rows.

| | Effect of a missing index on the child's foreign key column |
|---|---|
| Oracle | The child table is locked in **Share** mode during the parent change, blocking all DML on the child table. A classic cause of blocking and deadlocks |
| PostgreSQL | No table lock, but each parent delete scans the whole child table. Slow, and the transaction holds its locks for longer |

Index foreign key columns whenever the parent key can be deleted or updated.

## 8. Deadlocks

A **deadlock** occurs when two transactions each wait for a lock the other holds. Neither can proceed.

```
Time  Session A                               Session B
────  ──────────────────────────────────────  ──────────────────────────────────────
t1    UPDATE accounts ... WHERE id = 1;
      (locks row 1)
t2                                            UPDATE accounts ... WHERE id = 2;
                                              (locks row 2)
t3    UPDATE accounts ... WHERE id = 2;
      waits for B
t4                                            UPDATE accounts ... WHERE id = 1;
                                              waits for A

              ┌──────────── waits for ────────────┐
              ▼                                   │
         Session A                           Session B
              │                                   ▲
              └──────────── waits for ────────────┘
```

Both databases detect the cycle and break it:

| | Oracle | PostgreSQL |
|---|---|---|
| Detection | Within a few seconds | After waiting `deadlock_timeout` (default 1 s) |
| Victim | One session's **current statement** is rolled back | One session's **whole transaction** is aborted |
| Error | `ORA-00060: deadlock detected while waiting for resource` | `ERROR: deadlock detected` (SQLSTATE `40P01`) |
| Diagnostics | Trace file with the deadlock graph; alert log entry | Server log shows the processes and statements involved |

In Oracle, the victim's transaction is still open and still holds its earlier locks. The application must roll back, or the other session keeps waiting.

### Preventing deadlocks

| Technique | Why it works |
|-----------|--------------|
| Access rows in a consistent order (for example, always the lower `account_id` first) | A cycle cannot form if everyone locks in the same order |
| Keep transactions short | Fewer locks held, for less time |
| Lock everything needed up front: `SELECT ... WHERE account_id IN (1, 2) ORDER BY account_id FOR UPDATE` | All locks are taken in one ordered step |
| Index foreign keys (Oracle) | Removes the child-table share lock (Section 7) |
| Use `NOWAIT` or lock timeouts where waiting is not useful | Turns a potential deadlock into an immediate, handled error |

Deadlocks cannot be eliminated entirely in a busy system. Treat them like serialization failures: catch the error, roll back, and retry.

## 9. Lock Escalation

**Lock escalation** replaces many fine-grained locks with one coarse lock to save memory. For example, SQL Server converts row locks to a table lock after about 5,000 locks on one object in a statement. Escalation reduces concurrency sharply: one large update suddenly blocks the whole table.

```
Databases that escalate                Oracle and PostgreSQL

row row row row row ...                row locks stored in the data itself
      │  (thousands of locks                (ITL / tuple header)
      ▼   in lock memory)                         │
┌────────────────────┐                             ▼
│    TABLE LOCK      │                  no lock memory limit
└────────────────────┘                  ──► no escalation
```

| | Row lock escalation |
|---|---|
| Oracle | **Never.** Locks live in data blocks |
| PostgreSQL | **Never** for row locks |
| SQL Server, Db2 | Yes, by design |

Two related effects remain.

**Oracle ITL waits.** Each block has a limited number of ITL slots (starting at `INITRANS`). If many transactions update different rows in the **same block** at once and no space is left to add slots, sessions wait on `enq: TX - allocate ITL entry`. Raising `INITRANS` for very hot tables or indexes fixes it.

**PostgreSQL predicate lock escalation.** Under SERIALIZABLE (Section 11), PostgreSQL tracks what each transaction has *read* with **predicate locks** (`SIReadLock` in `pg_locks`). These are stored in shared memory and **do** escalate:

```
row-level predicate locks ──► page-level ──► whole relation
```

The thresholds are `max_pred_locks_per_page` (default 2), `max_pred_locks_per_relation` (default −2, meaning relative to the next setting) and `max_pred_locks_per_transaction` (default 64). Escalation does not block anyone. It makes conflict detection coarser, so more transactions fail with serialization errors.

A PostgreSQL side effect worth knowing: `SELECT ... FOR UPDATE` on many rows writes a lock marker into each row, dirtying every page it touches. Locking a million rows costs roughly as much I/O as updating them.

## 10. Optimistic vs Pessimistic Concurrency

The lost update in Section 4 has two standard solutions.

```
Pessimistic: lock first, then work
  read row FOR UPDATE ──► compute ──► update ──► commit
  (others wait at the first step)

Optimistic: work first, check at the end
  read row + version ──► compute ──► update WHERE version matches ──► 0 rows? retry
  (no one waits; a conflict is detected afterwards)
```

### Pessimistic

```sql
SELECT balance FROM accounts WHERE account_id = 1 FOR UPDATE;
-- application computes new balance
UPDATE accounts SET balance = :new_balance WHERE account_id = 1;
COMMIT;
```

The second session blocks at `SELECT ... FOR UPDATE` until the first commits, then reads the new balance. Nothing is lost.

### Optimistic

Add a version column (created in Section 1 for `orders`) and include it in the update:

```sql
-- 1. Read, remember the version
SELECT status, version FROM orders WHERE order_id = 1001;    -- version = 7

-- 2. Later, write only if nobody changed it
UPDATE orders
SET    status = 'SHIPPED', version = version + 1
WHERE  order_id = 1001
AND    version = 7;

-- 3. Check the affected row count
--    1 row  → success
--    0 rows → someone else changed it: reload and retry, or report a conflict
```

No lock is held between steps 1 and 2, so this works even when the steps are minutes apart, such as a user editing a form. Most ORMs support this pattern directly.

Built-in alternatives to a version column:

| | Column | Caveat |
|---|---|---|
| Oracle | `ORA_ROWSCN` | Block-level by default; row-level only if the table is created with `ROWDEPENDENCIES` |
| PostgreSQL | `xmin` | Changes on every update; wraps around over very long periods |

An explicit version column is clearer and portable.

### Choosing

| Situation | Better approach |
|-----------|-----------------|
| Conflicts are rare | Optimistic |
| Long gap between read and write (user think time, external calls) | Optimistic |
| Conflicts are frequent (hot rows, counters) | Pessimistic, or a single atomic statement |
| Retrying is expensive or has side effects | Pessimistic |
| The change fits in one SQL statement | Neither: `UPDATE ... SET balance = balance - 100 WHERE balance >= 100` |

The last row is often the best answer. A single statement that computes and checks inside the database needs no explicit lock and no version column.

## 11. Serializable Transactions

A schedule is **serializable** if its result is the same as running the transactions one after another in some order. It is the only level that prevents every anomaly, including write skew.

### Oracle SERIALIZABLE

Oracle's SERIALIZABLE is snapshot isolation (Section 5). It prevents lost updates by raising ORA-08177, but it **allows write skew**. The pending-orders example in Section 4 succeeds for both sessions.

To enforce such a rule in Oracle, turn the logical conflict into a row lock conflict. Lock a row that every competing transaction must touch:

```sql
-- Both sessions serialise on the customer row
SELECT customer_id FROM customers WHERE customer_id = 7 FOR UPDATE;

SELECT COUNT(*) FROM orders WHERE customer_id = 7 AND status = 'PENDING';
-- insert only if count < 3
INSERT INTO orders ...;
COMMIT;
```

This technique, *materialising the conflict*, works in every database and at every isolation level.

### PostgreSQL SERIALIZABLE (SSI)

Since version 9.1, PostgreSQL implements **Serializable Snapshot Isolation (SSI)**. Transactions run on snapshots as in REPEATABLE READ, and the database also tracks read/write dependencies between concurrent transactions. When the dependencies could form a cycle that no serial order could produce, one transaction is aborted.

```
Time  Session A (SERIALIZABLE)                Session B (SERIALIZABLE)
────  ──────────────────────────────────────  ──────────────────────────────────────
t1    SELECT COUNT(*) ... PENDING → 2
t2                                            SELECT COUNT(*) ... PENDING → 2
t3    INSERT pending order; COMMIT;  ok
t4                                            INSERT pending order;
                                              COMMIT;
                                              ERROR: could not serialize access due to
                                              read/write dependencies among transactions
                                              (SQLSTATE 40001)
```

No explicit locks are needed. The rule holds as long as **every** transaction that touches the data runs at SERIALIZABLE.

### Using SERIALIZABLE well in PostgreSQL

| Practice | Reason |
|----------|--------|
| Retry on SQLSTATE `40001` | Failures are part of normal operation, not bugs |
| Keep transactions short | Fewer overlapping transactions, fewer failures |
| Index the columns in `WHERE` clauses | Predicate locks are taken on the index pages read. A sequential scan locks the whole table, which causes false conflicts |
| Declare read-only transactions: `BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE` | The transaction waits for a safe snapshot, then runs with no risk of failure and no tracking overhead |
| Size `max_pred_locks_per_transaction` for large transactions | Avoids escalation to relation-level locks (Section 9) |

### Choosing a level

```
Does the transaction make decisions based on data it read,
and could a concurrent transaction invalidate that decision?
        │
        ├── No ──► READ COMMITTED
        │
        ▼
Can the decision be made inside one statement or protected by FOR UPDATE on a known row?
        │
        ├── Yes ──► READ COMMITTED + atomic statement / FOR UPDATE
        │
        ▼
PostgreSQL ──► SERIALIZABLE with retry
Oracle     ──► materialise the conflict with FOR UPDATE
```

## 12. Transaction Contention

**Contention** means sessions spend time waiting for each other instead of working. Most contention comes from a few recurring patterns.

### Hot rows

Many transactions update the same row: a global counter, a stock level, an account balance.

```
T1 ──► UPDATE counter ──► commit
T2 ─────── wait ────────► UPDATE counter ──► commit
T3 ─────────────── wait ────────────────────► UPDATE counter ──► commit
       throughput limited to one transaction at a time on that row
```

| Fix | How |
|-----|-----|
| Hold the lock for less time | Update the hot row **last** in the transaction, just before commit |
| Avoid the shared row | Use a sequence (Oracle `SEQUENCE`, PostgreSQL `IDENTITY`) instead of a counter table |
| Spread the row | Split one counter into N slots, update a random slot, sum them when reading |
| Record, then aggregate | Insert movements into a ledger table; compute totals periodically |

### Long transactions

A transaction open for a long time holds its locks and, in PostgreSQL, holds back VACUUM for the whole database (Section 3).

```sql
-- PostgreSQL: sessions with the oldest open transactions
SELECT pid, state, now() - xact_start AS xact_age, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start
LIMIT 10;
```

```sql
-- Oracle: active transactions and how long they have been open
SELECT s.sid, s.username, t.start_time, s.status, s.sql_id
FROM v$transaction t JOIN v$session s ON s.taddr = t.addr
ORDER BY t.start_time;
```

Common causes: user interaction inside a transaction, calls to external services before commit, and connection pools that return connections with an open transaction.

### Queue tables

Several workers take jobs from one table. With plain `FOR UPDATE`, every worker locks the same first row and the rest wait. `SKIP LOCKED` lets each worker take a different row:

```sql
-- PostgreSQL
SELECT order_id FROM orders
WHERE status = 'PENDING'
ORDER BY order_id
LIMIT 10
FOR UPDATE SKIP LOCKED;
```

```sql
-- Oracle
SELECT order_id FROM orders
WHERE status = 'PENDING'
ORDER BY order_id
FETCH FIRST 10 ROWS ONLY
FOR UPDATE SKIP LOCKED;
```

On older Oracle releases, combining `FETCH FIRST` with `FOR UPDATE` raises an error. The usual workaround is a cursor with `FOR UPDATE SKIP LOCKED` that fetches the first N rows.

### Hot index blocks (Oracle)

Inserts with increasing keys, such as sequence values, all go to the rightmost leaf block of the index. With many sessions inserting at once this shows up as `enq: TX - index contention` and `buffer busy waits`. Remedies include a hash-partitioned index, a reverse-key index (which cannot serve range scans), or Oracle 18c+ **scalable sequences**, which add an instance- and session-based prefix to spread inserts.

### Finding who blocks whom

**PostgreSQL**

```sql
SELECT pid,
       pg_blocking_pids(pid) AS blocked_by,
       wait_event_type, wait_event,
       now() - query_start AS waiting_for,
       query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Set `log_lock_waits = on` to log any lock wait longer than `deadlock_timeout`.

**Oracle**

```sql
SELECT sid, serial#, blocking_session, event, seconds_in_wait, sql_id
FROM v$session
WHERE blocking_session IS NOT NULL;
```

The wait event `enq: TX - row lock contention` means a session is waiting for a row lock held by another transaction.

| Field | Meaning |
|-------|---------|
| `pg_blocking_pids(pid)` / `BLOCKING_SESSION` | Session holding the lock |
| `wait_event_type = 'Lock'` / `event LIKE 'enq:%'` | Session is waiting for a lock |
| `state = 'idle in transaction'` (PostgreSQL) | Blocker is doing nothing but holding locks; usually an application bug |

## 13. A Systematic Approach to Blocking and Contention

```
1. Identify waiting sessions and their blockers
   PostgreSQL:  pg_stat_activity + pg_blocking_pids()
   Oracle:      V$SESSION.BLOCKING_SESSION, wait events
        │
        ▼
2. What is the blocker doing?
        │
        ├── idle in transaction / INACTIVE with open txn
        │        ──► application holds a transaction open; fix commit handling,
        │            set idle_in_transaction_session_timeout
        │
        ├── long-running statement
        │        ──► tune the statement (Chapters 01–03) or move it off-peak
        │
        └── DDL waiting for a lock
                 ──► lock_timeout / DDL_LOCK_TIMEOUT, run with retry
        │
        ▼
3. What kind of lock?
        │
        ├── row lock on the same few rows   ──► hot row pattern          Section 12
        ├── table lock                      ──► DDL, LOCK TABLE, or
        │                                       unindexed FK (Oracle)    Section 7
        └── ITL / index block waits (Oracle) ──► INITRANS, index design  Sections 9, 12
        │
        ▼
4. Deadlocks in the logs?
        ──► consistent lock order, shorter transactions, retry           Section 8
        │
        ▼
5. Serialization failures (ORA-08177, SQLSTATE 40001)?
        ──► retry loop; shorter transactions; indexes for predicate locks Section 11
        │
        ▼
6. Correctness issues (lost updates, broken business rules)?
        ──► atomic statements, FOR UPDATE, version columns,
            or SERIALIZABLE                                          Sections 10, 11
```

## 14. Oracle and PostgreSQL Reference

| Item | Oracle | PostgreSQL |
|------|--------|------------|
| Transaction start | Implicit with first DML | `BEGIN`; autocommit otherwise |
| DDL in a transaction | Implicit commit | Transactional |
| Failed statement | Only the statement is rolled back | Whole transaction aborted; use `SAVEPOINT` |
| Durability log | Redo log (LGWR) | WAL |
| Asynchronous commit | `COMMIT WRITE BATCH NOWAIT` | `synchronous_commit = off` |
| Old row versions | Undo tablespace | In the table; removed by `VACUUM` |
| Long snapshot risk | ORA-01555 snapshot too old | Bloat everywhere; wraparound pressure |
| Default isolation | READ COMMITTED | READ COMMITTED |
| Snapshot isolation | `SERIALIZABLE` | `REPEATABLE READ` |
| True serializable | Not available | `SERIALIZABLE` (SSI) |
| Serialization error | ORA-08177 | SQLSTATE `40001` |
| Row lock storage | ITL in the data block | Tuple header (`xmax`, multixact) |
| Row lock modes | `FOR UPDATE` | `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` |
| Lock wait options | `NOWAIT`, `WAIT n`, `SKIP LOCKED` | `NOWAIT`, `SKIP LOCKED`, `lock_timeout` |
| DML table lock | Row Exclusive (TM) | `ROW EXCLUSIVE` |
| DDL blocks queries | No | Yes (`ACCESS EXCLUSIVE`) |
| DDL wait limit | `DDL_LOCK_TIMEOUT` | `lock_timeout` |
| Deadlock error | ORA-00060; statement rolled back | SQLSTATE `40P01`; transaction aborted |
| Deadlock check delay | A few seconds | `deadlock_timeout` (1 s) |
| Row lock escalation | Never | Never (predicate locks escalate under SERIALIZABLE) |
| Row version marker | `ORA_ROWSCN` (`ROWDEPENDENCIES` for row-level) | `xmin` |
| Blocking sessions | `V$SESSION.BLOCKING_SESSION` | `pg_blocking_pids()` |
| Lock view | `V$LOCK` | `pg_locks` |
| Idle transaction guard | Profile `IDLE_TIME`, application settings | `idle_in_transaction_session_timeout` |

## 15. Short Summary

- ACID is delivered by logging for durability and by versioning plus locks for isolation. Oracle keeps old versions in undo; PostgreSQL keeps them in the table and relies on VACUUM.
- With MVCC, readers and writers never block each other. Only writers on the same row wait.
- Neither database allows dirty reads. Oracle SERIALIZABLE and PostgreSQL REPEATABLE READ are snapshot isolation, which still allows write skew. Only PostgreSQL SERIALIZABLE prevents it.
- Locks last until commit, so transaction length decides how long others wait. In PostgreSQL, most DDL blocks reads as well as writes, so run it with a lock timeout.
- Deadlocks come from inconsistent lock order. Lock in a fixed order, keep transactions short, and always retry the victim.
- Oracle and PostgreSQL store row locks in the data itself, so they never escalate row locks to table locks.
- Prevent lost updates with a single atomic statement where possible, otherwise with `FOR UPDATE` (pessimistic) or a version column (optimistic).
- Contention usually comes from hot rows, long or idle transactions, queue tables without `SKIP LOCKED`, and, in Oracle, unindexed foreign keys.
