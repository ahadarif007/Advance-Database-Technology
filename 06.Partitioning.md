# Chapter 06: Partitioning

Partitioning splits one large table into smaller physical pieces, called **partitions**, while applications still see a single table. A query for January can read only the January partition. A year of old data can be removed in milliseconds instead of hours. Maintenance can run on one piece at a time.

```sql
SELECT *
FROM orders
WHERE order_date >= DATE '2026-01-01'
  AND order_date <  DATE '2026-02-01';
```

With the table range-partitioned by month on `order_date`, the database scans only the January 2026 partition rather than the entire table.

This chapter covers the partitioning methods in **Oracle** and **PostgreSQL**, how partition pruning and partition-wise joins work, how to maintain partitioned tables, and how to choose a partition key.

## 1. Sample Schema

The examples use partitioned versions of the Chapter 01 tables:

| Table | Partitioned by | Method |
|-------|----------------|--------|
| `orders_p` | `order_date`, one partition per month | Range |
| `customers_p` | `country` | List |
| `order_items_p` | `order_id` | Hash |

The monthly partitions of `orders_p` run from January 2020 to December 2026: 84 partitions in total.

**Availability.** In PostgreSQL, declarative partitioning is built in from version 10, with most features used here arriving in versions 11 to 14. In Oracle, partitioning is a separately licensed option of Enterprise Edition.

## 2. How Partitioning Works

```
                         orders_p  (logical table: no data of its own)
                               │
        ┌──────────────┬───────┴───────┬──────────────┬──────────────┐
        ▼              ▼               ▼              ▼              ▼
   2020-01        2020-02          ...            2026-01        2026-02 ...
   (segment /     (segment /                      (segment /
    table)         table)                          table)
```

- The **partitioned table** is a logical object. Applications query and modify it as usual.
- Each **partition** is stored separately: an Oracle segment, or a PostgreSQL table in its own right.
- The **partition key** is the column (or columns) whose value decides which partition a row belongs to.
- The database routes each `INSERT` to the correct partition, and each query only to the partitions that can contain matching rows.

### What partitioning does and does not do

| Benefit | Source |
|---------|--------|
| Faster queries that filter on the partition key | Partition pruning (Section 8) |
| Faster large joins between tables partitioned alike | Partition-wise joins (Section 9) |
| Instant removal of old data | Dropping a partition instead of deleting rows (Section 10) |
| Maintenance on one piece at a time | Per-partition rebuild, compress, vacuum, statistics |
| Different storage per partition | Old partitions on cheaper storage or compressed |

Partitioning is not a substitute for indexes. A query that looks up one order by `order_id` without the partition key has to check every partition, which is **slower** than one index lookup on an unpartitioned table. Partitioning pays off for large tables whose queries and maintenance naturally follow the partition key.

## 3. Range Partitioning

Each partition holds a continuous range of key values. It is the natural choice for dates and other steadily increasing values.

```
order_date:  ── 2025-12 ──┬── 2026-01 ──┬── 2026-02 ──┬── 2026-03 ──►
                          │             │             │
                 ...  p_2025_12     p_2026_01     p_2026_02     ...
                  lower bound included, upper bound excluded
```

### PostgreSQL

```sql
CREATE TABLE orders_p (
    order_id     BIGINT        NOT NULL,
    customer_id  BIGINT        NOT NULL,
    status       TEXT          NOT NULL,
    order_date   DATE          NOT NULL,
    total_amount NUMERIC(12,2) NOT NULL,
    PRIMARY KEY (order_id, order_date)
) PARTITION BY RANGE (order_date);

CREATE TABLE orders_2026_01 PARTITION OF orders_p
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE orders_2026_02 PARTITION OF orders_p
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
-- ... one per month

CREATE TABLE orders_default PARTITION OF orders_p DEFAULT;
```

- `FROM` is inclusive, `TO` is exclusive.
- The `DEFAULT` partition (version 11+) catches rows that fit no other partition. Without it, such an insert fails.
- PostgreSQL does **not** create partitions automatically. They must exist before data arrives. The `pg_partman` extension, or a scheduled job, creates them ahead of time.
- The primary key must include the partition key. Section 7 explains why.

### Oracle

```sql
CREATE TABLE orders_p (
    order_id     NUMBER        NOT NULL,
    customer_id  NUMBER        NOT NULL,
    status       VARCHAR2(20)  NOT NULL,
    order_date   DATE          NOT NULL,
    total_amount NUMBER(12,2)  NOT NULL,
    CONSTRAINT pk_orders_p PRIMARY KEY (order_id)
)
PARTITION BY RANGE (order_date)
INTERVAL (NUMTOYMINTERVAL(1, 'MONTH'))
(
    PARTITION p_before_2020 VALUES LESS THAN (DATE '2020-01-01')
);
```

- `VALUES LESS THAN` is exclusive.
- **Interval partitioning** (11g+) creates a new monthly partition automatically the first time a row for that month is inserted. Only the first partition is defined by hand. Automatically created partitions get system names such as `SYS_P1234`. Refer to them with `PARTITION FOR (DATE '2026-01-15')`.
- Without `INTERVAL`, every partition is listed explicitly, and a `MAXVALUE` partition plays the role of a default.
- The primary key on `order_id` alone is allowed; Oracle backs it with a global index (Section 7).

## 4. List Partitioning

Each partition holds an explicit set of values. It suits columns with a small, known set of values, such as region, country or tenant.

```
country:   UK ──► p_uk
           FR ──► p_eu
           DE ──► p_eu
           (other) ──► p_other
```

### PostgreSQL

```sql
CREATE TABLE customers_p (
    customer_id BIGINT NOT NULL,
    name        TEXT   NOT NULL,
    email       TEXT   NOT NULL,
    country     TEXT   NOT NULL,
    city        TEXT   NOT NULL,
    PRIMARY KEY (customer_id, country)
) PARTITION BY LIST (country);

CREATE TABLE customers_uk    PARTITION OF customers_p FOR VALUES IN ('UK');
CREATE TABLE customers_eu    PARTITION OF customers_p FOR VALUES IN ('FR', 'DE');
CREATE TABLE customers_other PARTITION OF customers_p DEFAULT;
```

### Oracle

```sql
CREATE TABLE customers_p (
    customer_id NUMBER        PRIMARY KEY,
    name        VARCHAR2(100) NOT NULL,
    email       VARCHAR2(200) NOT NULL,
    country     VARCHAR2(2)   NOT NULL,
    city        VARCHAR2(50)  NOT NULL
)
PARTITION BY LIST (country)
(
    PARTITION p_uk    VALUES ('UK'),
    PARTITION p_eu    VALUES ('FR', 'DE'),
    PARTITION p_other VALUES (DEFAULT)
);
```

Oracle 12.2+ also offers **automatic list partitioning** (`PARTITION BY LIST (country) AUTOMATIC`), which creates a new partition for each new value, in the same way that interval partitioning works for ranges.

List partitions are often unevenly sized. Here `p_uk` holds 80% of customers. This is acceptable when the aim is pruning or per-region maintenance, but not when the aim is to spread work evenly.

## 5. Hash Partitioning

A hash function on the key decides the partition. Rows spread evenly, but values that are close together land in unrelated partitions.

```
order_id ──► hash() ──► remainder of division by 4
   1001  ──►  ...   ──►  2 ──► p2
   1002  ──►  ...   ──►  0 ──► p0
   1003  ──►  ...   ──►  3 ──► p3
   1004  ──►  ...   ──►  2 ──► p2

p0 ████████   p1 ████████   p2 ████████   p3 ████████    roughly equal
```

Hash partitioning is used to:

- spread a large table evenly when no natural range or list exists,
- enable partition-wise joins between tables hashed on the same key (Section 9),
- reduce contention on busy index blocks and table blocks (Chapter 04, Section 12).

It does **not** help range queries. Pruning is possible only for equality on the key.

### PostgreSQL (version 11+)

```sql
CREATE TABLE order_items_p (
    order_id   BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity   INT    NOT NULL,
    PRIMARY KEY (order_id, product_id)
) PARTITION BY HASH (order_id);

CREATE TABLE order_items_p0 PARTITION OF order_items_p FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE order_items_p1 PARTITION OF order_items_p FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE order_items_p2 PARTITION OF order_items_p FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE order_items_p3 PARTITION OF order_items_p FOR VALUES WITH (MODULUS 4, REMAINDER 3);
```

### Oracle

```sql
CREATE TABLE order_items_p (
    order_id   NUMBER NOT NULL,
    product_id NUMBER NOT NULL,
    quantity   NUMBER NOT NULL,
    CONSTRAINT pk_order_items_p PRIMARY KEY (order_id, product_id)
)
PARTITION BY HASH (order_id)
PARTITIONS 4;
```

In Oracle, use a **power of two** for the number of hash partitions (4, 8, 16, ...). Other numbers produce uneven partition sizes. Changing the count later requires `ADD PARTITION` or `COALESCE PARTITION` in Oracle, which redistribute rows, or a rebuild in PostgreSQL. Choose the count with growth in mind.

## 6. Composite Partitioning

Composite partitioning applies a second method inside each partition. The partitions are divided into **subpartitions**.

The most common combination is **range–hash**: range by date for pruning and data lifecycle, then hash by another key to spread each month's data and enable partition-wise joins.

```
                orders_p
                   │
     ┌─────────────┼─────────────┐              range by order_date
     ▼             ▼             ▼
  2026-01       2026-02       2026-03
  ┌──┬──┬──┬──┐ ┌──┬──┬──┬──┐ ┌──┬──┬──┬──┐     hash by customer_id
  │h0│h1│h2│h3│ │h0│h1│h2│h3│ │h0│h1│h2│h3│
  └──┴──┴──┴──┘ └──┴──┴──┴──┘ └──┴──┴──┴──┘

WHERE order_date in January AND customer_id = 42   ──►   one subpartition
```

### Oracle

```sql
CREATE TABLE orders_p (
    order_id     NUMBER NOT NULL,
    customer_id  NUMBER NOT NULL,
    status       VARCHAR2(20),
    order_date   DATE   NOT NULL,
    total_amount NUMBER(12,2)
)
PARTITION BY RANGE (order_date)
INTERVAL (NUMTOYMINTERVAL(1, 'MONTH'))
SUBPARTITION BY HASH (customer_id) SUBPARTITIONS 4
(
    PARTITION p_before_2020 VALUES LESS THAN (DATE '2020-01-01')
);
```

Oracle supports every combination of range, list and hash at both levels (for example range–list, list–range, hash–hash). A `SUBPARTITION TEMPLATE` defines the same subpartitions for every partition.

### PostgreSQL

PostgreSQL implements composite partitioning by making a partition itself a partitioned table:

```sql
CREATE TABLE orders_2026_01 PARTITION OF orders_p
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01')
    PARTITION BY HASH (customer_id);

CREATE TABLE orders_2026_01_h0 PARTITION OF orders_2026_01 FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE orders_2026_01_h1 PARTITION OF orders_2026_01 FOR VALUES WITH (MODULUS 4, REMAINDER 1);
-- ... h2, h3
```

Each level can use any method, and different partitions can even be subdivided differently.

### The cost of more partitions

Monthly partitions for 7 years with 4 subpartitions each make 336 storage objects. Every object adds metadata, planning work and files to manage. In PostgreSQL, planning time grows with the number of partitions a query cannot rule out early. Use composite partitioning when both levels serve a clear purpose, not by default.

## 7. Indexes on Partitioned Tables

Indexes on partitioned tables come in two kinds, and the difference affects uniqueness, pruning and maintenance.

```
Local index: one index piece per partition          Global index: one index for the whole table

  p_2026_01   p_2026_02   p_2026_03                   p_2026_01   p_2026_02   p_2026_03
  ┌───────┐   ┌───────┐   ┌───────┐                   ┌───────┐   ┌───────┐   ┌───────┐
  │ table │   │ table │   │ table │                   │ table │   │ table │   │ table │
  └───┬───┘   └───┬───┘   └───┬───┘                   └───▲───┘   └───▲───┘   └───▲───┘
  ┌───┴───┐   ┌───┴───┐   ┌───┴───┐                       └───────────┼───────────┘
  │ index │   │ index │   │ index │                          ┌────────┴────────┐
  └───────┘   └───────┘   └───────┘                          │  single index   │
                                                             └─────────────────┘
  dropping a partition drops its index piece          dropping a partition leaves stale entries
```

| | Local | Global |
|---|---|---|
| Structure | One index per partition, partitioned like the table | One index across all partitions (optionally partitioned by its own key) |
| Partition maintenance | Only the affected piece changes | Must be maintained or rebuilt |
| Unique on a column not in the partition key | Not possible | Possible |
| Lookup without the partition key | Searches every piece | One search |
| Oracle | `CREATE INDEX ... LOCAL` | Default for `CREATE INDEX` on a partitioned table |
| PostgreSQL | The only kind (version 11+: index on the parent is created on every partition) | Not available |

### Uniqueness

A local index can only guarantee uniqueness **within** each partition. Two partitions could each hold `order_id = 1001` unless the partition key is part of the unique key, which ensures that equal keys always land in the same partition.

- **PostgreSQL** therefore requires every primary key and unique constraint to include all partition key columns. That is why `orders_p` uses `PRIMARY KEY (order_id, order_date)`.
- **Oracle** can enforce `PRIMARY KEY (order_id)` with a global index, at the cost of global index maintenance.

### Global index maintenance (Oracle)

Dropping or truncating a partition leaves entries in global indexes that point to rows that no longer exist. Without extra clauses, the global index becomes `UNUSABLE` and queries that rely on it fail or fall back to other plans.

```sql
ALTER TABLE orders_p DROP PARTITION FOR (DATE '2020-01-15') UPDATE GLOBAL INDEXES;
```

From Oracle 12c, `UPDATE GLOBAL INDEXES` on `DROP` and `TRUNCATE` is a fast metadata operation. The stale entries are cleaned up later by a scheduled job (asynchronous global index maintenance).

## 8. Partition Pruning

**Partition pruning** removes partitions that cannot contain matching rows from the plan. It is the main performance benefit of partitioning.

```
WHERE order_date >= DATE '2026-01-01' AND order_date < DATE '2026-02-01'

 2020-01  2020-02   ...   2025-12  2026-01  2026-02   ...   2026-12
 [skip]   [skip]    ...   [skip]   [SCAN]   [skip]    ...   [skip]

 1 of 84 partitions read
```

### Static pruning: key known at planning time

**PostgreSQL**

```sql
EXPLAIN
SELECT * FROM orders_p
WHERE order_date >= DATE '2026-01-01' AND order_date < DATE '2026-02-01';
```

```
Seq Scan on orders_2026_01 orders_p
  Filter: ((order_date >= '2026-01-01'::date) AND (order_date < '2026-02-01'::date))
```

Only the January 2026 partition appears. Without pruning, the plan would show an `Append` node over all 85 partitions, including the default.

**Oracle**

```
---------------------------------------------------------------------
| Id | Operation               | Name     | Pstart | Pstop |
---------------------------------------------------------------------
|  0 | SELECT STATEMENT        |          |        |       |
|  1 |  PARTITION RANGE SINGLE |          |     74 |    74 |
|* 2 |   TABLE ACCESS FULL     | ORDERS_P |     74 |    74 |
---------------------------------------------------------------------
```

| Field | Meaning |
|-------|---------|
| `PARTITION RANGE SINGLE` | Exactly one partition is accessed |
| `PARTITION RANGE ITERATOR` | A contiguous set of partitions |
| `PARTITION RANGE ALL` | No pruning: every partition |
| `Pstart` / `Pstop` | First and last partition number accessed. Partition 74 is January 2026: `p_before_2020` is 1, and January 2020 is 2 |
| `KEY` in `Pstart` / `Pstop` | Partitions decided at run time |

### Dynamic pruning: key known only at run time

With bind variables, or values produced by another part of the query, pruning happens during execution.

**PostgreSQL** (version 11+):

```sql
PREPARE q(date, date) AS
SELECT * FROM orders_p WHERE order_date >= $1 AND order_date < $2;

EXPLAIN (ANALYZE) EXECUTE q('2026-01-01', '2026-02-01');
```

```
Append  (actual rows=... loops=1)
  Subplans Removed: 84
  -> Seq Scan on orders_2026_01 orders_p_1
       Filter: ((order_date >= $1) AND (order_date < $2))
```

`Subplans Removed` counts the partitions pruned at execution time. PostgreSQL also prunes at run time in a nested loop, where the partitioned table is the inner side and the key comes from the outer row. Pruning is controlled by `enable_partition_pruning` (default on).

**Oracle** shows `KEY` in `Pstart`/`Pstop` for bind variables. For joins, Oracle can build a **Bloom filter** from the other table and use it to skip partitions. This is called join-filter pruning and appears as `:BF0000` in `Pstart`/`Pstop`.

### What prevents pruning

Pruning requires a condition that the optimizer can compare directly with the partition bounds. The same rules as for index use apply (Chapter 01, Section 11):

| Condition | Pruned | Reason |
|-----------|:------:|--------|
| `order_date >= DATE '2026-01-01' AND order_date < DATE '2026-02-01'` | Yes | Direct range on the key |
| `order_date BETWEEN :a AND :b` | Yes, at run time | Bind values |
| `EXTRACT(MONTH FROM order_date) = 1` | No | Function on the key |
| `TRUNC(order_date) = DATE '2026-01-15'` (Oracle) | No | Function on the key |
| `TO_CHAR(order_date, 'YYYY-MM') = '2026-01'` | No | Function on the key; conversion to text |
| `order_date >= '2026-01-01'` compared as text | Depends | Implicit conversion may apply to the column instead of the literal |
| `customer_id = 42` on a table partitioned by date | No | Not the partition key |
| `order_date = :d OR customer_id = 42` | No | The `OR` branch without the key can match anywhere |

Check pruning in the actual plan whenever a query on a partitioned table is slower than expected.

## 9. Partition-Wise Joins

Chapter 03 (Section 12) introduced partition-wise joins for large tables. A **full partition-wise join** joins matching partitions of two tables pair by pair, instead of joining the whole tables.

```
Normal join                                  Full partition-wise join
                                             (both hashed by order_id into 4)
orders ──────────┐                           orders_h0 ⋈ order_items_p0
                 ├──► one large hash join    orders_h1 ⋈ order_items_p1
order_items ─────┘    (one large hash        orders_h2 ⋈ order_items_p2
                       table; may spill)     orders_h3 ⋈ order_items_p3
                                             four small joins; each fits in memory,
                                             and they can run in parallel
```

The examples in this section assume a table `orders_h`: `orders` hash-partitioned by `order_id` into 4 partitions, matching `order_items_p` (Section 5).

### Requirements

- Both tables are partitioned on the **join key**.
- They use the **same method** and **compatible bounds** (the same hash count, or matching ranges).
- The query joins on the partition key columns.

### PostgreSQL

Partition-wise join is **off** by default because it increases planning time:

```sql
SET enable_partitionwise_join = on;
SET enable_partitionwise_aggregate = on;   -- aggregates per partition, too
```

```
Append
  -> Hash Join
        Hash Cond: (oi.order_id = o.order_id)
        -> Seq Scan on order_items_p0 oi
        -> Hash
              -> Seq Scan on orders_h0 o
  -> Hash Join
        Hash Cond: (oi.order_id = o.order_id)
        -> Seq Scan on order_items_p1 oi
        -> Hash
              -> Seq Scan on orders_h1 o
  ...
```

Each partition pair has its own join under the `Append`. From version 13, the partitions can be matched even when the bounds are not exactly identical, as long as each partition of one table corresponds to at most one of the other.

### Oracle

Full partition-wise joins are chosen automatically when the tables are equi-partitioned on the join key:

```
|  1 |  PARTITION HASH ALL |             |  1 |  4 |
|* 2 |   HASH JOIN         |             |    |    |
|  3 |    TABLE ACCESS FULL| ORDERS_H    |  1 |  4 |
|  4 |    TABLE ACCESS FULL| ORDER_ITEMS_P |  1 |  4 |
```

The `PARTITION HASH ALL` iterator sits **above** the `HASH JOIN`. That placement means the join runs once per partition pair. In parallel plans it appears as `PX PARTITION HASH ALL`.

Oracle also supports **partial partition-wise joins** in parallel execution. Only one table is partitioned on the join key, and rows of the other table are redistributed on the fly to match its partitions.

### Range–hash and partition-wise joins

With the composite layout from Section 6, a join between `orders_p` (range by date, hash by `customer_id`) and a table hashed by `customer_id` into the same number of partitions can run partition-wise at the subpartition level, within each monthly partition.

## 10. Partition Maintenance

Much of the value of partitioning is operational. Whole partitions can be added, removed, loaded and reorganised as units.

### Rolling window

The most common pattern: keep a fixed period of data, add new partitions ahead of time, and remove the oldest.

```
Before:   [2019-12] [2020-01] [2020-02] ... [2026-11] [2026-12]
                ▲                                              ▲
             drop                                     add 2027-01 in advance

After:    [2020-01] [2020-02] ... [2026-11] [2026-12] [2027-01]
```

Removing a month by `DELETE` touches every row, generates undo and redo or WAL for each, and leaves bloat. Dropping a partition is a metadata change.

| Operation | `DELETE` of one month (~15,000 rows here, millions in production) | Drop partition |
|-----------|---------|----------------|
| Rows processed | Every row | None |
| Log volume | Proportional to rows | Minimal |
| Space returned | No (bloat / high water mark) | Yes, immediately |
| Duration | Minutes to hours | Milliseconds to seconds |

**PostgreSQL**

```sql
-- Create next month ahead of time
CREATE TABLE orders_2027_01 PARTITION OF orders_p
    FOR VALUES FROM ('2027-01-01') TO ('2027-02-01');

-- Remove the oldest month without blocking queries (version 14+)
ALTER TABLE orders_p DETACH PARTITION orders_2020_01 CONCURRENTLY;
DROP TABLE orders_2020_01;       -- or archive it first
```

A plain `DETACH PARTITION` takes an `ACCESS EXCLUSIVE` lock on the parent, blocking all queries (Chapter 04, Section 7). `CONCURRENTLY` avoids this but cannot run inside a transaction block.

**Oracle**

```sql
-- Interval partitioning adds new months automatically

ALTER TABLE orders_p DROP PARTITION FOR (DATE '2020-01-15') UPDATE GLOBAL INDEXES;

-- Or empty it but keep the partition
ALTER TABLE orders_p TRUNCATE PARTITION FOR (DATE '2020-01-15') UPDATE GLOBAL INDEXES;
```

### Bulk loading with exchange or attach

Load and index data in a separate table, then swap it into the partitioned table in one metadata operation. Queries never see a half-loaded partition.

```
1. create staging table with the same structure
2. load data into staging  (direct path / COPY, no impact on orders_p)
3. build indexes, gather statistics on staging
4. swap staging in as a partition  (metadata only)
```

**Oracle**: `EXCHANGE PARTITION` swaps the segment of a partition with a table:

```sql
ALTER TABLE orders_p
    EXCHANGE PARTITION FOR (DATE '2027-01-15') WITH TABLE orders_stage
    INCLUDING INDEXES WITHOUT VALIDATION
    UPDATE GLOBAL INDEXES;
```

`WITHOUT VALIDATION` skips checking that every row belongs in the partition. Use it only when the load process guarantees this.

**PostgreSQL**: `ATTACH PARTITION` turns an existing table into a partition:

```sql
-- A matching CHECK constraint lets ATTACH skip its validation scan
ALTER TABLE orders_stage
    ADD CONSTRAINT chk_range CHECK (order_date >= '2027-01-01' AND order_date < '2027-02-01');

ALTER TABLE orders_p ATTACH PARTITION orders_stage
    FOR VALUES FROM ('2027-01-01') TO ('2027-02-01');
```

Since version 12, `ATTACH PARTITION` takes only a `SHARE UPDATE EXCLUSIVE` lock on the parent, so queries and DML continue. Without the `CHECK` constraint, it scans the whole table to validate the rows. If a `DEFAULT` partition exists, it is also scanned for rows that belong in the new range.

### Reorganising partitions

| Task | Oracle | PostgreSQL |
|------|--------|------------|
| Split one partition into two | `SPLIT PARTITION` (online from 12.2) | Not available; create new partitions and move rows |
| Merge partitions | `MERGE PARTITIONS` | Not available; same approach |
| Move or compress an old partition | `MOVE PARTITION ... COMPRESS ... ONLINE` | Per-partition `ALTER TABLE ... SET TABLESPACE`; rebuild with `pg_repack` |
| Convert a normal table to partitioned | `ALTER TABLE ... MODIFY PARTITION BY ... ONLINE` (12.2+) | Not available in place; create a partitioned table and attach or copy data |
| Rebuild one partition's index | `ALTER INDEX ... REBUILD PARTITION ... ONLINE` | `REINDEX TABLE CONCURRENTLY` on the partition |

### Statistics

- **PostgreSQL**: autovacuum analyzes each partition, but **not the partitioned parent table**. Queries that span partitions use the parent's statistics, so run `ANALYZE orders_p` after large data changes, for example on a schedule after each load.
- **Oracle**: statistics exist per partition and for the whole table. Gathering global statistics by scanning everything is expensive. **Incremental statistics** build them from per-partition summaries, so only changed partitions are scanned:

```sql
EXEC DBMS_STATS.SET_TABLE_PREFS(USER, 'ORDERS_P', 'INCREMENTAL', 'TRUE');
EXEC DBMS_STATS.GATHER_TABLE_STATS(USER, 'ORDERS_P');
```

## 11. Choosing Partition Keys

The partition key is hard to change later, so choose it deliberately. Four questions decide it.

### 1. Which column do the important queries filter on?

Pruning only works on the key. If most queries filter by date, partition by date. If most filter by tenant, partition by tenant. A key that the main queries do not use makes every query scan every partition.

### 2. How does data leave the table?

If data is removed by age, a time-based range key turns retention into dropping partitions. This benefit alone often justifies partitioning.

### 3. Will the partitions be of reasonable and similar size?

```
Too few, too large                Balanced                      Too many, too small
[████████████████████]            [████] [████] [████] [████]   [▪][▪][▪][▪][▪][▪][▪][▪][▪]...
little pruning benefit            good pruning, manageable      planning overhead, many files,
                                  maintenance                   poor statistics per partition
```

| Guideline | Reason |
|-----------|--------|
| Partition tables that are large (typically tens of GB or more) or need data lifecycle management | Smaller tables rarely benefit |
| Aim for partitions from a few GB to tens of GB | Large enough to avoid overhead, small enough for fast maintenance |
| Keep the total in the hundreds, or low thousands at most | Planning time, metadata and open files grow with the count |
| Watch skew in list partitioning | One huge partition limits the benefit |

For `orders` with a million rows, about 65 MB, partitioning is not needed at all. The examples in this chapter show the technique at a size where it is easy to follow.

### 4. Is the key stable?

Updating a partition key column moves the row to another partition. That is effectively a delete plus an insert:

- **PostgreSQL** (version 11+) moves the row automatically.
- **Oracle** requires `ALTER TABLE ... ENABLE ROW MOVEMENT`. Otherwise the update fails.

In both, the row's address changes, and the move costs far more than an in-place update. Choose a key that is set once, such as an order date, not one that changes, such as a status.

### Common choices

| Table type | Typical key | Method |
|------------|-------------|--------|
| Orders, events, logs, transactions | Creation date | Range (interval in Oracle), monthly or daily |
| Multi-tenant data | Tenant ID | List (few large tenants) or hash (many tenants) |
| Regional data with regional operations | Region or country | List |
| Large table joined on a key, no natural range | Join key | Hash |
| Time-series with a large per-period volume | Date, then entity ID | Range–hash |

### Unique keys and the partition key

Because PostgreSQL requires the partition key in every unique constraint (Section 7), partitioning `orders` by `order_date` means `order_id` alone cannot be enforced as unique by the database. Common responses:

- Accept `(order_id, order_date)` as the key, and generate `order_id` from a sequence so that duplicates cannot arise in practice.
- Carry `order_date` in foreign keys that reference the table.
- In Oracle, use a global unique index on `order_id`, and accept its maintenance cost.

## 13. Oracle and PostgreSQL Reference

| Item | Oracle | PostgreSQL |
|------|--------|------------|
| Availability | Enterprise Edition, Partitioning option | Built in (10+) |
| Range | `PARTITION BY RANGE ... VALUES LESS THAN` | `PARTITION BY RANGE ... FOR VALUES FROM ... TO` |
| Automatic range partitions | `INTERVAL` | None; `pg_partman` or scheduled jobs |
| List | `PARTITION BY LIST ... VALUES (...)` | `PARTITION BY LIST ... FOR VALUES IN (...)` |
| Automatic list partitions | `AUTOMATIC` (12.2+) | None |
| Hash | `PARTITION BY HASH ... PARTITIONS n` (use a power of two) | `FOR VALUES WITH (MODULUS n, REMAINDER r)` (11+) |
| Default partition | `MAXVALUE` (range), `DEFAULT` (list) | `DEFAULT` (11+) |
| Composite | `SUBPARTITION BY`, all combinations | A partition that is itself partitioned |
| Local index | `LOCAL` | Index on the parent (11+) |
| Global index | Default; partitioned or not | Not available |
| Unique key without partition key | Global index | Not allowed |
| Pruning in plans | `PARTITION RANGE SINGLE / ITERATOR / ALL`, `Pstart` / `Pstop` | Only surviving partitions shown; `Subplans Removed` |
| Run-time pruning | `KEY`; Bloom filter `:BF0000` | Execution-time pruning (11+) |
| Partition-wise join | Automatic; full and partial | `enable_partitionwise_join` (default off) |
| Partition-wise aggregate | Automatic | `enable_partitionwise_aggregate` (default off) |
| Drop old data | `DROP PARTITION ... UPDATE GLOBAL INDEXES` | `DETACH PARTITION ... CONCURRENTLY` (14+), `DROP TABLE` |
| Load in bulk | `EXCHANGE PARTITION` | `ATTACH PARTITION` with a matching `CHECK` |
| Split / merge | `SPLIT PARTITION`, `MERGE PARTITIONS` | Not available |
| Convert existing table | `MODIFY PARTITION BY ... ONLINE` (12.2+) | Not available in place |
| Row moves on key update | `ENABLE ROW MOVEMENT` required | Automatic (11+) |
| Whole-table statistics | Incremental statistics | Manual `ANALYZE` on the parent |

## 14. Short Summary

- Partitioning splits a large table into separately stored pieces behind one logical table. It helps queries through pruning and helps operations through per-partition maintenance.
- Range suits dates and increasing values, list suits small known value sets, and hash spreads data evenly and supports partition-wise joins. Composite partitioning combines two of these.
- Pruning only happens when the query compares the partition key directly, without functions or conversions. Verify it in the plan.
- Local indexes keep partition maintenance cheap. Unique keys must include the partition key in PostgreSQL; Oracle can use global indexes at a maintenance cost.
- Tables partitioned the same way on a join key can be joined partition by partition, which keeps each join small and parallel.
- Dropping, attaching and exchanging partitions replace slow bulk `DELETE` and `INSERT` with metadata operations.
- Choose a key that the main queries filter on, that matches how data ages out, that produces reasonably sized partitions, and that never changes.
