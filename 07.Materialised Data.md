# Chapter 07: Materialised Data

Some queries are expensive no matter how well they are tuned. A dashboard that sums a year of orders reads a year of orders every time it loads. **Materialised data** avoids this by computing the result once, storing it, and reading the stored result instead. The price is extra storage, extra work when the source data changes, and results that may be slightly out of date.

```
Normal view                         Materialised view
    │                                   │
    ▼                                   ▼
Query executed when accessed        Result stored physically
                                        │
                                        ▼
                                    Refresh required when source data changes
```

This chapter covers materialised views in **Oracle** and **PostgreSQL**, how they are refreshed, and the related design techniques: precomputed aggregates, summary tables, denormalisation and CQRS read models.

## 1. Sample Schema

The examples use the schema from Chapter 01:

```
customers (1) ───< orders (N) ───< order_items (N) >─── (1) products
```

| Table | Rows |
|-------|------|
| `customers` | 100,000 |
| `orders` | 1,000,000 across about 2,000 days |
| `order_items` | ~3,000,000 |
| `products` | 10,000 |

The running example is a daily sales report:

```sql
SELECT order_date,
       COUNT(*)          AS order_count,
       SUM(total_amount) AS revenue
FROM orders
GROUP BY order_date;
```

It reads 1,000,000 rows to produce about 2,000.

## 2. Views vs Materialised Views

A **view** is a stored query. It holds no data. Each time it is queried, the database merges its definition into the calling query and runs it against the base tables (Chapter 01, Section 11).

A **materialised view** stores the result of its query as real rows on disk. Queries read those rows directly.

| | View | Materialised view |
|---|---|---|
| Stores data | No | Yes |
| Query cost | Full cost of the underlying query, every time | Cost of reading the stored result |
| Freshness | Always current | As of the last refresh |
| Storage | None | Like a table |
| Can be indexed | No (indexes on base tables are used) | Yes |
| Write overhead | None | Refresh work; in some modes, extra work on every DML |

```
Query on a view                              Query on a materialised view

SELECT ... FROM v_daily_sales                SELECT ... FROM mv_daily_sales
      │                                            │
      ▼                                            ▼
scan orders (1,000,000 rows)                 scan mv_daily_sales (2,000 rows)
      │
      ▼
aggregate to 2,000 rows
```

Materialisation makes sense when a result is **read far more often than its source changes**, and when readers can accept data that is some seconds, minutes or hours old.

## 3. Materialised Views

### PostgreSQL (version 9.3+)

```sql
CREATE MATERIALIZED VIEW mv_daily_sales AS
SELECT order_date,
       COUNT(*)          AS order_count,
       SUM(total_amount) AS revenue
FROM orders
GROUP BY order_date
WITH DATA;

CREATE UNIQUE INDEX ux_mv_daily_sales ON mv_daily_sales (order_date);

SELECT * FROM mv_daily_sales WHERE order_date >= DATE '2025-01-01';
```

- `WITH DATA` (the default) runs the query immediately. `WITH NO DATA` creates an empty, unreadable view that must be refreshed first.
- The view can be indexed like a table. The unique index is also required for concurrent refresh (Section 4).
- Queries must name the materialised view explicitly. PostgreSQL never redirects a query on `orders` to it.
- Refresh is always manual: `REFRESH MATERIALIZED VIEW`. There is no automatic or incremental refresh in core PostgreSQL.

### Oracle

```sql
CREATE MATERIALIZED VIEW mv_daily_sales
BUILD IMMEDIATE
REFRESH COMPLETE ON DEMAND
ENABLE QUERY REWRITE
AS
SELECT order_date,
       COUNT(*)          AS order_count,
       SUM(total_amount) AS revenue
FROM orders
GROUP BY order_date;
```

| Clause | Options | Meaning |
|--------|---------|---------|
| Build | `BUILD IMMEDIATE`, `BUILD DEFERRED` | Populate now, or at the first refresh |
| Refresh method | `COMPLETE`, `FAST`, `FORCE` | Recompute everything, apply only changes, or fast if possible else complete (default `FORCE`) |
| Refresh timing | `ON DEMAND`, `ON COMMIT`, `ON STATEMENT` (12.2+), `START WITH ... NEXT ...` | Manual, at every commit, after every DML statement, or on a schedule |
| Query rewrite | `ENABLE QUERY REWRITE` | Allow the optimizer to answer queries on the base tables from this view |

Oracle stores the result in an ordinary table with the same name as the view (the *container table*), which can be indexed.

### Query rewrite (Oracle only)

With query rewrite, applications keep querying the base tables. The optimizer recognises that a materialised view can answer the query and reads it instead.

```sql
-- The application queries ORDERS, not the materialised view
SELECT order_date, SUM(total_amount)
FROM orders
WHERE order_date >= DATE '2025-01-01'
GROUP BY order_date;
```

```
--------------------------------------------------------------
| Id | Operation                    | Name           | Rows |
--------------------------------------------------------------
|  0 | SELECT STATEMENT             |                |  180 |
|* 1 |  MAT_VIEW REWRITE ACCESS FULL| MV_DAILY_SALES |  180 |
--------------------------------------------------------------
```

Rewrite also works when the query is **coarser** than the view. A query grouping by month can be answered by summing the daily rows (Section 6).

| Setting | Default | Meaning |
|---------|---------|---------|
| `QUERY_REWRITE_ENABLED` | `TRUE` | Rewrite allowed for the instance or session |
| `QUERY_REWRITE_INTEGRITY` | `ENFORCED` | Rewrite only if the view is fresh and all relationships used are enforced by constraints. `STALE_TOLERATED` also uses stale views. `TRUSTED` also relies on `RELY` constraints and declared dimensions |

If a query is not rewritten as expected, `DBMS_MVIEW.EXPLAIN_REWRITE` reports the reason.

## 4. Refresh Strategies

A refresh strategy answers two questions: **how** the stored result is updated, and **when**.

### How: complete or incremental

```
Complete refresh                          Incremental (fast) refresh
  discard stored result                     read only the changes since last refresh
  re-run the whole query                    apply them to the stored result
  cost ∝ size of the source data            cost ∝ size of the changes
```

| | Complete | Incremental |
|---|---|---|
| Cost | Full query every time | Proportional to changes |
| Works for any query | Yes | Only for supported query shapes (Section 5) |
| Needs change tracking | No | Yes (Oracle materialised view logs) |
| Best when | Most of the source changes between refreshes, or the query is complex | Small changes to a large source |

### When: timing

```
freshness
  high │  ON STATEMENT / ON COMMIT          every DML pays the refresh cost
       │
       │  real-time MV (Oracle)             stale data + changes merged at query time
       │
       │  frequent scheduled refresh        e.g. every 5 minutes
       │
  low  │  nightly batch refresh             cheapest; data up to a day old
       └──────────────────────────────────────────────────────────────►
                                            cost added to writes and to the system
```

| Timing | Oracle | PostgreSQL |
|--------|--------|------------|
| On every commit | `REFRESH FAST ON COMMIT` | Not available (triggers or `pg_ivm`, Section 5) |
| On every statement | `REFRESH FAST ON STATEMENT` (12.2+) | Not available |
| On demand | `DBMS_MVIEW.REFRESH` | `REFRESH MATERIALIZED VIEW` |
| Scheduled | `START WITH ... NEXT ...`, or `DBMS_SCHEDULER` | External scheduler or the `pg_cron` extension |
| At query time | Real-time materialised views (12.2+) | Not available |

`ON COMMIT` and `ON STATEMENT` keep the view exactly current, but every transaction that changes the base table also updates the view. For an aggregate view, many transactions update the same few summary rows, which creates the hot-row contention described in Chapter 04 (Section 12). Use them for low write rates only.

### Refreshing in PostgreSQL

```sql
-- Blocks all reads of the view until finished
REFRESH MATERIALIZED VIEW mv_daily_sales;

-- Readers continue to see the old contents during the refresh (version 9.4+)
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_sales;
```

| | Plain | `CONCURRENTLY` |
|---|---|---|
| Lock | `ACCESS EXCLUSIVE`: reads blocked | `EXCLUSIVE`: reads allowed |
| Method | Rebuild the view | Compute the new result, compare it with the old one, apply only the differing rows |
| Speed | Faster | Slower, especially when most rows change |
| Requirement | None | A unique index on plain columns that covers all rows |

Both forms re-run the **whole** query. `CONCURRENTLY` reduces blocking, not work.

Scheduling with `pg_cron`:

```sql
SELECT cron.schedule('refresh-daily-sales', '*/15 * * * *',
                     'REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_sales');
```

### Refreshing in Oracle

```sql
-- method: 'C' complete, 'F' fast, '?' force
EXEC DBMS_MVIEW.REFRESH('MV_DAILY_SALES', method => 'C');

-- Complete refresh with TRUNCATE + direct-path insert: much faster,
-- but the view is empty to readers during the refresh
EXEC DBMS_MVIEW.REFRESH('MV_DAILY_SALES', method => 'C', atomic_refresh => FALSE);
```

| Parameter | Effect |
|-----------|--------|
| `atomic_refresh => TRUE` (default) | Refresh in one transaction with `DELETE` and `INSERT`. Readers see the old data until commit. Slower, and generates more undo and redo |
| `atomic_refresh => FALSE` | `TRUNCATE` then direct-path `INSERT`. Faster, but readers briefly see an empty view |

Refresh groups (`DBMS_REFRESH`) refresh several views together as of the same point in time, so related summaries stay consistent with each other.

### Checking staleness

```sql
-- Oracle
SELECT mview_name, staleness, last_refresh_type, last_refresh_date
FROM user_mviews;
```

PostgreSQL does not track staleness. Record the refresh time yourself, for example in a small log table written by the refresh job.

## 5. Incremental Materialised Views

An incremental refresh applies only the changes since the last refresh. For aggregates, the principle is simple:

```
stored:   order_date 2026-01-15   order_count 480   revenue 51,200

changes since last refresh:
  + insert order, 2026-01-15, 300
  + insert order, 2026-01-15, 120
  − delete order, 2026-01-15,  80

new:      order_date 2026-01-15   order_count 481   revenue 51,540
          (480 + 2 − 1)                               (51,200 + 300 + 120 − 80)
```

Only the affected groups are touched, however large the base table is.

### What can be maintained incrementally

| Expression | Incremental | Reason |
|------------|:-----------:|--------|
| `COUNT(*)`, `SUM(x)` | Yes | Add inserted values, subtract deleted ones |
| `AVG(x)` | Yes, if `SUM(x)` and `COUNT(x)` are also stored | Recomputed from the two |
| `MIN(x)`, `MAX(x)` | On insert only | Deleting the current minimum requires rescanning the group |
| `COUNT(DISTINCT x)` | No | Cannot tell whether a deleted value still occurs elsewhere in the group |
| Joins | Yes, with restrictions | Each change must be joined to the other tables |
| Window functions, `UNION`, complex subqueries | Generally no | Too many rows depend on each change |

### Oracle: fast refresh

Fast refresh needs a **materialised view log** on each base table. The log records every changed row, much like a change journal:

```sql
CREATE MATERIALIZED VIEW LOG ON orders
WITH ROWID, SEQUENCE (order_date, total_amount)
INCLUDING NEW VALUES;

CREATE MATERIALIZED VIEW mv_daily_sales
REFRESH FAST ON DEMAND
ENABLE QUERY REWRITE
AS
SELECT order_date,
       COUNT(*)            AS order_count,
       COUNT(total_amount) AS amount_count,     -- required for fast refresh of SUM
       SUM(total_amount)   AS revenue
FROM orders
GROUP BY order_date;
```

```
DML on orders ──► row written to MLOG$_ORDERS (materialised view log)
                        │
    DBMS_MVIEW.REFRESH(..., 'F')
                        │
                        ▼
      apply logged changes to mv_daily_sales, then purge the log
```

Rules that trip people up:

- Aggregate views need `COUNT(*)`, and a `COUNT(col)` for every `SUM(col)` or `AVG(col)`, to be fast-refreshable after deletes and updates.
- The log must include every column the view uses, plus `ROWID`, `SEQUENCE` and `INCLUDING NEW VALUES` for aggregate views.
- The log adds work to every DML statement on the base table.

Check what a view supports before relying on it:

```sql
-- Requires MV_CAPABILITIES_TABLE (created by $ORACLE_HOME/rdbms/admin/utlxmv.sql)
EXEC DBMS_MVIEW.EXPLAIN_MVIEW('MV_DAILY_SALES');

SELECT capability_name, possible, msgtxt
FROM mv_capabilities_table
WHERE capability_name LIKE 'REFRESH_FAST%';
```

**Partition Change Tracking (PCT).** When the base table is partitioned (Chapter 06), Oracle can recompute only the parts of the view that come from changed partitions, even without a materialised view log.

**Real-time materialised views** (12.2+) combine the stored result with the pending log entries at query time. Queries get current results without waiting for a refresh:

```sql
CREATE MATERIALIZED VIEW mv_daily_sales
REFRESH FAST ON DEMAND
ENABLE ON QUERY COMPUTATION
ENABLE QUERY REWRITE
AS SELECT ...;
```

The query pays for merging the pending changes, so refresh regularly to keep that cost small.

### PostgreSQL: incremental options

Core PostgreSQL has no incremental refresh. The options are:

**The `pg_ivm` extension.** It provides *incrementally maintainable materialised views*, updated by triggers in the same transaction as each change:

```sql
CREATE EXTENSION pg_ivm;

SELECT create_immv('immv_daily_sales',
  'SELECT order_date, COUNT(*) AS order_count, SUM(total_amount) AS revenue
   FROM orders GROUP BY order_date');
```

It behaves like Oracle's `ON STATEMENT` refresh: always current, with the maintenance cost added to every write. It supports a restricted set of queries, so check its documentation for the version you use.

**A summary table maintained by your own code.** This is the most common approach, covered in Section 7.

## 6. Precomputed Aggregates

A precomputed aggregate stores totals at a chosen level of detail (the **grain**) so that reports do not sum the raw rows.

```
Raw rows                 Daily aggregate              Monthly aggregate
orders                   (order_date)                 (month)
1,000,000 rows    ──►    ~2,000 rows          ──►     ~66 rows

The daily aggregate can answer daily, weekly, monthly and yearly queries.
The monthly aggregate can answer only monthly and yearly queries.
```

**Choose the finest grain that is still small enough.** A finer aggregate answers more queries, because coarser totals can be derived from it. The reverse is impossible.

### Additive, semi-additive and non-additive measures

Whether a stored value can be rolled up further depends on the measure:

| Measure | Type | Roll daily up to monthly | What to store |
|---------|------|--------------------------|---------------|
| `SUM(total_amount)`, `COUNT(*)` | Additive | Sum the daily values | The sum or count |
| `AVG(total_amount)` | Derived | Averaging daily averages is **wrong** when days have different counts | `SUM` and `COUNT`; compute the average when reading |
| Account balance, stock level | Semi-additive | Summing across time is wrong; take the last value | The value per period |
| `COUNT(DISTINCT customer_id)` | Non-additive | Adding daily distinct counts double-counts customers | Store at every grain needed, or use an approximate sketch |

```
Day 1: 2 orders, average 100     Day 2: 8 orders, average 50

Average of daily averages:  (100 + 50) / 2        = 75    wrong
From stored SUM and COUNT:  (200 + 400) / (2 + 8) = 60    correct
```

For approximate distinct counts, Oracle provides `APPROX_COUNT_DISTINCT_DETAIL` and `APPROX_COUNT_DISTINCT_AGG` (12.2+), whose results can be stored and combined. In PostgreSQL the `hll` (HyperLogLog) extension serves the same purpose.

### Multiple levels at once

`GROUPING SETS`, `ROLLUP` and `CUBE` compute several grains in one pass. Both databases support them:

```sql
SELECT p.category, o.order_date,
       SUM(oi.quantity * p.price) AS revenue,
       GROUPING(p.category)       AS is_all_categories
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p     ON p.product_id = oi.product_id
GROUP BY ROLLUP (o.order_date, p.category);
```

```
ROLLUP (order_date, category) produces:
  (order_date, category)   per day and category
  (order_date)             per day, all categories
  ()                       grand total
```

### Rolling up in Oracle query rewrite

Oracle can answer a monthly query from the daily materialised view on its own, because it can derive the month from `order_date`. For custom hierarchies, such as product → category, a `CREATE DIMENSION` statement declares the relationship. With `QUERY_REWRITE_INTEGRITY = TRUSTED`, the optimizer uses it to roll up.

## 7. Summary Tables

A **summary table** is an ordinary table that holds precomputed results and is maintained by your own code: an ETL job, a scheduled procedure, triggers or the application. It does the same job as a materialised view, with full control over how it is updated.

Use a summary table instead of a materialised view when:

- incremental refresh is needed and the database cannot provide it (core PostgreSQL),
- the maintenance logic is more than one query can express, such as handling late or corrected data,
- the table must keep history that the source no longer holds, such as figures for purged orders.

### Incremental maintenance with a watermark

The usual pattern processes only the rows that are new since the last run, identified by a **watermark**: the highest ID or timestamp already processed.

```
orders                                      summary_daily_sales
id: 1 ... 998,000 │ 998,001 ... 1,000,000
   already        │  new since the               ▲
   processed      │  last run ───────────────────┘
                  ▲
             watermark (stored in etl_watermark)
```

```sql
CREATE TABLE summary_daily_sales (
    order_date  DATE PRIMARY KEY,
    order_count BIGINT        NOT NULL,
    revenue     NUMERIC(14,2) NOT NULL
);

CREATE TABLE etl_watermark (
    job_name    TEXT PRIMARY KEY,
    last_id     BIGINT NOT NULL
);
```

**PostgreSQL**: upsert with `INSERT ... ON CONFLICT`:

```sql
WITH new_rows AS (
    SELECT order_date, COUNT(*) AS cnt, SUM(total_amount) AS amt
    FROM orders
    WHERE order_id >  (SELECT last_id FROM etl_watermark WHERE job_name = 'daily_sales')
      AND order_id <= :batch_end_id
    GROUP BY order_date
)
INSERT INTO summary_daily_sales AS s (order_date, order_count, revenue)
SELECT order_date, cnt, amt FROM new_rows
ON CONFLICT (order_date) DO UPDATE
SET order_count = s.order_count + EXCLUDED.order_count,
    revenue     = s.revenue     + EXCLUDED.revenue;

UPDATE etl_watermark SET last_id = :batch_end_id WHERE job_name = 'daily_sales';
COMMIT;
```

**Oracle**: the same logic with `MERGE` (also available in PostgreSQL 15+):

```sql
MERGE INTO summary_daily_sales s
USING (
    SELECT order_date, COUNT(*) AS cnt, SUM(total_amount) AS amt
    FROM orders
    WHERE order_id >  (SELECT last_id FROM etl_watermark WHERE job_name = 'daily_sales')
      AND order_id <= :batch_end_id
    GROUP BY order_date
) n
ON (s.order_date = n.order_date)
WHEN MATCHED THEN UPDATE
     SET s.order_count = s.order_count + n.cnt,
         s.revenue     = s.revenue     + n.amt
WHEN NOT MATCHED THEN INSERT (order_date, order_count, revenue)
     VALUES (n.order_date, n.cnt, n.amt);
```

`:batch_end_id` is the maximum `order_id` read at the start of the run. Fixing it first ensures that rows inserted during the run are left for the next run instead of being half-processed.

### Pitfalls of watermarks

| Problem | Cause | Remedy |
|---------|-------|--------|
| Missed rows | A transaction with a lower ID commits **after** the watermark passed it | Leave a safety margin, or reprocess a recent window every run |
| Updates and deletes ignored | Watermark on insert ID only | Watermark on an `updated_at` column, soft deletes, or change data capture (Section 9) |
| Double counting on retry | Summary updated but watermark not, or the reverse | Update both in **one transaction** |
| Late or corrected data | Old dates changed after they were summarised | Recompute affected dates entirely instead of adding deltas |

A robust simplification is to **recompute** whole groups rather than add deltas: delete and rebuild the summary rows for the last few days on each run. It is slightly more work and far fewer failure modes.

## 8. Denormalisation

A normalised schema stores each fact once. **Denormalisation** stores some facts redundantly, so that common queries need fewer joins or calculations. Materialised views and summary tables are forms of denormalisation. This section covers the smaller-scale techniques applied inside ordinary tables.

### Common forms

| Form | Example in the sample schema | Saves |
|------|------------------------------|-------|
| Stored derived value | `orders.total_amount`, the sum of the order's items | Aggregating `order_items` on every read |
| Copied column | `orders.customer_country` copied from `customers` | A join to filter orders by country |
| Pre-joined table | A reporting table with order, customer and product columns side by side | Several joins per query |
| Embedded collection | Order items stored as a JSON array in `orders` | A join and a second lookup |

`orders.total_amount` already exists in the sample schema. It is a denormalised value that must match `order_items`.

### The cost

Every redundant copy must be kept consistent when the source changes:

```
UPDATE customers SET country = 'FR' WHERE customer_id = 42;
       │
       └──► must also update every order of customer 42 that copies country
            (possibly thousands of rows; missed ones are now wrong)
```

| Cost | Detail |
|------|--------|
| Write amplification | One logical change updates many rows |
| Consistency risk | Any code path that forgets the copy produces wrong data |
| Storage | Repeated values in every row |
| Contention | Copies of hot values multiply locking (Chapter 04) |

### Keeping copies consistent

| Scope | Technique | Oracle | PostgreSQL |
|-------|-----------|--------|------------|
| Value computed from the **same row** | Generated column | Virtual column (`AS (...)`), can be indexed | `GENERATED ALWAYS AS (...) STORED` (12+) |
| Value from **other rows or tables** | Trigger | Row or compound trigger | Row trigger |
| Value from other tables, maintained later | Batch job or change data capture | Scheduler jobs, GoldenGate | `pg_cron`, logical decoding |
| Any | Application code in the same transaction | | |

```sql
-- PostgreSQL: derived from the same row, always consistent
ALTER TABLE order_items
    ADD COLUMN line_total NUMERIC(12,2)
    GENERATED ALWAYS AS (quantity * unit_price) STORED;

-- Oracle
ALTER TABLE order_items ADD (line_total AS (quantity * unit_price));
```

(Both assume an `order_items.unit_price` column.)

Triggers that maintain totals, such as `orders.total_amount` from `order_items`, work but turn every item change into an update of the parent row. Under concurrent inserts into the same order, that parent row becomes a hot row.

### When to denormalise

```
Is the query too slow after indexing and query tuning?
        │
        ├── No ──► stay normalised
        │
        ▼
Is the redundant value read far more often than its source changes?
        │
        ├── No ──► stay normalised; the writes will cost more than the reads save
        │
        ▼
Can the database keep it consistent (generated column, MV, trigger)?
        │
        ├── Yes ──► denormalise with that mechanism
        │
        └── No  ──► denormalise only with a reconciliation check that detects drift
```

A periodic reconciliation query that compares the copy with its source is cheap insurance:

```sql
SELECT o.order_id
FROM orders o
JOIN (SELECT order_id, SUM(quantity * unit_price) AS items_total
      FROM order_items GROUP BY order_id) i ON i.order_id = o.order_id
WHERE o.total_amount <> i.items_total;
```

## 9. CQRS Read Models

**CQRS** (Command Query Responsibility Segregation) separates the model used to **change** data from the model used to **read** it. Writes go to a normalised model designed for correctness. Reads go to one or more **read models**: denormalised structures shaped exactly like the screens and APIs that use them.

```
                  commands (place order, cancel order)
                                │
                                ▼
                  ┌───────────────────────────┐
                  │  Write model (normalised) │   orders, order_items, customers
                  │  constraints, transactions│
                  └─────────────┬─────────────┘
                                │ changes published
                                │ (outbox table, CDC, events)
                ┌───────────────┼────────────────┐
                ▼               ▼                ▼
      ┌──────────────┐  ┌───────────────┐  ┌──────────────┐
      │ customer     │  │ daily sales   │  │ search index │   read models,
      │ order history│  │ dashboard     │  │              │   updated asynchronously
      └──────┬───────┘  └──────┬────────┘  └──────┬───────┘
             ▼                 ▼                  ▼
                           queries
```

A read model is conceptually a materialised view maintained by the application, often asynchronously, and sometimes in a different database or search engine.

### Propagating changes

The hard part is getting every change to the read models **reliably**. Writing to the database and then sending a message separately fails when one succeeds and the other does not. Two patterns avoid this:

**Transactional outbox.** The change and an event row are written in the same transaction. A separate process reads the outbox and updates the read models.

```sql
BEGIN;
INSERT INTO orders (...) VALUES (...);
INSERT INTO outbox (event_type, payload)
VALUES ('OrderPlaced', '{"order_id": 1000001, "customer_id": 42, "amount": 250}');
COMMIT;
```

```
transaction ──► orders + outbox (atomic)
                        │
             relay process reads outbox ──► updates read models ──► marks event processed
```

**Change data capture (CDC).** A process reads the database's own log (Chapter 05, Section 6) and publishes each committed change:

| | Oracle | PostgreSQL |
|---|---|---|
| Built-in log reading | LogMiner, XStream | Logical decoding (`wal_level = logical`), logical replication |
| Common tools | GoldenGate, Debezium | Debezium, built-in logical replication |

For a read model inside the same database, the relay can be a scheduled job or a worker that polls the outbox using `FOR UPDATE SKIP LOCKED` (Chapter 04, Section 12). PostgreSQL's `LISTEN` / `NOTIFY` can wake the worker immediately instead of polling.

### Consequences

| Consequence | Detail |
|-------------|--------|
| Eventual consistency | A read model lags the write model by milliseconds to minutes |
| Read-your-own-writes | A user who just placed an order may not see it yet. Read the write model for that user's next request, or wait for the read model to catch up |
| Idempotency | Events can be delivered more than once. Updates must give the same result if repeated, for example by recording the last processed event ID per read model |
| Rebuildability | A read model can be dropped and rebuilt by replaying events or re-reading the write model. Plan for this |
| Operational cost | More moving parts: relay processes, monitoring of lag, failure handling |

CQRS is justified when read and write needs genuinely differ, such as high read volume, many different read shapes, or reads served from a different technology. For a single application with moderate load, materialised views or summary tables in the same database give most of the benefit with far less complexity.

## 10. Comparing the Approaches

| Approach | Freshness | Maintained by | Write overhead | Complexity |
|----------|-----------|---------------|----------------|------------|
| Normal view | Always current | Nothing | None | Lowest |
| Materialised view, complete refresh | As of last refresh | Database | None during DML; full query at refresh | Low |
| Materialised view, fast or incremental | As of last refresh, or current (`ON COMMIT`, `pg_ivm`) | Database | Change log or trigger on every DML | Medium |
| Oracle real-time MV | Current | Database | Change log on every DML; merge cost at query time | Medium |
| Summary table | As of last job run | Your code | None during DML | Medium |
| Denormalised column | Current if kept in the same transaction | Generated column, trigger, or application | On every related change | Medium |
| CQRS read model | Seconds to minutes behind | Your code and infrastructure | Outbox write or log reading | Highest |

```
1. Is the query slow after indexing and query tuning?            Chapters 01–03
        │
        ├── No ──► no materialisation needed
        │
        ▼
2. Is the result read much more often than the source changes?
        │
        ├── No ──► materialisation will cost more than it saves
        │
        ▼
3. How stale may the result be?
        │
        ├── Must be current
        │     ──► Oracle: ON STATEMENT / ON COMMIT fast refresh, or real-time MV
        │         PostgreSQL: pg_ivm, trigger-maintained summary
        │         (low write rates only)
        │
        ├── Minutes
        │     ──► scheduled fast refresh (Oracle) / REFRESH CONCURRENTLY or
        │         watermark summary table (PostgreSQL)
        │
        └── Hours
              ──► nightly complete refresh or batch summary
        │
        ▼
4. Choose the grain
        finest grain that is still small; store SUM and COUNT, not AVG     Section 6
        │
        ▼
5. Choose the mechanism
        one SQL query, database can refresh it    ──► materialised view
        custom logic, history, late data          ──► summary table
        one or two columns in an existing table   ──► denormalised column
        many read shapes, separate read stores    ──► CQRS read model
        │
        ▼
6. Make it observable
        record refresh time and lag; reconcile against the source
```

## 13. Short Summary

- A view re-runs its query on every access. A materialised view stores the result and must be refreshed, trading freshness for read speed.
- Complete refresh re-runs the whole query. Incremental refresh applies only the changes, but works only for supported query shapes and needs change tracking.
- Oracle offers fast refresh, on-commit and real-time materialised views, and query rewrite. Core PostgreSQL offers only complete refresh, with `CONCURRENTLY` to avoid blocking readers.
- Store aggregates at the finest useful grain, and store `SUM` and `COUNT` rather than averages or distinct counts, so they can be rolled up correctly.
- Summary tables give full control over maintenance. Watermarks make them incremental, provided the summary and the watermark are updated in one transaction and late changes are handled.
- Denormalised columns speed up reads at the cost of write amplification and consistency risk. Use generated columns or triggers where possible, and reconcile the rest.
- CQRS read models extend materialisation across services and stores, at the price of eventual consistency and operational complexity. A transactional outbox or change data capture keeps them reliable.
