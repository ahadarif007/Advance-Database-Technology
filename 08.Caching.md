# Chapter 08: Caching

A cache keeps a copy of data somewhere faster than its source, so repeated requests avoid repeated work. Every database already caches blocks in memory. Applications add further caches in their own memory and in shared stores such as Redis. Used well, caching removes most of the read load from the database. Used carelessly, it serves stale data, hides bugs, and can bring the database down at the moment the cache fails.

This chapter covers caching inside **Oracle** and **PostgreSQL**, caching in the application and in Redis, the standard read and write patterns, cache invalidation, and how to prevent cache stampedes.

## 2. Caching Layers

A request can be answered at several levels. The closer to the user, the faster the answer and the harder it is to keep up to date.

```
User
  │
  ▼
CDN / browser cache              whole HTTP responses                ~ms, closest to user
  │
  ▼
Application in-process cache     objects in the app's own memory     ~ns–µs
  │
  ▼
Distributed cache (Redis)        shared by all app instances         ~0.2–1 ms over network
  │
  ▼
Database result cache            finished query results              skips execution
  │                              (Oracle only)
  ▼
Database buffer cache            data blocks                         skips disk, not execution
  │
  ▼
OS page cache / storage          files and blocks                    ~µs–ms
```

| Layer | Caches | Kept current by | Chapter section |
|-------|--------|-----------------|-----------------|
| Buffer cache | Blocks | The database, automatically | 3 |
| Result cache | Query and function results | The database, on commit of changes | 4 |
| In-process cache | Application objects | Application: TTL, events | 5 |
| Distributed cache | Application objects | Application: TTL, deletes, events | 6 – 12 |

Only the database layers are always consistent with the data. Every cache above them is a copy that the application must keep correct.

## 3. Database Buffer Cache

Chapter 05 (Section 3) explained how the buffer cache works. Two points matter for caching strategy.

**It caches blocks, not answers.** A query that finds all its blocks in memory still parses, plans, joins, sorts and aggregates. A report that aggregates a million cached rows does no disk I/O and can still take seconds. The buffer cache removes I/O cost; the layers above remove execution cost.

**It is lost on restart.** After a restart or failover, every read goes to disk until the cache fills again, which can make the first minutes much slower than normal.

| | Oracle | PostgreSQL |
|---|---|---|
| Reload hot blocks after restart | No built-in reload; warm up with representative queries | `pg_prewarm` extension. With `shared_preload_libraries = 'pg_prewarm'`, the autoprewarm worker saves the list of cached blocks and reloads them at startup |
| Keep a table cached | `KEEP` buffer pool: `DB_KEEP_CACHE_SIZE`, then `ALTER TABLE products STORAGE (BUFFER_POOL KEEP)` | No pinning; `SELECT pg_prewarm('products')` loads it once |

```sql
-- PostgreSQL: load a table into shared buffers
CREATE EXTENSION pg_prewarm;
SELECT pg_prewarm('products');
```

## 4. Query-Result Caching

A **result cache** stores the finished output of a query and returns it directly when the same query runs again, skipping execution entirely.

### What each database caches internally

| Cache | Stores | Oracle | PostgreSQL |
|-------|--------|--------|------------|
| Buffer cache | Data blocks | Buffer cache | Shared buffers |
| Plan cache | Parsed statements and plans | Shared pool (library cache), shared by all sessions | Per session, for prepared statements only |
| Result cache | Query results | Server result cache | **None** |

A plan cache saves parsing and planning, not execution. Oracle shares plans across sessions when statements use bind variables. PostgreSQL keeps plans only for prepared statements within one session (Chapter 01, Section 13).

### Oracle Server Result Cache

The result cache is an area of the shared pool that stores query results and PL/SQL function results.

```sql
SELECT /*+ RESULT_CACHE */ category, COUNT(*) AS product_count
FROM products
GROUP BY category;
```

```
----------------------------------------------------------------------
| Id | Operation            | Name                       | Rows |
----------------------------------------------------------------------
|  0 | SELECT STATEMENT     |                            |   20 |
|  1 |  RESULT CACHE        | 8fbjhchhd9zwh5g0r1k5sv8ak2 |      |
|  2 |   HASH GROUP BY      |                            |   20 |
|  3 |    TABLE ACCESS FULL | PRODUCTS                   | 10000|
----------------------------------------------------------------------
```

The first run executes steps 2 and 3 and stores the result. Later runs stop at step 1.

| Control | Effect |
|---------|--------|
| `/*+ RESULT_CACHE */` hint | Cache this query |
| `RESULT_CACHE_MODE = MANUAL` (default) | Cache only hinted queries and annotated tables |
| `RESULT_CACHE_MODE = FORCE` | Cache every eligible query (rarely advisable) |
| `ALTER TABLE products RESULT_CACHE (MODE FORCE)` | Cache queries that use only annotated tables, without hints |
| `RESULT_CACHE_MAX_SIZE` | Total memory for the cache |
| `RESULT_CACHE_MAX_RESULT` | Largest share (%) of the cache one result may use (default 5) |

PL/SQL functions can cache their results by argument:

```sql
CREATE OR REPLACE FUNCTION category_count (p_category VARCHAR2)
RETURN NUMBER
RESULT_CACHE
IS
    v_count NUMBER;
BEGIN
    SELECT COUNT(*) INTO v_count FROM products WHERE category = p_category;
    RETURN v_count;
END;
/
```

**Invalidation is automatic and coarse.** Oracle records which tables each result depends on. When a transaction that changed any of those tables commits, **every** cached result that depends on the table is invalidated. The cache is therefore always correct, but it only pays off for tables that change rarely. On busy tables, results are invalidated constantly, and the cache's internal latch can itself become a bottleneck.

```sql
SELECT type, status, name, row_count
FROM v$result_cache_objects
WHERE type = 'Result';

EXEC DBMS_RESULT_CACHE.MEMORY_REPORT;
```

Oracle also offers a **client result cache**, which keeps results in the memory of OCI-based clients (`CLIENT_RESULT_CACHE_SIZE`), and, from Oracle Database 23ai, **True Cache**, a read-only in-memory instance placed in front of the primary database.

### PostgreSQL

PostgreSQL has no result cache. The closest options are:

| Need | Option |
|------|--------|
| Expensive aggregate read often | Materialised view or summary table (Chapter 07) |
| Repeated identical queries from many clients | `pgpool-II` in-memory query cache, placed between application and database |
| Anything else | Application-level cache (Section 5) |

MySQL had a server query cache and removed it in version 8.0, because invalidating results on every table change caused contention on write-heavy systems. The same limitation applies to Oracle's result cache on frequently changing tables.

## 5. Application-Level Caching

Application caches store data in the form the application uses, such as a product object or a rendered page fragment, and skip the database round trip entirely.

### In-process vs distributed

```
In-process cache                          Distributed cache

 App instance 1     App instance 2          App instance 1     App instance 2
 ┌────────────┐     ┌────────────┐          ┌────────────┐     ┌────────────┐
 │ cache      │     │ cache      │          │            │     │            │
 │ product:42 │     │ product:42 │          └─────┬──────┘     └─────┬──────┘
 │ (v1)       │     │ (v2)       │                └────────┬─────────┘
 └────────────┘     └────────────┘                         ▼
  copies can differ between instances              ┌──────────────┐
                                                   │ Redis        │
                                                   │ product:42   │  one shared copy
                                                   └──────────────┘
```

| | In-process | Distributed (Redis, Memcached) |
|---|---|---|
| Latency | Nanoseconds to microseconds | Sub-millisecond network round trip |
| Shared between instances | No; each instance has its own copy | Yes |
| Invalidation | Must reach every instance | One delete |
| Survives app restart | No | Yes |
| Capacity | Limited by app memory | Scales separately |
| Serialisation cost | None | Every read and write |

A common arrangement uses both: a small in-process cache with a very short TTL (seconds) in front of Redis, for the hottest keys such as the home page's featured products. This is sometimes called a **near cache** or two-level cache.

### What to cache

| Cache | Avoid caching |
|-------|---------------|
| Data read much more often than it changes | Data that must be exact at all times (balances, stock during checkout) |
| Expensive results (aggregates, joins, external API responses) | Cheap primary key lookups that are already fast in the database |
| Data where brief staleness is acceptable | Per-request data that is never reused |
| Data with a clear owner and a clear change event | Data changed by many paths that cannot all invalidate it |

### Measuring effectiveness

The **hit ratio** is the share of reads served from the cache:

```
hit ratio = hits / (hits + misses)
```

A cache with a low hit ratio adds a network call to every request and saves little. Track the hit ratio per key type, not only overall, and remove caching that does not pay for itself.

## 6. Redis

Redis is an in-memory data store widely used as a distributed cache. It keeps all data in memory, executes commands one at a time on a single main thread (so each command is atomic), and typically answers in well under a millisecond on a local network.

Since 2024, Redis has been distributed under source-available licences, with the AGPL added as an option in Redis 8. **Valkey**, a fork maintained under the Linux Foundation, is protocol-compatible. The commands in this chapter work in both.

### Data structures used for caching

| Structure | Commands | Typical use |
|-----------|----------|-------------|
| String | `GET`, `SET`, `INCR` | Serialised object (JSON), counters |
| Hash | `HGET`, `HSET`, `HGETALL` | Object with individually readable fields |
| Sorted set | `ZADD`, `ZRANGE`, `ZREVRANGE` | Leaderboards, top-N lists, time-ordered feeds |
| Set | `SADD`, `SMEMBERS` | Tags, memberships, keys to invalidate together |
| List / Stream | `LPUSH`, `XADD`, `XREADGROUP` | Queues, write-behind buffers (Section 10) |

```
SET product:42 '{"id":42,"name":"Desk Lamp","price":39.99}' EX 300
GET product:42
DEL product:42

HSET customer:7 name "Customer 7" country "UK"
HGET customer:7 country

ZADD top_products 1520 "product:42" 980 "product:17"
ZREVRANGE top_products 0 9 WITHSCORES
```

### Keys and expiry

- Use a consistent naming scheme: `<entity>:<id>`, such as `product:42` or `customer:7:orders:recent`.
- Give every cache key a **TTL** (time to live). `SET ... EX 300` expires the key after 300 seconds. The TTL is the safety net that eventually corrects any staleness the application fails to handle.
- `TTL product:42` shows the remaining lifetime.

### Memory limits and eviction

When Redis reaches `maxmemory`, the `maxmemory-policy` decides what happens:

| Policy | Evicts |
|--------|--------|
| `noeviction` (default) | Nothing; writes fail with an error |
| `allkeys-lru` | Least recently used key |
| `allkeys-lfu` | Least frequently used key |
| `volatile-lru` / `volatile-lfu` | Least recently / frequently used key **with a TTL** |
| `volatile-ttl` | Key with a TTL that expires soonest |
| `allkeys-random` / `volatile-random` | A random key |

For a pure cache, set `maxmemory` and use `allkeys-lru` or `allkeys-lfu`. The default `noeviction` suits Redis used as a data store, not as a cache.

### Persistence and availability

| Concern | Options |
|---------|---------|
| Persistence | RDB snapshots, AOF (append-only file), or none. A pure cache often runs with persistence off and is rebuilt from the database |
| High availability | Replicas with Redis Sentinel for automatic failover |
| Scaling out | Redis Cluster, which shards keys across nodes by hash slot |

Design so that the application still works, more slowly, if Redis is unavailable. The database must be able to carry at least a degraded load without the cache (Section 12).

### Monitoring

```
INFO stats        # keyspace_hits, keyspace_misses, evicted_keys, expired_keys
INFO memory       # used_memory, maxmemory
```

A rising `evicted_keys` count means the cache is too small for the working set.

## 7. Cache-Aside

**Cache-aside** (also called *lazy loading*) is the most common pattern. The application checks the cache first. On a miss, it reads the database and stores the result in the cache.

```
Read
  App ──1. GET product:42──► Redis
   │  ◄─── hit: return ─────┘
   │
   │  miss
   ├──2. SELECT ... ────────► Database
   │  ◄─── row ─────────────┘
   └──3. SET product:42 ... EX 300 ──► Redis

Write
  App ──1. UPDATE products ...; COMMIT ──► Database
   └──2. DEL product:42 ─────────────────► Redis
```

```
function get_product(id):
    cached = redis.GET("product:" + id)
    if cached is not null:
        return deserialize(cached)

    row = db.query("SELECT product_id, name, category, price
                    FROM products WHERE product_id = :id", id)
    if row is null:
        return null

    redis.SET("product:" + id, serialize(row), EX = 300)
    return row

function update_price(id, new_price):
    db.execute("UPDATE products SET price = :p WHERE product_id = :id", new_price, id)
    db.commit()
    redis.DEL("product:" + id)
```

| Strength | Weakness |
|----------|----------|
| Only requested data is cached | First request for each key is slow (a miss) |
| Cache failure only slows reads; the app still works | Application code handles caching logic |
| Works with any database and any cache | Window for stale data between the database write and the delete (Section 11) |

On a write, **delete** the key rather than updating it. Deleting is idempotent and cannot store a wrong value. The next read reloads the current row.

## 8. Read-Through

**Read-through** moves the loading logic into the cache layer. The application asks only the cache. On a miss, the cache itself calls a loader function that reads the database.

```
App ──get(product:42)──► Cache layer ── miss ──► loader ──► Database
 ▲                           │                                 │
 └──────── value ────────────┘◄──────────── row ───────────────┘
                     (stored in the cache on the way back)
```

```
cache = Cache(
    loader = function(key):
        id = parse_id(key)
        return db.query("SELECT ... FROM products WHERE product_id = :id", id),
    ttl = 300
)

product = cache.get("product:42")       # loads on miss, transparently
```

The data flow is the same as cache-aside. The difference is **where the code lives**: in a caching library or service (for example Caffeine or Ehcache in Java, or a Redis-based caching library) instead of every call site.

| Strength | Weakness |
|----------|----------|
| Loading logic in one place | Requires a library or cache product that supports loaders |
| Libraries can coalesce concurrent misses for the same key (Section 12) | Less flexible when loading rules differ per call |

## 9. Write-Through

**Write-through** sends every write through the cache layer, which updates both the cache and the database **synchronously** before confirming.

```
App ──write(product:42)──► Cache layer ──1. UPDATE + COMMIT──► Database
                               │
                               ├──2. store new value in cache
                               ▼
                           confirm to app  (only after both succeed)
```

```
function write_product(product):
    db.execute("UPDATE products SET name = :n, price = :p WHERE product_id = :id", ...)
    db.commit()
    redis.SET("product:" + product.id, serialize(product), EX = 300)
```

| Strength | Weakness |
|----------|----------|
| Cache holds fresh data right after each write; reads rarely miss | Every write pays for two updates |
| Simple read path | Data written but never read still fills the cache |
| | Database and cache can still diverge if the process fails between the two steps |

Write the database **first**. If the cache update fails, the cache is merely stale until its TTL expires. If the cache were updated first and the database write failed, the cache would contain data that never existed.

Write-through is often combined with read-through, giving a cache that is both loaded and updated by the same layer.

## 10. Write-Behind

**Write-behind** (also *write-back*) confirms a write as soon as it reaches the cache. The database is updated **later**, asynchronously, often in batches.

```
App ──write──► Cache ──confirm──► App          (fast)
                 │
                 └── queue ──► background worker ──► Database
                               (batched, delayed by ms to seconds)
```

```
function record_view(product_id):
    redis.INCR("views:product:" + product_id)              # confirmed immediately

# background worker, every 10 seconds
function flush_views():
    for each key in redis.SCAN("views:product:*"):
        count = redis.GETDEL(key)                           # read and reset atomically
        db.execute("UPDATE product_stats
                    SET view_count = view_count + :c
                    WHERE product_id = :id", count, id_from(key))
    db.commit()
```

Ten thousand view events become one `UPDATE` per product every ten seconds.

| Strength | Weakness |
|----------|----------|
| Very fast writes | **Data loss** if the cache fails before flushing |
| Batching reduces database load, especially on hot rows (Chapter 04, Section 12) | The database lags behind the cache |
| Absorbs write bursts | Harder to reason about ordering, retries and failures |

Use write-behind only for data where losing the last few seconds is acceptable: counters, analytics, activity timestamps, rate-limit windows. Never use it for orders, payments or balances. For durable asynchronous writes, use a persistent queue such as Redis Streams with consumer groups or a message broker, and make the database update idempotent.

### Comparing the patterns

| Pattern | Who loads the cache | Write path | Consistency | Typical use |
|---------|---------------------|------------|-------------|-------------|
| Cache-aside | Application, on miss | DB, then delete key | Stale window up to TTL | General-purpose default |
| Read-through | Cache layer, on miss | Any | Same as cache-aside | Libraries with loaders |
| Write-through | Cache layer, on write | DB and cache, synchronously | Fresh after each write | Read-heavy data that must be fresh after edits |
| Write-behind | Cache layer, on write | Cache now, DB later | Database lags; loss possible | Counters, telemetry |
| Write-around | Application, on miss | DB only; cache not touched | Stale until TTL or miss | Data rarely read after being written |

## 11. Cache Invalidation

Invalidation means removing or replacing a cached value when its source changes. It is the part of caching where most bugs occur.

### Strategies

| Strategy | How | Freshness | Effort |
|----------|-----|-----------|--------|
| TTL only | Every key expires after a fixed time | Stale for up to the TTL | Lowest |
| Delete on write | Code that changes the row deletes the key | Fresh, apart from race windows | Every write path must do it |
| Versioned keys | Key includes a version: `product:42:v17` | Old versions are simply never read again | Version must be known when reading |
| Event-driven | Database changes publish events; a listener deletes keys | Fresh within event latency | Infrastructure |

Use **TTL on every key** regardless of the main strategy. It limits the damage of any missed invalidation.

### Event-driven invalidation from the database

Invalidating from the database catches every change, including those made by batch jobs, other services or manual fixes that the application's code never sees.

**PostgreSQL**: a trigger sends a notification, and a listener process deletes the key:

```sql
CREATE FUNCTION notify_product_change() RETURNS trigger AS $$
BEGIN
    PERFORM pg_notify('product_changed', OLD.product_id::text);
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_product_change
AFTER UPDATE OR DELETE ON products
FOR EACH ROW EXECUTE FUNCTION notify_product_change();
```

```
listener:  LISTEN product_changed;
           on notification(payload):  redis.DEL("product:" + payload)
```

Notifications are delivered only when the transaction commits, which is exactly the right moment. They are not stored, however: a listener that is disconnected misses them. For guaranteed delivery, use logical decoding or Debezium (Chapter 07, Section 9).

**Oracle**: **Continuous Query Notification** (`DBMS_CQ_NOTIFICATION`) registers queries or tables and calls back when committed changes affect them. The registration can be at object level (any change to the table) or query-result level (only changes that alter the registered query's result). Oracle GoldenGate or XStream serve the same purpose at larger scale.

### The race condition in cache-aside

Delete-on-write still leaves a window in which a stale value can be written back into the cache:

```
Time  Reader (cache miss)                     Writer
────  ──────────────────────────────────────  ──────────────────────────────────────
t1    GET product:42          → miss
t2    SELECT price            → 39.99
t3                                            UPDATE price = 44.99; COMMIT
t4                                            DEL product:42
t5    SET product:42 = 39.99                  (stale value cached until the TTL expires)
```

The reader loaded the old value before the update and stored it after the delete. The same happens when the reader queries a replica that has not yet applied the update.

| Mitigation | How it helps |
|------------|--------------|
| Short TTL | Limits how long the stale value survives |
| Delayed second delete | Writer deletes again a short time later (for example after one second), removing values written back in the gap |
| Version check on set | Store the row's version with the value, and only overwrite a cached value with a higher version (a Redis Lua script can compare and set atomically) |
| Leases | The cache hands a token to the first reader on a miss; a delete invalidates the token, so the reader's later `SET` is rejected |

For most data, a short TTL plus delete-on-write is enough. The heavier mitigations are for data where even brief staleness is costly.

### Invalidating derived keys

A single product change can affect many cached items: the product page, its category listing, search results, and "top products". Keep track of the dependencies explicitly:

```
SADD deps:product:42 "product:42" "category:7:page:1" "top_products"

on change of product 42:
    keys = SMEMBERS deps:product:42
    DEL keys...
```

When dependencies become too many to track, rely on TTLs for derived data and invalidate only the direct keys.

## 12. Cache Stampede Prevention

A **cache stampede** (also *thundering herd* or *dog-piling*) happens when a popular key expires or is deleted, and many requests miss at once. They all query the database for the same value at the same moment.

```
product:42 expires at t = 0

  requests ─┬─► miss ─► SELECT ... ─┐
            ├─► miss ─► SELECT ... ─┤
            ├─► miss ─► SELECT ... ─┼─► database: hundreds of identical
            ├─► miss ─► SELECT ... ─┤   queries at the same moment
            └─► miss ─► SELECT ... ─┘
```

For an expensive query, such as a category aggregate, a stampede can saturate the database and slow down everything else. Related failure modes:

| Problem | Cause |
|---------|-------|
| Stampede on one hot key | A popular key expires |
| Cache avalanche | Many keys expire together (same TTL set at the same time), or the cache restarts empty |
| Cache penetration | Requests for keys that do not exist (for example `product:999999999`) always miss and always reach the database |

### 1. Add jitter to TTLs

Randomise expiry so that keys created together do not expire together:

```
ttl = 300 + random_int(0, 60)
redis.SET(key, value, EX = ttl)
```

This prevents avalanches cheaply and should be the default.

### 2. Let only one request rebuild (locking)

The first request that misses takes a short-lived lock and rebuilds the value. The others wait briefly and read the new value, or serve a stale copy.

```
function get_with_lock(key, load):
    value = redis.GET(key)
    if value is not null:
        return value

    token = random_token()
    if redis.SET("lock:" + key, token, NX = true, PX = 5000):
        # this request rebuilds
        value = load()
        redis.SET(key, value, EX = 300 + random_int(0, 60))
        release_lock("lock:" + key, token)
        return value
    else:
        # another request is rebuilding
        sleep(50 ms)
        return get_with_lock(key, load)     # retry with a limit in real code
```

`SET ... NX PX 5000` sets the lock only if it does not exist, with a 5-second expiry so that a crashed rebuilder cannot hold it forever. Release the lock only if it still holds your token, using a small Lua script that compares and deletes atomically, so a request never deletes a lock that has since been taken by another.

Within one application instance, **request coalescing** (often called *single-flight*) does the same without Redis: concurrent callers for the same key wait on one shared in-flight load. Many caching libraries do this automatically.

### 3. Serve stale data while refreshing

Store the value with a **logical expiry** that is earlier than the real TTL. After the logical expiry, one request refreshes the value in the background while everyone continues to receive the old value.

```
stored value: { data: ..., refresh_after: 12:00:00 }     Redis TTL: 12:10:00

12:00:05  request sees refresh_after has passed
          ──► takes lock, starts background refresh
          ──► returns the current (slightly stale) data immediately
12:00:05  other requests ──► return the current data; lock is held, no refresh
12:00:06  refresh completes ──► new value stored with a new refresh_after
```

No request ever waits on the database for a hot key. This is the same idea as the HTTP `stale-while-revalidate` directive.

### 4. Refresh early, probabilistically

Each request that reads a key close to its expiry decides at random whether to refresh it early. The probability rises as expiry approaches, so one request usually refreshes the key shortly before it expires, without any lock. A widely used formula (known as XFetch) refreshes when:

```
now − delta × beta × ln(random()) ≥ expiry

delta = time the last recomputation took
beta  = tuning factor, typically 1 (higher refreshes earlier)
random() in (0, 1], so −ln(random()) is a positive random number
```

Expensive values (large `delta`) are refreshed earlier, since a stampede on them costs the most.

### 5. Refresh in the background, never expire

For a small set of very hot, expensive keys, a scheduled job recomputes the value every N seconds and overwrites it. Requests never miss. The job can read from a materialised view or summary table (Chapter 07).

### 6. Cache negative results

To stop penetration, cache the fact that a key does not exist, with a short TTL:

```
if row is null:
    redis.SET("product:" + id, "__none__", EX = 60)
```

For very large key spaces probed with random IDs, a Bloom filter of valid IDs can reject impossible keys before they reach the cache or the database.

### Choosing

| Technique | Prevents | Cost |
|-----------|----------|------|
| TTL jitter | Avalanche | None; always use |
| Negative caching | Penetration | Small; short TTL |
| Lock / single-flight | Stampede on a key | Waiting requests; lock handling |
| Stale-while-refreshing | Stampede and latency spikes | Slightly stale reads |
| Probabilistic early refresh | Stampede, without locks | Occasional extra recomputation |
| Background refresh | All misses for chosen keys | A job per key set |

### Protecting the database when the cache fails

If Redis becomes unavailable, every request becomes a miss. The database should be protected independently of the cache:

- Limit database connections with a connection pool (PgBouncer, Oracle Database Resident Connection Pooling, or the application pool), so a surge queues instead of overwhelming the server.
- Use timeouts and circuit breakers on cache calls, so a slow Redis does not stall every request.
- Keep the in-process near cache (Section 5) as a last line for the hottest keys.

## 15. Short Summary

- Caches exist at many layers. The database's own caches are always consistent; every cache above them is a copy the application must keep correct.
- The buffer cache removes disk I/O but not execution. Oracle's result cache removes execution too, but is invalidated by any committed change to a dependent table, so it suits rarely changing data. PostgreSQL has no result cache.
- In-process caches are fastest but duplicated per instance. Redis is shared and survives app restarts, at the cost of a network round trip and serialisation.
- Cache-aside with delete-on-write is the default pattern. Read-through centralises loading, write-through keeps the cache fresh after writes, and write-behind trades durability for write speed.
- Give every key a TTL. Invalidate on write or from database change events, and be aware of the race that can write a stale value back after a delete.
- Prevent stampedes with TTL jitter, a single rebuilder per key, serving stale data while refreshing, and negative caching. Protect the database so that it survives a cache outage.
