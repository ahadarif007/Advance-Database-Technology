# Chapter 09: Replication and Read Scaling

Replication keeps copies of a database on several servers. The copies serve two purposes. They **survive failures**: if the main server is lost, a copy takes over. And they **share the read load**: queries that only read data can run on the copies, leaving the main server free for writes.

```
                ┌── Read Replica
Application ────┼── Read Replica
                │
                └── Primary
                     │
                     └── Writes
```

Copies are never perfectly in step with the primary. This chapter explains how **Oracle** and **PostgreSQL** replicate data, the trade-off between synchronous and asynchronous replication, how to handle replication lag and read-after-write consistency, how failover works, and where quorum-based systems fit.

## 2. Primary/Replica Architecture

One server, the **primary**, accepts all writes. Every change is recorded in its log (redo in Oracle, WAL in PostgreSQL; Chapter 05, Section 6). The log is shipped to one or more **replicas** (Oracle: **standby databases**), which replay it to reproduce the same changes.

```
                    writes
Application ───────────────────► Primary
     │                              │
     │                              │ log records (redo / WAL)
     │                    ┌─────────┴─────────┐
     │                    ▼                   ▼
     │               Replica 1            Replica 2
     │               replays log          replays log
     │                    ▲                   ▲
     └──── reads ─────────┴───────────────────┘
```

### Physical and logical replication

| | Physical | Logical |
|---|---|---|
| What is shipped | Block-level changes from the log | Row changes (`INSERT` / `UPDATE` / `DELETE`) |
| Replica content | Byte-for-byte copy of the whole database | Chosen tables; can hold extra tables and indexes |
| Replica writable | No (read-only at most) | Yes |
| Versions | Same major version and platform | Can differ |
| Typical use | High availability, read scaling | Upgrades, migrations, partial copies, integration |
| Oracle | Data Guard physical standby | Data Guard logical standby, GoldenGate |
| PostgreSQL | Streaming replication | Logical replication (publications and subscriptions, 10+) |

This chapter focuses on **physical replication**, the standard basis for read replicas and failover in both databases.

### Not to be confused with

- **Oracle RAC** (Real Application Clusters): several instances share **one** copy of the database on shared storage. It protects against server failure, not storage or site failure, and it is not replication.
- **Multi-primary replication**, where several nodes accept writes (for example GoldenGate bidirectional, or PostgreSQL logical replication in both directions), brings write conflicts that this chapter does not cover.

## 3. Building a Replica

### PostgreSQL: streaming replication

```
Primary                                         Replica (standby)
┌──────────────┐     WAL stream over TCP       ┌──────────────┐
│ walsender    │ ────────────────────────────► │ walreceiver  │
└──────────────┘                               │      │       │
                                               │      ▼       │
                                               │ startup      │
                                               │ process      │ replays WAL
                                               │ (recovery)   │
                                               └──────────────┘
```

On the primary:

```sql
CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD '...';
```

```
# postgresql.conf (defaults already suitable in recent versions)
wal_level = replica
max_wal_senders = 10

# pg_hba.conf
host  replication  replicator  10.0.0.0/24  scram-sha-256
```

On the replica, copy the primary and start it as a standby:

```bash
pg_basebackup -h primary.db -U replicator -D /var/lib/postgresql/data -R -X stream -C -S replica1
```

| Option | Meaning |
|--------|---------|
| `-R` | Write `standby.signal` and `primary_conninfo`, so the server starts as a standby (version 12+) |
| `-X stream` | Stream WAL during the backup so the copy is consistent |
| `-C -S replica1` | Create a **replication slot** named `replica1` on the primary |

A **replication slot** makes the primary keep WAL until the replica has received it. Without one, a replica that falls far behind can find the WAL it needs already deleted and must be rebuilt. With one, a replica that is down indefinitely makes WAL pile up on the primary until the disk fills. Set `max_slot_wal_keep_size` (version 13+) to cap this.

`hot_standby = on` (the default) lets the replica serve read-only queries while it replays.

### Oracle: Data Guard

```
Primary                                         Physical standby
┌──────────────┐     redo transport            ┌──────────────┐
│ LGWR / TT    │ ────────────────────────────► │ RFS          │ receives redo
└──────────────┘     (SYNC or ASYNC)           │ standby redo │
                                               │ logs         │
                                               │      │       │
                                               │      ▼       │
                                               │ MRP          │ Redo Apply
                                               └──────────────┘
```

Setup is usually done with RMAN (`DUPLICATE TARGET DATABASE FOR STANDBY FROM ACTIVE DATABASE`) and managed with the **Data Guard Broker** command-line tool `DGMGRL`:

```
DGMGRL> CREATE CONFIGURATION shop AS PRIMARY DATABASE IS shop_p CONNECT IDENTIFIER IS shop_p;
DGMGRL> ADD DATABASE shop_s AS CONNECT IDENTIFIER IS shop_s;
DGMGRL> ENABLE CONFIGURATION;
DGMGRL> SHOW CONFIGURATION;
```

| Standby type | Behaviour |
|--------------|-----------|
| Physical standby | Applies redo; mounted, not open for queries |
| Physical standby with **Active Data Guard** | Open read-only **while** applying redo. A separately licensed option |
| Snapshot standby | Temporarily read-write for testing; changes are discarded when it is converted back |
| Logical standby | Applies changes as SQL; can hold extra objects |

Serving reads from an Oracle standby therefore requires **Active Data Guard**. Without it, a standby protects against failure but cannot share query load.

## 4. Read Replicas

### What read scaling achieves

```
Without replicas                         With two replicas

Primary: 100% of reads + writes          Primary:   writes + 15% of reads
                                         Replica 1: ~40% of reads
                                         Replica 2: ~40% of reads
```

| Scales | Does not scale |
|--------|----------------|
| Read queries | Writes: every replica replays **every** write |
| Heavy reports, isolated from OLTP | Primary log generation and shipping |
| Geographic read latency (replica near users) | Data size: each replica stores everything |

Adding replicas helps a read-heavy system. It does nothing for a write-bound one. The options there are covered in earlier chapters (tuning, batching, partitioning) and in sharding, which splits writes across independent databases.

### Routing reads

The application, a connection pooler or a proxy decides which server each query goes to.

| Approach | How | Examples |
|----------|-----|----------|
| Two connection pools in the application | "write" pool to the primary, "read" pool to replicas | Most frameworks support separate read and write data sources |
| Driver-level routing | Connection string lists all hosts and a target role | PostgreSQL libpq `target_session_attrs`; JDBC `targetServerType` |
| Proxy | A proxy inspects or routes by port | Pgpool-II, HAProxy, cloud endpoints |
| Database services | Clients connect to a service that runs only on the chosen role | Oracle role-based services |

**PostgreSQL**, with libpq (and drivers built on it):

```
# Writes: connect to whichever host is currently the primary
postgresql://app@db1,db2,db3/shop?target_session_attrs=read-write

# Reads: prefer a standby, fall back to the primary; spread across hosts (16+)
postgresql://app@db1,db2,db3/shop?target_session_attrs=prefer-standby&load_balance_hosts=random
```

| `target_session_attrs` | Connects to |
|------------------------|-------------|
| `any` (default) | First host that accepts the connection |
| `read-write` / `primary` | The primary |
| `read-only` / `standby` | A standby (version 14+) |
| `prefer-standby` | A standby if one is available, otherwise any host (14+) |

**Oracle** uses **role-based services**: a service is defined to start only when the database has a given role, so connections follow the role after a failover.

```sql
-- On the primary (propagated to the standby through redo)
BEGIN
  DBMS_SERVICE.CREATE_SERVICE('shop_ro', 'shop_ro');
END;
/
-- With Oracle Clusterware / Oracle Restart:
-- srvctl add service -db shop_s -service shop_ro -role PHYSICAL_STANDBY
```

The application connects to `shop_rw` for writes and `shop_ro` for reads, without knowing which server currently holds which role.

### What should stay on the primary

- All writes, and reads inside a transaction that also writes.
- Reads that decide a write (check stock, then reserve it).
- Reads that must reflect the user's own last change (Section 8).
- `SELECT ... FOR UPDATE` and any locking read.

Oracle 19c+ Active Data Guard can **redirect occasional DML** from a standby session to the primary (`ADG_REDIRECT_DML`). It is meant for rare writes from mostly read-only applications, not as a general write path.

### Long queries on replicas

A replica must both answer queries and apply changes, and the two can conflict.

**PostgreSQL.** If replay needs to remove row versions that a running query on the standby still needs, the standby waits up to `max_standby_streaming_delay` (default 30 s), then cancels the query:

```
ERROR: canceling statement due to conflict with recovery
```

| Setting | Effect | Cost |
|---------|--------|------|
| Raise `max_standby_streaming_delay` | Queries survive longer | Replica falls further behind while it waits |
| `hot_standby_feedback = on` | Primary keeps row versions that standby queries need | Bloat on the **primary** (Chapter 04, Section 3) |
| Dedicated reporting replica with a large delay | Long reports run undisturbed | That replica is often stale; do not route user traffic to it |

**Oracle.** Queries on an Active Data Guard standby read consistent data from undo, like on the primary. Very long queries can meet ORA-01555 if the required undo has been overwritten (Chapter 04, Section 3).

## 5. Asynchronous Replication

With **asynchronous** replication, the primary confirms a commit as soon as the change is safe in **its own** log. The log is shipped to replicas afterwards.

```
Time  Primary                          Replica
────  ───────────────────────────────  ─────────────────────────────
t1    UPDATE ...; COMMIT
t2    log flushed locally
t3    "commit complete" to client
t4    ship log record  ─────────────►  received
t5                                     replayed; change now visible
```

| Strength | Weakness |
|----------|----------|
| Commit latency unaffected by replicas or distance | Replicas are behind by the replication lag (Section 7) |
| A slow or failed replica never blocks the primary | On primary failure, commits not yet shipped are **lost** |

Asynchronous replication is the default in both databases.

- **PostgreSQL**: any standby not listed in `synchronous_standby_names`.
- **Oracle**: redo transport with `ASYNC`, used by the **Maximum Performance** protection mode (the default).

---

## 6. Synchronous Replication

With **synchronous** replication, the primary waits for confirmation from one or more replicas before telling the client that the commit succeeded.

```
Time  Primary                          Sync replica
────  ───────────────────────────────  ─────────────────────────────
t1    UPDATE ...; COMMIT
t2    log flushed locally
      ship log record  ─────────────►  received and written
t3                     ◄─────────────  acknowledgement
t4    "commit complete" to client
```

Every commit now includes a network round trip. Within one data centre this adds well under a millisecond to a few milliseconds. Across regions it adds tens of milliseconds to **every** commit.

### How far the replica must get

The key question is what the replica has done before it acknowledges:

| Level | Replica has | Survives | PostgreSQL `synchronous_commit` | Oracle |
|-------|-------------|----------|---------------------------------|--------|
| Received in memory | Log in memory | Primary crash | `remote_write` | `SYNC NOAFFIRM` (FastSync) |
| Written to disk | Log flushed to disk | Primary and replica crash | `on` (default, when a sync standby is configured) | `SYNC AFFIRM` |
| Applied | Change replayed and visible to queries | Also gives read-after-write on that replica | `remote_apply` | Not a transport setting; see Section 8 |

`synchronous_commit` can be set per transaction in PostgreSQL. Important writes can wait for the replica while bulk or low-value writes do not:

```sql
BEGIN;
SET LOCAL synchronous_commit = remote_apply;
INSERT INTO orders ...;
COMMIT;
```

### PostgreSQL configuration

```
# postgresql.conf on the primary
synchronous_standby_names = 'FIRST 1 (replica1, replica2)'
```

| Form | Meaning |
|------|---------|
| `FIRST 1 (replica1, replica2)` | Wait for the first available in priority order: `replica1`, else `replica2` |
| `ANY 2 (replica1, replica2, replica3)` | Wait for any 2 of the 3 (quorum commit, version 10+) |

The names match each standby's `application_name` in its `primary_conninfo`.

If no synchronous standby is available, commits on the primary **wait indefinitely**. PostgreSQL never downgrades to asynchronous on its own. Always list more candidates than you require (for example `ANY 1 (replica1, replica2)`), or have failover tooling adjust the setting.

### Oracle protection modes

Oracle Data Guard combines transport settings into three protection modes:

| Mode | Transport | If no standby can acknowledge |
|------|-----------|-------------------------------|
| Maximum Performance (default) | `ASYNC` | Nothing changes; the primary continues |
| Maximum Availability | `SYNC` | Primary waits up to `NET_TIMEOUT`, then continues unsynchronised; resynchronises when the standby returns |
| Maximum Protection | `SYNC` | Primary **shuts down** rather than commit without a standby copy |

```
DGMGRL> EDIT DATABASE shop_s SET PROPERTY LogXptMode = 'SYNC';
DGMGRL> EDIT CONFIGURATION SET PROTECTION MODE AS MaxAvailability;
```

For zero data loss over long distances, Oracle offers a **Far Sync instance** (12c+): a lightweight instance close to the primary that receives redo synchronously and forwards it asynchronously to the distant standby.

### Choosing

```
Is losing the last few seconds of commits on primary failure acceptable?
        │
        ├── Yes ──► asynchronous
        │
        ▼
Is there a replica close enough for sync latency to be acceptable?
        │
        ├── Yes ──► synchronous to the nearby replica (FIRST 1 / ANY 1, or Maximum Availability),
        │           asynchronous to the rest
        │
        └── No  ──► Oracle Far Sync, or accept async to the remote site
```

## 7. Replication Lag

**Replication lag** is how far a replica is behind the primary. It has three parts:

```
Primary commit ──► shipped ──► received ──► written ──► replayed (visible)
                   └───────── transport lag ────────┘└─ apply lag ─┘
                   └──────────────── total lag ────────────────────┘
```

| Cause | Typical signs |
|-------|---------------|
| Network bandwidth or latency | Transport lag grows with write volume |
| Replica I/O or CPU too slow | Received but not replayed; apply lag grows |
| Large single transactions | Lag jumps, then drops; nothing is visible until the whole transaction is replayed |
| Replay waiting for standby queries | Apply lag grows while long queries run (Section 4) |
| Bulk operations (index builds, `VACUUM FULL`, large loads) | Burst of log volume |
| Replica down or disconnected | Lag grows without limit |

Under normal load on a well-provisioned local replica, lag is typically milliseconds. Under bursts it can reach seconds or minutes. Design the application for the bursts, not the average.

### Measuring lag: PostgreSQL

On the primary:

```sql
SELECT application_name, state, sync_state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS replay_behind,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
```

| Field | Meaning |
|-------|---------|
| `sent_lsn`, `write_lsn`, `flush_lsn`, `replay_lsn` | Log position reached at each stage |
| `pg_wal_lsn_diff(...)` | Distance in bytes between two positions |
| `write_lag`, `flush_lag`, `replay_lag` | Time taken for recent WAL to reach each stage |
| `sync_state` | `async`, `sync`, `potential` or `quorum` |

On a replica:

```sql
SELECT pg_last_wal_receive_lsn(),
       pg_last_wal_replay_lsn(),
       now() - pg_last_xact_replay_timestamp() AS time_since_last_replayed_commit;
```

The last value grows during quiet periods on the primary even when the replica is fully caught up, because no new commits arrive. Compare log positions for an exact measure.

### Measuring lag: Oracle

```sql
-- On the standby
SELECT name, value, time_computed
FROM v$dataguard_stats
WHERE name IN ('transport lag', 'apply lag');
```

```
DGMGRL> SHOW DATABASE shop_s;
  Transport Lag:  0 seconds
  Apply Lag:      2 seconds
```

### Alerting

Alert on lag relative to what the application tolerates, not on any non-zero value. Useful thresholds: lag above the application's staleness budget, and lag that keeps growing for several minutes, which indicates the replica cannot keep up.

## 8. Read-After-Write Consistency

**Read-after-write consistency** (also *read-your-own-writes*) means that after a user changes data, that user's later reads show the change. Asynchronous replicas do not guarantee it.

```
Time  Customer 42                    Primary                 Replica
────  ─────────────────────────────  ──────────────────────  ───────────────────────
t1    place order                ──► INSERT order 1000001;
                                     COMMIT
t2    open "My orders"       ─────────────────────────────►  query runs
                                                             order not replayed yet
      "Where is my order?"   ◄─────────────────────────────  list without 1000001
t3                                                           order replayed
```

Related guarantees:

| Guarantee | Meaning | Violated when |
|-----------|---------|---------------|
| Read-after-write | You see your own changes | Your read goes to a replica that has not replayed your write |
| Monotonic reads | You never see data go back in time | Consecutive reads hit replicas with different lag |
| Consistent prefix | You see changes in the order they happened | Rarely an issue with physical replication, which replays in order |

### Techniques

**1. Read from the primary after a write.** After a user writes, route that user's reads to the primary for a short period, somewhat longer than typical lag:

```
on write by user U:
    session["read_primary_until"] = now() + 5 seconds

on read by user U:
    if now() < session["read_primary_until"]:
        use primary
    else:
        use replica
```

Simple and effective. It fails only when lag exceeds the window.

**2. Track the log position (causal reads).** After the write, record the primary's log position. Read from a replica only once it has replayed past that position.

```sql
-- PostgreSQL, on the primary after COMMIT
SELECT pg_current_wal_lsn();                -- e.g. 3/5A0C2E8

-- On the replica before reading
SELECT pg_last_wal_replay_lsn() >= '3/5A0C2E8'::pg_lsn AS caught_up;
```

```
if caught_up: read from the replica
else:         wait briefly and retry, or read from the primary
```

Store the position in the user's session or a cookie. This gives exact read-after-write with no fixed time window.

**3. Wait for apply at commit.** In PostgreSQL, `synchronous_commit = remote_apply` with the replicas listed in `synchronous_standby_names` makes the commit wait until the listed synchronous replicas have **applied** the change. Reads on those replicas then always see it. The cost is commit latency on every such transaction, and it only covers the synchronous replicas.

**4. Bound staleness on the replica (Oracle).** Active Data Guard sessions can refuse to run queries when the standby is too far behind:

```sql
-- On the standby session: fail if apply lag exceeds 2 seconds
ALTER SESSION SET STANDBY_MAX_DATA_DELAY = 2;

-- 0 = run only if the standby is fully caught up with the primary
ALTER SESSION SET STANDBY_MAX_DATA_DELAY = 0;
```

A query that would violate the limit fails with ORA-03172, and the application can retry on the primary.

**5. Stick to one replica.** Routing each user to the same replica, for example by hashing the user ID, provides monotonic reads. It does not provide read-after-write on its own.

### Choosing

| Technique | Guarantee | Cost |
|-----------|-----------|------|
| Primary for N seconds after a write | Read-after-write, if lag < N | Extra primary load after writes |
| Log position tracking | Exact read-after-write | Application logic; session state |
| `remote_apply` (PostgreSQL) | Read-after-write on sync replicas | Slower commits |
| `STANDBY_MAX_DATA_DELAY` (Oracle) | Bounded staleness | Queries fail when the standby lags |
| Sticky replica per user | Monotonic reads | Uneven load |
| Accept staleness | None | None; fine for catalogues and reports |

Apply these only where they matter: the pages a user sees immediately after their own changes. Product browsing does not need them.

## 9. Failover

**Failover** promotes a replica to primary when the primary fails. **Switchover** does the same deliberately, with no data loss, for maintenance.

### Two measures

| Measure | Question | Determined by |
|---------|----------|---------------|
| **RPO** (Recovery Point Objective) | How much committed data may be lost? | Sync or async replication |
| **RTO** (Recovery Time Objective) | How long may the service be down? | Detection time, promotion time, client redirection |

```
Async replication:  RPO = lag at the moment of failure (seconds, sometimes more)
Sync replication:   RPO = 0 for commits confirmed to clients
```

### The steps

```
1. Detect        primary unreachable for longer than a threshold
      │
2. Decide        is it really down, or only unreachable from here?
      │          which replica is most up to date?
      │
3. Fence         make sure the old primary can no longer accept writes
      │
4. Promote       replica finishes applying received log, becomes primary
      │
5. Redirect      clients reconnect to the new primary
      │
6. Rebuild       old primary rejoins as a replica, or is rebuilt
```

### Split brain

If the old primary is still running but only **appears** failed, for example because of a network partition, promoting a replica creates two primaries. Both accept writes, and the data diverges in ways that cannot be merged automatically.

```
          network partition
               ║
   Primary A   ║   Replica B (promoted)
   still up,   ║   now also primary,
   accepting   ║   accepting writes
   writes      ║
               ║
   two different versions of the truth
```

Preventing split brain is the main job of failover tooling. It requires an independent decision-maker (a quorum, Section 10) and **fencing**: shutting down, isolating or demoting the old primary before or during promotion.

### PostgreSQL

PostgreSQL provides promotion but **no automatic failover** in core:

```sql
-- On the replica (version 12+)
SELECT pg_promote();
```

```bash
# Or from the shell
pg_ctl promote -D /var/lib/postgresql/data
```

Automatic failover is provided by external tools:

| Tool | How it decides |
|------|----------------|
| **Patroni** | Leader lock in a distributed consensus store (etcd, Consul, ZooKeeper). Only the holder of the lock may run as primary |
| **pg_auto_failover** | A monitor node tracks node health and orchestrates promotion |
| **repmgr** | Daemons on each node vote; can use a witness node |
| Managed cloud services | Provider-managed failover and DNS endpoint |

After a failover, the old primary may contain WAL that was never shipped. `pg_rewind` rewinds it to the point where the timelines diverged so it can rejoin as a replica without a full copy.

Clients find the new primary through a multi-host connection string with `target_session_attrs=read-write` (Section 4), a virtual IP, DNS, or a proxy such as HAProxy that checks each node's role.

### Oracle

Data Guard Broker performs switchover and failover:

```
DGMGRL> SWITCHOVER TO shop_s;          -- planned, no data loss
DGMGRL> FAILOVER TO shop_s;            -- unplanned
DGMGRL> REINSTATE DATABASE shop_p;     -- old primary rejoins as standby
```

**Fast-Start Failover (FSFO)** automates failover. A separate **observer** process, ideally at a third site, monitors both databases. If the observer and the standby both lose contact with the primary for longer than `FastStartFailoverThreshold` (default 30 s), the standby is promoted. A primary that has lost contact with both of them stops itself, so the two can never both accept writes.

```
DGMGRL> ENABLE FAST_START FAILOVER;
DGMGRL> START OBSERVER;
```

`REINSTATE` needs **Flashback Database** on the old primary to rewind it to before the failover point. Without flashback, the old primary must be rebuilt.

Clients reconnect through role-based services (Section 4). Transparent Application Failover (TAF) and **Application Continuity** can replay in-flight work after a failover so users do not see errors.

### Practise it

A failover that has never been tested usually fails in production. Run regular switchovers, measure the actual RTO and RPO, and confirm that applications reconnect correctly.

## 10. Quorum-Based Systems

A **quorum** is the minimum number of nodes that must agree before an action counts. Quorums let a group of servers keep working correctly when some of them fail or are cut off, without ever producing two conflicting answers.

### Majority quorum

With **N** nodes, a majority is `floor(N/2) + 1`. Any two majorities share at least one node, so two groups can never both believe they are in charge.

| Nodes | Majority | Failures tolerated |
|-------|----------|--------------------|
| 2 | 2 | 0 |
| 3 | 2 | 1 |
| 4 | 3 | 1 |
| 5 | 3 | 2 |

```
5 nodes split by a network partition

   [A] [B] [C]   ║   [D] [E]
   3 of 5 = majority    2 of 5 = minority
   continues            stops accepting writes
```

Use an **odd number** of nodes. A fourth node adds cost without tolerating more failures than three.

### Where quorums appear

**1. Deciding who is primary.** The failover tools in Section 9 use a quorum so that only one node can be promoted:

- Patroni stores the leader lock in etcd, Consul or ZooKeeper, which are themselves quorum-based (etcd uses the Raft consensus algorithm).
- Oracle Fast-Start Failover treats primary, standby and observer as three voters. A failover needs two of them.

**2. Quorum commit.** A commit is confirmed once a quorum of replicas has it.

- PostgreSQL: `synchronous_standby_names = 'ANY 2 (r1, r2, r3)'`. A commit waits for any 2 of the 3. One slow or failed replica does not stall commits.

**3. Consensus replication.** Every write is replicated through a consensus protocol (Raft or Paxos). A write succeeds when a majority stores it, and a new leader is elected automatically by majority vote.

```
Raft write, 3 replicas
  client ──► leader ──► append to log
                    ├──► follower 1    ack
                    └──► follower 2    (slow)
             leader has 2 of 3 ──► commit ──► reply to client
```

Examples: etcd, CockroachDB, YugabyteDB, Google Spanner, and Oracle Globally Distributed Database with Raft replication (Oracle Database 23ai).

**4. Leaderless quorums (Dynamo-style).** Any node accepts reads and writes. With **N** copies, a write waits for **W** acknowledgements and a read queries **R** replicas:

```
W + R > N   ──►   every read overlaps at least one node with the latest write

N = 3, W = 2, R = 2:
  write ──► [X] [X] [ ]
  read  ──► [ ] [X] [X]        at least one copy read is up to date
```

Examples: Apache Cassandra and Amazon DynamoDB, with tunable consistency levels. Oracle and PostgreSQL do not work this way.

### Trade-offs

| | Primary/replica (Oracle, PostgreSQL) | Consensus / quorum systems |
|---|---|---|
| Write latency | Local commit (async) or one replica round trip (sync) | Round trip to a majority on every write |
| Minimum nodes for automatic failover | Two databases plus an independent witness | Three |
| Failover | External tooling or FSFO; seconds to tens of seconds | Built in; typically seconds |
| Consistency after failover | RPO > 0 with async | No committed write lost while a majority survives |
| Operational model | Mature, familiar SQL databases | Distributed SQL or NoSQL systems with their own trade-offs |

The two approaches often combine: a PostgreSQL primary with replicas, managed by Patroni, whose leader election relies on a Raft-based etcd cluster.

## 13. Short Summary

- A primary accepts writes and ships its log to replicas, which replay it. Physical replication copies the whole database and is the basis for read replicas and failover in both Oracle and PostgreSQL.
- Replicas scale reads, not writes. Route stale-tolerant reads to replicas and keep writes, locking reads and read-then-write logic on the primary.
- Asynchronous replication keeps commits fast but can lose recent commits on failover. Synchronous replication loses nothing confirmed, at the cost of a replica round trip per commit and the risk of stalled commits if no sync replica is available.
- Replication lag is usually milliseconds but can grow to minutes under bursts, large transactions or conflicts with replica queries. Measure it in log positions as well as time.
- Read-after-write consistency needs deliberate handling: read from the primary after a write, track log positions, wait for apply, or bound staleness on the replica.
- Failover is detection, decision, fencing, promotion and redirection. PostgreSQL relies on external tools such as Patroni; Oracle provides Data Guard Broker and Fast-Start Failover.
- Quorums prevent split brain by requiring a majority to agree. They underpin failover decisions, quorum commit, and consensus-replicated databases.
