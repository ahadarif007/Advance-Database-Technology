# Chapter 11: Distributed Database Concepts

Chapters 09 and 10 spread one database across several servers, through replication and sharding. Once data lives on more than one machine, a new class of problems appears: messages are delayed or lost, servers fail independently, clocks disagree, and two servers can hold different answers to the same question at the same moment.

This chapter covers the ideas that explain how distributed databases behave under these conditions: the CAP theorem, consistency models, distributed transactions and two-phase commit, consensus, quorums, leader/follower designs and distributed locks. It connects each idea to what **Oracle** and **PostgreSQL** provide, and to the replication and sharding designs from the previous two chapters.

## 1. Sample Scenario

The shop now runs in two regions:

```
        EU region                                US region
┌───────────────────────────┐            ┌───────────────────────────┐
│ app servers               │            │ app servers               │
│ database node(s)          │◄──────────►│ database node(s)          │
└───────────────────────────┘    WAN     └───────────────────────────┘
                              ~80–100 ms round trip
```

| Data | Requirement |
|------|-------------|
| Stock level of a product | Must never be oversold |
| Customer's shopping cart | Should always accept changes, even during network problems |
| Product reviews and view counts | May be briefly out of date |
| Nightly settlement job | Must run on exactly one server |

Each requirement leads to a different choice in this chapter.

## 2. Why Distribution Is Hard

On one server, a write either happens or it does not, and every reader sees the same data. With several servers, three facts change that.

### 1. The network is unreliable

A request to another node can be lost, delayed, duplicated or delivered out of order. Crucially, **a slow node and a dead node look the same**:

```
Node A ──── request ────► Node B

No reply after 2 seconds. Possible reasons:
  the request was lost             (B never saw it)
  B is down                        (B never processed it)
  B processed it, reply was lost   (the change HAS happened)
  B is just slow                   (the change may happen later)

A cannot tell which.
```

Every distributed protocol must cope with this uncertainty. Retrying is safe only if the operation is **idempotent**, meaning that repeating it has the same effect as doing it once.

### 2. Nodes fail independently

Some nodes keep working while others fail: a **partial failure**. A single-server database is either up or down. A distributed one can be half up, and the half that is up must decide whether to continue.

### 3. There is no shared clock

Server clocks drift and are corrected by NTP, typically to within milliseconds, but sometimes far worse. Two events on different servers cannot be ordered reliably by their timestamps.

```
Node A clock: 12:00:00.010   writes price = 40
Node B clock: 12:00:00.004   writes price = 45     (B's clock is 8 ms slow)

By timestamp, A's write is "later" and wins.
In reality, B's write happened 2 ms after A's.
```

Databases therefore order events with **logical clocks** instead of wall-clock time. Oracle's SCN and PostgreSQL's LSN are logical clocks for a single database. Distributed systems use similar ideas across nodes: Lamport clocks, hybrid logical clocks (CockroachDB), or tightly bounded physical clocks (Google Spanner's TrueTime).

## 3. CAP Theorem

The CAP theorem concerns three properties of a replicated data system:

| Property | Meaning in the theorem |
|----------|------------------------|
| **C**onsistency | Every read returns the most recent write (linearizability, Section 5) |
| **A**vailability | Every request to a working node receives a non-error response |
| **P**artition tolerance | The system keeps operating when the network splits nodes into groups that cannot communicate |

### What the theorem actually says

It is often summarised as "pick two of three". The precise statement is narrower:

> **When a network partition occurs, a system must choose between consistency and availability.**

Partitions are not optional: networks do fail. So the real choice is how the system behaves **during** a partition.

```
             partition
                 ║
   EU node       ║       US node
   stock = 1     ║       stock = 1
                 ║
   customer in EU buys the last item
                 ║
   US customer tries to buy the same item. The US node cannot reach EU.

   Choice C (consistency):  US node refuses or waits             ──► no oversell, but an error
   Choice A (availability): US node accepts with its local copy  ──► answer given, but oversold
```

| Choice during a partition | Behaviour | Suits |
|---------------------------|-----------|-------|
| **CP** | Nodes that cannot confirm they are current refuse requests or wait | Stock, balances, unique usernames |
| **AP** | Every node answers from local data; conflicts are resolved later | Shopping carts, likes, session data, caches |

When there is no partition, a system can be both consistent and available.

### PACELC: the trade-off without a partition

Partitions are rare. A more useful everyday question is captured by the **PACELC** extension:

```
if Partition:  choose Availability or Consistency
Else:          choose Latency or Consistency
```

Even when the network is healthy, strong consistency costs latency, because each write or read must coordinate with other nodes. Synchronous replication between EU and US adds a ~90 ms round trip to every commit. Asynchronous replication avoids that cost but gives up consistency on the replicas.

### Where Oracle and PostgreSQL fit

A single-primary database with replicas (Chapter 09) can be configured on either side:

| Configuration | During a partition | Without a partition |
|---------------|--------------------|---------------------|
| Reads and writes on the primary only | CP: clients cut off from the primary get errors | Consistent; latency of one server |
| Async replicas serving reads | Replicas stay available but stale (AP for reads) | Low latency, stale reads |
| PostgreSQL synchronous standby | Commits wait if no sync standby is reachable (C over A) | Commit latency includes the standby round trip |
| Oracle Maximum Availability | Waits up to `NET_TIMEOUT`, then continues unsynchronised (A over C after the timeout) | Commit latency includes the standby round trip |
| Oracle Maximum Protection | Primary shuts down rather than commit without a standby (C over A) | Commit latency includes the standby round trip |

CAP describes a whole system, not a product. The same database can be CP for one table and AP for another, depending on how the application reads and writes it.

## 4. Consistency Models

A **consistency model** is a contract: it states which values a read is allowed to return, given the writes that have happened. Stronger models are easier to program against and more expensive to provide.

```
stronger, slower, more coordination
  ▲
  │  Linearizable          reads see the latest write, everywhere, immediately
  │
  │  Sequential            all clients see writes in one agreed order (may lag)
  │
  │  Causal                writes that depend on each other appear in order;
  │                        unrelated writes may appear in any order
  │
  │  Session guarantees    read-your-writes, monotonic reads (per client)
  │
  │  Eventual              replicas converge if writes stop; no ordering promise
  ▼
weaker, faster, more available
```

| Model | Guarantee | Example of what it rules out |
|-------|-----------|------------------------------|
| **Linearizable** | Once a write completes, every later read anywhere returns it (or something newer) | Reading the old price after the update returned success |
| **Sequential** | Every client sees all writes in the same order, possibly late | Two clients seeing two updates in opposite orders |
| **Causal** | If write B depended on write A (for example, a reply to a comment), everyone sees A before B | Seeing a reply before the comment it answers |
| **Read-your-writes** | A client always sees its own earlier writes | Your new order missing from "My orders" (Chapter 09, Section 8) |
| **Monotonic reads** | A client never sees data move back in time | A count of 5, then 3, then 5 on refresh |
| **Eventual** | If writes stop, all replicas eventually hold the same value | Nothing in the meantime |

### Consistency is not isolation

Two different ideas share similar words:

| | Isolation (Chapter 04) | Consistency model (this chapter) |
|---|---|---|
| Concerns | **Transactions**: groups of operations on many rows | **Single operations**: reads and writes of an item across replicas |
| Strongest level | Serializable | Linearizable |
| Question answered | Do concurrent transactions behave as if run one at a time? | Does a read reflect the latest write in real time? |

A system can be serializable without being linearizable: a serializable transaction on an asynchronous replica sees a consistent but **old** snapshot. **Strict serializability** combines both. Transactions behave as if run one at a time, in an order that respects real time. A single Oracle or PostgreSQL primary provides this at its serializable level for transactions that run on it. Google Spanner and some distributed SQL databases provide it across nodes.

## 5. Strong Consistency

A system is **strongly consistent** (formally, **linearizable**) if it behaves as though there were a single copy of the data, and every operation takes effect at one instant between its start and its end.

```
Time ─────────────────────────────────────────────────────────────►

Client 1:  [── write price = 45 ──]
                                    ok
Client 2:                               [── read ──]  must return 45
Client 3:            [── read ──]                     may return 40 or 45
                     (overlaps the write)
```

Once the write has returned, no reader anywhere may see the old value.

### How it is achieved

All approaches route each operation through a point that knows the latest state:

| Approach | How reads stay current | Cost |
|----------|------------------------|------|
| Single primary, reads on primary | Only one copy is ever read | Primary handles all reads; replicas only for failover |
| Synchronous replication with `remote_apply`, reads on sync replicas | Commit waits until replicas have applied it (Chapter 09, Section 6) | Commit latency; covers only the sync replicas |
| Consensus with leader reads | Leader confirms it is still leader (lease or majority check) before reading | A round trip or a lease per read |
| Quorum reads and writes with `W + R > N` | Read overlaps the latest write | Not fully linearizable on its own (Section 10) |

### In Oracle and PostgreSQL

- Reads and writes on the **primary** are linearizable for single operations, and committed transactions are visible to every new statement immediately.
- Reads on **asynchronous replicas** are not. They are consistent snapshots of an earlier moment.
- The techniques for read-after-write (Chapter 09, Section 8) bring replica reads closer to strong consistency for the cases that need it.

### The price

```
Strong consistency across regions: every write coordinates across the WAN

  EU client ──► EU leader ──► US replica ack (~90 ms) ──► commit
             └─────────────── ≥ 90 ms per write ────────────────┘
```

Use strong consistency where an incorrect read causes real harm: stock, money, uniqueness, permissions. Use weaker models where it does not.

## 6. Eventual Consistency

**Eventual consistency** guarantees only that if no new writes arrive, all replicas will eventually hold the same value. In between, different replicas may return different values.

```
t0  write "cart: +lamp" accepted by EU node

        EU node:  cart = [lamp]
        US node:  cart = []          ◄ stale

t1  change propagates

        EU node:  cart = [lamp]
        US node:  cart = [lamp]      ◄ converged
```

It is everywhere in practice: asynchronous replicas (Chapter 09), caches (Chapter 08), CQRS read models and summary tables (Chapter 07), DNS, and leaderless databases such as Cassandra and DynamoDB.

### Conflicts

If two nodes accept writes to the same item during the same window, the writes **conflict**, and the system must decide the final value. This happens in multi-leader and leaderless systems (Section 11), not in single-primary Oracle or PostgreSQL setups, where all writes go to one node.

```
Partition: EU and US both accept a change to customer 42's cart

  EU:  cart = [lamp, desk]       (added desk)
  US:  cart = [lamp, chair]      (added chair)

After the partition heals, which cart is correct?
```

| Resolution strategy | Result for the cart | Risk |
|---------------------|---------------------|------|
| **Last writer wins (LWW)** by timestamp | Either `[lamp, desk]` or `[lamp, chair]` | One write is silently lost; clock skew decides the winner (Section 2) |
| **Keep all versions** (version vectors / siblings) | Both versions returned; the application merges them | Application complexity |
| **CRDT** (conflict-free replicated data type) | `[lamp, desk, chair]` automatically | Only for data types with a defined merge |
| **Application rule** | Business-specific merge (for example, highest priority wins) | Must be written and tested per entity |

### CRDTs

A **CRDT** is a data type whose concurrent updates can always be merged without conflict, in any order, to the same result:

| CRDT | Merge rule | Use |
|------|------------|-----|
| G-Counter (grow-only counter) | Each node counts its own increments; total = sum of all nodes' counts | View counts, likes |
| PN-Counter | Two G-Counters: one for increments, one for decrements | Counters that go up and down |
| OR-Set (observed-remove set) | Additions and removals tagged so that concurrent add and remove resolve predictably | Shopping carts, tags |
| LWW-Register | Keeps the value with the highest timestamp | Simple fields where losing a concurrent write is acceptable |

```
G-Counter for product views

  EU node counts:  {EU: 120, US:  0}
  US node counts:  {EU:   0, US: 80}
  merge (max per node): {EU: 120, US: 80}  ──► total 200 on both nodes
```

### Multi-writer setups in Oracle and PostgreSQL

| | Oracle | PostgreSQL |
|---|---|---|
| Bidirectional replication | GoldenGate active-active | Logical replication in both directions; `origin = none` (version 16+) prevents changes looping back |
| Conflict detection and resolution | GoldenGate Conflict Detection and Resolution (CDR), including timestamp-based rules | Not built in: the apply worker stops on errors such as unique violations; resolution needs manual action or external tools |

Multi-writer database replication is hard to operate correctly. Prefer designs where each item has one home: shard by region (Chapter 10) so that EU customers are written only in the EU, and replicate asynchronously for reads elsewhere.

### Living with eventual consistency

| Practice | Reason |
|----------|--------|
| Make updates idempotent | Changes may be applied more than once |
| Prefer commutative operations (`+1`) over overwrites (`= 7`) | Commutative operations converge regardless of order |
| Show freshness to users where it matters ("updated 2 min ago") | Sets expectations |
| Measure convergence lag | "Eventually" should have a known bound in practice |
| Provide session guarantees for each user's own data | Users notice their own missing writes first (Chapter 09, Section 8) |

## 7. Distributed Transactions

A **distributed transaction** changes data on more than one node and must still be atomic: all changes commit or none do. Chapter 10 (Section 10) showed why this matters for cross-shard writes. This section covers the general picture.

A distributed transaction needs two things:

| Requirement | Problem | Mechanism |
|-------------|---------|-----------|
| **Atomic commit** | All participants must reach the same commit or abort decision | Two-phase commit (Section 8), or commit through consensus |
| **Isolation across nodes** | Readers must not see the transaction committed on one node and not yet on another | Global snapshots or timestamps (for example, Oracle synchronises SCNs between databases in a distributed transaction; Spanner uses commit timestamps) |

### Where distributed transactions appear

| Situation | Example |
|-----------|---------|
| Several databases joined by links | Oracle database links, PostgreSQL `postgres_fdw` |
| Database plus message broker | Commit an order and publish an event atomically |
| Sharded databases | Cross-shard updates (Chapter 10) |
| Several services, each with its own database | Order service, payment service, inventory service |

### The XA standard

**XA** (from X/Open) is the standard interface between a **transaction manager** (in the application server or a library) and **resource managers** (databases, message brokers). The transaction manager runs two-phase commit across all of them.

```
                 Transaction manager (app server / library)
                 ┌──────────┼────────────────┐
                 ▼          ▼                ▼
            Oracle DB   PostgreSQL DB   Message broker
          (XA resource) (XA resource)   (XA resource)
```

| | Oracle | PostgreSQL |
|---|---|---|
| XA support | Full: XA in JDBC and OCI drivers, `DBMS_XA` package | Through drivers (for example the JDBC `PGXADataSource`), built on `PREPARE TRANSACTION`; requires `max_prepared_transactions > 0` |
| Native distributed transactions | Automatic two-phase commit across database links | `postgres_fdw` does not use two-phase commit for writes to several servers |

### Avoiding them

Distributed transactions are slow, can block, and couple systems tightly. The usual alternatives were covered earlier:

- **Co-locate** data that changes together (Chapter 10, Section 5).
- **Transactional outbox** for database plus messaging (Chapter 07, Section 9).
- **Sagas** with compensating actions for multi-service processes (Chapter 10, Section 10).

## 8. Two-Phase Commit

Chapter 10 introduced the two phases. This section covers what each side records, how failures are handled, and why 2PC can block.

### The protocol step by step

```
Coordinator                                  Participant (each one)
───────────                                  ──────────────────────
send PREPARE ───────────────────────────────► do the work, write all changes and
                                              a "prepared" record durably;
                                              keep locks
           ◄─────────────────────────────────  vote YES  (or NO, then roll back)

all YES?  write "commit" decision durably
          (the commit point)
send COMMIT ────────────────────────────────► commit, release locks
           ◄─────────────────────────────────  ack

any NO?   write "abort", send ROLLBACK
```

The **commit point** is the moment the coordinator durably records its decision. Before it, the transaction can still be aborted. After it, the transaction **will** commit, even if every node crashes and restarts.

### What happens on failure

| Failure | State | Outcome |
|---------|-------|---------|
| Participant fails **before** voting | No vote received | Coordinator aborts the transaction |
| Participant fails **after** voting YES | Prepared record on disk | On restart, it asks the coordinator for the decision; until then, it holds locks |
| Coordinator fails **before** the commit point | No decision recorded | On recovery, aborts (presumed abort) |
| Coordinator fails **after** the commit point | Decision recorded | On recovery, re-sends COMMIT to all participants |
| Coordinator **unreachable** while participants are prepared | Participants cannot decide alone | **Blocked**: locks held, transaction in doubt |

### The blocking window

```
Participant timeline

  working ──► PREPARED ─────────────── waiting for decision ──────────────► COMMIT
              (voted YES:                    │
               can no longer abort           coordinator down?
               on its own; locks held)       ──► stays here, holding locks,
                                                 until the coordinator returns
                                                 or an operator decides
```

A prepared participant has promised to commit if told to, so it cannot roll back on its own. Nor can it commit, because another participant might have voted NO. Rows locked by an in-doubt transaction stay locked, blocking other work.

Three-phase commit was proposed to avoid blocking, but it relies on assumptions about timing that real networks break, and it is rarely used. Modern distributed databases instead make the coordinator itself fault-tolerant by **replicating its decision through consensus** (Section 9). Spanner runs two-phase commit between groups that are each replicated with Paxos, so a coordinator failure is handled by electing a new leader that already knows the decision.

### Resolving in-doubt transactions

**PostgreSQL**

```sql
SELECT gid, prepared, owner, database FROM pg_prepared_xacts;

COMMIT PREPARED 'xfer-8841';        -- if the coordinator decided commit
ROLLBACK PREPARED 'xfer-8841';      -- if it decided abort, or never decided
```

Prepared transactions survive restarts, hold locks, and prevent VACUUM from removing old row versions (Chapter 04, Section 3). Alert on any prepared transaction older than a few minutes.

**Oracle**

Oracle resolves in-doubt distributed transactions automatically through the `RECO` background process once the databases can reach each other again. When manual action is needed:

```sql
SELECT local_tran_id, global_tran_id, state, fail_time
FROM dba_2pc_pending;

COMMIT FORCE '1.21.17';
-- or
ROLLBACK FORCE '1.21.17';
```

Before forcing, find out the decision taken on the other databases, for example from `DBA_2PC_PENDING` on the coordinator. Forcing the opposite decision on one participant breaks atomicity permanently.

## 9. Consensus

**Consensus** is the problem of getting several nodes to agree on a value, or on an ordered sequence of values, even when some nodes fail and messages are delayed. It is the foundation of leader election, replicated logs, distributed locks and fault-tolerant commit.

A consensus protocol must guarantee:

| Property | Meaning |
|----------|---------|
| Agreement | No two nodes decide different values |
| Validity | The decided value was proposed by some node |
| Termination | Every working node eventually decides, as long as a majority is up and can communicate |

Agreement is never violated, whatever the failures. Progress (termination) needs a working majority (Chapter 09, Section 10). A well-known result (FLP) shows that no protocol can guarantee progress in a fully asynchronous network with even one faulty node, so practical protocols use timeouts to make progress when the network behaves reasonably.

### Raft

**Raft** is the most widely used consensus protocol, designed to be easier to understand than its predecessor, Paxos. It works through a **leader** that replicates a log to **followers**.

**Leader election**

```
Term 1: Node A is leader, sends heartbeats
        A ── heartbeat ──► B
        A ── heartbeat ──► C

A crashes. B hears no heartbeat before its (randomised) election timeout.

Term 2: B becomes candidate, votes for itself, asks the others
        B ── vote for me (term 2)? ──► C   ── yes
        B has 2 of 3 votes (a majority)    ──► B is leader for term 2

A recovers, sees term 2 > its term 1  ──► becomes a follower
```

- Time is divided into numbered **terms**. Each term has at most one leader.
- A node votes for at most one candidate per term, so two candidates cannot both win a majority.
- Randomised timeouts make split votes rare.
- A candidate wins only if its log is at least as up to date as the voters', so a new leader always has every committed entry.

**Log replication**

```
Client ──► Leader: append "SET stock[42] = 3" at index 7 (term 2)
             │
             ├──► Follower B: append index 7   ── ack
             └──► Follower C: append index 7   (slow)

Leader has the entry on 2 of 3 nodes ──► index 7 is COMMITTED
            ──► apply to state machine ──► reply to client
            ──► tell followers "committed up to 7" in the next heartbeat
```

An entry is committed once a majority stores it. Any future leader must have it, because any majority that elects the new leader overlaps the majority that stored the entry.

### Where consensus is used

| System | Protocol | Purpose |
|--------|----------|---------|
| etcd | Raft | Configuration, leader election (Kubernetes, Patroni) |
| Apache ZooKeeper | Zab | Coordination, locks, leader election |
| Consul | Raft | Service discovery, configuration, locks |
| CockroachDB, YugabyteDB, TiDB | Raft (per data range) | Replication of every row |
| Google Spanner | Paxos (per data split) | Replication; 2PC between groups |
| Oracle Globally Distributed Database (23ai) | Raft | Replication of shards, automatic failover |

Core PostgreSQL contains no consensus protocol. High-availability setups obtain it from an external store, as Patroni does with etcd (Chapter 09, Section 9). Oracle Data Guard's Fast-Start Failover uses a simpler majority among primary, standby and observer.

### Consensus vs two-phase commit

| | Two-phase commit | Consensus |
|---|---|---|
| Agreement needed from | **All** participants | A **majority** |
| Each participant holds | Different data (one shard each) | The same data (replicas) |
| Purpose | Atomic commit across different data | Agreeing on one replicated history |
| One node down | Blocks the transaction | Continues while a majority is up |

They solve different problems and are often combined: 2PC across shards, consensus within each shard's replicas.

## 10. Quorum Reads and Writes

Chapter 09 (Section 10) covered majority quorums in primary/replica systems, where they decide failover and confirm commits. Leaderless systems go further and use quorums for **every** read and write. This section explains how, and where the guarantee falls short.

### The parameters

| Symbol | Meaning |
|--------|---------|
| `N` | Number of replicas of each item |
| `W` | Replicas that must acknowledge a write |
| `R` | Replicas that must answer a read |

```
N = 3, W = 2, R = 2

write v2 ──► [v2] [v2] [v1]       2 acks: write succeeds; replica 3 missed it
read     ──► [  ] [v2] [v1]       2 answers: v2 and v1. Take the newest: v2
                   └── overlap guaranteed because W + R = 4 > 3
```

### Tuning the trade-off

| Setting (N = 3) | Write | Read | Survives |
|-----------------|-------|------|----------|
| `W = 3, R = 1` | Slow; fails if any replica is down | Fast | Reads with 2 nodes down; no writes with 1 down |
| `W = 1, R = 3` | Fast | Slow; fails if any replica is down | Writes with 2 nodes down; no reads with 1 down |
| `W = 2, R = 2` | Moderate | Moderate | Reads and writes with 1 node down |
| `W = 1, R = 1` | Fast | Fast | Highest availability; **no overlap**, eventual consistency only |

In Apache Cassandra these are consistency levels per query: `ONE`, `QUORUM`, `LOCAL_QUORUM` (majority within one data centre), `ALL`. `LOCAL_QUORUM` avoids cross-region latency while staying consistent within a region.

### Keeping replicas in sync

A replica that missed writes must be repaired:

| Mechanism | How |
|-----------|-----|
| **Read repair** | A read that finds a stale replica writes the newer value back to it |
| **Hinted handoff** | If a replica is down, another node stores the write with a "hint" and delivers it when the replica returns |
| **Anti-entropy** | A background process compares replicas (using Merkle trees of hashes) and copies missing data |

```
read with R = 2 finds:  replica 2 = v2, replica 3 = v1
        ──► return v2 to the client
        ──► write v2 to replica 3   (read repair)
```

### Why W + R > N is not enough for strong consistency

The overlap guarantees that a read **contacts** a replica with the latest successful write. It does not guarantee linearizability:

| Situation | Effect |
|-----------|--------|
| A write fails after reaching only 1 of the required 2 replicas | It is not rolled back; some reads see it, others do not |
| A read runs concurrently with a write | One reader sees the new value, a later reader the old one |
| Conflicts resolved by last-writer-wins | Clock skew can discard a write that "succeeded" (Section 6) |
| **Sloppy quorums** with hinted handoff | Writes counted on substitute nodes do not overlap with reads on the home replicas |

Strong consistency in leaderless systems needs extra mechanisms, such as Cassandra's lightweight transactions, which run a Paxos round per operation.

### Quorums in Oracle and PostgreSQL

Oracle and PostgreSQL are single-leader systems and do not use read/write quorums. Quorums appear only on the commit path:

- PostgreSQL `synchronous_standby_names = 'ANY 2 (r1, r2, r3)'` confirms a commit once any 2 standbys have it (Chapter 09, Section 6).
- Oracle Raft replication (23ai Globally Distributed Database) commits each change once a majority of replicas have it.

## 11. Leader/Follower Architecture

Chapter 09 described leader/follower (primary/replica) replication in Oracle and PostgreSQL. This section compares it with the alternatives and covers the problem of a leader that does not know it has been replaced.

### Three replication topologies

```
Single leader                 Multi-leader                    Leaderless

  writes                        writes      writes              writes / reads
    │                             │           │                 │     │     │
    ▼                             ▼           ▼                 ▼     ▼     ▼
 [Leader]                     [Leader EU]◄─►[Leader US]       [N1]  [N2]  [N3]
  │    │                         │             │               any node accepts;
  ▼    ▼                         ▼             ▼               quorums decide
[F1]  [F2]                     [F]           [F]
```

| | Single leader | Multi-leader | Leaderless |
|---|---|---|---|
| Who accepts writes | One node | One leader per site | Any node |
| Write conflicts | None | Yes; must be resolved (Section 6) | Yes; resolved by versions or LWW |
| Write latency for remote users | Round trip to the leader's site | Local | Local, with quorum |
| Failover | Needed when the leader fails | Each site continues | Not needed |
| Consistency | Strong on the leader | Eventual between sites | Tunable (Section 10) |
| Examples | Oracle Data Guard, PostgreSQL streaming replication, Raft-based systems | Oracle GoldenGate active-active, bidirectional PostgreSQL logical replication | Cassandra, DynamoDB, Riak |

Oracle and PostgreSQL are single-leader by design. Raft-based databases are also single-leader per data range, with automatic election. Multi-leader and leaderless designs trade conflict handling for local writes and higher availability.

Oracle RAC is a different model: several instances share one copy of the data on shared storage and coordinate through a cache-fusion interconnect. It needs no data replication between instances, but all instances depend on the same storage and are normally in one data centre.

### The stale leader problem

A leader can be replaced while it is not looking: during a long garbage-collection pause, a VM freeze, or a network partition. When it resumes, it may still believe it is the leader.

```
Time   Old leader A                          Cluster
────   ─────────────────────────────────     ───────────────────────────────
t1     leader (term 5), holds lease
t2     paused (GC / VM freeze) ...
t3                                           no heartbeat; B elected (term 6)
t4                                           B accepts writes
t5     resumes, still thinks it is leader
       accepts a write                      ──► two leaders: split brain
```

Defences:

| Defence | How |
|---------|-----|
| **Leases** | A leader may act only while its time-limited lease is valid, and a new leader waits for the old lease to expire. Depends on bounded clock drift |
| **Epoch / term numbers** | Every message carries the leader's term. Nodes reject messages from a lower term |
| **Fencing** | The old leader is forcibly cut off: shut down, its storage access revoked, or its writes rejected (Section 12) |
| **Self-demotion** | A leader that cannot reach a majority steps down (Oracle FSFO primary shutdown; Patroni demotes a primary that loses its leader lock) |

## 12. Distributed Locks

A **distributed lock** ensures that only one process, across many servers, performs an action at a time: running the nightly settlement job, processing one customer's queue, or refreshing one cache key (Chapter 08, Section 12).

### Option 1: Locks in the database

If every process already connects to the same database, its locks are the simplest and most reliable choice. The database is the single point of truth, and locks are released automatically when the session or transaction ends.

**PostgreSQL advisory locks** are application-defined locks on a number. The database never takes them on its own.

```sql
-- Try to take the lock; returns true or false immediately
SELECT pg_try_advisory_lock(hashtext('nightly_settlement'));

-- ... run the job ...

SELECT pg_advisory_unlock(hashtext('nightly_settlement'));
```

| Function | Scope | Released |
|----------|-------|----------|
| `pg_advisory_lock(key)` | Session | By `pg_advisory_unlock` or session end; waits if held |
| `pg_try_advisory_lock(key)` | Session | Same; returns `false` instead of waiting |
| `pg_advisory_xact_lock(key)` | Transaction | At commit or rollback |
| `pg_try_advisory_xact_lock(key)` | Transaction | Same; returns `false` instead of waiting |

Held advisory locks appear in `pg_locks` with `locktype = 'advisory'`.

Session-level advisory locks do not work through a connection pooler in transaction mode, such as PgBouncer's `pool_mode = transaction`, because consecutive statements may run on different server sessions. Use the transaction-level functions in that case.

**Oracle `DBMS_LOCK`** provides named user locks:

```sql
DECLARE
    l_handle VARCHAR2(128);
    l_status INTEGER;
BEGIN
    DBMS_LOCK.ALLOCATE_UNIQUE('nightly_settlement', l_handle);  -- note: commits

    l_status := DBMS_LOCK.REQUEST(
                    lockhandle        => l_handle,
                    lockmode          => DBMS_LOCK.X_MODE,
                    timeout           => 0,
                    release_on_commit => FALSE);

    IF l_status = 0 THEN
        -- lock acquired: run the job
        l_status := DBMS_LOCK.RELEASE(l_handle);
    ELSIF l_status = 1 THEN
        NULL;  -- timeout: another session holds it
    END IF;
END;
/
```

| `REQUEST` return value | Meaning |
|------------------------|---------|
| 0 | Success |
| 1 | Timeout |
| 2 | Deadlock |
| 3 | Parameter error |
| 4 | Already own the lock |
| 5 | Illegal lock handle |

`ALLOCATE_UNIQUE` performs a commit, so call it before starting the transaction that needs the lock. Execute permission on `DBMS_LOCK` must be granted explicitly.

A simpler portable alternative is a row lock on a dedicated table:

```sql
SELECT * FROM job_locks WHERE job_name = 'nightly_settlement' FOR UPDATE NOWAIT;
```

The lock lasts until the transaction ends (Chapter 04, Section 6).

### Option 2: Coordination services

When there is no single shared database, or locks must survive a database failover, use a consensus-based coordination service:

| Service | Mechanism |
|---------|-----------|
| etcd | Lease attached to a key; the key disappears when the lease expires |
| ZooKeeper | Ephemeral sequential nodes that vanish when the client's session ends |
| Consul | Sessions with health checks and TTLs |

These are fault-tolerant because the lock state itself is replicated by consensus (Section 9).

### Option 3: Redis

`SET lock:key token NX PX 30000` creates a lock with a 30-second expiry (Chapter 08, Section 12). On a single Redis instance this is fast and adequate for **efficiency** locks, where an occasional duplicate run only wastes work. It is not safe for **correctness** locks: if the instance fails over to a replica that had not yet received the lock, two clients can both hold it. The multi-instance *Redlock* algorithm depends on timing assumptions about clocks and pauses, and its safety for correctness is disputed. For correctness, use a database lock or a consensus-based service with fencing.

### The expiring lock problem and fencing tokens

Any lock with an expiry, or any lock lost when a session is presumed dead, has the same weakness as the stale leader in Section 11:

```
Time   Client 1                              Client 2                 Storage
────   ──────────────────────────────────    ─────────────────────    ────────────
t1     acquire lock (expires t3)
t2     long pause (GC) ...
t3                                           lock expired;
                                             acquire lock
t4                                           write data       ──────► accepted
t5     resumes, believes it holds the lock
       write data   ──────────────────────────────────────────────►   accepted
                                                                       (corrupted)
```

The fix is a **fencing token**: a number that increases every time the lock is granted. The client sends its token with every write, and the storage rejects any token lower than the highest it has seen.

```
Client 1 gets lock with token 33, pauses
Client 2 gets lock with token 34, writes with token 34   ──► storage records 34
Client 1 resumes, writes with token 33                   ──► rejected (33 < 34)
```

In a database, the check is a conditional update:

```sql
UPDATE settlement_state
SET    last_run_date = :run_date,
       fencing_token = :token
WHERE  id = 1
AND    fencing_token < :token;
-- 0 rows updated: a newer lock holder has already written; stop
```

etcd revisions and ZooKeeper zxids increase monotonically and serve directly as fencing tokens. A PostgreSQL sequence or Oracle sequence can generate them for database-based locks.

### Choosing a lock

| Need | Choice |
|------|--------|
| Processes share one database | Advisory lock / `DBMS_LOCK` / `FOR UPDATE NOWAIT` |
| Lock must survive database failover, or no shared database | etcd, ZooKeeper or Consul |
| Avoid duplicate work; occasional duplicates are harmless | Redis `SET NX PX` |
| Duplicates would corrupt data | Any of the above **plus** fencing tokens checked by the storage |

## 13. A Systematic Approach to Distributed Data

```
1. For each kind of data, what is the cost of a wrong or stale read?
        │
        ├── harmful (stock, money, uniqueness, permissions)
        │       ──► strong consistency: single leader, reads on the leader,
        │           or consensus-based storage                          Sections 5, 9
        │
        ├── annoying only to the user who wrote it
        │       ──► session guarantees: read-your-writes, monotonic reads
        │                                                               Section 4
        │
        └── harmless if brief (counts, reviews, catalogues)
                ──► eventual consistency: async replicas, caches        Section 6
        │
        ▼
2. During a partition, should this data stay writable?
        │
        ├── no  ──► CP: reject or wait on the minority side             Section 3
        └── yes ──► AP: accept locally; define conflict resolution
                    (CRDT, application merge; avoid blind LWW)          Section 6
        │
        ▼
3. Does one operation change data on several nodes?
        │
        ├── avoid if possible: co-locate, outbox, saga
        └── otherwise: 2PC with monitoring of in-doubt transactions     Sections 7, 8
        │
        ▼
4. How are leaders chosen and old leaders stopped?
        consensus or a majority witness; terms; fencing                 Sections 9, 11
        │
        ▼
5. Do processes need mutual exclusion?
        database lock if one shared database; coordination service
        otherwise; fencing tokens whenever correctness depends on it    Section 12
        │
        ▼
6. Measure
        replication and convergence lag, in-doubt transactions,
        failover time, conflict counts
```

## 15. Short Summary

- Distributed systems face lost and delayed messages, partial failures and unreliable clocks. A slow node is indistinguishable from a failed one, so operations should be idempotent and ordered by logical clocks.
- CAP says that during a network partition a system must choose consistency or availability. PACELC adds that without a partition the choice is between consistency and latency.
- Consistency models range from linearizable to eventual. Isolation levels concern transactions; consistency models concern replicas. Choose per kind of data, not per system.
- Strong consistency means reading through a single up-to-date point, at the cost of coordination latency. Eventual consistency needs a conflict strategy; CRDTs and application merges avoid the silent losses of last-writer-wins.
- Distributed transactions need atomic commit across nodes. Two-phase commit provides it but blocks when the coordinator is unreachable after participants have prepared; monitor and resolve in-doubt transactions.
- Consensus protocols such as Raft let a majority agree on a leader and on an ordered log, and keep working while a majority is up. Two-phase commit needs all participants; consensus needs a majority.
- Quorum reads and writes with `W + R > N` make reads overlap the latest write, but do not by themselves provide linearizability.
- Single-leader systems such as Oracle and PostgreSQL avoid write conflicts but need failover; stale leaders must be stopped with terms, leases and fencing.
- Distributed locks are simplest and safest in the shared database. Any lock that can expire needs fencing tokens when correctness depends on it.
