# Chapter 12: Write Optimisation

Most tuning advice is about reads: indexes, plans and caches. Writes have their own costs, and they are paid on every row. Each insert crosses the network, checks constraints, updates every index, generates log records, and at commit waits for the log to reach disk. A program that writes one row at a time pays all of these costs once per row, and is often 10 to 100 times slower than it needs to be.

This chapter covers the techniques that remove most of that cost: batching statements and commits, bulk loading, upserts, reducing log volume, group commit, trimming indexes and foreign-key checks, and asynchronous writes. Each is shown for **Oracle** and **PostgreSQL**, together with the durability or consistency trade-off it makes.

## 1. How a Write Is Processed

One insert followed by a commit goes through these steps:

```
Application                                  Database
    │                                            │
    │ ── INSERT INTO order_items ... ──────────► │  1. network round trip
    │                                            │  2. parse and bind (cheap if prepared)
    │                                            │  3. foreign-key checks: look up parent rows
    │                                            │  4. write the row into a table block
    │                                            │  5. add an entry to every index
    │                                            │  6. generate log records for 4 and 5
    │ ◄───────────────────────── 1 row ───────── │
    │                                            │
    │ ── COMMIT ───────────────────────────────► │  7. flush the log to disk and wait
    │ ◄───────────────────────── done ────────── │
```

Each step is paid at a different rate:

| Step | Paid once per | Reduced by |
|------|---------------|------------|
| Network round trip | statement | Batch inserts (Section 3), bulk loading (Section 4) |
| Parse | statement | Prepared statements, batching |
| Foreign-key check | row, per foreign key | Section 10 |
| Index maintenance | row, per index | Section 9; drop and rebuild for large loads (Section 4) |
| Log generation | byte changed | WAL optimisation (Section 7) |
| Log flush | commit | Transaction batching (Section 6), group commit (Section 8), async commit (Section 11) |

The principle behind this chapter:

> **Pay fixed costs once per batch, not once per row, and remove per-row work that is not needed.**

### A worked example

Assume a network round trip of 0.3 ms, a log flush of 0.5 ms, and 0.05 ms of real work per row. Inserting 10,000 rows:

```
One row per statement, autocommit on
  per row:  0.3 (insert trip) + 0.3 (commit trip) + 0.5 (flush) + 0.05   ≈ 1.15 ms
  total:    10,000 × 1.15 ms                                             ≈ 11.5 s

1,000 rows per statement, one commit at the end
  10 statements × 0.3 ms + 1 commit (0.3 + 0.5 ms) + 10,000 × 0.05 ms    ≈ 0.5 s
```

The database did the same useful work in both cases. Almost all of the difference is waiting.

## 2. Sample Schema

The examples use the shop schema from Chapter 01:

```
customers (1) ───< orders (N) ───< order_items (N) >─── (1) products
```

Two tables are added, each representing a common write pattern:

| Table | Write pattern | Rows |
|-------|---------------|------|
| `product_daily_sales` | Upsert: one row per product per day, updated many times | ~3,650,000 (10,000 products × 365 days) |
| `page_views` | High-volume append, losing the last second is acceptable | ~50,000,000 per month |

**PostgreSQL**

```sql
CREATE TABLE product_daily_sales (
    product_id BIGINT        NOT NULL REFERENCES products,
    sale_date  DATE          NOT NULL,
    qty        INT           NOT NULL,
    revenue    NUMERIC(12,2) NOT NULL,
    PRIMARY KEY (product_id, sale_date)
);

CREATE TABLE page_views (
    view_id     BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT,
    product_id  BIGINT      NOT NULL,
    viewed_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Staging table for bulk loads (Section 4)
CREATE UNLOGGED TABLE orders_stage (LIKE orders INCLUDING DEFAULTS);
```

**Oracle** (only the differences)

```sql
-- NUMBER instead of BIGINT/INT, TIMESTAMP WITH TIME ZONE and SYSTIMESTAMP
-- instead of TIMESTAMPTZ and now().
-- No UNLOGGED tables; a staging table uses NOLOGGING (Section 4):
CREATE TABLE orders_stage NOLOGGING AS SELECT * FROM orders WHERE 1 = 0;
```

## 3. Batch Inserts

A **batch insert** sends many rows in one statement or one network call, so the round trip and parse cost is shared by all of them.

Instead of:

```sql
INSERT INTO customers (name, email, country, city) VALUES ('A', 'a@mail.com', 'UK', 'London');
INSERT INTO customers (name, email, country, city) VALUES ('B', 'b@mail.com', 'FR', 'Paris');
INSERT INTO customers (name, email, country, city) VALUES ('C', 'c@mail.com', 'DE', 'Berlin');
...
```

send the rows together:

```sql
INSERT INTO customers (name, email, country, city)
VALUES ('A', 'a@mail.com', 'UK', 'London'),
       ('B', 'b@mail.com', 'FR', 'Paris'),
       ('C', 'c@mail.com', 'DE', 'Berlin');
```

There are three ways to batch, and both databases support all of them in some form.

### 1. Multi-row VALUES

| | Syntax |
|---|---|
| PostgreSQL | `INSERT ... VALUES (...), (...), (...)` (all supported versions) |
| Oracle 23ai | The same syntax (table value constructor) |
| Oracle 19c and earlier | `INSERT ALL INTO t VALUES (...) INTO t VALUES (...) SELECT * FROM dual` |

`INSERT ALL` works, but parsing becomes slow with many rows. On Oracle before 23ai, prefer array binding.

### 2. Array binding (driver batching)

The application prepares one statement and sends many sets of bind values in one call. This is the most common method in application code.

```java
// JDBC, both databases
PreparedStatement ps = conn.prepareStatement(
    "INSERT INTO order_items (order_id, product_id, quantity) VALUES (?, ?, ?)");
for (Item it : items) {
    ps.setLong(1, it.orderId);
    ps.setLong(2, it.productId);
    ps.setInt(3, it.qty);
    ps.addBatch();
    if (++n % 1000 == 0) ps.executeBatch();   // send every 1,000 rows
}
ps.executeBatch();
conn.commit();
```

| Driver | Behaviour |
|--------|-----------|
| Oracle JDBC / OCI | True array DML: one call, one execution for the whole batch |
| PostgreSQL JDBC | Sends the statements together in one network exchange. With `reWriteBatchedInserts=true` (default `false`) it also rewrites them into multi-row `VALUES` statements, which is usually several times faster |
| psycopg 3 (Python) | `executemany()` uses pipeline mode (3.1+) |
| psycopg2 (Python) | `executemany()` sends one statement per row; use `psycopg2.extras.execute_values()` |

In PL/SQL, the equivalent is `FORALL`:

```sql
DECLARE
    TYPE t_ids IS TABLE OF NUMBER;
    l_order t_ids; l_prod t_ids; l_qty t_ids;
BEGIN
    -- fill the collections, for example with BULK COLLECT
    FORALL i IN 1 .. l_order.COUNT SAVE EXCEPTIONS
        INSERT INTO order_items (order_id, product_id, quantity)
        VALUES (l_order(i), l_prod(i), l_qty(i));
END;
```

`FORALL` sends the whole collection to the SQL engine in one context switch. `SAVE EXCEPTIONS` continues past failing rows and reports them afterwards in `SQL%BULK_EXCEPTIONS` (raising ORA-24381).

### 3. Arrays as parameters (PostgreSQL)

A statement with many rows in `VALUES` has many bind parameters, and the protocol allows at most 65,535 per statement. Passing one array per column avoids the limit and keeps the statement text constant:

```sql
INSERT INTO order_items (order_id, product_id, quantity)
SELECT * FROM unnest($1::bigint[], $2::bigint[], $3::int[]);
```

Three parameters, any number of rows, and one cached plan.

### Choosing a batch size

```
Rows per second, one client (illustrative)

batch size 1      ██                              round trips dominate
batch size 10     ███████████
batch size 100    ████████████████████████
batch size 1,000  ███████████████████████████     close to the limit
batch size 10,000 ███████████████████████████     no further gain, more memory
```

Gains flatten after a few hundred rows. **100 to 1,000 rows per batch** is a good default. Very large batches use more memory on both sides and make a failure more expensive to retry.

## 4. Bulk Loading

**Bulk loading** means loading a large volume of data, such as a file import or a table copy, through a path built for volume rather than through ordinary inserts. These paths skip much of the per-row work: they format whole blocks at once, and can reduce logging and defer index maintenance.

### PostgreSQL: COPY

```sql
-- Server-side file (needs the pg_read_server_files role or superuser)
COPY orders_stage (customer_id, status, order_date, total_amount)
FROM '/data/orders_2026_10.csv' WITH (FORMAT csv, HEADER true);

-- Client-side file, from psql
\copy orders_stage (customer_id, status, order_date, total_amount) FROM 'orders.csv' WITH (FORMAT csv, HEADER true)
```

Drivers expose the same protocol (`CopyManager` in JDBC, `cursor.copy()` in psycopg 3). `COPY` is typically several times faster than even well-batched inserts.

| Option | Effect |
|--------|--------|
| `FREEZE` | Writes rows already frozen, so a later `VACUUM` does not have to rewrite them. Only allowed if the table was created or truncated in the same transaction |
| `ON_ERROR ignore` (17+) | Skips rows that fail type conversion instead of aborting the whole load |
| `LOG_VERBOSITY verbose` (17+) | Logs each skipped row |

### Oracle: direct-path load

A **direct-path load** formats complete blocks in memory and writes them above the table's high water mark (Chapter 05, Section 9), bypassing the buffer cache.

```sql
-- From a query or an external table
INSERT /*+ APPEND */ INTO orders_stage
SELECT * FROM orders_ext;          -- external table over a CSV file
COMMIT;                            -- required before the session reads the table again

-- From array-bound VALUES (11gR2+)
INSERT /*+ APPEND_VALUES */ INTO orders_stage VALUES (:1, :2, :3, :4, :5);
```

Outside the database, **SQL\*Loader** with `DIRECT=TRUE` does the same from a file, and **Data Pump** (`impdp`) moves data between Oracle databases.

Direct path has rules that surprise people:

| Rule | Consequence |
|------|-------------|
| The table is locked exclusively until commit | No other session can modify it during the load |
| The session cannot read or modify the table before commit | ORA-12838 |
| Free space below the high water mark is not reused | Deleted space is not refilled |
| **Enabled triggers or foreign keys on the table** | Oracle silently uses a conventional insert instead (Section 10) |

### Reducing logging during a load

| | Oracle | PostgreSQL |
|---|---|---|
| Mechanism | `NOLOGGING` table + direct-path insert: minimal redo | `UNLOGGED` table: no WAL at all |
| What is lost after a crash | Blocks loaded this way cannot be restored from earlier backups | The table is emptied |
| Replication | Not replicated to Data Guard standbys | Not replicated to standbys |
| Overridden by | `FORCE LOGGING` (common on Data Guard primaries) | — |
| Afterwards | Take a backup | `ALTER TABLE ... SET LOGGED` writes the whole table to WAL |

Both are suited to **staging tables** whose data can be reloaded from the source file. Never use them for data that exists nowhere else. PostgreSQL can also skip WAL for `COPY` into a table created or truncated in the same transaction, but only when `wal_level = minimal`, which also disables replication and archiving.

### Indexes during large loads

Updating an index row by row during a load is slow: each insert finds and modifies an index leaf block. Building the index after the load sorts all keys once and writes the index sequentially.

```
Load with 3 indexes in place     ████████████████████████████████
Load, then build 3 indexes       ████████████ + ██████
```

A common rule of thumb: drop and rebuild when the load adds more than about 10–20% of the table's existing rows.

| | Oracle | PostgreSQL |
|---|---|---|
| Suspend an index | `ALTER INDEX idx UNUSABLE` (DML skips it while `SKIP_UNUSABLE_INDEXES = TRUE`, the default) | `DROP INDEX` |
| Rebuild | `ALTER INDEX idx REBUILD` (optionally `PARALLEL`, `NOLOGGING`) | `CREATE INDEX` (raise `maintenance_work_mem` first) |
| Caveat | An unusable **unique** index makes inserts fail (ORA-01502) | Rebuilding a primary key requires dropping the constraint |

Direct-path inserts in Oracle already defer index maintenance: keys are collected and merged into the indexes once, at the end of the statement.

### A complete load into a live table

```
1. Load the file into a staging table        COPY / external table + APPEND
2. Clean and validate in the staging table   set-based SQL, not row by row
3. Move into the target in one statement     INSERT ... SELECT, or upsert (Section 5)
4. Refresh statistics                        ANALYZE / DBMS_STATS.GATHER_TABLE_STATS
```

Rows that fail constraints can be captured instead of aborting the load:

```sql
-- Oracle: DML error logging
EXEC DBMS_ERRLOG.CREATE_ERROR_LOG('ORDERS');     -- creates ERR$_ORDERS

INSERT INTO orders SELECT * FROM orders_stage
LOG ERRORS INTO err$_orders ('load 2026-10') REJECT LIMIT UNLIMITED;
```

PostgreSQL has no equivalent for constraint errors. Filter invalid rows in the staging table first (step 2), or use `ON CONFLICT DO NOTHING` for duplicate keys.

## 5. Upserts

An **upsert** inserts a row if its key does not exist and updates it if it does. A typical case is keeping running totals:

```
Sale of product 42 on 2026-10-11, qty 3:
    no row for (42, 2026-10-11)  ──► insert  qty = 3
    row exists                   ──► update  qty = qty + 3
```

### The patterns to avoid

| Pattern | Problem |
|---------|---------|
| `SELECT`; if not found `INSERT`, else `UPDATE` | Two round trips. Two sessions can both find nothing and both insert, so one fails with a duplicate key |
| `UPDATE`; if 0 rows, `INSERT` | Same race condition |
| `INSERT`; on duplicate-key error, `UPDATE` | An error per existing row. In PostgreSQL the error aborts the transaction unless each insert runs in a savepoint |

Both databases provide a single atomic statement instead.

### PostgreSQL: INSERT ... ON CONFLICT (9.5+)

```sql
INSERT INTO product_daily_sales AS s (product_id, sale_date, qty, revenue)
VALUES (42, DATE '2026-10-11', 3, 59.97)
ON CONFLICT (product_id, sale_date)
DO UPDATE SET qty     = s.qty     + EXCLUDED.qty,
              revenue = s.revenue + EXCLUDED.revenue;
```

| Element | Meaning |
|---------|---------|
| `ON CONFLICT (cols)` | The unique index or constraint that defines "already exists" |
| `EXCLUDED` | The row that was proposed for insertion |
| `DO NOTHING` | Skip existing rows (insert-if-absent) |
| `DO UPDATE ... WHERE` | Update only when the condition holds |

`ON CONFLICT` is safe under concurrency: two sessions upserting the same key never produce a duplicate-key error.

### Oracle: MERGE

```sql
MERGE INTO product_daily_sales s
USING (SELECT 42 AS product_id, DATE '2026-10-11' AS sale_date,
              3 AS qty, 59.97 AS revenue FROM dual) n
ON (s.product_id = n.product_id AND s.sale_date = n.sale_date)
WHEN MATCHED THEN
    UPDATE SET s.qty = s.qty + n.qty, s.revenue = s.revenue + n.revenue
WHEN NOT MATCHED THEN
    INSERT (product_id, sale_date, qty, revenue)
    VALUES (n.product_id, n.sale_date, n.qty, n.revenue);
```

PostgreSQL 15+ also supports `MERGE`, and 17+ adds `RETURNING` and `WHEN NOT MATCHED BY SOURCE`.

### Concurrency differences

| Statement | Two sessions insert the same new key at the same time |
|-----------|--------------------------------------------------------|
| PostgreSQL `ON CONFLICT` | Safe: the second session waits, then updates |
| PostgreSQL `MERGE` | Can fail with a unique violation; retry |
| Oracle `MERGE` | Can fail with ORA-00001; retry |

For high-concurrency single-row upserts in PostgreSQL, prefer `ON CONFLICT`. Use `MERGE` for set-based synchronisation between tables, where its extra clauses (delete, conditional branches) are useful. In Oracle, `MERGE` with a retry on ORA-00001 is the standard approach.

### Bulk upserts

Upsert a whole batch in one statement, from a staging table or an array:

```sql
-- PostgreSQL
INSERT INTO product_daily_sales AS s (product_id, sale_date, qty, revenue)
SELECT product_id, sale_date, sum(qty), sum(revenue)
FROM sales_stage
GROUP BY product_id, sale_date              -- one row per key
ON CONFLICT (product_id, sale_date)
DO UPDATE SET qty = s.qty + EXCLUDED.qty, revenue = s.revenue + EXCLUDED.revenue;
```

The `GROUP BY` matters. If the same key appears twice in one statement, both databases refuse:

| | Error |
|---|---|
| PostgreSQL | `ON CONFLICT DO UPDATE command cannot affect row a second time` |
| Oracle | ORA-30926: unable to get a stable set of rows in the source tables |

### Avoid updating rows that have not changed

An update that sets a column to its current value still writes a new row version (PostgreSQL) or generates undo and redo (Oracle), and still fires triggers. When syncing data that is mostly unchanged, add a condition:

```sql
-- PostgreSQL
ON CONFLICT (product_id) DO UPDATE SET price = EXCLUDED.price
WHERE products.price IS DISTINCT FROM EXCLUDED.price;

-- Oracle
WHEN MATCHED THEN UPDATE SET p.price = n.price
WHERE DECODE(p.price, n.price, 0, 1) = 1     -- DECODE treats two NULLs as equal
```

One more PostgreSQL detail: an identity or sequence value is consumed for every proposed row, including rows that end up as updates. Upsert-heavy tables therefore show large gaps in their generated keys. This is harmless, but should not surprise anyone.

## 6. Transaction Batching

Every commit waits for a log flush (Section 1, step 7). **Transaction batching** groups many rows into one transaction so that this wait is paid once per batch.

```
Commit per row (10,000 rows)          Commit per 1,000 rows
  insert, flush                         insert × 1,000, flush
  insert, flush                         insert × 1,000, flush
  insert, flush                         ...
  ... 10,000 flushes                    ... 10 flushes
```

At 0.5 ms per flush, one session committing every row can never exceed about 2,000 rows per second, however fast the rest of the system is. On cloud block storage, where a flush often takes 1–2 ms, the ceiling is lower still.

### Autocommit

Many tools commit after every statement by default, which silently turns a loop into commit-per-row.

| Client | Default |
|--------|---------|
| JDBC (both databases) | Autocommit **on**; call `setAutoCommit(false)` |
| psql | Autocommit on |
| SQL\*Plus, SQL Developer | Autocommit off |
| psycopg 2 and 3 | Autocommit off (an implicit transaction) |

### Too large is also a problem

A single transaction covering millions of rows has its own costs:

| Cost | Oracle | PostgreSQL |
|------|--------|------------|
| Locks held until commit | Other writers on the same rows wait | Same |
| Old versions kept | Undo grows; long-running readers risk ORA-01555 | `VACUUM` cannot remove dead rows anywhere in the database while it runs |
| Failure near the end | Rollback can take as long as the work | Rollback is instant, but all work is lost |
| Replication | Large burst of redo to apply | Large burst of WAL; logical replication sends it only after commit |

A good default is **1,000 to 10,000 rows, or about a second of work, per transaction**, with the job written so it can restart from the last committed batch.

### Chunking a large UPDATE or DELETE

```sql
-- PostgreSQL 11+: a procedure can commit between chunks
CREATE PROCEDURE purge_cancelled() LANGUAGE plpgsql AS $$
DECLARE n bigint;
BEGIN
    LOOP
        DELETE FROM orders
        WHERE order_id IN (SELECT order_id FROM orders
                           WHERE status = 'CANCELLED' AND order_date < DATE '2024-01-01'
                           LIMIT 5000);
        GET DIAGNOSTICS n = ROW_COUNT;
        EXIT WHEN n = 0;
        COMMIT;
    END LOOP;
END $$;

CALL purge_cancelled();
```

```sql
-- Oracle
BEGIN
    LOOP
        DELETE FROM orders
        WHERE status = 'CANCELLED' AND order_date < DATE '2024-01-01'
          AND ROWNUM <= 5000;
        EXIT WHEN SQL%ROWCOUNT = 0;
        COMMIT;
    END LOOP;
END;
/
```

The inner query must find its rows through an index. Otherwise each chunk rescans the table, and the job becomes quadratic. If the rows to remove form whole partitions, dropping or truncating the partition is far cheaper than any delete (Chapter 06).

## 7. WAL Optimisation

The log (redo in Oracle, WAL in PostgreSQL; Chapter 05, Section 6) is written for every change. Reducing **how much** is logged lowers I/O, replication traffic and archive storage. Making **each flush cheap** lowers commit latency.

### Measure log volume first

```sql
-- PostgreSQL 13+: WAL generated by one statement
EXPLAIN (ANALYZE, WAL)
INSERT INTO order_items (order_id, product_id, quantity)
SELECT order_id, 1, 1 FROM orders WHERE order_id <= 10000;
```

```
Insert on order_items  (actual time=95.2..95.2 rows=0 loops=1)
  WAL: records=30217 fpi=118 bytes=2457810
```

| Field | Meaning |
|-------|---------|
| `records` | WAL records: one for the row, one per index entry |
| `fpi` | Full-page images, written the first time a page changes after a checkpoint |
| `bytes` | Total WAL generated |

Server-wide totals are in `pg_stat_wal` (14+): `wal_records`, `wal_fpi`, `wal_bytes`, and `wal_buffers_full`.

```sql
-- Oracle: redo generated by the current session so far
SELECT n.name, s.value
FROM v$mystat s JOIN v$statname n ON n.statistic# = s.statistic#
WHERE n.name IN ('redo size', 'redo entries');
```

Run the query before and after a statement and subtract. In SQL\*Plus, `SET AUTOTRACE TRACEONLY STATISTICS` reports `redo size` directly.

### What reduces log volume

| Technique | Oracle | PostgreSQL |
|-----------|--------|------------|
| Fewer indexes | One set of redo per index entry (Section 9) | One WAL record per index entry |
| Updates that touch no indexed column | Index unaffected | HOT updates: no index WAL. Needs free space in the page (`fillfactor`) |
| Fewer full-page images | Not applicable | Less frequent checkpoints: raise `max_wal_size`, `checkpoint_timeout` (Chapter 05, Section 7) |
| Compress page images | Not applicable | `wal_compression` (default `off`; `lz4` or `zstd` in 15+) |
| Bulk load path | Direct path + `NOLOGGING` (Section 4) | `UNLOGGED` tables; `COPY` with `wal_level = minimal` |
| Temporary work tables | Global temporary tables; `TEMP_UNDO_ENABLED = TRUE` (12c+) removes the redo for their undo | Temporary tables are not WAL-logged |
| Skip unchanged rows | `WHERE` clause on `MERGE` update | `WHERE` clause on `ON CONFLICT` update (Section 5) |

Set-based statements also generate less log than row-by-row loops, because each log record carries some fixed overhead. Batching (Sections 3 and 6) therefore reduces log volume as well as round trips.

### What makes flushes cheap

| Item | Oracle | PostgreSQL |
|------|--------|------------|
| Log storage | Fast, low-latency devices, separate from datafiles | Same, for `pg_wal` |
| Log buffer size | `LOG_BUFFER` (usually adequate by default) | `wal_buffers` (default `-1`: 1/32 of `shared_buffers`, up to 16 MB) |
| Signal that the buffer is too small | Wait event `log buffer space` | `wal_buffers_full` rising in `pg_stat_wal` |
| Log file size | Large enough for a switch every 15–20 minutes at peak (Chapter 05, Section 7) | `max_wal_size` large enough that checkpoints are time-triggered |

Never set `fsync = off` in PostgreSQL for data you need. Unlike asynchronous commit (Section 11), it can corrupt the whole cluster after an operating-system crash or power loss.

## 8. Group Commit

**Group commit** lets many sessions that commit at nearly the same moment share one log flush.

```
Without group commit                    With group commit
  session A: write + flush                session A ─┐
  session B: write + flush                session B ─┼─► one write + one flush
  session C: write + flush                session C ─┘
  3 flushes                               1 flush, all three commits durable
```

While one flush is in progress, more commits arrive and wait. The next flush writes all of their log records together. The more concurrent committers there are, the more each flush carries, so total throughput rises even though each disk flush takes the same time.

Group commit helps **many concurrent sessions**. It does nothing for one session committing in a loop, because that session never has a second commit waiting. For a single loader, use transaction batching (Section 6).

### Oracle

The log writer (LGWR) does this automatically: when it writes, it writes everything in the log buffer, including the commit records of every session waiting at that moment. From 12c, LGWR can use helper processes (LG00, LG01, ...) on systems with many CPUs.

The key wait events:

| Event | Measures |
|-------|----------|
| `log file sync` | What a committing session waits for, end to end |
| `log file parallel write` | How long LGWR's actual disk write takes |

If `log file sync` is much larger than `log file parallel write`, the time goes to scheduling and too many commits, not to storage: batch commits. If the two are close, the log storage is slow.

### PostgreSQL

Group commit also happens automatically: backends waiting for the WAL flush lock find their records already flushed by another backend. Two settings can make the effect stronger:

| Parameter | Default | Meaning |
|-----------|---------|---------|
| `commit_delay` | `0` (µs) | Wait this long before flushing, so that more commits can join |
| `commit_siblings` | `5` | Only wait if at least this many other transactions are active |

`commit_delay` adds latency to every commit and only pays off under heavy concurrent commit load on storage with a slow flush. The PostgreSQL documentation suggests starting at about half the single 8 kB write flush time reported by the `pg_test_fsync` tool, then measuring throughput. Leave it at `0` unless measurements show a gain.

## 9. Reducing Unnecessary Indexes

Every index is updated on every insert and delete, and on every update that changes one of its columns (Chapter 02, Section 15).

```
Insert cost into orders (illustrative)

table only                 ██
+ primary key              ████
+ 3 secondary indexes      ██████████
+ 6 secondary indexes      ████████████████
```

An index that no query uses is pure cost: slower writes, more log, more storage, and in PostgreSQL fewer HOT updates.

### Finding unused indexes

```sql
-- PostgreSQL: indexes never scanned since statistics were last reset
SELECT s.relname AS table_name, s.indexrelname AS index_name,
       s.idx_scan, s.last_idx_scan,                       -- last_idx_scan: 16+
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size
FROM pg_stat_user_indexes s
JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE s.idx_scan = 0
  AND NOT i.indisunique                                   -- keep PK and unique indexes
ORDER BY pg_relation_size(s.indexrelid) DESC;
```

```sql
-- Oracle 12.2+: index usage is tracked automatically
SELECT i.table_name, i.index_name, u.total_access_count, u.last_used
FROM user_indexes i
LEFT JOIN dba_index_usage u
       ON u.name = i.index_name AND u.owner = USER
WHERE u.name IS NULL OR u.last_used < SYSDATE - 90;
```

| Caveat | Why it matters |
|--------|----------------|
| Statistics are per server | An index used only by reports on a replica shows zero use on the primary. Check every server |
| Observation period | Month-end and year-end jobs may use an index rarely but critically. Observe for at least one full business cycle |
| Oracle tracking is sampled by default | `DBA_INDEX_USAGE` can miss indexes used very rarely |
| Constraint indexes | Primary key and unique indexes enforce rules even if no query reads them. Indexes on foreign keys prevent locking problems (Chapter 04, Section 7) |

### Finding redundant indexes

An index whose columns are a leading prefix of another index is usually redundant:

```
idx_orders_customer        (customer_id)
idx_orders_customer_date   (customer_id, order_date)    ◄── can serve both
```

The composite index serves any query the single-column one serves (Chapter 02, Section 5). Exceptions: the shorter index enforces uniqueness, or it is much smaller and used by a very hot query.

### Removing safely

1. In Oracle, make the index `INVISIBLE` first. The optimizer ignores it, but it is still maintained, so it can be made visible again instantly (Chapter 02, Section 14).
2. In PostgreSQL there is no invisible index. Record the definition (`pg_get_indexdef`) and drop with `DROP INDEX CONCURRENTLY` to avoid blocking writes.
3. Watch for plan changes on the affected queries, then drop for good.

### Indexes and HOT updates (PostgreSQL)

An index on a frequently updated column, such as `orders.status`, prevents HOT updates for every change to that column. Check the ratio:

```sql
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_user_tables
ORDER BY n_tup_upd DESC;
```

A low `hot_pct` on a heavily updated table means either an index covers an updated column or pages have no free space (lower `fillfactor`, for example to 90).

## 10. Avoiding Excessive Foreign-Key Checks

A foreign key guarantees that every child row has a parent. To enforce it, each child insert, or update of the key, looks up the parent row:

```
INSERT INTO order_items (order_id, product_id, quantity) VALUES (5001, 42, 3);
    ├── check orders:   does order_id 5001 exist?     index lookup + lock
    └── check products: does product_id 42 exist?     index lookup + lock
```

| | How the check is done |
|---|---|
| PostgreSQL | An internal trigger runs `SELECT 1 FROM parent WHERE key = $1 FOR KEY SHARE` per row, per foreign key |
| Oracle | An internal lookup on the parent's primary key index, per row, per foreign key |

For normal OLTP writes this cost is small, and **foreign keys should stay**: they prevent orphaned data that is very hard to clean up later. The cost becomes significant in three situations.

### 1. Bulk loads

Loading 10 million `order_items` rows performs 20 million parent lookups. For data already validated in staging (Section 4, step 2), the checks are repeated work.

```sql
-- PostgreSQL: drop the constraint, load, re-add without checking, then validate
ALTER TABLE order_items DROP CONSTRAINT order_items_product_id_fkey;
-- ... load ...
ALTER TABLE order_items ADD CONSTRAINT order_items_product_id_fkey
    FOREIGN KEY (product_id) REFERENCES products NOT VALID;      -- new rows checked from now
ALTER TABLE order_items VALIDATE CONSTRAINT order_items_product_id_fkey;
```

`NOT VALID` enforces the constraint for new rows but skips existing ones. `VALIDATE CONSTRAINT` then checks existing rows in one set-based pass, holding only a `SHARE UPDATE EXCLUSIVE` lock, so normal inserts and updates continue.

```sql
-- Oracle: the same idea
ALTER TABLE order_items DISABLE CONSTRAINT fk_items_product;
-- ... direct-path load: now really direct path (Section 4) ...
ALTER TABLE order_items ENABLE NOVALIDATE CONSTRAINT fk_items_product;
ALTER TABLE order_items ENABLE VALIDATE   CONSTRAINT fk_items_product;
```

Enabling `NOVALIDATE` first, then `VALIDATE`, lets the validation run without blocking DML on the table. In Oracle this matters twice: an enabled foreign key also turns a direct-path insert into a conventional one.

Avoid shortcuts that skip checking altogether, such as PostgreSQL's `session_replication_role = replica` or `DISABLE TRIGGER ALL`. They leave constraints marked valid over data that was never checked.

### 2. Hot parent rows

In PostgreSQL, each check takes a `FOR KEY SHARE` lock on the parent row. Thousands of concurrent inserts referencing the same parent (one popular product, one "unknown customer" placeholder) all lock the same row. Several shared lockers are recorded as a **multixact**, which adds overhead and can show up as `MultiXact*` waits. Oracle does not lock the parent row this way, but frequent updates to the parent's key columns cause contention in both systems.

### 3. Foreign keys that are not needed

Some tables do not need database-enforced relationships:

| Table | Foreign key worth having? |
|-------|---------------------------|
| `order_items → orders`, `order_items → products` | Yes: core business data |
| `page_views → products` | Usually not: high-volume, append-only, loss-tolerant, and a view of a deleted product is still a valid fact |
| Data warehouse fact tables loaded from validated sources | Often declared but not enforced: Oracle `RELY DISABLE NOVALIDATE` keeps the information for the optimizer without checking |

### Deferring checks does not remove them

`DEFERRABLE INITIALLY DEFERRED` moves the check to commit time. It is useful when rows must be inserted in an order that temporarily violates the constraint. It does not reduce the number of checks; in PostgreSQL the queued checks still run one per row at commit.

### The parent side

Deleting or updating a parent key checks the child table. Without an index on the child's foreign key column, that check is a full scan of the child table in PostgreSQL, and a table-level lock in Oracle (Chapter 04, Section 7). Index foreign key columns whenever parents are deleted or rekeyed.

## 11. Async Writes

The previous sections make writes cheaper without changing what is guaranteed. This section trades a **small, bounded risk of losing recent writes** for speed. It suits data such as `page_views`, and never orders or payments.

### Asynchronous commit

The commit returns before the log reaches disk. The log writer flushes it a moment later.

```
Synchronous commit                    Asynchronous commit
  COMMIT ──► flush ──► return           COMMIT ──► return
                                                   flush happens shortly after
```

```sql
-- PostgreSQL: per transaction, per session, or per role
BEGIN;
SET LOCAL synchronous_commit = off;
INSERT INTO page_views (customer_id, product_id) VALUES (7, 42);
COMMIT;

ALTER ROLE tracking_app SET synchronous_commit = off;
```

```sql
-- Oracle
COMMIT WRITE BATCH NOWAIT;

ALTER SESSION SET COMMIT_WAIT = 'NOWAIT';         -- with COMMIT_LOGGING = 'BATCH'
```

| | Oracle | PostgreSQL |
|---|---|---|
| Setting | `COMMIT_WAIT = NOWAIT`, `COMMIT_LOGGING = BATCH`, or `COMMIT WRITE ...` | `synchronous_commit = off` |
| What a crash can lose | The most recent commits not yet written by LGWR | Commits from up to 3 × `wal_writer_delay` (default 200 ms, so up to 600 ms) |
| Risk of corruption | None | None |
| Scope | Session, statement or system | Transaction, session, role, database or system |

The database stays consistent after a crash: it is as if the last few transactions never happened. Applying it per transaction lets critical and non-critical writes share one database.

PL/SQL already applies a similar optimisation on its own: `COMMIT` statements inside a PL/SQL block do not wait for the log flush, except the last one before control returns to the client. This is why a PL/SQL loop that commits every row is faster than the same loop driven from a client, though it still pays the other per-commit costs.

`synchronous_commit` also controls waiting for synchronous standbys (`remote_write`, `on`, `remote_apply`); see Chapter 09.

### Tables that skip logging

`UNLOGGED` tables (PostgreSQL) and `NOLOGGING` direct-path loads (Oracle) were covered in Section 4. An unlogged table is emptied after a crash, so it is suitable only for data that can be rebuilt, such as staging, session data or a cache table.

### Buffered ingestion (Oracle Memoptimized Rowstore)

Oracle 19c+ offers **fast ingest** for high-frequency single-row inserts, such as sensor or click data:

```sql
CREATE TABLE page_views ( ... ) MEMOPTIMIZE FOR WRITE;

INSERT /*+ MEMOPTIMIZE_WRITE */ INTO page_views (customer_id, product_id, viewed_at)
VALUES (:1, :2, SYSTIMESTAMP);
```

Rows are buffered in memory (the large pool) and written to the table in batches in the background. Inserted rows are not visible to queries until written, buffered rows can be lost on an instance failure, and the feature has restrictions (for example, no triggers or LOB columns). `DBMS_MEMOPTIMIZE.WRITE_END` flushes the buffer on demand.

PostgreSQL has no built-in equivalent.

### Application-level buffering

The application, or a queue between it and the database, collects writes and inserts them in batches:

```
web servers ──► queue (Kafka, Redis stream, in-memory buffer) ──► writer ──► database
   accept the event                                    every 1 s or 1,000 events:
   and return immediately                              one multi-row INSERT or COPY
```

This turns many tiny transactions into a few large ones (Sections 3 and 6) and absorbs traffic spikes. The trade-offs are:

| Trade-off | Mitigation |
|-----------|------------|
| Events in an in-memory buffer are lost if the process dies | Use a durable queue when loss is unacceptable |
| A reader may not see a write for a short time | Acceptable only for data that tolerates staleness (Chapter 11, Section 6) |
| Retries can insert duplicates | Give each event a unique ID and insert with `ON CONFLICT DO NOTHING` or `MERGE` (Section 5) |

### Choosing a level of durability

| Data | Approach | Can lose on crash |
|------|----------|-------------------|
| Orders, payments, stock | Synchronous commit, batched where possible | Nothing |
| Page views, metrics, logs | Asynchronous commit or application buffering | Up to about a second |
| Staging and derived data | `UNLOGGED` / `NOLOGGING` | The whole table, reloaded from source |

## 12. A Systematic Approach to Slow Writes

```
1. Where does the time go?
        PostgreSQL: pg_stat_activity.wait_event, pg_stat_statements
        Oracle:     ASH / AWR wait events, V$SQL
        │
        ▼
2. Many executions, about one row each?
        pg_stat_statements: rows / calls ≈ 1
        V$SQL: ROWS_PROCESSED / EXECUTIONS ≈ 1
        waits on client round trips ("SQL*Net message from client", ClientRead)
        │
        └── yes ──► batch inserts, array binding, set-based SQL          Section 3
        │
        ▼
3. Large one-off or recurring import?
        └── yes ──► COPY / direct path, staging table, indexes after     Section 4
        │
        ▼
4. Commit waits dominate?
        Oracle: log file sync      PostgreSQL: WALSync / WALWrite
        │
        ├── many commits per second from few sessions
        │       ──► fewer, larger transactions; check autocommit          Section 6
        ├── flush itself slow (log file parallel write high)
        │       ──► faster log storage                                    Section 7
        └── loss of the last second acceptable
                ──► asynchronous commit for that data                     Section 11
        │
        ▼

        redo size / pg_stat_wal, EXPLAIN (ANALYZE, WAL)
        ──► fewer indexes, HOT updates, fewer full-page images,

```

## 14. Short Summary

- A write pays per statement (round trip, parse), per row (constraint checks, index entries, log records) and per commit (log flush). Tuning means paying the first and last once per batch and removing per-row work that is not needed.
- Send rows in batches of a few hundred to a thousand: multi-row `VALUES`, driver array binding, `FORALL`, or arrays with `unnest()`.
- For large volumes, use the bulk path: `COPY` in PostgreSQL, direct-path loads in Oracle. Load into staging, build indexes afterwards, then move data with one set-based statement.
- Use the database's atomic upsert (`ON CONFLICT`, `MERGE`) instead of select-then-insert. Deduplicate the batch and skip rows that have not changed.
- Commit every 1,000 to 10,000 rows. Commit-per-row caps throughput at the log flush rate; one huge transaction blocks cleanup, holds locks, and is costly to fail.
- Measure log volume with `EXPLAIN (ANALYZE, WAL)` or `redo size`, and reduce it with fewer indexes, HOT updates, fewer full-page images and unlogged staging. Never disable `fsync`.
- Group commit lets concurrent sessions share log flushes automatically; it does not help a single session that commits too often.
- Every index and foreign key adds work to each write. Keep the ones that enforce rules or serve queries, remove the rest, and validate constraints after bulk loads instead of during them.
- Asynchronous commit, unlogged tables and buffered ingestion trade a bounded loss of recent writes for speed. Apply them per kind of data, never to data that must not be lost.
