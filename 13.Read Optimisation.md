# Chapter 13: Read Optimisation

Every read of a table follows one of a small number of **access paths**. The optimizer chooses between them on every query, and the choice is often the single largest factor in how long a query takes.

```
Full Table Scan
       ↓
Index Scan
       ↓
Index-Only Scan
```

A common assumption is that an index always makes a query faster. It does not. If a query needs a large share of a table, or if the rows it needs are scattered across most of the table's blocks, reading the whole table sequentially is cheaper than following an index.

This chapter brings together the access paths in **Oracle** and **PostgreSQL**, shows how the optimizer prices each one with worked numbers, and explains the factors that move the decision. It draws on earlier chapters: execution plans (Chapter 01), index design (Chapter 02) and I/O patterns (Chapter 05).

## 1. Sample Setup

The examples use the `orders` table from Chapter 01:

| Property | Value |
|----------|-------|
| Rows | 1,000,000 |
| Blocks / pages | 8,334 (8 KB each, about 120 rows per block) |
| `order_id` | Inserted in order: physical order matches the key |
| `customer_id` | Random: physical order unrelated to the key |
| `status` | 90% SHIPPED, 9% PENDING, 1% CANCELLED; every 100th row inserted is CANCELLED |

```sql
CREATE INDEX idx_orders_customer  ON orders (customer_id);
CREATE INDEX idx_orders_status    ON orders (status);
CREATE INDEX idx_orders_cust_date ON orders (customer_id, order_date);
-- order_id is the primary key
```

Plan outputs in this chapter are representative. Exact costs and timings depend on version, configuration and hardware.

## 2. The Access Paths

```
                 reads                                   suitable when the query needs

Full table scan  every block of the table, in order      a large share of the table

Bitmap /         index entries, then the table blocks    a moderate number of rows
batched scan     that contain matches, in block order

Index scan       index entries, then one table visit     few rows
                 per matching row, in index order

Index-only scan  index entries only                      few or many rows, if the index
                                                         holds every column needed
```

| Path | PostgreSQL | Oracle |
|------|-----------|--------|
| Full table scan | `Seq Scan`, `Parallel Seq Scan` | `TABLE ACCESS FULL` |
| Index scan | `Index Scan` | `INDEX RANGE SCAN` / `INDEX UNIQUE SCAN` + `TABLE ACCESS BY INDEX ROWID` |
| Bitmap / batched scan | `Bitmap Index Scan` + `Bitmap Heap Scan` | `TABLE ACCESS BY INDEX ROWID BATCHED`; bitmap conversions |
| Index-only scan | `Index Only Scan` | Index operation with no table access step; `INDEX FAST FULL SCAN` |

The rest of this chapter explains each path, then how the optimizer chooses.

## 3. Full Table Scan

A full table scan reads every block of the table from the first to the last (in Oracle, up to the high water mark; Chapter 05, Section 9) and checks each row against the `WHERE` clause.

```
blocks:  [1][2][3][4][5][6][7][8] ... [8334]
          └──── large sequential reads, start to finish ────┘
          every row checked against the filter
```

Its cost depends only on **table size**, never on how many rows match. Reading 10 rows or 900,000 rows from it costs about the same.

**PostgreSQL**

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'SHIPPED';
```

```
Seq Scan on orders  (cost=0.00..20834.00 rows=900000 width=30)
                    (actual time=0.011..96.4 rows=900000 loops=1)
  Filter: (status = 'SHIPPED'::text)
  Rows Removed by Filter: 100000
```

**Oracle**

```
---------------------------------------------------
| Id | Operation         | Name   | Rows   | Cost |
---------------------------------------------------
|  0 | SELECT STATEMENT  |        |  900K  |      |
|* 1 |  TABLE ACCESS FULL| ORDERS |  900K  |      |
---------------------------------------------------
   1 - filter("STATUS"='SHIPPED')
```

### Why it is efficient

| Advantage | Detail |
|-----------|--------|
| Large reads | Oracle reads many blocks per request (`DB_FILE_MULTIBLOCK_READ_COUNT`); PostgreSQL benefits from OS read-ahead and, in recent versions, combined and asynchronous reads (Chapter 05, Section 5) |
| Each block read once | No block is visited twice |
| No index overhead | No index blocks to read |
| Parallelism | The table is split into ranges read by several workers |

```
PostgreSQL parallel scan                       Oracle parallel scan

Gather                                         PX COORDINATOR
  Workers Planned: 2                             PX SEND QC (RANDOM)
  -> Parallel Seq Scan on orders                   PX BLOCK ITERATOR
                                                     TABLE ACCESS FULL  ORDERS
```

### When it is chosen

- The query needs a large share of the rows.
- The rows it needs are spread over most of the blocks (Section 8).
- The table is small: a few blocks are cheaper to read than an index descent.
- No usable index exists, or the predicate cannot use one (a function on the column; Chapter 01, Section 11).

## 4. Index Scan

An index scan descends the B-tree to the first matching key, walks the leaf entries in key order, and for each entry fetches the row from the table using its row address.

```
Index (customer_id)                         Table blocks
  root ─► branch ─► leaf
                     42 → block 1523, row 7 ──────────►  block 1523
                     42 → block   88, row 2 ──────────►  block   88
                     42 → block 6610, row 4 ──────────►  block 6610
                     43 → ...  stop

  3–4 index block reads                     one table block visit per matching row,
                                            in whatever order the index gives
```

**PostgreSQL**

```
Index Scan using idx_orders_customer on orders  (cost=0.42..44.61 rows=10 width=30)
                                               (actual time=0.019..0.041 rows=11 loops=1)
  Index Cond: (customer_id = 42)
```

**Oracle**

```
| Id | Operation                           | Name                | Rows | Cost |
|  0 | SELECT STATEMENT                    |                     |   10 |   13 |
|  1 |  TABLE ACCESS BY INDEX ROWID BATCHED| ORDERS              |   10 |   13 |
|* 2 |   INDEX RANGE SCAN                  | IDX_ORDERS_CUSTOMER |   10 |    3 |
```

### Its cost

```
cost ≈ index descent + leaf blocks read + table blocks visited
                                          └── the dominant part
```

The table visits dominate. Each is potentially a **random read**, and the same block may be visited many times if matching rows are scattered. The cost grows with the number of matching rows, unlike a full scan.

### When it is chosen

- Few rows match (high selectivity; Chapter 02, Section 4).
- The matching rows are physically close together (Section 8).
- The index also provides a needed sort order, so a sort step is avoided (Section 9).

## 5. Bitmap and Batched Index Scans

Between "few rows" and "most rows" lies a middle ground where a plain index scan visits too many blocks randomly, yet a full scan reads too much. Both databases have a hybrid for this range: collect the row addresses from the index first, then read the table **in block order**.

```
Plain index scan                         Bitmap / batched scan

index order:  1523, 88, 6610, 88, 1523   addresses sorted by block:  88, 1523, 6610
              each fetched as it comes   each block read once, in ascending order
              block 88 read twice        reads move forward through the file
              block 1523 read twice
```

### PostgreSQL: bitmap scans

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id BETWEEN 1000 AND 1500;
```

```
Bitmap Heap Scan on orders  (cost=95.88..12804.21 rows=5010 width=30)
                            (actual time=1.31..9.92 rows=4987 loops=1)
  Recheck Cond: ((customer_id >= 1000) AND (customer_id <= 1500))
  Heap Blocks: exact=4120
  -> Bitmap Index Scan on idx_orders_customer  (cost=0.00..94.63 rows=5010 width=0)
        Index Cond: ((customer_id >= 1000) AND (customer_id <= 1500))
```

| Field | Meaning |
|-------|---------|
| `Bitmap Index Scan` | Builds a bitmap of matching row locations from the index |
| `Bitmap Heap Scan` | Reads the table blocks marked in the bitmap, in block order |
| `Heap Blocks: exact=` | Blocks read with exact row positions |
| `Heap Blocks: lossy=` | Bitmap exceeded `work_mem` and kept only block numbers; every row in those blocks is rechecked |
| `Recheck Cond` | Condition re-applied to rows when the bitmap is lossy |

Bitmaps can also **combine indexes**: `BitmapAnd` and `BitmapOr` merge bitmaps from separate indexes before touching the table.

```
WHERE customer_id = 42 OR status = 'CANCELLED'

BitmapOr
  -> Bitmap Index Scan on idx_orders_customer   (customer_id = 42)
  -> Bitmap Index Scan on idx_orders_status     (status = 'CANCELLED')
```

### Oracle: batched access and bitmap conversion

`TABLE ACCESS BY INDEX ROWID BATCHED` (12c+) collects a batch of row addresses from the index and fetches the table blocks in sorted order, which serves the same purpose. To combine B-tree indexes, Oracle converts their row addresses into bitmaps on the fly:

```
TABLE ACCESS BY INDEX ROWID BATCHED  ORDERS
  BITMAP CONVERSION TO ROWIDS
    BITMAP OR
      BITMAP CONVERSION FROM ROWIDS
        INDEX RANGE SCAN  IDX_ORDERS_CUSTOMER
      BITMAP CONVERSION FROM ROWIDS
        INDEX RANGE SCAN  IDX_ORDERS_STATUS
```

Unlike a plain index scan, a bitmap scan returns rows in **block order**, not key order. If the query needs key order, a sort follows.

## 6. Index-Only Scan

An index-only scan answers the query from the index alone, with no table access. It requires an index containing every column the query references (Chapter 02, Sections 6 and 7).

```sql
SELECT order_date FROM orders WHERE customer_id = 42;   -- served by idx_orders_cust_date
```

```
PostgreSQL                                          Oracle

Index Only Scan using idx_orders_cust_date          |* 1 | INDEX RANGE SCAN | IDX_ORDERS_CUST_DATE |
  Index Cond: (customer_id = 42)                    (no TABLE ACCESS step)
  Heap Fetches: 0
```

Because the table visit is the expensive part of an index scan, removing it changes the economics completely. An index-only scan stays cheap even when it returns **many** rows, because it reads only densely packed index blocks.

```sql
-- Count orders per customer: reads only the (much smaller) index
SELECT customer_id, COUNT(*) FROM orders GROUP BY customer_id;
```

| | PostgreSQL | Oracle |
|---|---|---|
| Whole-index read for many rows | `Index Only Scan` over the full index | `INDEX FAST FULL SCAN`: multi-block reads of all index blocks, unordered |
| Extra condition | Pages must be marked all-visible, or `Heap Fetches` rise; keep tables vacuumed | None |
| `COUNT(*)` from an index | Any B-tree index | Only an index on a `NOT NULL` column (Chapter 02, Section 2) |

## 7. How the Optimizer Prices Each Path

The optimizer computes an estimated cost for each available path and picks the cheapest (Chapter 01, Section 3). The formulas below are simplified, but they show which inputs matter.

### PostgreSQL

```
Full scan   = pages × seq_page_cost  +  rows × (cpu_tuple_cost + cpu_operator_cost × filters)

Index scan  = index pages read
            + table pages fetched × (cost per page)
            + matching rows × cpu costs

            cost per page is interpolated between
              random_page_cost (4.0)   when correlation = 0   (rows scattered)
              seq_page_cost    (1.0)   when correlation = ±1  (rows in index order)
            using correlation²
```

The number of table pages fetched is estimated from the number of matching rows and the table size, accounting for rows that share a page. `correlation` comes from `pg_stats` (Chapter 05, Section 13).

### Oracle

```
Full scan   ≈ table blocks, divided by the effect of multi-block reads, plus CPU

Index scan  ≈ BLEVEL
            + LEAF_BLOCKS       × index selectivity
            + CLUSTERING_FACTOR × table selectivity
```

`CLUSTERING_FACTOR` (in `USER_INDEXES`) estimates how many table blocks a full walk of the index would visit. It ranges from the number of table blocks (rows perfectly ordered) to the number of rows (rows completely scattered).

### Worked example: same row count, opposite decisions

Two queries each return **10,000 rows (1%)**:

```sql
-- A: range on order_id (physical order matches the index)
SELECT * FROM orders WHERE order_id BETWEEN 500001 AND 510000;

-- B: range on customer_id (physical order unrelated to the index)
SELECT * FROM orders WHERE customer_id BETWEEN 50001 AND 51000;
```

```
A: order_id range                          B: customer_id range
   matching rows sit in ~84 adjacent         matching rows scattered over
   blocks                                    ~6,000 of the 8,334 blocks

   index ──► [84 consecutive blocks]         index ──► [scattered blocks across the table]
```

**Oracle**, with `BLEVEL` 2 and about 2,200 leaf blocks for each index:

| | A: `order_id` | B: `customer_id` |
|---|---|---|
| `CLUSTERING_FACTOR` | ≈ 8,334 (table blocks) | ≈ 990,000 (close to rows) |
| Index cost ≈ 2 + 2,200 × 0.01 + CF × 0.01 | 2 + 22 + 84 ≈ **108** | 2 + 22 + 9,900 ≈ **9,924** |
| Full scan cost | A few thousand at most (8,334 blocks in large reads) | Same |
| Choice | **Index** | **Full scan** |

**PostgreSQL**, with default cost settings (full scan with this range filter ≈ 23,300):

| | A: `order_id` | B: `customer_id` |
|---|---|---|
| `correlation` | ≈ 1.0 | ≈ 0.0 |
| Table pages fetched | ≈ 84 | ≈ 6,250 |
| Cost per page | ≈ `seq_page_cost` (1.0) | ≈ `random_page_cost` (4.0) |
| Table I/O cost | ≈ 90 | ≈ 25,000 |
| Choice | **Index scan** | **Bitmap heap scan** or **sequential scan**: a plain index scan is more expensive than both |

Both databases reach the same conclusion: the number of rows is identical, but the number and pattern of **blocks** differ by two orders of magnitude.

## 8. Rows vs Blocks: Why an Index Can Lose at 1%

Selectivity is usually discussed in rows. The real cost is in **blocks**. An index helps only if the matching rows occupy few blocks.

`status = 'CANCELLED'` matches 1% of rows. But every 100th row inserted is cancelled, and each block holds about 120 rows:

```
block 1:   rows 1–120     cancelled: rows 100          ──► 1 match
block 2:   rows 121–240   cancelled: rows 200          ──► 1 match
block 3:   rows 241–360   cancelled: rows 300          ──► 1 match
...
every block contains at least one cancelled order
```

| Measure | Value |
|---------|-------|
| Rows matched | 10,000 (1%) |
| Blocks containing a match | ~8,334 (100%) |

Any index-based plan must read essentially every block of the table, and a plain index scan would read them in random order. A full scan reads the same blocks sequentially without the index overhead, so it wins despite the 1% row selectivity.

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'CANCELLED';
```

```
Bitmap Heap Scan on orders  (actual rows=10000 loops=1)
  Recheck Cond: (status = 'CANCELLED'::text)
  Heap Blocks: exact=8334                     ◄── every page of the table
  -> Bitmap Index Scan on idx_orders_status  (actual rows=10000 loops=1)
```

`Heap Blocks: exact=8334` shows directly that the "selective" query touched the entire table. The same effect appears in Oracle as a clustering factor close to the row count.

If the cancelled orders were stored together, for example in a separate partition (Chapter 06) or a table reorganised by status, the same 10,000 rows would fill about 84 blocks, and the index would win easily.

> Rows decide how many results there are. **Blocks decide how much work it takes to find them.**

## 9. ORDER BY and LIMIT

An index returns rows **in key order**. When a query sorts by the indexed columns and needs only the first few rows, the index can stop early, avoiding both a full read and a sort.

```sql
SELECT * FROM orders
WHERE customer_id = 42
ORDER BY order_date DESC
FETCH FIRST 5 ROWS ONLY;
```

```
Index (customer_id, order_date), read backwards from the newest entry for customer 42:
  (42, 2025-06-30) ─► row      1
  (42, 2025-03-14) ─► row      2
  (42, 2024-11-02) ─► row      3
  (42, 2024-07-19) ─► row      4
  (42, 2024-02-11) ─► row      5   stop
```

```
PostgreSQL                                              Oracle
Limit                                                   COUNT STOPKEY
  -> Index Scan Backward using idx_orders_cust_date       TABLE ACCESS BY INDEX ROWID  ORDERS
        Index Cond: (customer_id = 42)                       INDEX RANGE SCAN DESCENDING  IDX_ORDERS_CUST_DATE
```

The optimizer favours plans with a low **startup cost** for such queries: the cost to produce the first row (the first number in PostgreSQL's `cost=startup..total`). Oracle's `FIRST_ROWS(n)` hint and its automatic handling of `FETCH FIRST` / `ROWNUM` do the same.

### The LIMIT trap

The early-stop plan can go badly wrong when a filter is applied to rows read in index order:

```sql
SELECT * FROM orders
WHERE status = 'CANCELLED'
ORDER BY order_id
FETCH FIRST 10 ROWS ONLY;
```

The optimizer may walk the primary key index in `order_id` order and filter each row, expecting to find 10 cancelled orders after about 1,000 rows (1% selectivity). That holds if cancelled orders are spread evenly. If they are concentrated at the end, for example because cancellation is a recent feature, the scan reads almost the whole table, row by row through the index.

| Symptom | Fix |
|---------|-----|
| `Limit` over an `Index Scan` with a large `Rows Removed by Filter` | Index that matches both filter and order: `(status, order_id)` |
| | Or a partial index (PostgreSQL): `ON orders (order_id) WHERE status = 'CANCELLED'` (Chapter 02, Section 11) |

## 10. Factors That Shift the Choice

| Factor | Pushes toward | Why | Reference |
|--------|---------------|-----|-----------|
| Few matching rows | Index | Fewer table visits | Chapter 02, Section 4 |
| Matching rows in few blocks (good clustering) | Index | Table visits become near-sequential | Sections 7, 8 |
| Query needs only indexed columns | Index-only scan | No table visits at all | Section 6 |
| Sort or `LIMIT` on indexed columns | Index | Avoids a sort; stops early | Section 9 |
| Many matching rows, or rows spread over most blocks | Full scan | Each block read once, sequentially | Sections 3, 8 |
| Small table | Full scan | Fewer reads than an index descent | Section 3 |
| Parallel query enabled | Full scan | Full scans parallelise easily | Section 3 |
| Function or conversion on the indexed column | Full scan | Index cannot be used | Chapter 01, Section 11 |
| Stale or missing statistics | Either, wrongly | Row and block estimates are wrong | Chapter 01, Section 13 |
| Bind variables with skewed data | Either, wrongly for some values | One plan reused for different selectivities | Chapter 01, Section 13 |

### Cost parameters

| Parameter | Database | Default | Effect of lowering it |
|-----------|----------|---------|-----------------------|
| `random_page_cost` | PostgreSQL | 4.0 | Index access looks cheaper. On SSDs, about 1.1 is common |
| `effective_cache_size` | PostgreSQL | 4 GB | (Raising it) planner assumes repeated index reads are more often cached |
| `effective_io_concurrency` | PostgreSQL | Version dependent | (Raising it) bitmap heap scans prefetch more pages |
| System statistics | Oracle | Default values until gathered | `DBMS_STATS.GATHER_SYSTEM_STATS` measures real single-block and multi-block read times |
| `OPTIMIZER_INDEX_COST_ADJ` | Oracle | 100 | Index access looks cheaper. A legacy setting; changing it affects every query and is rarely advisable |

Change cost parameters only to describe the hardware more accurately, and test with a representative workload. Lowering them to force indexes on one query affects every other query too.

## 11. When the Optimizer Chooses Wrongly

A wrong access path almost always comes from a wrong estimate of rows or blocks, rarely from the cost formula itself.

### Diagnose

1. Get the **actual** plan (Chapter 01, Section 5).
2. Compare estimated and actual rows on the scan node.
3. For bitmap scans, check `Heap Blocks`. For index scans, check `Buffers` or Oracle's `Buffers` column against the rows returned.
4. Force the alternative and compare real timings:

```sql
-- PostgreSQL (session only, for testing)
SET enable_seqscan = off;        -- also enable_indexscan, enable_bitmapscan, enable_indexonlyscan
EXPLAIN ANALYZE SELECT ...;
RESET enable_seqscan;
```

```sql
-- Oracle
SELECT /*+ FULL(o) */  * FROM orders o WHERE ...;
SELECT /*+ INDEX(o idx_orders_customer) */ * FROM orders o WHERE ...;
```

If the forced plan is faster **and** the estimates on the original plan were wrong, fix the estimates. If the estimates were right but the forced plan is still faster, the cost parameters do not match the hardware.

### Fix

| Finding | Fix |
|---------|-----|
| Row estimate wrong | Gather statistics; histograms for skewed columns; extended statistics for related columns (Chapter 01, Sections 12–13) |
| Rows scattered over too many blocks | Covering index; better clustering (`CLUSTER`, IOT, partitioning, load order) (Chapter 02, Section 13) |
| Index cannot be used | Rewrite the predicate, or add an expression index (Chapter 02, Section 10) |
| Index scan chosen, full scan faster on SSD-backed but uncached data | Review cost parameters and system statistics |
| Full scan chosen, index faster on fast storage | Lower `random_page_cost` (PostgreSQL) or gather system statistics (Oracle) |
| `LIMIT` walks the wrong index | Composite or partial index matching filter and order (Section 9) |
| Plan correct for some bind values only | Histograms with adaptive cursor sharing (Oracle); `plan_cache_mode` (PostgreSQL) |

Avoid leaving hints or `enable_* = off` in production code. They freeze one decision while data and hardware change around it.

## 12. A Systematic Approach to Access Path Problems

```
1. Capture the actual plan; find the scan node that dominates time or buffers
        │
        ▼
2. Estimated rows ≈ actual rows?
        │
        ├── No ──► fix statistics first; re-check                     Section 11
        │
        ▼
3. Which path, and is it plausible?
        │
        ├── Full scan, few rows returned
        │        ──► usable index exists?
        │              no  ──► create one / make the predicate sargable
        │              yes ──► check blocks: are the rows spread
        │                      across most of the table?              Section 8
        │
        ├── Index scan, many rows returned, high buffers
        │        ──► covering index, better clustering, or let it use
        │            a full / bitmap scan                             Sections 5, 6
        │
        ├── Bitmap scan with lossy blocks
        │        ──► raise work_mem for the query                     Section 5
        │
        └── Limit + index scan with large Rows Removed by Filter
                 ──► index matching both filter and ORDER BY          Section 9
        │
        ▼
4. Compare with the forced alternative (hints / enable_*)
        │
        ├── forced plan faster, estimates right ──► review cost parameters
        └── forced plan slower                  ──► current choice is correct
        │
        ▼
5. Make the good path natural
        statistics, index design, clustering, partitioning;
        not permanent hints
```

## 13. Oracle and PostgreSQL Reference

| Item | Oracle | PostgreSQL |
|------|--------|------------|
| Full scan | `TABLE ACCESS FULL` | `Seq Scan` |
| Parallel full scan | `PX BLOCK ITERATOR` + `TABLE ACCESS FULL` | `Gather` + `Parallel Seq Scan` |
| Index scan | `INDEX RANGE SCAN` / `UNIQUE SCAN` + `TABLE ACCESS BY INDEX ROWID` | `Index Scan` |
| Descending index read | `INDEX RANGE SCAN DESCENDING` | `Index Scan Backward` |
| Sorted-block table access | `TABLE ACCESS BY INDEX ROWID BATCHED` | `Bitmap Heap Scan` |
| Combining indexes | `BITMAP CONVERSION FROM ROWIDS`, `BITMAP AND / OR` | `BitmapAnd`, `BitmapOr` |
| Index-only access | Index step without table access | `Index Only Scan` (`Heap Fetches`) |
| Whole-index read | `INDEX FAST FULL SCAN`, `INDEX FULL SCAN` | `Index Only Scan` over the full index |
| Early stop | `COUNT STOPKEY`, `FIRST_ROWS(n)` | `Limit` with low startup cost |
| Physical order metric | `CLUSTERING_FACTOR` | `pg_stats.correlation` |
| Index cost inputs | `BLEVEL`, `LEAF_BLOCKS`, `CLUSTERING_FACTOR` | Index pages, correlation, `random_page_cost` |
| I/O cost calibration | System statistics | `random_page_cost`, `seq_page_cost`, `effective_cache_size` |
| Force full scan | `/*+ FULL(t) */` | `SET enable_indexscan = off`, `enable_bitmapscan = off` |
| Force index | `/*+ INDEX(t idx) */` | `SET enable_seqscan = off` |
| Blocks touched | `Buffers` in `ALLSTATS LAST` | `BUFFERS` option; `Heap Blocks` on bitmap scans |

## 14. Short Summary

- A full table scan reads every block once, sequentially; its cost depends on table size, not on how many rows match.
- An index scan reads a few index blocks and then one table block per matching row, often randomly; its cost grows with the matching rows.
- Bitmap and batched scans sort row addresses by block before reading the table, covering the middle ground between the two.
- An index-only scan removes table access entirely and stays cheap even for many rows, provided the index holds every needed column.
- The optimizer prices each path from estimated rows, table and index size, and physical ordering (clustering factor or correlation). The same row count can favour an index on one column and a full scan on another.
- What matters is how many **blocks** the matching rows occupy. A 1% predicate whose rows are spread across every block is cheaper with a full scan.
- Indexes also win when they provide sort order for `ORDER BY` with `LIMIT`, but a filter applied during an ordered index walk can turn into a near-full scan.
- When the choice looks wrong, check the estimates first, then the physical layout, then the cost parameters; avoid permanent hints.
