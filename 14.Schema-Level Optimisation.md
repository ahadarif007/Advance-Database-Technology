# Chapter 14: Schema-Level Optimisation

Query tuning works within the limits the schema sets. A poorly chosen data type, a random primary key, a missing foreign key index or a generic key-value table can make every query slower, and no index or hint fully compensates. Schema decisions are also the hardest to change later, because data, applications and integrations come to depend on them.

This chapter covers the schema design choices with the largest effect on performance in **Oracle** and **PostgreSQL**: normalisation, data types, key design, foreign key indexes, table width, JSON, the EAV anti-pattern and temporal data.

## 2. Normalisation vs Denormalisation

**Normalisation** organises data so that each fact is stored once. It removes redundancy, and with it the anomalies that arise when copies of a fact disagree.

### The normal forms that matter in practice

```
Unnormalised order row
┌──────────┬────────────┬──────────────────┬──────────────────────────────┐
│ order_id │ customer   │ customer_country │ items                        │
├──────────┼────────────┼──────────────────┼──────────────────────────────┤
│ 1001     │ Customer 42│ UK               │ "lamp x1, desk x2"           │
└──────────┴────────────┴──────────────────┴──────────────────────────────┘
```

| Normal form | Rule | Fix in the example |
|-------------|------|--------------------|
| **1NF** | One value per column; no lists or repeating groups | Move items into rows of `order_items` |
| **2NF** | Non-key columns depend on the **whole** key | In `order_items (order_id, product_id)`, `product_name` depends only on `product_id`: move it to `products` |
| **3NF** | Non-key columns depend **only** on the key, not on other non-key columns | `customer_country` depends on the customer, not the order: keep it in `customers` |

The normalised result is the four-table schema used throughout this series.

### What normalisation buys

| Benefit | Example |
|---------|---------|
| One update per fact | Changing a customer's country updates one row |
| No contradictions | An order cannot show a different country from its customer |
| Narrow tables | Smaller rows, more rows per block (Section 8) |
| Constraints express the rules | Foreign keys, unique keys, `NOT NULL` |

### When to denormalise

Denormalisation adds redundancy back, deliberately, to make specific reads cheaper. Chapter 07 (Section 8) covered the forms, costs and consistency mechanisms. The rule of thumb:

```
OLTP schema           normalise to 3NF; denormalise selectively, with a mechanism
                      that keeps copies correct (generated columns, triggers, MVs)

Analytical schema     denormalise into a star schema: a large fact table
                      (one row per order line) surrounded by wide dimension tables
                      (customer, product, date)
```

```
Star schema

               dim_date
                  │
  dim_customer ── fact_sales ── dim_product
                  │
               dim_store
```

Star schemas trade update convenience, which matters little in a warehouse loaded in batches, for simple joins and fast aggregation.

## 3. Appropriate Data Types

The data type decides how much space a value takes, how fast comparisons are, which indexes can be used, and which invalid values the database rejects.

### Recommended types

| Data | PostgreSQL | Oracle | Avoid |
|------|-----------|--------|-------|
| Integer IDs and counts | `INTEGER` (4 bytes), `BIGINT` (8 bytes) | `NUMBER(10)`, `NUMBER(19)` | Text, or `NUMBER` without precision for keys |
| Money and exact decimals | `NUMERIC(12,2)` | `NUMBER(12,2)` | `REAL`, `DOUBLE PRECISION`, `BINARY_DOUBLE`: rounding errors |
| Measurements, scientific values | `DOUBLE PRECISION` | `BINARY_DOUBLE` | `NUMERIC` where exactness is not needed (slower arithmetic) |
| Text | `TEXT` or `VARCHAR(n)` | `VARCHAR2(n CHAR)` | `CHAR(n)`: blank-padded |
| Date only | `DATE` | `DATE` (always includes time; truncate or constrain) | Text |
| Point in time | `TIMESTAMPTZ` | `TIMESTAMP WITH TIME ZONE`, or `TIMESTAMP` in UTC | Text; local time without zone for global systems |
| True / false | `BOOLEAN` | `BOOLEAN` (23ai+); earlier `NUMBER(1)` or `CHAR(1)` with a `CHECK` | Free text such as `'Y'`, `'yes'`, `'1'` mixed |
| UUID | `UUID` (16 bytes) | `RAW(16)` | `VARCHAR(36)`: more than twice the size |
| Small fixed set of values | Lookup table, `CHECK`, or `ENUM` type | Lookup table or `CHECK` | Unconstrained text |

### Points that differ between the databases

**Oracle `NUMBER`** is a variable-length decimal format of 1 to 22 bytes. Small integers are compact, but arithmetic is slower than with native binary integers. Declare precision (`NUMBER(10)`) so that out-of-range values are rejected.

**Oracle treats an empty string as `NULL`.** `''` inserted into a `VARCHAR2` column is stored as NULL, so `WHERE name = ''` never matches. PostgreSQL distinguishes `''` from `NULL`. Portable code must not rely on either behaviour.

**Oracle `DATE` includes a time of day.** `WHERE order_date = DATE '2026-01-15'` misses rows stored with a non-midnight time. Either store midnight consistently (enforced by a `CHECK (order_date = TRUNC(order_date))`) or query with a range.

**PostgreSQL `TEXT` and `VARCHAR(n)`** perform identically. `VARCHAR(n)` only adds a length check. Oracle `VARCHAR2(n)` defaults to `n` **bytes** unless `NLS_LENGTH_SEMANTICS = CHAR` or `CHAR` is specified, which matters for multi-byte characters.

### Why types affect performance

| Wrong type | Consequence |
|------------|-------------|
| Numbers or dates stored as text | Implicit conversions disable indexes (Chapter 01, Section 11); wrong ordering (`'10' < '9'`); no range checks |
| Mismatched types on join columns (`INTEGER` vs `BIGINT`, `NUMBER` vs `VARCHAR2`) | Conversion on one side of the join; index on that side may not be usable |
| Oversized types (`BIGINT` for a 3-value status, `CHAR(200)`) | Larger rows and indexes; fewer rows per block |
| Floating point for money | Silent rounding: `0.1 + 0.2 ≠ 0.3` |
| Unbounded text for codes | Invalid values enter, statistics become noisy |

Join and foreign key columns must use **exactly the same type** on both sides.

In PostgreSQL, column order also affects row size through alignment padding (Chapter 05, Section 13).

## 4. Primary-Key Design

Every table needs a primary key: it identifies rows, it is the target of foreign keys, and it is backed by a unique index.

### Properties of a good primary key

| Property | Reason |
|----------|--------|
| Unique and `NOT NULL` | Definition of a key |
| **Stable**: never changes | Changing it means updating every referencing row and index entry |
| **Small** | Copied into every foreign key and, in PostgreSQL and Oracle, stored in every index on the key |
| **Simple**: one column where practical | Simpler joins and foreign keys |
| Insert-friendly | Increasing values append to the end of the index; random values insert everywhere (Section 6) |

### Generating keys

**PostgreSQL** (version 10+): identity columns.

```sql
CREATE TABLE orders (
    order_id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers,
    ...
);
```

`GENERATED ALWAYS` rejects manually supplied values unless `OVERRIDING SYSTEM VALUE` is used. Prefer it to the older `SERIAL` pseudo-type, which creates a sequence with looser ownership and permissions.

**Oracle** (12c+): identity columns, or a sequence as the column default.

```sql
CREATE TABLE orders (
    order_id    NUMBER GENERATED ALWAYS AS IDENTITY (CACHE 1000) PRIMARY KEY,
    customer_id NUMBER NOT NULL REFERENCES customers,
    ...
);

-- or
CREATE SEQUENCE order_seq CACHE 1000;
CREATE TABLE orders (
    order_id NUMBER DEFAULT order_seq.NEXTVAL PRIMARY KEY,
    ...
);
```

### Sequence caching

| | Oracle | PostgreSQL |
|---|---|---|
| Default cache | 20 | 1 |
| Effect of a larger cache | Fewer updates to the sequence's dictionary entry; less contention under high insert rates | Each session pre-allocates values; fewer sequence accesses |
| Cost | Unused cached values are lost on restart: gaps | Each session's unused values are lost when it ends: gaps |

Gaps are normal in both databases, also from rolled-back transactions. Never rely on sequence values being consecutive. If a business needs gapless numbers, such as invoice numbers in some jurisdictions, generate them separately with explicit locking.

On Oracle RAC, sequences with `ORDER` force instances to coordinate on every value. Use `NOORDER` (the default) with a large cache, or scalable sequences (18c+) for insert-heavy tables (Chapter 04, Section 12).

### Composite primary keys

Composite keys are appropriate for association tables and for child tables that are always accessed through their parent:

```sql
-- association: one row per product per order
PRIMARY KEY (order_id, product_id)

-- child identified within its parent, co-located for sharding (Chapter 10)
PRIMARY KEY (customer_id, order_id)
```

For other tables, a single-column key keeps foreign keys and joins simple.

## 5. Surrogate vs Natural Keys

| | Natural key | Surrogate key |
|---|---|---|
| Definition | A real-world attribute that identifies the row | A generated value with no business meaning |
| Examples | Email address, ISO country code, product SKU, VAT number | `customer_id` from an identity column, a UUID |
| Stability | Can change (people change email; products get re-coded) | Never changes |
| Size | Often long text | Small integer or 16 bytes |
| Meaningful in queries | Yes; sometimes avoids a join | No; always joined to get the meaning |
| Format changes | Business rule change can break the key | Unaffected |

```
Natural key as PK: customer changes email

customers.email (PK)  'old@x.com' ──► 'new@x.com'
          │
          ├── orders.customer_email        × 1,200 rows to update
          ├── reviews.customer_email       ×    40 rows to update
          └── every index on those columns
```

### Recommendation

Use a **surrogate primary key**, and enforce the natural key with a **unique constraint**:

```sql
CREATE TABLE customers (
    customer_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- surrogate
    email       TEXT NOT NULL,
    CONSTRAINT uq_customers_email UNIQUE (email)                   -- natural key still unique
);
```

The surrogate gives stable, compact references. The unique constraint keeps the business rule and supports lookups by email.

Natural keys remain a good choice when they are short, standardised and truly stable: ISO country codes (`'GB'`), ISO currency codes (`'EUR'`). Lookup tables keyed this way save a join, because the code is meaningful on its own.

## 6. UUID vs Sequential IDs

Both are surrogate keys. The difference is how they behave in a B-tree index.

### Insert pattern

```
Sequential IDs                              Random UUIDs (version 4)

index leaf blocks                           index leaf blocks
[1-100][101-200][201-300][301-  ]◄ insert   [a1..][3f..][7c..][c2..][e9..]
                                  here         ▲     ▲     ▲     ▲     ▲
all new keys go to the rightmost leaf       new keys land in any leaf

hot leaf stays in memory                    every leaf must be in memory
full leaf: allocate a new one, no split     full leaf: split into two half-full leaves
```

| Effect | Sequential | Random UUID |
|--------|------------|-------------|
| Leaf blocks touched by inserts | One | Any of them |
| Page splits | Rare (append) | Constant; leaves end up about 70% full |
| Index size | Compact | Larger |
| Cache needed for fast inserts | The rightmost leaf | The entire index |
| PostgreSQL WAL volume | Low | Higher: each newly touched page after a checkpoint writes a full-page image (Chapter 05, Section 6) |
| Key size | 4 or 8 bytes | 16 bytes |
| Contention | One hot block under very high concurrency (Oracle `enq: TX - index contention`) | None |

On a small table this makes no difference. Once the index no longer fits in memory, random inserts turn into random reads, and insert throughput can drop sharply.

### Where UUIDs are worth it

| Need | Why UUID helps |
|------|----------------|
| IDs generated outside the database (clients, offline devices, other services) | No round trip to a sequence |
| Merging data from several databases or shards | No collisions (Chapter 10, Section 10) |
| IDs exposed in URLs or APIs | Not guessable; do not reveal volume (order 1000001 tells competitors your order count) |

### Time-ordered UUIDs

**UUID version 7** places a millisecond timestamp in the leading bits, followed by random bits. New values are roughly increasing, so they insert near the right edge of the index like a sequence, while staying globally unique and hard to guess.

```
UUIDv4:  3f2a91c4-7e1b-4d6a-9c0e-5b8f2a1d7e43     random throughout
UUIDv7:  0192f3a1-6c40-7b2e-8d14-9a7c3e5f1b20     time prefix, then random
         └────── timestamp ─────┘
```

| | Generate | Store |
|---|---|---|
| PostgreSQL | `gen_random_uuid()` for v4 (13+); `uuidv7()` (18+); earlier versions: generate v7 in the application | `UUID` |
| Oracle | `SYS_GUID()` returns a 16-byte globally unique value; generate v7 in the application for time ordering | `RAW(16)` |

### Recommendation

```
IDs only used inside the database?                ──► BIGINT identity / sequence
IDs generated outside, merged, or public?         ──► UUIDv7 (time-ordered)
Need a public ID but want compact internal joins? ──► BIGINT primary key
                                                      + UUID column with a unique index
```

## 7. Foreign-Key Indexing

A foreign key constraint does **not** create an index on the referencing column, in either Oracle or PostgreSQL. The primary key on the parent side is indexed automatically. The foreign key column on the child side is not.

```
customers (PK customer_id: indexed automatically)
     ▲
     │  orders.customer_id REFERENCES customers
     │
orders.customer_id: NOT indexed unless you create the index
```

### Why the index matters

| Operation | Without an index on `orders.customer_id` |
|-----------|-------------------------------------------|
| Join from customer to their orders | Full scan or hash join of `orders` for every lookup |
| `DELETE FROM customers WHERE ...` | Full scan of `orders` per deleted customer to check for references |
| Update of `customers.customer_id` | Same as delete |
| `ON DELETE CASCADE` | Full scan of `orders` to find the rows to delete |
| Locking (Oracle) | Share lock on the whole child table during the parent change, blocking DML (Chapter 04, Section 7) |

### Finding unindexed foreign keys

The queries below check that the first foreign key column is the leading column of some index, which covers the common single-column case.

**PostgreSQL**

```sql
SELECT c.conrelid::regclass AS child_table,
       c.conname           AS constraint_name,
       a.attname           AS fk_column
FROM pg_constraint c
JOIN pg_attribute a
  ON a.attrelid = c.conrelid AND a.attnum = c.conkey[1]
WHERE c.contype = 'f'
  AND NOT EXISTS (
        SELECT 1 FROM pg_index i
        WHERE i.indrelid = c.conrelid
          AND i.indkey[0] = c.conkey[1]);
```

**Oracle**

```sql
SELECT c.table_name, c.constraint_name, cc.column_name
FROM user_constraints c
JOIN user_cons_columns cc
  ON cc.constraint_name = c.constraint_name AND cc.position = 1
WHERE c.constraint_type = 'R'
  AND NOT EXISTS (
        SELECT 1 FROM user_ind_columns ic
        WHERE ic.table_name      = c.table_name
          AND ic.column_name     = cc.column_name
          AND ic.column_position = 1);
```

### When an index can be skipped

An index on a foreign key costs write overhead like any other index. It can be omitted only when **all** of these hold:

- parent rows are never deleted and their keys never change,
- no query joins or filters the child table by that column,
- in Oracle, no concurrent DML on the child table must proceed during parent changes.

For typical tables such as `orders.customer_id` or `order_items.order_id`, the index is needed. For `order_items.product_id`, it is needed if products are ever deleted or if queries ask "which orders contain this product".

## 8. Wide vs Narrow Tables

A **wide** table has many columns or large rows. A **narrow** table has few, small columns.

```
8 KB block

Narrow rows (60 bytes)       ~120 rows per block    ████████████████████████████
Wide rows (600 bytes)        ~12 rows per block     ███
                                                    10x more blocks for the same rows
```

| Effect of wide rows | Detail |
|---------------------|--------|
| Fewer rows per block | Every scan reads more blocks; the buffer cache holds fewer rows |
| More I/O for queries that need few columns | The whole row is read even if only two columns are used |
| PostgreSQL update cost | MVCC writes a **complete new row version** on every update (Chapter 04, Section 3); updating a counter in a 2 KB row writes 2 KB |
| Oracle update cost | In-place update, but growing rows can migrate (Chapter 05, Section 9) |
| Very many columns | Oracle splits rows with more than 255 columns into several row pieces; PostgreSQL has a hard limit of 1,600 columns |

### Splitting by access pattern

Split a wide table when its columns have clearly different access patterns (Chapter 10, Section 4):

```
products (wide)                                   products                product_content
┌────┬──────┬───────┬───────┬─────────────────┐   ┌────┬──────┬───────┐    ┌────┬─────────────────┐
│ id │ name │ price │ stock │ description,    │   │ id │ name │ price │    │ id │ description,    │
│    │      │       │       │ specs, manuals  │ ► │    │      │ stock │    │    │ specs, manuals  │
└────┴──────┴───────┴───────┴─────────────────┘   └────┴──────┴───────┘    └────┴─────────────────┘
                                                  read and updated often   read on the detail page only
```

| Split off | Reason |
|-----------|--------|
| Large, rarely read columns | Keep the frequently scanned table narrow |
| Frequently updated columns (counters, `last_seen_at`) | In PostgreSQL, avoids rewriting the whole wide row on each update; keeps HOT updates possible |
| Optional columns that are mostly NULL | Store only for rows that have them |

Do not split columns that are almost always read together. Every split adds a join to queries that need both halves.

## 9. JSON vs Relational Columns

Both databases can store and index JSON documents. JSON suits some data well and other data badly.

### Storage types

| | PostgreSQL | Oracle |
|---|---|---|
| Recommended type | `JSONB`: parsed binary format; supports indexing and fast key access | `JSON` type (21c+): binary OSON format |
| Text-based type | `JSON`: stores the original text; reparsed on every access | `VARCHAR2`, `CLOB` or `BLOB` with an `IS JSON` check constraint (earlier versions) |
| Large documents | Moved out of line by TOAST (Chapter 05, Section 2) | LOB storage |

```sql
-- PostgreSQL
CREATE TABLE product_attributes (
    product_id BIGINT PRIMARY KEY REFERENCES products,
    attrs      JSONB NOT NULL
);

SELECT product_id FROM product_attributes
WHERE attrs ->> 'colour' = 'black';

-- Oracle 21c+
CREATE TABLE product_attributes (
    product_id NUMBER PRIMARY KEY REFERENCES products,
    attrs      JSON NOT NULL
);

SELECT product_id FROM product_attributes
WHERE JSON_VALUE(attrs, '$.colour') = 'black';
```

### Indexing JSON

| Need | PostgreSQL | Oracle |
|------|-----------|--------|
| One known key | Expression index: `CREATE INDEX ON product_attributes ((attrs ->> 'colour'))` | Function-based index on `JSON_VALUE(attrs, '$.colour')` |
| Containment of any key/value | GIN index: `CREATE INDEX ON product_attributes USING gin (attrs jsonb_path_ops)`, queried with `attrs @> '{"colour":"black"}'` | JSON search index: `CREATE SEARCH INDEX ... FOR JSON` |
| Values inside arrays | GIN index | Multivalue index (21c+) |

### When to use which

| Use relational columns when | Use JSON when |
|-----------------------------|---------------|
| The field is filtered, joined, sorted or aggregated often | Attributes vary by row and are rarely queried individually |
| Constraints are needed (`NOT NULL`, foreign keys, `CHECK`) | The document is stored and returned as a whole (API payloads, settings) |
| The field is updated on its own frequently | The structure is owned by another system and changes outside your control |
| The optimizer needs statistics on it | The set of attributes is open-ended (product specifications by category) |

### Hidden costs of JSON

| Cost | Detail |
|------|--------|
| Statistics | The optimizer has no statistics on keys inside a document unless they are indexed by expression (Chapter 01, Section 12), so row estimates fall back to fixed guesses |
| Updates | Changing one key rewrites the whole document; in PostgreSQL, a large TOASTed document is rewritten in full |
| Storage | Key names are repeated in every row |
| Type safety | `"price": "12.50"` and `"price": 12.5` can both appear unless validated |
| Constraints | No foreign keys into JSON values |

### The hybrid pattern

Keep frequently queried fields as real columns, and the variable remainder as JSON. Where a field lives in the JSON but must be queried efficiently, promote it with a generated column:

```sql
-- PostgreSQL: generated column from a JSON key, indexable and with statistics
ALTER TABLE product_attributes
    ADD COLUMN colour TEXT GENERATED ALWAYS AS (attrs ->> 'colour') STORED;
CREATE INDEX ON product_attributes (colour);

-- Oracle: virtual column
ALTER TABLE product_attributes
    ADD (colour VARCHAR2(30) AS (JSON_VALUE(attrs, '$.colour')));
CREATE INDEX ix_pa_colour ON product_attributes (colour);
```

Oracle 23ai also offers **JSON Relational Duality Views**, which present normalised tables as updatable JSON documents. Applications get documents; storage stays relational.

## 10. The EAV Anti-Pattern

**Entity–Attribute–Value** (EAV) stores every attribute as a separate row in one generic table:

```
product_attribute_values
┌────────────┬────────────┬────────────┐
│ product_id │ attribute  │ value      │
├────────────┼────────────┼────────────┤
│ 42         │ colour     │ black      │
│ 42         │ weight_kg  │ 1.2        │
│ 42         │ voltage    │ 230        │
│ 43         │ colour     │ white      │
│ 43         │ pages      │ 320        │
└────────────┴────────────┴────────────┘
```

It looks flexible: new attributes need no schema change. In practice it makes almost everything else harder and slower.

### The problems

| Problem | Example |
|---------|---------|
| **No types** | `value` is text: `weight_kg > 1.0` compares strings unless every query casts, and a cast of a bad value fails at query time |
| **No constraints** | Nothing prevents `colour = 'blakc'`, a missing required attribute, or a duplicate attribute |
| **Pivoting** | Reading one product with N attributes needs N self-joins or a pivot |
| **Poor estimates** | Statistics describe the whole `value` column across all attributes, so estimates for "weight > 1" are meaningless |
| **Row explosion** | 1 million products × 30 attributes = 30 million rows, each with its own row overhead and index entries |

The query for "black products under 2 kg" shows the shape:

```sql
SELECT c.product_id
FROM product_attribute_values c
JOIN product_attribute_values w
  ON w.product_id = c.product_id AND w.attribute = 'weight_kg'
WHERE c.attribute = 'colour' AND c.value = 'black'
  AND CAST(w.value AS NUMERIC) < 2;
```

Every additional condition adds another self-join.

### Alternatives

| Situation | Better design |
|-----------|---------------|
| Attributes are known and shared by most rows | Ordinary columns |
| Attributes differ by category (books vs lamps) | One table for shared columns plus a table per category with its own columns |
| Attributes are open-ended and user-defined | JSON column (Section 9) with expression or GIN indexes for queried keys |
| A few attributes are queried heavily | Promote them to real columns; keep the rest in JSON |

EAV remains defensible only when attributes are fully user-defined, are rarely queried, and JSON support is unavailable. In current Oracle and PostgreSQL versions, JSON covers that case with far fewer problems.

## 11. Temporal Tables

**Temporal tables** keep the history of data over time, not only its current state. Two kinds of time are involved:

| Time | Question answered | Set by | Example |
|------|-------------------|--------|---------|
| **System time** (transaction time) | What did the database contain at time T? | The database, automatically | Audit: what did the record say before the correction? |
| **Application time** (valid time) | What was true in the real world at time T? | The application | A price valid from 1 January to 31 March |

A table that tracks both is **bitemporal**.

```
Application time: price of product 42

  €39.99           │ €44.99                         │ €42.00
  ─────────────────┼────────────────────────────────┼──────────────►
  2025-01-01       2026-01-01                       2026-04-01

System time: when each row was recorded or corrected in the database
```

### Oracle

**Flashback Query** reads data as it was at an earlier time, reconstructed from undo (Chapter 04, Section 3):

```sql
SELECT price FROM products
AS OF TIMESTAMP SYSTIMESTAMP - INTERVAL '10' MINUTE
WHERE product_id = 42;
```

It reaches back only as far as undo is retained (`UNDO_RETENTION`), typically hours.

**Flashback Data Archive** (renamed **Flashback Time Travel** in 23ai) keeps system-time history for years, in a separate store, and the same `AS OF` syntax reads it:

```sql
CREATE FLASHBACK ARCHIVE fda_5y TABLESPACE fda_ts RETENTION 5 YEAR;
ALTER TABLE products FLASHBACK ARCHIVE fda_5y;
```

**Temporal Validity** (12c+) declares application-time periods:

```sql
CREATE TABLE product_prices (
    product_id NUMBER       NOT NULL,
    price      NUMBER(10,2) NOT NULL,
    valid_from TIMESTAMP,
    valid_to   TIMESTAMP,
    PERIOD FOR valid_time (valid_from, valid_to)
);

SELECT price FROM product_prices
AS OF PERIOD FOR valid_time TIMESTAMP '2026-01-15 00:00:00'
WHERE product_id = 42;
```

### PostgreSQL

PostgreSQL has no built-in system versioning. The usual approaches are a history table maintained by a trigger, or an extension such as `temporal_tables`.

```sql
CREATE TABLE products_history (LIKE products);
ALTER TABLE products_history
    ADD COLUMN valid_from TIMESTAMPTZ NOT NULL,
    ADD COLUMN valid_to   TIMESTAMPTZ NOT NULL;
-- An AFTER UPDATE OR DELETE trigger copies the old row with its validity period
```

For application time, **range types** with an **exclusion constraint** prevent overlapping periods:

```sql
CREATE EXTENSION btree_gist;

CREATE TABLE product_prices (
    product_id BIGINT        NOT NULL,
    price      NUMERIC(10,2) NOT NULL,
    valid      TSTZRANGE     NOT NULL,
    EXCLUDE USING gist (product_id WITH =, valid WITH &&)
);

SELECT price FROM product_prices
WHERE product_id = 42
  AND valid @> TIMESTAMPTZ '2026-01-15 00:00:00+00';
```

The exclusion constraint rejects a second price for product 42 whose period overlaps an existing one. PostgreSQL 18 adds `WITHOUT OVERLAPS` for primary and unique keys, which expresses the same rule declaratively.

### Performance considerations

| Concern | Recommendation |
|---------|----------------|
| History grows without limit | Partition the history table by time and drop or archive old partitions (Chapter 06) |
| Current-state queries slowed by history | Keep current rows and history in separate tables, as system versioning does |
| "As of" lookups | Index on `(key, valid_from)`, or a GiST index on the range column |
| Write cost | Each update writes a history row too; avoid temporal tracking on high-frequency counters |

## 12. A Systematic Approach to Schema Design

```
1. Model the data in 3NF                                            Section 2
        each fact once; constraints express the rules
        │
        ▼
2. Choose exact types
        integers for IDs, exact decimals for money, real date/time types,
        identical types on both sides of every join                 Section 3
        │
        ▼
3. Design keys
        surrogate BIGINT identity by default;
        UUIDv7 when IDs are generated outside, merged or public;
        natural keys as unique constraints                          Sections 4–6
        │
        ▼
4. Index every foreign key that is joined, or whose parent
   is deleted or updated                                            Section 7
        │
        ▼
5. Check row width
        split off large rarely-read columns and hot updated columns  Section 8
        │
        ▼
6. Variable attributes?
        known and queried   ──► columns
        variable, rarely queried ──► JSON (+ generated columns for hot keys)
        never EAV                                                   Sections 9, 10
        │
        ▼
7. History needed?
        audit ──► system time (Flashback Time Travel / history table)
        business validity ──► application-time periods              Section 11
        │
        ▼
8. Denormalise last, for measured read problems, with a mechanism
   that keeps copies correct                                        Chapter 07
```

## 13. Oracle and PostgreSQL Reference

| Item | Oracle | PostgreSQL |
|------|--------|------------|
| Integer types | `NUMBER(p)` (variable length) | `SMALLINT`, `INTEGER`, `BIGINT` |
| Exact decimal | `NUMBER(p,s)` | `NUMERIC(p,s)` |
| Text | `VARCHAR2(n [BYTE\|CHAR])` | `TEXT`, `VARCHAR(n)` |
| Empty string | Stored as NULL | Distinct from NULL |
| Date / time | `DATE` (with time), `TIMESTAMP [WITH TIME ZONE]` | `DATE`, `TIMESTAMP`, `TIMESTAMPTZ` |
| Boolean | `BOOLEAN` (23ai+) | `BOOLEAN` |
| UUID storage | `RAW(16)` | `UUID` |
| UUID generation | `SYS_GUID()` | `gen_random_uuid()` (13+), `uuidv7()` (18+) |
| Identity column | `GENERATED ... AS IDENTITY` (12c+) | `GENERATED ... AS IDENTITY` (10+) |
| Sequence cache default | 20 | 1 |
| FK index created automatically | No | No |
| Unindexed FK effect on locking | Share lock on child table | No table lock; slow parent changes |
| Column limit | 1,000 (4,096 with extended limits in 23ai) | 1,600 |
| JSON type | `JSON` (21c+, OSON) | `JSONB` |
| JSON key index | Function-based index on `JSON_VALUE` | Expression index on `->>` |
| JSON general index | JSON search index; multivalue index (21c+) | GIN (`jsonb_ops`, `jsonb_path_ops`) |
| Derived column | Virtual column | `GENERATED ALWAYS AS (...) STORED` (12+) |
| Documents over relational tables | JSON Relational Duality Views (23ai) | Not built in |
| Short-term history | Flashback Query (undo) | Not available |
| Long-term system-time history | Flashback Time Travel / Flashback Data Archive | Trigger-maintained history table; extensions |
| Application-time periods | Temporal Validity (`PERIOD FOR`) | Range types + exclusion constraints; `WITHOUT OVERLAPS` (18+) |

## 14. Short Summary

- Normalise OLTP schemas to 3NF so each fact is stored once. Denormalise only for measured read problems, with a mechanism that keeps copies correct; analytical schemas use star schemas instead.
- Use exact, appropriately sized types, and identical types on both sides of every join. Text for numbers or dates, floats for money and mismatched join types all cost correctness and performance.
- Primary keys should be small, stable and simple. Use identity columns or cached sequences, and expect gaps.
- Prefer surrogate primary keys with unique constraints on natural keys; keep natural keys for short, stable standard codes.
- Random UUIDs scatter inserts across the whole index. Use sequential IDs internally, and time-ordered UUIDv7 where IDs must be generated outside the database or exposed publicly.
- Neither database indexes foreign key columns automatically. Index them for joins, parent deletes and, in Oracle, to avoid child-table locks.
- Keep frequently scanned tables narrow; split off large rarely-read columns and frequently updated ones.
- Use JSON for variable, rarely queried attributes and relational columns for anything filtered, joined or constrained. Avoid EAV.
- Temporal requirements split into system time (audit) and application time (validity). Oracle provides both natively; PostgreSQL uses history tables, range types and exclusion constraints.
