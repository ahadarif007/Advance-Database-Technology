# Chapter 15: Advanced Aggregation

Aggregation turns many rows into few: totals, averages, counts, rankings. On small tables any approach is fast. On hundreds of millions of rows, the choice of algorithm, the memory available, the shape of a window definition and whether an exact answer is needed decide whether a query takes milliseconds or hours.

```sql
SELECT
    department_id,
    AVG(salary) OVER (
        PARTITION BY department_id
    )
FROM employees;
```

This query looks simple, but at scale it sorts the entire table and holds each department's rows in memory before returning any of them. This chapter explains how **Oracle** and **PostgreSQL** execute aggregations and window functions, what each costs, and the alternatives: incremental, precomputed and approximate aggregation.

## 1. Sample Schema

The examples use the `orders` table from Chapter 01 and a new `employees` table for the window function examples:

```sql
-- PostgreSQL
CREATE TABLE employees (
    employee_id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    department_id INT           NOT NULL,
    hire_date     DATE          NOT NULL,
    salary        NUMERIC(10,2) NOT NULL
);

INSERT INTO employees (department_id, hire_date, salary)
SELECT (g % 50) + 1,
       DATE '2010-01-01' + (g % 5000),
       30000 + (g % 70000)
FROM generate_series(1, 1000000) g;

ANALYZE employees;
```

Oracle differences: `NUMBER` types, and `CONNECT BY LEVEL <= 1000000` instead of `generate_series` (Chapter 01, Section 2).

| Table | Rows | Groups of interest |
|-------|------|--------------------|
| `employees` | 1,000,000 | 50 departments, ~20,000 employees each |
| `orders` | 1,000,000 | ~100,000 customers, ~2,000 dates, 3 statuses |

## 2. How GROUP BY Is Executed

Every `GROUP BY` must bring rows with the same key together. There are two ways to do it:

```
Hash aggregation                          Sort aggregation

read rows in any order                    sort rows by the group key
look up each key in a hash table          read sorted rows; a group ends
update that group's running totals        when the key changes

  row (dept 7)  ─► [7: sum, count]          dept 1, dept 1, dept 1 ─► emit dept 1
  row (dept 2)  ─► [2: sum, count]          dept 2, dept 2         ─► emit dept 2
  row (dept 7)  ─► [7: sum, count]          dept 3, ...
  ...                                       ...
  emit all groups at the end                emit each group as soon as it ends
```

| | Hash | Sort |
|---|---|---|
| Memory needed | One entry **per group** | Rows to sort (unless input is already sorted) |
| Output order | None | Sorted by group key |
| First row returned | After all input is read | After the sort; then streams |
| Works on already sorted input | No benefit | No sort needed: very cheap |

The optimizer chooses based on the estimated number of groups, the memory available, and whether the input is already sorted or the output must be.

## 3. Hash Aggregation

```sql
SELECT status, COUNT(*), SUM(total_amount)
FROM orders
GROUP BY status;
```

**PostgreSQL**

```
HashAggregate  (cost=23334.00..23334.03 rows=3 width=48)
               (actual time=210.4..210.4 rows=3 loops=1)
  Group Key: status
  Batches: 1  Memory Usage: 24kB
  -> Seq Scan on orders  (actual rows=1000000 loops=1)
```

**Oracle**

```
| Id | Operation          | Name   | Rows |
|  0 | SELECT STATEMENT   |        |    3 |
|  1 |  HASH GROUP BY     |        |    3 |
|  2 |   TABLE ACCESS FULL| ORDERS | 1000K|
```

Three groups need three hash table entries, however many rows there are. Hash aggregation is ideal when **the number of groups is small** relative to the input.

### Memory and spilling

The hash table needs memory proportional to the number of groups times the size of each group's state.

```
GROUP BY status           3 groups           ~ kilobytes       fits easily
GROUP BY customer_id      100,000 groups     ~ megabytes       usually fits
GROUP BY order_id         1,000,000 groups   ~ tens of MB      may not fit
```

| | Memory limit | When exceeded | Shown in the plan |
|---|---|---|---|
| PostgreSQL | `work_mem × hash_mem_multiplier` (multiplier default 2.0 from version 15) | From version 13, spills partitions of groups to disk and processes them in turn. Earlier versions avoided hash aggregation when it was not expected to fit, and could exceed memory when the estimate was wrong | `Batches: 5  Memory Usage: 8241kB  Disk Usage: 31000kB` |
| Oracle | PGA work area (`PGA_AGGREGATE_TARGET`) | Spills to temporary tablespace | `Used-Tmp` in `ALLSTATS LAST`; one-pass or multi-pass work areas in `V$SQL_WORKAREA` |

Spilling works, but writing and re-reading groups from disk can make the aggregation several times slower. As with hash joins (Chapter 03, Section 5), the fix is more memory for that query, fewer groups, or narrower group state.

```sql
-- PostgreSQL: more memory for this session only
SET work_mem = '256MB';
```

An underestimated number of groups is a common cause of spilling. The planner estimates groups from the column's distinct-value statistics (`n_distinct`), and for several grouping columns it multiplies them unless extended statistics describe their relationship (Chapter 01, Section 12).

## 4. Sort Aggregation

```sql
SELECT customer_id, COUNT(*), SUM(total_amount)
FROM orders
GROUP BY customer_id
ORDER BY customer_id;
```

**PostgreSQL**

```
GroupAggregate  (actual rows=99995 loops=1)
  Group Key: customer_id
  -> Index Scan using idx_orders_customer on orders  (actual rows=1000000 loops=1)
```

Rows arrive from the index already in `customer_id` order, so no sort is needed. Each group is emitted as soon as the next customer starts, and the result is already in `ORDER BY` order.

Without a suitable index, a `Sort` node appears below `GroupAggregate`:

```
GroupAggregate
  Group Key: customer_id
  -> Sort
        Sort Key: customer_id
        Sort Method: external merge  Disk: 25480kB
        -> Seq Scan on orders
```

**Oracle**

| Operation | Meaning |
|-----------|---------|
| `SORT GROUP BY` | Sort the input, then aggregate; output sorted |
| `SORT GROUP BY NOSORT` | Input already sorted (from an index); aggregate without sorting |
| `SORT GROUP BY ROLLUP` | Sort-based aggregation for `ROLLUP` |

### Sorting cost

```
Sort in memory:   O(n log n) CPU
Sort on disk:     write sorted runs to disk ──► merge them back      several passes over the data
                  (PostgreSQL "external merge", Oracle one-pass / multi-pass)
```

A sort spills when the input exceeds `work_mem` (PostgreSQL) or the PGA work area (Oracle). Unlike hash aggregation, a sort's memory need grows with the **number of input rows**, not the number of groups.

PostgreSQL 13+ also has **Incremental Sort**: if the input is already sorted by a prefix of the required keys, only rows within each prefix group are sorted.

## 5. Choosing Between Hash and Sort

| Situation | Better choice |
|-----------|---------------|
| Few groups, unsorted input | Hash |
| Input already sorted by the group key (index, merge join output) | Sort-based, with no sort step |
| Output must be sorted by the group key anyway | Sort-based (hash would need a sort afterwards) |
| Very many groups, little memory | Sort-based: external sorts degrade more gracefully |
| `LIMIT` on grouped output in key order | Sort-based from an index: can stop early |

### DISTINCT is an aggregation

`SELECT DISTINCT` and `UNION` (without `ALL`) remove duplicates the same two ways: `HashAggregate` / `HASH UNIQUE`, or `Unique` over a `Sort` / `SORT UNIQUE`. The same memory and ordering rules apply.

### COUNT(DISTINCT ...) is expensive

```sql
SELECT order_date, COUNT(DISTINCT customer_id)
FROM orders
GROUP BY order_date;
```

Each group must track every distinct value it has seen, not just a running total. PostgreSQL evaluates `DISTINCT` inside an aggregate by sorting that aggregate's input, which can dominate the query. Rewriting it as two levels of grouping often lets the planner hash instead:

```sql
SELECT order_date, COUNT(*)
FROM (
    SELECT DISTINCT order_date, customer_id
    FROM orders
) d
GROUP BY order_date;
```

For large data where an exact count is not required, approximate distinct counts are far cheaper (Section 10).

### Conditional aggregation in one pass

Several filtered totals can be computed in a single scan instead of one query each:

```sql
-- PostgreSQL: FILTER clause
SELECT order_date,
       COUNT(*)                                     AS all_orders,
       COUNT(*) FILTER (WHERE status = 'CANCELLED') AS cancelled,
       SUM(total_amount) FILTER (WHERE status = 'SHIPPED') AS shipped_revenue
FROM orders
GROUP BY order_date;

-- Oracle (and PostgreSQL): CASE inside the aggregate
SELECT order_date,
       COUNT(*)                                              AS all_orders,
       COUNT(CASE WHEN status = 'CANCELLED' THEN 1 END)      AS cancelled,
       SUM(CASE WHEN status = 'SHIPPED' THEN total_amount END) AS shipped_revenue
FROM orders
GROUP BY order_date;
```

## 6. Window Functions

A **window function** computes a value over a set of rows related to the current row, **without collapsing them**. `GROUP BY` returns one row per group; a window function returns every input row with an extra computed column.

```
GROUP BY department_id                    AVG(salary) OVER (PARTITION BY department_id)

dept │ avg                                emp │ dept │ salary │ dept_avg
─────┼────────                            ────┼──────┼────────┼─────────
   1 │ 64,980                               1 │    1 │ 31,000 │ 64,980
   2 │ 65,010                               2 │    1 │ 72,500 │ 64,980
 ...                                       ...│    1 │    ... │ 64,980
                                           51 │    2 │ 48,000 │ 65,010
50 rows                                    1,000,000 rows
```

### The parts of a window

```sql
function(...) OVER (
    PARTITION BY ...      -- which rows form each window (like GROUP BY, but rows are kept)
    ORDER BY ...          -- order of rows within the partition
    ROWS | RANGE | GROUPS BETWEEN ... AND ...   -- the frame: which rows feed the function
)
```

| Part | Effect | Example |
|------|--------|---------|
| `PARTITION BY` | Splits rows into independent groups | Per department |
| `ORDER BY` | Orders rows inside each partition | By hire date |
| Frame | Selects the subset of the partition used for the current row | Last 3 rows; all rows up to this one |

### Common functions

| Category | Functions | Needs `ORDER BY` |
|----------|-----------|:----------------:|
| Ranking | `ROW_NUMBER`, `RANK`, `DENSE_RANK`, `NTILE` | Yes |
| Offset | `LAG`, `LEAD`, `FIRST_VALUE`, `LAST_VALUE` | Yes |
| Aggregate | `SUM`, `AVG`, `COUNT`, `MIN`, `MAX` | Optional |

### Typical uses

```sql
-- Running total of revenue by date
SELECT order_date, daily_revenue,
       SUM(daily_revenue) OVER (ORDER BY order_date) AS running_total
FROM (SELECT order_date, SUM(total_amount) AS daily_revenue
      FROM orders GROUP BY order_date) d;

-- Each employee's salary compared with the department average
SELECT employee_id, department_id, salary,
       salary - AVG(salary) OVER (PARTITION BY department_id) AS diff_from_avg
FROM employees;

-- Latest 3 orders per customer
SELECT * FROM (
    SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date DESC) AS rn
    FROM orders o
) t
WHERE rn <= 3;
```

### The default frame trap

When a window has `ORDER BY` but no explicit frame, the default frame is:

```
RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
```

`RANGE` treats rows with **equal** `ORDER BY` values (peers) as one unit. A running total ordered by a non-unique column jumps by the whole tie group at once:

```
order_date │ amount │ SUM(amount) OVER (ORDER BY order_date)
───────────┼────────┼───────────────────────────────────────
2026-01-01 │    100 │ 100
2026-01-02 │     50 │ 250    ◄ both 01-02 rows show 250,
2026-01-02 │    100 │ 250    ◄ not 150 then 250
2026-01-03 │     70 │ 320
```

Use `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` for a row-by-row running total, and add a unique tie-breaker to `ORDER BY` if the order must be deterministic. `ROWS` frames are also cheaper to compute, because peers need not be identified.

## 7. The Execution Cost of Window Functions

### How a window function is executed

```
1. Sort       all input rows by (PARTITION BY columns, ORDER BY columns)
                  │
2. Partition  walk the sorted rows; a partition ends when the PARTITION BY key changes
                  │
3. Compute    for each row, evaluate the function over its frame
                  │
4. Emit       every row, with the computed value
```

For the example from the introduction:

```sql
SELECT department_id,
       AVG(salary) OVER (PARTITION BY department_id)
FROM employees;
```

**PostgreSQL**

```
WindowAgg  (actual time=310.2..612.8 rows=1000000 loops=1)
  -> Sort  (actual time=310.1..402.5 rows=1000000 loops=1)
        Sort Key: department_id
        Sort Method: external merge  Disk: 25432kB
        -> Seq Scan on employees  (actual rows=1000000 loops=1)
```

**Oracle**

```
| Id | Operation          | Name      | Rows  |
|  0 | SELECT STATEMENT   |           | 1000K |
|  1 |  WINDOW SORT       |           | 1000K |
|  2 |   TABLE ACCESS FULL| EMPLOYEES | 1000K |
```

### Where the cost comes from

| Cost | Detail |
|------|--------|
| **Sorting all rows** | `O(n log n)` over the whole input, even though only 50 averages exist. Often the largest cost; spills to disk for large inputs |
| **Buffering partitions** | `AVG` over the whole partition cannot be emitted until the partition's last row is read, so each partition (here ~20,000 rows) is held in memory, spilling to disk if too large |
| **Frame evaluation** | Cheap for whole-partition aggregates and running totals; potentially expensive for sliding frames with some functions |
| **Every row is returned** | 1,000,000 output rows, against 50 for a `GROUP BY` |

### Frame evaluation cost

```
whole partition:  SUM over the partition once, reuse for every row        O(n)
running total:    add each new row to the previous total                  O(n)
sliding frame:    ROWS BETWEEN 99 PRECEDING AND CURRENT ROW
                    SUM:  add the new row, subtract the row leaving        O(n)
                    MAX:  the row leaving may have been the max ──► rescan  up to O(n × frame size)
```

PostgreSQL uses a *moving-aggregate* mode (inverse transition functions) for functions such as `SUM` and `COUNT`, so sliding frames stay linear. `MIN` and `MAX` have no inverse and may recompute over the frame. Oracle optimises frame evaluation internally in a similar way.

### Several windows in one query

Each **distinct** combination of `PARTITION BY` and `ORDER BY` needs its own sort:

```sql
SELECT employee_id,
       AVG(salary)  OVER (PARTITION BY department_id)                    AS a,   -- sort 1
       RANK()       OVER (PARTITION BY department_id ORDER BY salary)    AS b,   -- sort 2
       ROW_NUMBER() OVER (ORDER BY hire_date)                            AS c    -- sort 3
FROM employees;
```

Windows with the same partitioning and compatible ordering share one sort. Where possible, give related windows the same definition, and name it once:

```sql
SELECT employee_id,
       RANK()      OVER w AS salary_rank,
       AVG(salary) OVER w AS running_avg
FROM employees
WINDOW w AS (PARTITION BY department_id ORDER BY salary);
```

The `WINDOW` clause is supported by PostgreSQL and by Oracle 21c+.

### Reducing the cost

**1. Avoid the sort with an index.** An index on the partition and order columns delivers rows already sorted:

```sql
CREATE INDEX idx_emp_dept_salary ON employees (department_id, salary);
```

```
PostgreSQL                                       Oracle
WindowAgg                                        WINDOW NOSORT
  -> Index Scan using idx_emp_dept_salary          INDEX FULL SCAN  IDX_EMP_DEPT_SALARY
```

For a full-table window, the index is useful only if reading the table in index order is cheap: an index-only scan, or good clustering (Chapter 13, Section 8). Otherwise a sequential scan plus sort may still win.

**2. Aggregate first when the result per group is all that is needed.** If the query only needs each department's average next to each employee, a `GROUP BY` plus join can be cheaper than sorting a million rows:

```sql
SELECT e.employee_id, e.department_id, d.avg_salary
FROM employees e
JOIN (SELECT department_id, AVG(salary) AS avg_salary
      FROM employees GROUP BY department_id) d
  ON d.department_id = e.department_id;
```

```
Window version:    sort 1,000,000 rows ──► WindowAgg
Aggregate + join:  HashAggregate (50 groups) ──► hash join with 1,000,000 rows, no sort
```

The aggregate version reads the table twice but needs no sort and almost no memory. Measure both: on large tables it often wins, while the window version reads the table only once.

**3. Filter before the window.** A filter applied outside the window cannot be pushed below it unless it is on the `PARTITION BY` columns (Chapter 01, Section 7). Put filters in the inner query whenever the meaning allows:

```sql
-- Sorts all departments, then discards most
SELECT * FROM (
    SELECT e.*, RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS r
    FROM employees e
) t
WHERE department_id IN (3, 7) AND r <= 5;
```

Both databases push `department_id IN (3, 7)` into the inner query here, because it is a `PARTITION BY` column. A filter on `hire_date` in the same position would not be pushed, because it would change which rows are ranked.

**4. Top-N per group: let the database stop early.**

```sql
SELECT * FROM (
    SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date DESC) AS rn
    FROM orders o
) t
WHERE rn <= 3;
```

| | Optimisation |
|---|---|
| Oracle | `WINDOW SORT PUSHED RANK`: the sort keeps only the top N rows per partition instead of sorting everything |
| PostgreSQL 15+ | A **run condition** on the `WindowAgg` (`Run Condition: (row_number() OVER (?) <= 3)`) stops evaluating the window function once the condition can no longer be true |

When only a few groups are needed, a lateral join with `LIMIT` that uses an index per group avoids the window entirely:

```sql
-- PostgreSQL (Oracle 12c+ supports CROSS APPLY / LATERAL similarly)
SELECT c.customer_id, o.*
FROM customers c
CROSS JOIN LATERAL (
    SELECT * FROM orders o
    WHERE o.customer_id = c.customer_id
    ORDER BY o.order_date DESC
    LIMIT 3
) o
WHERE c.country = 'FR';
```

With an index on `(customer_id, order_date)`, each customer costs one short index scan (Chapter 13, Section 9).

**5. Give large sorts enough memory**, per query, as for hash aggregation (Section 3).

## 8. Incremental Aggregation

**Incremental aggregation** updates an aggregate as new data arrives, instead of recomputing it from all the data. Chapter 07 covered incremental materialised views (Section 5) and watermark-based summary tables (Section 7). This section covers the property that makes any aggregate incremental, and common patterns.

### Mergeable state

An aggregate can be maintained incrementally if its **state** can be updated with new rows and combined with other states.

| Aggregate | State to keep | Update with new row `x` | Merge two states |
|-----------|---------------|-------------------------|------------------|
| `COUNT` | count | `count + 1` | add |
| `SUM` | sum | `sum + x` | add |
| `AVG` | sum, count | both | add both, then divide |
| `MIN` / `MAX` | current min / max | compare | compare |
| Variance | count, sum, sum of squares | all three | add all three |
| `COUNT(DISTINCT)` | set of all values seen | add to set | union (large) |
| Approximate distinct | HyperLogLog sketch (Section 10) | update sketch | merge sketches (small) |
| Median, percentiles | all values (exact) or a digest (approximate) | insert | merge digests (approximate only) |

Store the **state**, not the final value. An average stored as a single number cannot be updated or combined correctly; a sum and a count can (Chapter 07, Section 6).

`MIN` and `MAX` are incremental for inserts only. When the current minimum is deleted, the group must be recomputed.

### Time-bucketed aggregation

A common pattern for event and order data is to aggregate into small time buckets as data arrives, then combine buckets for any larger period:

```
raw orders ──► per-minute buckets ──► per-hour ──► per-day
              (updated continuously)  (combined from minutes)

"Revenue in the last 24 hours" = sum of 1,440 minute buckets, not a scan of every order
```

```sql
-- PostgreSQL: add this batch of orders into minute buckets
INSERT INTO revenue_by_minute AS r (bucket, order_count, revenue)
SELECT date_trunc('minute', created_at), COUNT(*), SUM(total_amount)
FROM orders
WHERE order_id > :last_processed_id AND order_id <= :batch_end_id
GROUP BY 1
ON CONFLICT (bucket) DO UPDATE
SET order_count = r.order_count + EXCLUDED.order_count,
    revenue     = r.revenue     + EXCLUDED.revenue;
```

Oracle uses `MERGE` with `TRUNC(created_at, 'MI')` for the same purpose. Both assume a `created_at` timestamp column.

### Running totals in queries

A running total over ordered data is itself incremental: each row adds to the previous value. A `ROWS`-framed window computes it in one pass (Section 6). Storing cumulative totals in a table is rarely worth it, because a correction to an early row changes every later value.

## 9. Precomputed Aggregates

Precomputing stores aggregates ahead of time so queries read the stored results. Chapter 07 covered the techniques in full: materialised views and Oracle query rewrite (Sections 3 and 4), choosing the grain and handling additive, semi-additive and non-additive measures (Section 6), and summary tables (Section 7).

The aggregation-specific points to remember:

| Point | Reason |
|-------|--------|
| Choose the finest grain that is still small | Coarser totals can be derived from finer ones, never the reverse |
| Store mergeable state (`SUM` and `COUNT`, sketches) | Allows correct roll-ups and incremental updates (Section 8) |
| Use `ROLLUP`, `CUBE` or `GROUPING SETS` to build several grains in one pass | One scan instead of one per grain |
| Non-additive measures need their own precomputation, or approximate sketches | Distinct counts cannot be summed across groups |

```sql
-- Both databases: daily, monthly and total revenue in one pass
SELECT EXTRACT(YEAR FROM order_date)  AS yr,
       EXTRACT(MONTH FROM order_date) AS mon,
       order_date,
       SUM(total_amount)              AS revenue
FROM orders
GROUP BY ROLLUP (EXTRACT(YEAR FROM order_date),
                 EXTRACT(MONTH FROM order_date),
                 order_date);
```

PostgreSQL executes grouping sets with `MixedAggregate` or `GroupAggregate` nodes; Oracle with `SORT GROUP BY ROLLUP` or `HASH GROUP BY` variants.

## 10. Approximate Aggregation

Some aggregates are expensive to compute exactly because they need to remember every value: distinct counts, medians, percentiles, top-N. At large scale, an answer within 1–2% is often just as useful and orders of magnitude cheaper.

| Exact | Cost | Approximate alternative |
|-------|------|------------------------|
| `COUNT(DISTINCT x)` | Memory proportional to distinct values; sort or large hash | HyperLogLog sketch: a few KB, error around 1–2% |
| `PERCENTILE_CONT(0.95)`, `MEDIAN` | Sort of every value in the group | Approximate percentile digests |
| Top N most frequent values | Count of every distinct value | Approximate top-N |
| `COUNT(*)` on a huge table | Full scan | Table statistics or sampling |

### HyperLogLog in brief

HyperLogLog estimates the number of distinct values from the hashes of the values. In a random hash, a run of `k` leading zero bits occurs about once in every `2^k` values, so the longest run seen indicates roughly how many distinct values there were. Using many registers, each tracking a subset of the hashes, and averaging them gives a stable estimate.

```
value ──► hash ──► first bits choose a register; leading zeros of the rest are counted
                   each register keeps the maximum seen

registers: [3][5][2][7][4][3] ...   (thousands of small registers, a few KB in total)
estimate   ≈ function of the register values
error      ≈ 1.04 / √(number of registers)        e.g. ~0.8% with 16,384 registers
```

Two important properties: the sketch has a **fixed size** no matter how many values it sees, and two sketches can be **merged**, so daily sketches can be combined into a monthly distinct count without double counting (Section 8).

### Oracle

Oracle provides approximate functions natively:

| Function | Version | Purpose |
|----------|---------|---------|
| `APPROX_COUNT_DISTINCT(x)` | 12c | Approximate distinct count |
| `APPROX_COUNT_DISTINCT_DETAIL` / `APPROX_COUNT_DISTINCT_AGG` / `TO_APPROX_COUNT_DISTINCT` | 12.2 | Store sketches, merge them, then read the estimate |
| `APPROX_PERCENTILE(p)`, `APPROX_MEDIAN` | 12.2 | Approximate percentiles and median |
| `APPROX_COUNT`, `APPROX_SUM`, `APPROX_RANK` | 18c | Approximate top-N queries |

```sql
SELECT order_date, APPROX_COUNT_DISTINCT(customer_id) AS approx_customers
FROM orders
GROUP BY order_date;
```

Existing exact queries can be switched to approximate evaluation without code changes:

```sql
ALTER SESSION SET approx_for_count_distinct = TRUE;   -- COUNT(DISTINCT) becomes approximate
ALTER SESSION SET approx_for_percentile     = 'ALL';  -- percentile functions become approximate
ALTER SESSION SET approx_for_aggregation    = TRUE;   -- both
```

### PostgreSQL

Core PostgreSQL has no approximate aggregate functions. Common options:

| Need | Option |
|------|--------|
| Approximate distinct counts, mergeable | `hll` extension (HyperLogLog data type and aggregates) |
| Approximate percentiles, mergeable | `tdigest` extension |
| Estimate over a sample | `TABLESAMPLE SYSTEM (1)` (block sample, fast) or `TABLESAMPLE BERNOULLI (1)` (row sample, more uniform), version 9.5+ |
| Row count of a large table | `SELECT reltuples FROM pg_class WHERE relname = 'orders'` (from the last `ANALYZE` or `VACUUM`) |

```sql
-- hll extension: store a sketch per day, merge for any period
CREATE EXTENSION hll;

CREATE TABLE daily_customer_sketch AS
SELECT order_date, hll_add_agg(hll_hash_bigint(customer_id)) AS customers
FROM orders
GROUP BY order_date;

SELECT hll_cardinality(hll_union_agg(customers))
FROM daily_customer_sketch
WHERE order_date >= DATE '2026-01-01' AND order_date < DATE '2026-02-01';
```

### Sampling

Both databases can aggregate a random sample instead of the full table:

```sql
-- PostgreSQL: about 1% of blocks
SELECT AVG(total_amount) FROM orders TABLESAMPLE SYSTEM (1);

-- Oracle: about 1% of rows; SAMPLE BLOCK (1) samples blocks instead
SELECT AVG(total_amount) FROM orders SAMPLE (1);
```

Sampling gives good estimates for averages and proportions over large, evenly distributed data. It is unreliable for rare values, for sums that must be scaled up, and for distinct counts, which do not scale linearly with sample size.

### When approximation is appropriate

| Appropriate | Not appropriate |
|-------------|-----------------|
| Dashboards, trends, monitoring | Billing, payroll, financial reporting |
| Unique visitor counts, reach estimates | Inventory and stock levels |
| Exploratory analysis | Anything audited or legally reported |
| Percentile latencies over large logs | Small datasets, where exact is already cheap |

State the approximation where results are shown, so readers do not treat estimates as exact figures.

## 11. Aggregation at Scale

Beyond choosing the algorithm, a few techniques apply to any large aggregation.

### Parallel aggregation

Both databases split large aggregations into two phases:

```
            Final aggregate      (combine partial results: sum of sums, sum of counts)
                   │
     ┌─────────────┼─────────────┐
     ▼             ▼             ▼
  Partial       Partial       Partial          (each worker aggregates its share of rows)
  aggregate     aggregate     aggregate
     │             │             │
  rows 1/3      rows 2/3      rows 3/3
```

```
PostgreSQL                                   Oracle
Finalize HashAggregate                       PX COORDINATOR
  -> Gather                                    PX SEND QC
        Workers Planned: 2                       HASH GROUP BY         (final)
        -> Partial HashAggregate                   PX RECEIVE
              -> Parallel Seq Scan on orders         PX SEND HASH
                                                       HASH GROUP BY   (partial)
                                                         PX BLOCK ITERATOR
                                                           TABLE ACCESS FULL ORDERS
```

Only aggregates with mergeable state (Section 8) can be split this way. Exact `COUNT(DISTINCT)` limits parallel aggregation, which is another reason to prefer approximate sketches at scale.

### Partition-wise aggregation

When the `GROUP BY` includes the partition key, each partition can be aggregated independently (Chapter 06, Section 9):

- **PostgreSQL**: `enable_partitionwise_aggregate = on` (default off).
- **Oracle**: applied automatically where possible.

### Aggregate before joining

Aggregating the large side before a join reduces the rows the join must process (Chapter 03, Section 12):

```sql
-- Join 3,000,000 item rows, then aggregate
SELECT p.category, SUM(oi.quantity)
FROM order_items oi JOIN products p ON p.product_id = oi.product_id
GROUP BY p.category;

-- Aggregate items per product (10,000 rows), then join
SELECT p.category, SUM(i.qty)
FROM (SELECT product_id, SUM(quantity) AS qty FROM order_items GROUP BY product_id) i
JOIN products p ON p.product_id = i.product_id
GROUP BY p.category;
```

Oracle can perform this transformation automatically (*group-by placement*); PostgreSQL generally needs it written explicitly.

### Read less

Aggregation speed often depends more on how much data is read than on the aggregation itself:

| Technique | Reference |
|-----------|-----------|
| Covering index for the grouped and aggregated columns (index-only scan) | Chapter 13, Section 6 |
| Partition pruning to the needed time range | Chapter 06, Section 8 |
| Column storage or in-memory columnar format for analytics | Chapter 05, Section 11 |
| Precomputed aggregates | Section 9 |

        │
        ▼

        │
        ▼

        ▼

## 14. Short Summary

- `GROUP BY` runs as hash aggregation (memory per group, unordered output) or sort aggregation (sorted output, free when input is already ordered). The optimizer picks by estimated group count, memory and required order.
- Both spill to disk when memory runs out. Check for spills in the plan and fix them with better group estimates or more memory for the query, not a larger global setting.
- `COUNT(DISTINCT)` must remember every value per group. Rewrite it as two levels of grouping, or use approximate distinct counts where exactness is not required.
- Window functions keep every row and usually sort the whole input by their partition and order keys. Each distinct window definition can add another sort, and whole-partition aggregates buffer entire partitions.
- Reduce window cost by unifying window definitions, using indexes that deliver sorted input, aggregating and joining instead of windowing when only a per-group value is needed, filtering before the window, and using top-N optimisations or `LATERAL` with `LIMIT`.
- The default window frame with `ORDER BY` is `RANGE`, which groups ties; use `ROWS` for row-by-row running totals.
- Incremental and precomputed aggregation depend on mergeable state: store sums and counts, not averages; store sketches, not distinct counts.
- Approximate aggregation (HyperLogLog, percentile digests, sampling) gives answers within a small error at a fraction of the cost. Oracle provides it natively; PostgreSQL through extensions.
