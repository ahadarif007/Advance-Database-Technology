# Chapter 16: Query Anti-Patterns

An **anti-pattern** is a way of writing a query that looks reasonable, returns the right answer, and still performs badly. It usually works in development, where tables are small, and only causes problems in production, where they are large.

The same few anti-patterns account for most slow application queries. This chapter shows how to recognise each one in the SQL text and in the execution plan, why it is slow, and what to write instead, for **Oracle** and **PostgreSQL**. Earlier chapters explain some of the underlying mechanics in depth; this chapter focuses on recognising the patterns and refers back for detail.

## 1. What Makes a Query an Anti-Pattern

A well-written query does work in proportion to the **rows it returns**. An anti-pattern does work in proportion to something larger: the size of the table, the number of columns, or the number of times the application calls the database.

```
Rows returned:       20
Work done by a good query:          ██                         ~20 rows read
Work done by an anti-pattern:       ██████████████████████...  1,000,000 rows read,
                                                               or 21 round trips,
                                                               or 2 KB per row instead of 40 bytes
```

Because this extra work grows with data volume, the query gets slower every month without any code change.

| Anti-pattern | Extra work grows with | Section |
|--------------|----------------------|---------|
| `SELECT *` | Number and size of columns | 3 |
| `WHERE function(column) = ...` | Table size (index cannot be used) | 4 |
| `LIKE '%abc'` | Table size (index cannot be used) | 5 |
| N+1 queries | Number of rows displayed (one query each) | 6 |
| `ORDER BY` an unindexed column | Table size (everything is read and sorted) | 7 |
| Very large `IN` lists | List length (parsing, plan cache, probes) | 8 |
| Unnecessary correlated subqueries | Number of outer rows (one subquery each) | 9 |

Related patterns are covered in other chapters: `NOT IN` with nullable subqueries (Chapter 01, Section 9), large `OFFSET` pagination and `OR` across different columns (Chapter 01, Section 11), and row-by-row writes (Chapter 12).

## 3. SELECT *

`SELECT *` returns every column of every table in the query. Applications rarely need all of them.

```sql
-- Product list page: shows name and price only
SELECT * FROM products ORDER BY name;
```

### Why it is slow

| Cost | Effect |
|------|--------|
| More data transferred | 10,000 products × 2 KB description = 20 MB, instead of about 400 KB for name and price |
| No index-only access | The database must visit the table even when an index holds every column actually needed |
| Wider sorts and hashes | Every column is carried through `ORDER BY`, `GROUP BY` and hash joins, so they spill to disk sooner |
| Large values fetched | PostgreSQL must read and decompress TOASTed values; Oracle fetches LOBs, often with extra round trips |
| Fragile code | A new column changes the result shape. Views defined with `*` are expanded when created and do not pick up new columns |

### Index-only access in practice

```sql
CREATE INDEX idx_orders_cust_date_amt ON orders (customer_id, order_date, total_amount);

SELECT order_date, total_amount FROM orders WHERE customer_id = 42;   -- columns listed
SELECT *                        FROM orders WHERE customer_id = 42;   -- all columns
```

```
Columns listed (PostgreSQL)
Index Only Scan using idx_orders_cust_date_amt on orders  (actual rows=11 loops=1)
  Index Cond: (customer_id = 42)
  Heap Fetches: 0
  Buffers: shared hit=4

SELECT *
Index Scan using idx_orders_customer on orders  (actual rows=11 loops=1)
  Index Cond: (customer_id = 42)
  Buffers: shared hit=14
```

| Field | Meaning |
|-------|---------|
| `Index Only Scan` | All needed columns came from the index |
| `Heap Fetches: 0` | No table pages were visited (Chapter 02, Section 7) |
| `Buffers: shared hit` | Pages read: 4 instead of 14 |

In Oracle, the same difference shows as an `INDEX RANGE SCAN` with no `TABLE ACCESS BY INDEX ROWID` step above it.

### Seeing which columns a plan carries

```sql
-- PostgreSQL: "Output:" lines list the columns at each node
EXPLAIN (VERBOSE) SELECT * FROM orders WHERE customer_id = 42;

-- Oracle: the Column Projection section
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'TYPICAL +PROJECTION'));
```

### When `*` is fine

| Use | Why it is acceptable |
|-----|----------------------|
| `EXISTS (SELECT * FROM ...)` | No columns are returned; the optimizer ignores the list |
| `COUNT(*)` | Counts rows; it does not read all columns |
| Ad hoc queries in a console | Not part of application code |

ORMs often generate the equivalent of `SELECT *` by loading whole entities. Use projections (DTO queries, `only()`/`values()` in Django, `load_only()` in SQLAlchemy) for list pages and reports.

## 4. Functions on Indexed Columns

An index stores column **values** in order. When a query wraps the column in a function, it searches for the function's **result**, which the index does not contain. The database must compute the function for every row.

```sql
-- Orders for March 2024
SELECT * FROM orders WHERE TO_CHAR(order_date, 'YYYY-MM') = '2024-03';
```

```
PostgreSQL
Seq Scan on orders  (actual time=0.02..402.6 rows=15500 loops=1)
  Filter: (to_char((order_date)::timestamp with time zone, 'YYYY-MM'::text) = '2024-03'::text)
  Rows Removed by Filter: 984500

Oracle
|* 1 |  TABLE ACCESS FULL | ORDERS |
   1 - filter(TO_CHAR(INTERNAL_FUNCTION("ORDER_DATE"),'YYYY-MM')='2024-03')
```

| Signal | Meaning |
|--------|---------|
| Full scan with a `Filter` / `filter()` that contains a function on the column | The index on the column could not be used |
| `Rows Removed by Filter` close to the table size | Almost all the work was wasted |
| `INTERNAL_FUNCTION` (Oracle) | A conversion was applied to the column |

### Fix 1: rewrite as a range on the raw column

```sql
SELECT * FROM orders
WHERE order_date >= DATE '2024-03-01'
  AND order_date <  DATE '2024-04-01';
```

```
Bitmap Heap Scan on orders  (actual time=1.9..8.7 rows=15500 loops=1)
  Recheck Cond: ((order_date >= '2024-03-01'::date) AND (order_date < '2024-04-01'::date))
  ->  Bitmap Index Scan on idx_orders_date  (actual rows=15500 loops=1)
```

Functions on the **other side** of the comparison are fine, because they are computed once: `order_date >= CURRENT_DATE - 7` uses the index.

### Fix 2: index the expression

When the expression cannot be rewritten, such as a case-insensitive search, index it (Chapter 02, Section 10):

```sql
CREATE INDEX idx_customers_upper_email ON customers ((UPPER(email)));   -- PostgreSQL
CREATE INDEX idx_customers_upper_email ON customers (UPPER(email));     -- Oracle

SELECT * FROM customers WHERE UPPER(email) = 'C42@MAIL.COM';
```

For case-insensitive comparison without functions, PostgreSQL offers the `citext` type and nondeterministic ICU collations (12+), and Oracle offers case-insensitive collations such as `BINARY_CI` (12.2+).

### Common forms

| Not indexable | Indexable |
|---------------|-----------|
| `TO_CHAR(order_date, 'YYYY-MM') = '2024-03'` | Range on `order_date` |
| `TRUNC(order_date) = DATE '2024-03-01'` (Oracle) | `order_date >= DATE '2024-03-01' AND order_date < DATE '2024-03-02'` |
| `order_date::date = '2024-03-01'` on a timestamp (PostgreSQL) | Range on the timestamp |
| `UPPER(email) = ...` | Expression index on `UPPER(email)` |
| `COALESCE(status, 'NEW') = 'NEW'` | `(status = 'NEW' OR status IS NULL)` |
| `total_amount + 10 > 110` | `total_amount > 100` |
| `customer_id = 42.0` (PostgreSQL: column cast to `numeric`) | `customer_id = 42` |
| `phone = 12345` on a `VARCHAR2` (Oracle: `TO_NUMBER("PHONE")`) | `phone = '12345'` |

The last two are **implicit conversions**: the database converts the column to match the type of the value. The query text has no visible function, so these are easy to miss. Bind variables of the wrong type from application code cause the same problem, for example a Java `String` bound against a `NUMBER` column.

## 5. Leading-Wildcard LIKE

A B-tree index is sorted by the leading characters of the value, like a phone book sorted by surname.

```
LIKE 'Cust%'      starts-with: jump to "Cust", read forward      index range scan
LIKE '%4242'      ends-with:   could be anywhere in the index     full scan
LIKE '%4242%'     contains:    could be anywhere in the index     full scan
```

```sql
SELECT * FROM customers WHERE name LIKE '%4242%';
```

```
Seq Scan on customers  (actual time=0.03..28.4 rows=20 loops=1)
  Filter: (name ~~ '%4242%'::text)
  Rows Removed by Filter: 99980
```

`~~` is PostgreSQL's internal name for `LIKE`. On 100,000 rows this takes milliseconds; on 50 million it takes seconds, on every search.

Note that `LIKE 'prefix%'` can use a normal B-tree in Oracle, but in PostgreSQL only under the `C` collation or with a `text_pattern_ops` index (Chapter 02, Section 2).

### Choose the fix by what users search for

| Search need | Oracle | PostgreSQL |
|-------------|--------|------------|
| Starts with | B-tree index | B-tree with `text_pattern_ops` |
| Ends with a known part (for example an email domain) | Index a virtual column holding that part | Index an expression or generated column holding that part |
| Contains any substring | Oracle Text `CONTEXT` index with the `SUBSTRING_INDEX` wordlist option | `pg_trgm` GIN index |
| Contains words (search box) | Oracle Text, `CONTAINS` | Full-text search: `tsvector`, GIN index, `@@` |

### Substring search in PostgreSQL: trigram index

A **trigram** is a group of three consecutive characters. `pg_trgm` indexes every trigram of every value, so a search for `%4242%` looks up the trigrams `424` and `242`.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_customers_name_trgm ON customers USING gin (name gin_trgm_ops);

SELECT * FROM customers WHERE name LIKE '%4242%';     -- also ILIKE and regular expressions
```

```
Bitmap Heap Scan on customers  (actual time=0.15..0.21 rows=20 loops=1)
  Recheck Cond: (name ~~ '%4242%'::text)
  ->  Bitmap Index Scan on idx_customers_name_trgm  (actual rows=20 loops=1)
```

Search strings shorter than three characters produce no full trigram and fall back to scanning the whole index. A trigram index is also several times larger than a B-tree and slows writes (Chapter 12, Section 9).

### Ends-with: store the searched part

```sql
-- Find customers by email domain: WHERE email LIKE '%@example.com'

-- PostgreSQL 12+
ALTER TABLE customers ADD COLUMN email_domain TEXT
    GENERATED ALWAYS AS (split_part(email, '@', 2)) STORED;
CREATE INDEX idx_customers_domain ON customers (email_domain);

-- Oracle
ALTER TABLE customers ADD (email_domain AS (SUBSTR(email, INSTR(email, '@') + 1)));
CREATE INDEX idx_customers_domain ON customers (email_domain);

SELECT * FROM customers WHERE email_domain = 'example.com';
```

A search on a fixed suffix is usually a search on a separate piece of data. Giving that piece its own column turns the wildcard search into an equality lookup.

## 6. N+1 Queries

The **N+1 problem** is one query to fetch a list, followed by one more query for **each** item in the list.

```python
orders = db.query("SELECT order_id, customer_id, total_amount FROM orders "
                  "WHERE status = 'PENDING' ORDER BY order_date DESC "
                  "FETCH FIRST 50 ROWS ONLY")                    # 1 query
for o in orders:
    o.customer = db.query("SELECT name FROM customers "
                          "WHERE customer_id = %s", o.customer_id)   # + 50 queries
```

It is most often produced by an ORM loading related objects lazily, the first time code accesses them (`order.customer.name` in a template).

### Why it is slow, and why it is hard to see

```
Timeline for one page (0.5 ms network round trip, 0.1 ms per query in the database)

N+1:   ▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌   51 × 0.6 ms ≈ 31 ms
Join:  ▌                                                     1 × 0.7 ms ≈ 0.7 ms
```

Every individual query is fast, so none appears in a slow-query log. The cost is in the **number of calls**: round trips, parsing, and connection time (Chapter 17, Section 8). A list of 1,000 rows makes 1,001 calls.

### How to detect it

```sql
-- PostgreSQL (pg_stat_statements): very frequent, very fast statements
SELECT calls, round(mean_exec_time::numeric, 3) AS mean_ms, rows, query
FROM pg_stat_statements
ORDER BY calls DESC
LIMIT 10;

-- Oracle
SELECT executions, ROUND(elapsed_time / NULLIF(executions, 0) / 1000, 3) AS mean_ms,
       rows_processed, sql_text
FROM v$sqlstats
ORDER BY executions DESC
FETCH FIRST 10 ROWS ONLY;
```

A statement with far more calls than the request rate, each returning about one row, usually comes from a loop. ORM SQL logging and application tracing (APM) tools show the pattern directly: the same statement repeated with different key values within one request.

### Fix 1: a join

```sql
SELECT o.order_id, o.total_amount, c.name
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE o.status = 'PENDING'
ORDER BY o.order_date DESC
FETCH FIRST 50 ROWS ONLY;
```

### Fix 2: one batch query for the related rows

Useful when the related rows are a one-to-many collection, where a join would repeat the parent columns for every child:

```sql
-- PostgreSQL: one array parameter holding the 50 customer IDs
SELECT customer_id, name FROM customers WHERE customer_id = ANY($1);

-- Oracle: a collection parameter (Section 8)
SELECT customer_id, name FROM customers
WHERE customer_id IN (SELECT column_value FROM TABLE(:ids));
```

Two queries in total, however many rows are displayed.

### In ORMs

| ORM | Join in one query | Batch query per relation |
|-----|-------------------|--------------------------|
| JPA / Hibernate | `JOIN FETCH`, entity graphs | `@BatchSize`, `hibernate.default_batch_fetch_size` |
| Django | `select_related()` | `prefetch_related()` |
| SQLAlchemy | `joinedload()` | `selectinload()` |
| Rails (Active Record) | `eager_load` | `preload` (`includes` chooses) |

Avoid join-fetching **two** one-to-many collections in one query. The result is their Cartesian product: 10 items × 10 payments returns 100 rows per order. Load the second collection with a batch query instead.

## 7. Sorting a Large Table on an Unindexed Column

```sql
SELECT * FROM orders ORDER BY total_amount DESC;
```

Without an index that provides this order, the database must read **every row** and sort them before returning the first one.

Sorting is not a problem in itself. Sorting a few thousand rows, a filtered result, or a nightly report is normal and often cheaper than maintaining another index. The pattern becomes a problem when a **frequent** query sorts a **large** input to return only a few rows, or when the sort spills to disk. An index is one fix, but not always the right one: each index has write and storage costs (Chapter 02), and a better filter or a precomputed result may serve the query as well.

### With LIMIT: still reads everything

```sql
-- Top 20 orders by amount
SELECT * FROM orders ORDER BY total_amount DESC FETCH FIRST 20 ROWS ONLY;
```

```
PostgreSQL
Limit  (actual time=298.1..298.1 rows=20 loops=1)
  ->  Sort  (actual time=298.1..298.1 rows=20 loops=1)
        Sort Key: total_amount DESC
        Sort Method: top-N heapsort  Memory: 30kB
        ->  Seq Scan on orders  (actual rows=1000000 loops=1)

Oracle
|  1 |  VIEW                    |        |
|* 2 |   WINDOW SORT PUSHED RANK|        |
|  3 |    TABLE ACCESS FULL     | ORDERS |
```

Both databases are smart enough to keep only the best 20 rows in memory (`top-N heapsort`, `WINDOW SORT PUSHED RANK`), but they still read all 1,000,000.

With an index on the sort column, they read 20 index entries and stop:

```sql
CREATE INDEX idx_orders_amount ON orders (total_amount);
```

```
PostgreSQL
Limit  (actual time=0.03..0.06 rows=20 loops=1)
  ->  Index Scan Backward using idx_orders_amount on orders  (actual rows=20 loops=1)

Oracle
|  1 |  VIEW                       |                   |
|* 2 |   WINDOW NOSORT STOPKEY     |                   |
|  3 |    TABLE ACCESS BY INDEX ROWID | ORDERS         |
|  4 |     INDEX FULL SCAN DESCENDING | IDX_ORDERS_AMOUNT |
```

| Field | Meaning |
|-------|---------|
| `Index Scan Backward` / `INDEX FULL SCAN DESCENDING` | Reads the index in reverse order; an ascending index serves `DESC` |
| `WINDOW NOSORT STOPKEY` | No sort; stops after the requested rows |

### Without LIMIT: the sort spills to disk

When the rows to sort do not fit in sort memory, the database writes sorted runs to temporary files and merges them:

```
PostgreSQL
Sort  (actual time=2210.4..2905.3 rows=1000000 loops=1)
  Sort Key: total_amount DESC
  Sort Method: external merge  Disk: 61432kB

Oracle
| Id | Operation          | Name   | Rows  | TempSpc |
|  1 |  SORT ORDER BY     |        | 1000K |     72M |
|  2 |   TABLE ACCESS FULL| ORDERS | 1000K |         |
```

| Signal | Meaning |
|--------|---------|
| `Sort Method: external merge  Disk:` | Sort exceeded `work_mem` (default 4 MB) and used temp files |
| `TempSpc` in the plan; `direct path write temp` waits | Sort exceeded the PGA work area |

`SELECT *` (Section 3) makes this worse: every column is carried through the sort.

### Fixes, in order of preference

| Fix | When it applies |
|-----|-----------------|
| Do not sort | The order is not actually used, for example data passed to another process |
| Filter first | Sort only the rows that will be shown: `WHERE customer_id = 42 ORDER BY order_date` |
| Index matching filter and order | Equality columns first, then the sort column: `(customer_id, order_date)` serves `WHERE customer_id = ? ORDER BY order_date DESC` |
| Keyset pagination | Pages through the index instead of sorting and skipping with `OFFSET` (Chapter 01, Section 11) |
| More memory for that query | Large sorts that are genuinely needed: `SET LOCAL work_mem = '256MB'` (PostgreSQL); `PGA_AGGREGATE_TARGET` (Oracle) |

An index helps when the query needs **the first few rows** in order. For a full export of a large table, reading through the index visits table blocks in random order, and a full scan plus a sort is usually faster.

Mixed directions need a matching index: `ORDER BY customer_id ASC, order_date DESC` needs an index on `(customer_id, order_date DESC)`. PostgreSQL 13+ can also use an index that provides only the first sort column and sort the rest in small groups (`Incremental Sort`).

## 8. Very Large IN Lists

```sql
SELECT * FROM orders WHERE customer_id IN (17, 42, 108, 391, ... 5,000 values ...);
```

Long `IN` lists usually come from application code that fetched IDs in one query, then sends them back in another.

### Why it is slow

| Cost | Oracle | PostgreSQL |
|------|--------|------------|
| Parse and plan time | Grows with list length | Grows with list length |
| Every list length is different SQL text | A new hard parse each time; the shared pool fills with near-duplicate cursors | Separate prepared statements and plans |
| Hard limit | 1,000 expressions per list (ORA-01795) | 65,535 bind parameters per statement |
| Estimates | Each value estimated separately; errors add up | Each value estimated separately; errors add up |

The second row is often the more serious one. With literals, `IN (1,2)` and `IN (1,2,3)` are different statements to the plan cache. Thousands of variants push useful cursors out of Oracle's shared pool and cause latch contention during parsing.

Splitting a list into chunks of 1,000 joined with `OR` to get around ORA-01795 is itself an anti-pattern: it keeps every cost above and adds more.

### Fix 1: do not send the list back

If the IDs came from the database, keep them there:

```sql
-- Instead of: fetch IDs of customers in Paris, then send them back in IN (...)
SELECT o.*
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE c.city = 'Paris';
```

### Fix 2: bind the list as one parameter

One statement text for any list length, parsed once:

```sql
-- PostgreSQL: one array parameter
SELECT * FROM orders WHERE customer_id = ANY($1::bigint[]);
```

```sql
-- Oracle: one collection parameter (bound as SYS.ODCINUMBERLIST or your own TABLE OF NUMBER type)
SELECT /*+ DYNAMIC_SAMPLING(t 2) */ o.*
FROM orders o
WHERE o.customer_id IN (SELECT t.column_value FROM TABLE(:ids) t);
```

Without statistics or sampling, Oracle assumes a collection holds 8,168 rows (for an 8 KB block size), whatever its real size. A hint such as `DYNAMIC_SAMPLING` lets it see the actual count and choose a sensible join.

### Fix 3: very large lists go into a temporary table

For tens of thousands of values, load them and join:

```sql
-- PostgreSQL
CREATE TEMP TABLE tmp_ids (id bigint PRIMARY KEY) ON COMMIT DROP;
COPY tmp_ids FROM STDIN;           -- or a batched INSERT
ANALYZE tmp_ids;                   -- autovacuum never analyzes temporary tables
SELECT o.* FROM orders o JOIN tmp_ids t ON t.id = o.customer_id;
```

```sql
-- Oracle: a global temporary table, created once
CREATE GLOBAL TEMPORARY TABLE tmp_ids (id NUMBER PRIMARY KEY) ON COMMIT DELETE ROWS;
-- per request: array insert into tmp_ids, then join
```

### If literals cannot be avoided

Some frameworks generate `IN (?, ?, ?)` with one bind per value. Padding the list to a few fixed sizes (for example 10, 50, 100, 500, repeating the last value) limits the number of distinct statements. Hibernate does this with `hibernate.query.in_clause_parameter_padding = true`.

## 9. Unnecessary Correlated Subqueries

A correlated subquery refers to the outer query, so it is logically evaluated once per outer row (Chapter 01, Section 8). When the optimizer cannot turn it into a join, it really does run once per row.

Not every correlated subquery is a problem:

| Form | Verdict |
|------|---------|
| `EXISTS` / `NOT EXISTS` | Fine: becomes a semi-join or anti-join |
| Correlated lookup for a small outer set (a page of 20 rows) with an index | Fine |
| Scalar subqueries in the `SELECT` list of a large result | Anti-pattern |
| Several subqueries reading the same table for the same key | Anti-pattern |
| `UPDATE ... SET col = (correlated subquery)` over many rows | Anti-pattern |
| `(SELECT COUNT(*) ...) > 0` | Anti-pattern: use `EXISTS`, which stops at the first match |

### Several scalar subqueries on the same table

```sql
SELECT c.customer_id, c.name,
       (SELECT COUNT(*)          FROM orders o WHERE o.customer_id = c.customer_id) AS order_count,
       (SELECT MAX(order_date)   FROM orders o WHERE o.customer_id = c.customer_id) AS last_order,
       (SELECT SUM(total_amount) FROM orders o WHERE o.customer_id = c.customer_id) AS total_spent
FROM customers c
WHERE c.country = 'UK';
```

```
PostgreSQL
Seq Scan on customers c  (actual time=0.05..2841.3 rows=80000 loops=1)
  Filter: (country = 'UK'::text)
  SubPlan 1
    ->  Aggregate  (actual rows=1 loops=80000)
          ->  Index Only Scan using idx_orders_customer on orders o  (actual rows=10 loops=80000)
  SubPlan 2
    ->  Aggregate  (actual rows=1 loops=80000)
          ->  Index Scan using idx_orders_customer on orders o_1  (actual rows=10 loops=80000)
  SubPlan 3
    ->  Aggregate  (actual rows=1 loops=80000)
          ->  Index Scan using idx_orders_customer on orders o_2  (actual rows=10 loops=80000)
```

| Signal | Meaning |
|--------|---------|
| `SubPlan` with `loops` equal to the outer row count | The subquery ran once per row: 240,000 executions here |
| Oracle: `SORT AGGREGATE` steps above the main plan with `Starts` of 80,000 | The same, in Oracle's layout |

Rewrite as one aggregation and one join:

```sql
SELECT c.customer_id, c.name,
       COALESCE(a.order_count, 0) AS order_count,
       a.last_order, a.total_spent
FROM customers c
LEFT JOIN (SELECT customer_id,
                  COUNT(*)          AS order_count,
                  MAX(order_date)   AS last_order,
                  SUM(total_amount) AS total_spent
           FROM orders
           GROUP BY customer_id) a ON a.customer_id = c.customer_id
WHERE c.country = 'UK';
```

`orders` is read once with a hash aggregate, and joined with a hash join. The `LEFT JOIN` and `COALESCE` keep customers with no orders, as the original did.

### Correlated UPDATE

```sql
-- Updates every product, running the subquery once per product,
-- and sets price to NULL where no staged price exists
UPDATE products p
SET price = (SELECT s.price FROM price_stage s WHERE s.product_id = p.product_id);
```

Use a join-based update instead:

```sql
-- PostgreSQL
UPDATE products p
SET price = s.price
FROM price_stage s
WHERE s.product_id = p.product_id
  AND p.price IS DISTINCT FROM s.price;

-- Oracle (all versions): MERGE
MERGE INTO products p
USING price_stage s ON (s.product_id = p.product_id)
WHEN MATCHED THEN UPDATE SET p.price = s.price
WHERE DECODE(p.price, s.price, 0, 1) = 1;

-- Oracle 23ai: direct joins in UPDATE
UPDATE products p
SET p.price = s.price
FROM price_stage s
WHERE s.product_id = p.product_id;
```

The join form updates only matching rows, never sets missing prices to `NULL`, and lets the optimizer choose a hash join.

### Latest row per group

"Each customer's most recent order" is often written as a correlated `MAX`. A window function does it in one pass:

```sql
SELECT * FROM (
    SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date DESC) AS rn
    FROM orders o
) t
WHERE rn = 1;
```

For a **small** set of customers, a correlated top-1 lookup using an index on `(customer_id, order_date)` is better, because it reads one index entry per customer instead of the whole table: `LATERAL (... ORDER BY order_date DESC FETCH FIRST 1 ROW ONLY)` in PostgreSQL, and `CROSS APPLY` or `LATERAL` in Oracle 12c+. The choice depends on the number of outer rows, as with nested loop versus hash join (Chapter 03, Section 7).

## 10. A Systematic Approach to Finding Anti-Patterns

```
1. Find the statements that use the most total time
        PostgreSQL: pg_stat_statements ORDER BY total_exec_time DESC
        Oracle:     V$SQLSTATS / AWR "SQL ordered by Elapsed Time"
        │
        ▼
2. High call count, tiny mean time, ~1 row per call?
        └── yes ──► N+1 queries: join or batch query                  Section 6
        │
        ▼
3. Many near-identical statements that differ only in list length?
        └── yes ──► large IN lists: join, array/collection bind,
                    temporary table                                   Section 8
        │
        ▼
4. Get the actual plan (Chapter 01, Section 5) and look for:
        │
        ├── full scan, Filter contains a function or conversion
        │       ──► sargable rewrite or expression index              Section 4
        │
        ├── full scan, Filter is LIKE '%...'
        │       ──► trigram / Oracle Text / separate column           Section 5
        │
        ├── Sort over the whole table; external merge / TempSpc
        │       ──► index matching filter and order, filter first     Section 7
        │
        ├── SubPlan loops / FILTER Starts = outer row count
        │       ──► join, aggregate once, window function             Section 9
        │
        └── table access where an index holds all needed columns;
            very wide rows in Output / Projection
                ──► list only the needed columns                      Section 3
        │
        ▼
5. Re-measure with production-sized data
        An anti-pattern hidden by a small test table returns
        as soon as the table grows.
```

## 12. Short Summary

- An anti-pattern does work in proportion to table size, column count or call count, instead of the rows returned. It gets slower as data grows, without any code change.
- List only the columns you need. `SELECT *` moves more data, prevents index-only scans and widens every sort and hash.
- Keep indexed columns bare in `WHERE` clauses: rewrite functions as ranges, index the expression when you cannot, and watch for implicit type conversions.
- A leading wildcard cannot use a B-tree. Use a trigram index or Oracle Text for substrings, full-text search for words, and a separate indexed column for fixed suffixes.
- N+1 queries are invisible in slow-query logs because each call is fast. Find them by call counts, and fix them with a join or one batch query per relation.
- Sorting on an unindexed column reads and sorts the whole table even with `LIMIT`. An index matching the filter and order lets the query stop after the first rows.
- Long `IN` lists cost parse time and flood the plan cache. Keep IDs in the database, bind them as one array or collection, or load them into a temporary table.
- Correlated subqueries are fine as `EXISTS` and for small outer sets. Replace per-row scalar subqueries and correlated updates with one aggregation and a join.
