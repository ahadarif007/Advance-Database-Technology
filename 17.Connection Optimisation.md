# Chapter 17: Connection Optimisation

Every query reaches the database through a **connection**: a network session, authenticated, with its own server process or thread and memory. How an application opens, shares, holds and releases connections has a large effect on performance, and it is often overlooked because it lives in application configuration rather than in SQL.

A database can have perfectly optimised queries and still perform badly because the application's connection pool is too large, too small, or holds connections for too long. This chapter covers connection pooling, pool sizing, connection lifetime, idle connections, prepared statements, network round trips, transaction duration and connection saturation, for **Oracle** and **PostgreSQL**.

## 1. What a Connection Costs

### Opening a connection

```
Application                                     Database server
    │ ── TCP handshake ───────────────────────►  │
    │ ── TLS handshake (if enabled) ──────────►  │
    │                                            │  listener / postmaster accepts
    │                                            │  starts a server process
    │ ── authentication (SCRAM, password) ────►  │  checks credentials
    │                                            │  sets up session memory, loads catalog data
    │ ◄──────────────────────────── ready ────── │
    │
    several network round trips and a new process: typically a few ms to tens of ms
```

| | Oracle (dedicated server) | PostgreSQL |
|---|---|---|
| Accepted by | Listener, which hands the connection to a new server process | Postmaster, which forks a new backend process |
| Server-side unit | One OS process per connection (threads with `THREADED_EXECUTION = TRUE`) | One OS process per connection |
| Session memory | PGA, UGA, session cursor cache | Backend memory, catalog and plan caches |

A query that runs in 1 ms is dominated by connection setup if the application opens a new connection for it.

### Keeping a connection open

An open connection is not free either. Each one holds a server process and memory whether it is working or not, and the database has a hard limit on how many can exist (Section 10). The rest of this chapter is about keeping a **small number of connections busy**, instead of a large number mostly idle.

## 2. Sample Scenario

The shop's web tier at peak:

| Item | Value |
|------|-------|
| Application instances | 12 |
| Connection pool per instance | 50 |
| Total possible connections | 600 |
| Database server | 16 CPU cores, fast SSD |
| Peak requests | 3,000 per second |
| Database time per request | 3 queries, about 6 ms in total, inside one transaction |

Configured connections: 600. Connections actually needed, as Section 4 shows: about 20. This gap is typical and is the source of most of the problems in this chapter.

## 3. Connection Pooling

A **connection pool** keeps a set of open connections and lends them to application threads. A thread borrows a connection, runs its work, and returns it. The connection stays open for the next thread.

```
Without a pool                            With a pool
  request ──► connect ──► query ──►         request ──► borrow ──► query ──► return
              disconnect                                   ▲                    │
  every request pays connection setup                      └──── pool ◄─────────┘
                                                        setup paid once per connection
```

### Where the pool lives

| Type | Examples | Suits |
|------|----------|-------|
| In the application | HikariCP (Java), Oracle UCP, SQLAlchemy pool, `node-postgres` Pool, Go `database/sql` | Long-running application servers |
| Between application and database (PostgreSQL) | PgBouncer, pgpool-II, cloud proxies such as Amazon RDS Proxy | Many application instances, short-lived processes, serverless functions |
| Inside the database (Oracle) | Database Resident Connection Pooling (DRCP), Shared Server | Many processes that cannot share an application pool (PHP, Python scripts) |

Most production systems use an application pool. An external pooler is added when the **total** number of application processes is large, because each process's pool adds up at the database.

### PgBouncer pool modes

PgBouncer accepts many client connections and maps them onto a few server connections.

| `pool_mode` | Server connection is returned to the pool | Client connections per server connection |
|-------------|-------------------------------------------|-----------------------------------------|
| `session` (default) | When the client disconnects | One |
| `transaction` | At the end of each transaction | Many |
| `statement` | After each statement (no multi-statement transactions) | Many |

`transaction` mode gives the largest reduction in server connections, but consecutive transactions from one client may run on different server sessions. Anything that lives in the **session** therefore breaks:

| Feature | Behaviour in transaction mode |
|---------|-------------------------------|
| `SET` without `LOCAL` | Applies to whichever client uses that server session next |
| Session-level advisory locks | Held by the wrong session (Chapter 11, Section 12) |
| `LISTEN` / `NOTIFY` | Notifications may go to another client |
| Temporary tables across transactions | May not be visible in the next transaction |
| Prepared statements | Supported at the protocol level from PgBouncer 1.21 (`max_prepared_statements`); SQL-level `PREPARE` is not |

### Oracle DRCP

DRCP keeps a pool of server processes inside the database that many client processes share:

```sql
EXEC DBMS_CONNECTION_POOL.START_POOL();
EXEC DBMS_CONNECTION_POOL.CONFIGURE_POOL(minsize => 10, maxsize => 40);
```

Clients request a pooled server in the connect string:

```
myhost:1521/shop:POOLED                                       -- Easy Connect
(DESCRIPTION=...(CONNECT_DATA=(SERVICE_NAME=shop)(SERVER=POOLED)))
```

Oracle 23ai adds **implicit connection pooling**, which returns the pooled server at statement or transaction boundaries without application changes, similar to PgBouncer's modes.

## 4. Pool Sizing

The most common mistake is a pool that is far too large.

### How many connections are actually busy

**Little's Law** gives the number of connections in use at once:

```
connections in use  =  arrival rate  ×  time each request holds a connection

Scenario (Section 2):  3,000 requests/s  ×  0.006 s  =  18 connections
```

On average only 18 of the 600 configured connections are doing anything. Allowing for peaks, about 30 would be plenty.

### Why more connections make things slower

A database server can only run as many things at once as it has CPU cores and I/O capacity. Beyond that, extra active connections do not add work done; they add waiting.

```
Throughput
   │          ┌──────────┐
   │        ╱             ╲
   │      ╱                 ╲___
   │    ╱                        ╲______
   │  ╱                                 ╲________
   └──────────────────────────────────────────────►  active connections
      8     16     32     64    128    256    512
                ▲
          around 2 × CPU cores
```

| Too many active connections cause | Why |
|-----------------------------------|-----|
| CPU context switching | The OS keeps switching between hundreds of processes |
| Lock and latch contention | More sessions competing for the same rows, buffers and internal structures |
| Cache thrashing | Each process's working data evicts the others' from CPU caches and the buffer cache |
| Memory pressure | Every active query may use `work_mem` / PGA for sorts and hashes |

Oracle's Real-World Performance group has demonstrated this repeatedly: reducing a pool from thousands of connections to under a hundred cut response times by an order of magnitude on the same hardware.

### A starting formula

A widely used starting point (from the PostgreSQL wiki, popularised by HikariCP):

```
connections  =  (CPU cores × 2)  +  effective disk spindles

16 cores, SSD (counted as about 1):   16 × 2 + 1  ≈  33
```

This is the **total for the database**, not per application instance. Divide it among instances:

```
33 connections ÷ 12 instances  ≈  3 per instance   (round up to 4)
```

Then measure. If threads wait for connections while the database CPU is idle, increase the pool. If the database is busy and waits on locks or CPU, decrease it.

### Let requests queue in the application

With a small pool, extra requests wait in the pool's queue for a few milliseconds. That is the intended behaviour. A short queue in the application is far cheaper than hundreds of sessions competing inside the database.

```
600-connection pool                       30-connection pool
  600 sessions inside the database          30 sessions inside the database
  all slow, high contention                 each fast; others wait briefly in the pool
```

### HikariCP settings

| Setting | Default | Recommendation |
|---------|---------|----------------|
| `maximumPoolSize` | 10 | Size from the calculation above |
| `minimumIdle` | Same as `maximumPoolSize` | Leave equal: a fixed-size pool avoids connection churn under load |
| `connectionTimeout` | 30,000 ms | Lower (for example 2–5 s) so overload fails fast instead of piling up |
| `maxLifetime` | 1,800,000 ms (30 min) | Section 5 |
| `idleTimeout` | 600,000 ms (10 min) | Only applies when `minimumIdle` is below the maximum |

| PgBouncer setting | Default | Meaning |
|-------------------|---------|---------|
| `default_pool_size` | 20 | Server connections per database and user pair |
| `max_client_conn` | 100 | Client connections PgBouncer accepts |
| `reserve_pool_size` | 0 | Extra server connections allowed when clients wait too long |

## 5. Connection Lifetime

A pooled connection can live for days. Closing and replacing connections on a schedule avoids problems that build up over time.

| Problem with very old connections | Explanation |
|-----------------------------------|-------------|
| Memory growth | PostgreSQL backends cache catalog and plan data for every table they touch; Oracle sessions accumulate cursors and PGA |
| Silently dropped connections | Firewalls, NAT gateways and load balancers drop idle TCP sessions without telling either side; the next query fails |
| Unbalanced load after failover or scaling | Existing connections stay on old nodes; only new connections use new replicas (Chapter 09) |
| Stale credentials or settings | Rotated passwords and changed parameters only apply to new sessions |

### Settings

| Purpose | Pool / client | Oracle | PostgreSQL |
|---------|---------------|--------|------------|
| Retire connections after a time | HikariCP `maxLifetime`; PgBouncer `server_lifetime` (default 3,600 s) | DRCP `max_lifetime_session` | — |
| Detect dead connections | Pool validation on borrow (JDBC `isValid()`) | `SQLNET.EXPIRE_TIME` in `sqlnet.ora` | `tcp_keepalives_idle`, `tcp_keepalives_interval`, `tcp_keepalives_count` |

Set the pool's maximum lifetime **shorter than any network or database timeout** in the path, for example 30 minutes when the firewall drops idle sessions after 60. HikariCP spreads retirements with a small random variation so connections do not all reconnect at the same moment.

Do not make lifetimes very short. Reconnecting every few seconds brings back the setup cost from Section 1.

### Short-lived processes

Serverless functions, CGI scripts and some PHP deployments start a new process per request, so an in-process pool never gets reused. Each invocation opens and closes a connection. Put a pool outside the process: PgBouncer or a cloud proxy for PostgreSQL, DRCP for Oracle.

## 6. Idle Connections

An idle connection has finished its work and is waiting for the next request. Idle connections are normal in a pool, but large numbers of them waste resources, and one kind is dangerous.

### Session states

```sql
-- PostgreSQL
SELECT state, count(*) FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state;

-- Oracle
SELECT status, count(*) FROM v$session
WHERE type = 'USER'
GROUP BY status;
```

| PostgreSQL `state` | Oracle | Meaning |
|--------------------|--------|---------|
| `active` | `ACTIVE` | Running a statement |
| `idle` | `INACTIVE` | Connected, no open transaction. Costs memory and a connection slot |
| `idle in transaction` | `INACTIVE` with a row in `V$TRANSACTION` | **Transaction open, nothing running**. Holds locks and old row versions |
| `idle in transaction (aborted)` | — | A statement failed; the transaction waits for `ROLLBACK` |

### Plain idle connections

Each idle PostgreSQL backend is a process using a few megabytes, and every connection counts against `max_connections`. Hundreds of idle connections also made PostgreSQL's snapshot calculation slower before version 14, which improved it substantially. In Oracle, each idle dedicated server process holds its PGA and counts against `PROCESSES`.

The fix is a correctly sized pool (Section 4). Timeouts are a safety net for clients that leak connections:

| | Oracle | PostgreSQL |
|---|---|---|
| Disconnect idle sessions | `MAX_IDLE_TIME` (12.2+, minutes); profile `IDLE_TIME` | `idle_session_timeout` (14+, default 0 = off) |

Do not apply an idle timeout to a pool's own connections without also setting the pool's idle timeout or lifetime below it. Otherwise the pool hands out connections that the server has already closed.

### Idle in transaction

A session that began a transaction and then stopped sending statements keeps everything the transaction holds:

```
BEGIN;
UPDATE orders SET status = 'SHIPPED' WHERE order_id = 1001;     -- row locked
... application calls a payment API, waits 30 s, or crashes mid-request ...
                                                                -- lock still held
                                                                -- PostgreSQL: VACUUM held back
```

| | Oracle | PostgreSQL |
|---|---|---|
| End sessions idle inside a transaction | `MAX_IDLE_BLOCKER_TIME` (21c+): idle sessions that block others | `idle_in_transaction_session_timeout` (9.6+, default 0) |
| Limit total transaction time | Resource Manager | `transaction_timeout` (17+) |

A value such as `idle_in_transaction_session_timeout = '60s'` for application roles is a common safeguard. The root cause is almost always in application code (Section 9).

## 7. Prepared Statements

Before a statement runs, the database parses it and chooses a plan (Chapter 01, Section 1). A **prepared statement** separates the SQL text from its values, so the parse and plan can be reused for different values:

```sql
-- Values inside the text: every customer_id is a new statement
SELECT * FROM orders WHERE customer_id = 42;
SELECT * FROM orders WHERE customer_id = 43;

-- Bind variable: one statement, executed with different values
SELECT * FROM orders WHERE customer_id = ?;      -- JDBC
SELECT * FROM orders WHERE customer_id = :id;    -- Oracle
SELECT * FROM orders WHERE customer_id = $1;     -- PostgreSQL protocol
```

Bind variables also prevent SQL injection, which alone is reason enough to use them.

### Oracle: hard and soft parses

Oracle shares parsed cursors across all sessions in the **shared pool**.

| Parse type | What happens | Cost |
|------------|--------------|------|
| Hard parse | New SQL text: full parse and optimisation, cursor added to the shared pool | High; takes shared pool latches/mutexes |
| Soft parse | Text found in the shared pool; reuse the plan | Low |
| No parse | The session or driver kept the cursor open and executes it again | Lowest |

An application using literals hard-parses almost every statement. Besides the CPU, this causes contention on the shared pool and pushes useful cursors out.

```sql
-- Hard parses per execution, system-wide
SELECT name, value FROM v$sysstat
WHERE name IN ('parse count (total)', 'parse count (hard)', 'execute count');
```

| Setting | Default | Effect |
|---------|---------|--------|
| `CURSOR_SHARING` | `EXACT` | `FORCE` replaces literals with binds automatically; a stopgap for applications that cannot be changed |
| `SESSION_CACHED_CURSORS` | 50 | Cursors cached per session, turning repeated soft parses into cheaper ones |
| JDBC implicit statement cache | Off | `setImplicitCachingEnabled(true)` with a cache size keeps cursors open in the driver: no parse at all |

### PostgreSQL: per-connection prepared statements

PostgreSQL has no shared plan cache. Prepared statements and their plans belong to **one connection**, which is one more reason to keep pooled connections long-lived.

```sql
PREPARE orders_by_customer (bigint) AS
    SELECT * FROM orders WHERE customer_id = $1;

EXECUTE orders_by_customer(42);
```

Drivers do this automatically through the extended query protocol.

| Setting | Default | Effect |
|---------|---------|--------|
| pgjdbc `prepareThreshold` | 5 | A statement becomes a named server-side prepared statement after 5 executions |
| `plan_cache_mode` (12+) | `auto` | First 5 executions get custom plans for their values; then a generic plan is used if its estimated cost is not much worse |

### Bind variables and skewed data

A plan reused for all values may suit some values badly, for example `status = 'CANCELLED'` (1%) versus `'SHIPPED'` (90%). Oracle handles this with bind peeking and adaptive cursor sharing; PostgreSQL with `plan_cache_mode` (Chapter 01, Section 13). Use bind variables by default; consider literals only for a low-cardinality skewed column in a report query.

## 8. Network Round Trips

Every call to the database waits for at least one network round trip. The database cannot make that time shorter.

| Placement | Typical round trip |
|-----------|--------------------|
| Same host | < 0.1 ms |
| Same data centre or availability zone | 0.1–0.5 ms |
| Across availability zones | 0.5–2 ms |
| Across regions | 20–150 ms |

A request making 30 database calls across availability zones spends 15–60 ms on the network alone. Placing the application near the database, and reducing the number of calls, often helps more than any query tuning.

### Ways to reduce round trips

| Technique | Example | See |
|-----------|---------|-----|
| One query instead of a loop | Join instead of N+1 | Chapter 16, Section 6 |
| Batch writes | Multi-row `INSERT`, array binding | Chapter 12, Section 3 |
| Return generated values | `INSERT ... RETURNING order_id` (PostgreSQL); `RETURNING ... INTO` (Oracle) instead of a follow-up `SELECT` | |
| Fetch more rows per call | Larger fetch size | Below |
| Move a multi-step operation into the database | Stored procedure | |
| Send without waiting for each reply | Pipelining: libpq pipeline mode (14+), psycopg 3; Oracle 23ai pipelining (JDBC, OCI) | |
| Remove chatter | Pool validation queries on every borrow, repeated `SET` or autocommit changes | |

### Fetch size

A query returning 10,000 rows is fetched in chunks. Each chunk is a round trip.

| Client | Default | Notes |
|--------|---------|-------|
| Oracle JDBC | 10 rows per fetch | 10,000 rows = 1,000 round trips. Set `setFetchSize(500)` or `defaultRowPrefetch` |
| SQL\*Plus | `ARRAYSIZE` 15 | |
| PostgreSQL JDBC | All rows in one go (`fetchSize` 0) | Fast but can exhaust application memory. A fetch size only takes effect with autocommit off |
| psycopg | All rows at once | Use a named (server-side) cursor to stream |

```sql
-- Oracle: round trips made by the current session
SELECT n.name, s.value
FROM v$mystat s JOIN v$statname n ON n.statistic# = s.statistic#
WHERE n.name = 'SQL*Net roundtrips to/from client';
```

In PostgreSQL, sessions waiting for the next client message show `wait_event = 'ClientRead'`. Many short statements with high `ClientRead` time point to round trips.

## 9. Transaction Duration

A connection taken from the pool is held **from the start of the transaction to the end**, whether the database is working or not. Little's Law (Section 4) uses this holding time, not query time.

```
Request timeline, connection held for the whole transaction

BEGIN ─ query (2 ms) ─ call payment API (300 ms) ─ query (2 ms) ─ COMMIT
│◄──────────────────────────── 304 ms held ────────────────────────────►│
Database work: 4 ms.  Connection unavailable to anyone else: 304 ms.

3,000 requests/s × 0.304 s  =  912 connections needed, instead of 12
```

Long transactions also keep row locks and, in PostgreSQL, hold back VACUUM (Chapter 04, Section 12).

### Common causes

| Cause | Fix |
|-------|-----|
| HTTP calls, message publishing or file I/O inside the transaction | Do them before `BEGIN` or after `COMMIT`; use an outbox table for messages (Chapter 11, Section 7) |
| Framework opens a transaction for the whole request (`@Transactional` on a controller, "Open Session in View") | Put transaction boundaries around the database work only |
| Waiting for user input inside a transaction | Never; use optimistic concurrency instead (Chapter 04, Section 10) |
| Read-only requests running in a transaction that is never committed | Use autocommit or read-only transactions, and always end them |
| Exception path skips `COMMIT` / `ROLLBACK` | `try`/`finally` or the framework's transaction management; pools can roll back on return |

### Measuring

```sql
-- PostgreSQL: open transactions by age
SELECT pid, usename, state, now() - xact_start AS xact_age, left(query, 60) AS last_query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start
LIMIT 10;

-- Oracle
SELECT s.sid, s.username, s.status, t.start_time, s.sql_id, s.prev_sql_id
FROM v$transaction t JOIN v$session s ON s.taddr = t.addr
ORDER BY t.start_time;
```

Pools also report how long connections are held. HikariCP's `leakDetectionThreshold` logs a stack trace when a connection is held longer than the threshold, which identifies the code responsible.

## 10. Database Connection Saturation

**Connection saturation** is when the database, or the pool in front of it, cannot accept more work. It appears in two forms.

### 1. Out of connection slots

The database refuses new connections:

| | Limit | Error |
|---|---|---|
| PostgreSQL | `max_connections` (default 100), minus `superuser_reserved_connections` (default 3) and `reserved_connections` (16+) | `FATAL: sorry, too many clients already` |
| Oracle | `PROCESSES`, and `SESSIONS` (derived from it by default) | ORA-00020 (processes), ORA-00018 (sessions); TNS-12516 / TNS-12519 from the listener |
| Application pool | `maximumPoolSize` | HikariCP: `Connection is not available, request timed out after 30000ms` |

Raising `max_connections` or `PROCESSES` is rarely the right answer. It allows more simultaneous work, which leads to the second form.

### 2. Too much active work

All connections are open and running, and each runs slowly because they compete:

```
16 CPU cores

Healthy:     ████████████████                         16 active sessions, little waiting
Saturated:   ████████████████░░░░░░░░░░░░░░░░░░░░...  200 active sessions,
                                                      184 waiting for CPU, locks or I/O
```

A useful measure is **average active sessions** (AAS): how many sessions are working or waiting inside the database at a typical moment. When AAS is well above the number of CPU cores, the database is saturated.

```sql
-- PostgreSQL: active sessions and what they wait for, right now
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity
WHERE state = 'active' AND backend_type = 'client backend'
GROUP BY 1, 2
ORDER BY 3 DESC;

-- Oracle: average active sessions over the last 5 minutes (ASH samples once per second)
SELECT ROUND(COUNT(*) / 300, 1) AS avg_active_sessions
FROM v$active_session_history
WHERE sample_time > SYSTIMESTAMP - INTERVAL '5' MINUTE;
```

### The retry storm

Saturation feeds itself when clients react badly:

```
database slows ──► requests time out ──► clients retry ──► more load ──► database slower
                        │
                        └── pools grow toward their maximum, opening more connections
```

After a failover, every application instance reconnects at the same moment (a **logon storm**), and each connection is expensive to set up (Section 1).

| Protection | How |
|------------|-----|
| Fixed, small pools | The total across all instances stays below what the database handles well |
| Short `connectionTimeout` | Fail fast instead of queueing indefinitely |
| Retries with exponential backoff and random jitter | Spread reconnects and retries over time |
| Listener connection rate limit (Oracle) | `CONNECTION_RATE_<listener>` with `RATE_LIMIT` in `listener.ora` |
| Pooler in front of the database (PostgreSQL) | PgBouncer queues clients instead of opening backends |
| Workload separation | Separate pools, and Oracle Resource Manager consumer groups, so batch jobs cannot starve the web tier |

## 11. A Systematic Approach to Connection Problems

```
1. Count connections on the database, by state
        pg_stat_activity.state  /  V$SESSION.STATUS
        │
        ├── total near max_connections / PROCESSES?
        │       ──► do not raise the limit first; find who holds them       Section 10
        │
        ├── many "idle"?
        │       ──► pools are oversized for the workload                   Sections 4, 6
        │
        └── any "idle in transaction" for more than a few seconds?
                ──► application holds transactions open;
                    fix the code, add a timeout as a safety net            Sections 6, 9
        │
        ▼
2. Compare active sessions with CPU cores
        AAS (Oracle ASH) / count of active sessions (PostgreSQL)
        │
        └── far above cores? ──► shrink pools; requests should queue in the
                                  application, not in the database          Section 4
        │
        ▼
3. Application threads waiting for a connection while database CPU is low?
        └── yes ──► check holding time first (Section 9), then grow the pool
        │
        ▼
4. High connection rate?
        listener log / log_connections
        └── yes ──► add or fix pooling; external pooler for
                    short-lived processes                                   Sections 3, 5
        │
        ▼
5. High parse rate?
        Oracle: parse count (hard) / execute count
        PostgreSQL: many one-off statements in pg_stat_statements
        └── yes ──► bind variables, statement caching                       Section 7
        │
        ▼
6. Many fast calls per request, high ClientRead / SQL*Net round trips?
        └── yes ──► fewer calls: joins, batching, fetch size, pipelining    Section 8
```

## 13. Short Summary

- Opening a connection costs several round trips and a new server process; holding one costs memory and a connection slot. Keep a small number of connections busy.
- Use a pool in every long-running application. Add an external pooler (PgBouncer, a cloud proxy, Oracle DRCP) when many processes or short-lived functions connect.
- Size pools from Little's Law and the database's cores, not from the number of application threads. The total across all instances matters, and requests should queue in the application rather than in the database.
- Retire connections before network devices or the database drop them, but not so often that setup cost returns.
- Plain idle connections waste resources; idle-in-transaction sessions hold locks and block cleanup. Fix the application, and use timeouts as a safety net.
- Use bind variables. Oracle shares parsed plans across sessions; PostgreSQL keeps them per connection.
- Network round trips are often the largest part of response time. Reduce the number of calls, raise fetch sizes, and keep the application close to the database.
- A connection is held for the whole transaction. External calls inside a transaction multiply the connections needed.
- Raising the connection limit rarely fixes saturation. Small fixed pools, fail-fast timeouts and retries with backoff and jitter keep the database out of overload.
