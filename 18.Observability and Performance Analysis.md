# Chapter 18: Observability and Performance Analysis

Performance work starts with measurement. Without it, tuning is guesswork: an index is added for a query that was never slow, or memory is doubled while the real problem is a lock held by an idle session. **Observability** means the database exposes enough information to answer two questions at any moment: where is the time going, and which statements are responsible?

This chapter covers the metrics that matter most, what each one tells you, and how to read them in **Oracle** and **PostgreSQL**. It starts with the tools (execution plans, statement statistics, slow-statement capture and activity history) and then works through each metric with the views and queries that measure it.

## 1. Sample Workload

The examples use the shop schema from Chapter 01:

```
customers (1) ───< orders (N) ───< order_items (N) >─── (1) products
```

An online shop runs three kinds of work against it:

| Workload | Example statement | Profile |
|----------|-------------------|---------|
| Order history page | `SELECT ... FROM orders WHERE customer_id = :id ORDER BY order_date DESC` | Very frequent, should take about 1 ms |
| Checkout | `INSERT INTO orders ...`, `UPDATE products SET stock = stock - :q ...` | Frequent, short transactions, row locks |
| Daily sales report | `SELECT ... GROUP BY ...` over all orders | Rare, reads millions of rows |

The tools in this chapter must be switched on before they can collect anything.

**PostgreSQL** (`postgresql.conf`; changing `shared_preload_libraries` requires a restart)

```
shared_preload_libraries   = 'pg_stat_statements,auto_explain'
track_io_timing            = on      # I/O timings in plans and statistics
compute_query_id           = auto    # default; query_id in pg_stat_activity (14+)
log_min_duration_statement = 500ms   # log statements slower than this
auto_explain.log_min_duration = 2s   # log the plan of statements slower than this
```

```sql
CREATE EXTENSION pg_stat_statements;
```

Before enabling `track_io_timing` on a new platform, run the `pg_test_timing` utility. On systems with a slow clock source the timing overhead is noticeable.

**Oracle**

```sql
SHOW PARAMETER statistics_level                  -- TYPICAL (default) or ALL
SHOW PARAMETER control_management_pack_access    -- DIAGNOSTIC+TUNING by default on Enterprise Edition
```

Most Oracle instrumentation (`V$` views, wait events, SQL trace) is always on and free. ASH, AWR and ADDM require the **Diagnostics Pack**, and SQL Monitor requires the **Tuning Pack**. Both are separately licensed options of Enterprise Edition. Without them, use **Statspack** (`?/rdbms/admin/spcreate.sql`), the free predecessor of AWR.

## 2. How Databases Report Performance

### Time is the primary measure

Users experience time, so the most useful measure inside the database is time too. A session that is working on a request is, at any moment, in one of two states:

```
                    session time
        ┌───────────────┴───────────────────┐
     on CPU                              waiting
  (parsing, reading                ┌──────┼──────────┬──────────┐
   buffers, sorting,              I/O    lock     commit    network,
   joining)                                       (log)     latch, ...
```

**Oracle** calls the sum of these **DB time**: total time spent by sessions in database calls, excluding idle time. Each wait is classified by a named **wait event** (for example `db file sequential read`, `enq: TX - row lock contention`). PostgreSQL has the same idea through the `wait_event_type` and `wait_event` columns of `pg_stat_activity`. It does not keep a cumulative DB time total.

**Average active sessions (AAS)** is DB time divided by elapsed time. An AAS of 6 on an 8-core server means, on average, six sessions are working or waiting at once.

```
AAS  =  DB time / wall-clock time

AAS well below CPU cores     database is not the bottleneck
AAS near CPU cores, mostly   CPU saturated; reduce work per statement
  on CPU
AAS high, mostly waiting     find the dominant wait event
```

### Three ways to collect data

| Method | How it works | Examples | Cost |
|--------|--------------|----------|------|
| Cumulative counters | Totals since start or last reset | `pg_stat_statements`, `pg_stat_database`, `V$SYSSTAT`, `V$SQLSTATS` | Very low |
| Sampling | Records what active sessions are doing every N seconds | ASH, polling `pg_stat_activity` | Low |
| Tracing | Records every event for one session or statement | SQL trace (10046), `EXPLAIN ANALYZE`, `auto_explain` | Higher; use selectively |

### Counters must be read as deltas

Cumulative counters grow from the moment they are reset. A raw value says little. The difference between two readings over a known interval is what matters:

```
09:00  xact_commit = 81,204,000
09:05  xact_commit = 81,804,000
                     ─────────
       600,000 commits in 300 s  =  2,000 commits per second
```

Oracle's AWR and Statspack produce these deltas automatically between snapshots. In PostgreSQL, save snapshots of the views into a table or use a monitoring system that does so. `stats_reset` columns in the PostgreSQL views, and `STARTUP_TIME` in `V$INSTANCE`, show when counting began.

## 3. EXPLAIN and EXPLAIN ANALYZE

Chapter 01, Section 5 explains how to read estimated and actual plans. This section covers the options that make plans useful for analysis.

### PostgreSQL

```sql
EXPLAIN (ANALYZE, BUFFERS, SETTINGS, WAL)
SELECT * FROM orders WHERE customer_id = 42 ORDER BY order_date DESC;
```

| Option | Version | Adds |
|--------|---------|------|
| `ANALYZE` | All | Executes the statement; actual rows, loops and time per node |
| `BUFFERS` | All; on by default with `ANALYZE` from 18 | Shared hits, reads, dirtied and written; temp blocks |
| `TIMING` | All | Per-node timing (default on with `ANALYZE`); turn off to reduce overhead |
| `SETTINGS` | 12+ | Planner settings that differ from the defaults |
| `WAL` | 13+ | WAL records and bytes generated |
| `GENERIC_PLAN` | 16+ | Plan for a statement with `$1` placeholders, without values |
| `SERIALIZE` | 17+ | Cost of converting result rows for the client |
| `MEMORY` | 17+ | Memory used by the planner |
| `FORMAT JSON` | All | Machine-readable output for plan visualisers |

With `track_io_timing = on`, each node also shows `I/O Timings`, which separates time spent waiting on storage from time spent on CPU.

### Oracle

For a statement that already ran, find its `SQL_ID` and display the plan from the cursor cache:

```sql
SELECT sql_id, child_number, executions, sql_text
FROM v$sql
WHERE sql_text LIKE 'SELECT * FROM orders WHERE customer_id%';

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR('8vj1f2x7k9p3q', NULL, 'ALLSTATS LAST +PEEKED_BINDS'));
```

| Source | Function | Use |
|--------|----------|-----|
| Cursor cache (current plans) | `DBMS_XPLAN.DISPLAY_CURSOR` | Actual plan of a recent execution |
| AWR (historical plans) | `DBMS_XPLAN.DISPLAY_AWR` | Plan a statement used days ago, for regressions |
| SQL Monitor | `DBMS_SQLTUNE.REPORT_SQL_MONITOR` | Long-running statement, live or recent (Section 5) |

Row-source statistics (`A-Rows`, `Buffers`, `A-Time`) are collected only when the statement runs with the `GATHER_PLAN_STATISTICS` hint or with `STATISTICS_LEVEL = ALL` in the session.

### Limits of a single plan

A plan explains one execution of one statement. It does not show which statements matter, how often they run or what they wait for under concurrency. Use plans once Sections 4 to 6 have identified the statement worth examining.

## 4. Statement Statistics: pg_stat_statements and V$SQLSTATS

Both databases keep cumulative statistics per **normalised statement**: the SQL text with literal values replaced, so `customer_id = 42` and `customer_id = 43` count as one statement. This is the most valuable single tool for finding what to tune.

### PostgreSQL: pg_stat_statements

```sql
SELECT queryid,
       calls,
       round(total_exec_time::numeric, 0)           AS total_ms,
       round(mean_exec_time::numeric, 2)            AS mean_ms,
       rows,
       shared_blks_hit + shared_blks_read           AS blocks,
       temp_blks_written,
       left(query, 60)                              AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

```
 queryid  | calls    | total_ms  | mean_ms | rows     | blocks      | temp | query
----------+----------+-----------+---------+----------+-------------+------+--------------------------------
 -4728... | 9,214,033| 2,764,210 |    0.30 | 9,214,033|  46,070,165 |    0 | SELECT * FROM products WHERE p
  1932... |   412,880| 1,981,824 |    4.80 | 4,128,800| 845,578,240 |    0 | SELECT * FROM orders WHERE cus
  7710... |        30|   912,300 | 30410.0 |   300,000| 250,104,000 | 8812 | SELECT p.category, SUM(oi.qty
```

| Field | Meaning |
|-------|---------|
| `queryid` | Hash of the normalised statement; matches `query_id` in `pg_stat_activity` (14+) |
| `calls` | Number of executions |
| `total_exec_time` / `mean_exec_time` | Total and average execution time in ms (named `total_time` / `mean_time` before 13) |
| `min_exec_time`, `max_exec_time`, `stddev_exec_time` | Spread of execution times |
| `rows` | Total rows returned or affected |
| `shared_blks_hit` / `shared_blks_read` | Blocks found in shared buffers / read from the OS |
| `temp_blks_written` | Blocks spilled to temporary files by sorts and hashes |
| `shared_blk_read_time` | Time reading blocks; needs `track_io_timing` (named `blk_read_time` before 17) |
| `wal_bytes` | WAL generated (13+) |
| `total_plan_time` | Planning time (13+); needs `pg_stat_statements.track_planning = on`, off by default |

The view keeps `pg_stat_statements.max` statements (default 5000). When it is full, the least-used entries are evicted. `pg_stat_statements_info` (14+) counts evictions in `dealloc`. A steadily rising count means statements with literals that vary are crowding out the rest, usually because the application does not use bind variables.

Reset the statistics with `SELECT pg_stat_statements_reset();` before a test, then compare.

### Oracle: V$SQLSTATS

`V$SQL` has one row per child cursor. `V$SQLSTATS` has one row per statement and plan, keeps entries after the cursor ages out of the shared pool, and is cheaper to query. Use it for top-SQL lists.

```sql
SELECT sql_id,
       executions,
       ROUND(elapsed_time / 1e6)                                   AS total_s,
       ROUND(elapsed_time / NULLIF(executions, 0) / 1000, 2)       AS mean_ms,
       ROUND(cpu_time / 1e6)                                       AS cpu_s,
       buffer_gets,
       rows_processed,
       SUBSTR(sql_text, 1, 60)                                     AS sql_text
FROM v$sqlstats
ORDER BY elapsed_time DESC
FETCH FIRST 10 ROWS ONLY;
```

| Field | Meaning |
|-------|---------|
| `SQL_ID` | Identifier of the statement text |
| `PLAN_HASH_VALUE` | Identifier of the plan; a change signals a new plan |
| `EXECUTIONS` | Number of executions |
| `ELAPSED_TIME` / `CPU_TIME` | Total time in **microseconds** |
| `USER_IO_WAIT_TIME`, `CONCURRENCY_WAIT_TIME`, `APPLICATION_WAIT_TIME` | Time in waits by class; application waits are mostly row locks |
| `BUFFER_GETS` | Logical reads (blocks read from the buffer cache) |
| `DISK_READS` | Blocks read from storage |
| `ROWS_PROCESSED` | Rows returned or affected |
| `PARSE_CALLS` | Parse requests from the client |

Oracle assigns a different `SQL_ID` to each literal value. Statements that differ only in literals share a `FORCE_MATCHING_SIGNATURE` in `V$SQL`, which groups them:

```sql
SELECT force_matching_signature, COUNT(*) AS versions, SUM(executions) AS execs
FROM v$sql
GROUP BY force_matching_signature
HAVING COUNT(*) > 100
ORDER BY versions DESC;
```

A signature with thousands of versions is an application using literals instead of bind variables, which causes hard parsing (Section 12).

For history beyond the shared pool, AWR stores per-snapshot deltas in `DBA_HIST_SQLSTAT` (Section 6).

## 5. Capturing Slow Statements: Logs, auto_explain and SQL Monitor

Statement statistics show averages. To see individual slow executions, with their parameters and plans, capture them as they happen.

### PostgreSQL: the server log

```
log_min_duration_statement = 500ms     # default -1 (off); 0 logs every statement
log_line_prefix = '%m [%p] %q%u@%d app=%a '
```

```
2026-10-11 09:14:02.118 UTC [41822] shop@prod app=web LOG:  duration: 1840.212 ms
  execute <unnamed>: SELECT * FROM orders WHERE customer_id = $1 ORDER BY order_date DESC
2026-10-11 09:14:02.118 UTC [41822] shop@prod app=web DETAIL:  Parameters: $1 = '58213'
```

On busy servers, logging every statement above a low threshold produces large logs. Sampling (13+) logs only a share of them:

| Parameter | Effect |
|-----------|--------|
| `log_min_duration_statement` | Log every statement at or above this duration |
| `log_min_duration_sample` (13+) | Lower threshold, applied with sampling |
| `log_statement_sample_rate` (13+) | Fraction of statements above `log_min_duration_sample` that are logged |
| `log_transaction_sample_rate` (12+) | Fraction of whole transactions logged statement by statement |

Log analysers such as pgBadger turn these logs into reports of the slowest and most frequent statements.

### PostgreSQL: auto_explain

The log shows that a statement was slow. `auto_explain` also logs **the plan it used**, which matters when a plan depends on parameter values or changes over time.

| Parameter | Default | Purpose |
|-----------|---------|---------|
| `auto_explain.log_min_duration` | -1 (off) | Log plans of statements at or above this duration |
| `auto_explain.log_analyze` | off | Include actual rows and timings (`EXPLAIN ANALYZE` output) |
| `auto_explain.log_buffers` | off | Include buffer counts; needs `log_analyze` |
| `auto_explain.log_timing` | on | Per-node timings when `log_analyze` is on |
| `auto_explain.log_nested_statements` | off | Include statements run inside functions |
| `auto_explain.sample_rate` | 1 | Fraction of statements considered |

`log_analyze` instruments **every** statement, because the database cannot know in advance which ones will be slow. Per-node timing is the expensive part. A common production setting is `log_analyze = on`, `log_buffers = on`, `log_timing = off`, which keeps row counts and buffers at much lower cost.

### Oracle: SQL Monitor

Oracle monitors a statement automatically when it runs in parallel or has used more than 5 seconds of CPU or I/O in a single execution. The `/*+ MONITOR */` hint forces monitoring for a shorter statement.

```sql
SELECT sql_id, status, ROUND(elapsed_time / 1e6) AS elapsed_s, sql_text
FROM v$sql_monitor
ORDER BY sql_exec_start DESC;

SELECT DBMS_SQLTUNE.REPORT_SQL_MONITOR(sql_id => 'a7x9m2k4c1q8z', type => 'TEXT')
FROM dual;
```

The report shows the plan with actual rows, time and waits per step, updated while the statement is still running. It is the most direct way to see where a long-running query spends its time, and it requires the Tuning Pack.

### Oracle: SQL trace

SQL trace records every call, wait and bind value for a session. It needs no extra licence.

```sql
-- Trace another session, including waits and binds
EXEC DBMS_MONITOR.SESSION_TRACE_ENABLE(session_id => 214, serial_num => 3391, waits => TRUE, binds => TRUE);
-- ... reproduce the problem ...
EXEC DBMS_MONITOR.SESSION_TRACE_DISABLE(session_id => 214, serial_num => 3391);

-- Location of trace files
SELECT value FROM v$diag_info WHERE name = 'Diag Trace';
```

```bash
tkprof orcl_ora_41822.trc report.txt sort=exeela,fchela
```

`tkprof` summarises the trace per statement: parse, execute and fetch counts, CPU, elapsed time, rows and the waits behind them. It is the Oracle tool to use when one user action is slow and the cause must be proven, not inferred.

## 6. Activity Sampling and History: pg_stat_activity, ASH and AWR

Statement statistics answer "what has been expensive overall". Sampling answers "what was happening at 09:14, when users complained".

### PostgreSQL: pg_stat_activity

One row per server process, showing what it is doing now:

```sql
SELECT pid, usename, application_name, state,
       wait_event_type, wait_event,
       now() - query_start AS running_for,
       query_id, left(query, 60) AS query
FROM pg_stat_activity
WHERE backend_type = 'client backend' AND state <> 'idle'
ORDER BY query_start;
```

| `state` | Meaning |
|---------|---------|
| `active` | Executing a statement |
| `idle` | Connected, waiting for the client to send a statement |
| `idle in transaction` | Inside an open transaction, doing nothing; may hold locks |
| `idle in transaction (aborted)` | As above, after an error; must be rolled back |

| `wait_event_type` | Typical meaning |
|-------------------|-----------------|
| null (with `state = 'active'`) | On CPU, or in a wait that is not instrumented |
| `IO` | Reading or writing data files or WAL (`DataFileRead`, `WALSync`) |
| `Lock` | Waiting for a heavyweight lock, such as a row or table lock (Section 16) |
| `LWLock` | Waiting for an internal lock on a shared structure (`BufferMapping`, `WALWrite`) |
| `Client` | Waiting for the client (`ClientRead`, `ClientWrite`) |
| `IPC` | Waiting for another process, such as a parallel worker |

PostgreSQL keeps no history of this view. To build one, sample it every few seconds into a table, use a monitoring agent that does, or install the third-party `pg_wait_sampling` extension, which samples wait events in shared memory.

### Oracle: Active Session History (ASH)

Oracle samples every **active** session once per second and stores the samples in memory in `V$ACTIVE_SESSION_HISTORY`. One sample in ten is kept on disk in `DBA_HIST_ACTIVE_SESS_HISTORY`.

Because each sample represents about one second, **counting samples estimates DB time**:

```sql
-- What were sessions doing between 09:10 and 09:20?
SELECT NVL(event, 'ON CPU') AS activity, sql_id, COUNT(*) AS seconds
FROM v$active_session_history
WHERE sample_time BETWEEN TIMESTAMP '2026-10-11 09:10:00'
                      AND TIMESTAMP '2026-10-11 09:20:00'
GROUP BY NVL(event, 'ON CPU'), sql_id
ORDER BY seconds DESC
FETCH FIRST 10 ROWS ONLY;
```

```
ACTIVITY                          SQL_ID          SECONDS
--------------------------------  -------------  -------
enq: TX - row lock contention     4kq8v1n2b7x0m      1,812
ON CPU                            a7x9m2k4c1q8z        640
db file sequential read           8vj1f2x7k9p3q        205
```

| Column | Meaning |
|--------|---------|
| `SESSION_STATE` | `ON CPU` or `WAITING` |
| `EVENT`, `WAIT_CLASS` | Wait event when waiting |
| `SQL_ID`, `SQL_PLAN_HASH_VALUE`, `SQL_PLAN_LINE_ID` | Statement, plan and plan step being executed |
| `BLOCKING_SESSION` | Session holding the resource waited for |
| `CURRENT_OBJ#` | Object being accessed |

In the example, 30 minutes of the 10-minute window were spent waiting for one row lock: on average three sessions were stuck at once. That is the problem to fix first.

### Oracle: AWR and ADDM

The **Automatic Workload Repository (AWR)** takes a snapshot of cumulative statistics every hour by default and keeps 8 days of history. An AWR report compares two snapshots and lists, for that interval, the top wait events, top SQL by time, CPU and reads, and instance activity.

```sql
EXEC DBMS_WORKLOAD_REPOSITORY.CREATE_SNAPSHOT;   -- manual snapshot before and after a test
@?/rdbms/admin/awrrpt.sql                        -- AWR report between two snapshots
@?/rdbms/admin/ashrpt.sql                        -- ASH report for a time range
@?/rdbms/admin/addmrpt.sql                       -- ADDM findings and recommendations
```

**ADDM** (Automatic Database Diagnostic Monitor) analyses each AWR interval and ranks findings by the DB time they account for, for example "SQL statements consuming significant database time" or "row lock waits".

Read an AWR report in this order: **Load Profile** (how busy), **Top Foreground Events** (where time went), **SQL ordered by Elapsed Time** (which statements). Most of the report exists to support those three sections.

## 7. The Statistics Views

Both databases expose their counters as views. The ones below cover most analysis.

**PostgreSQL**

| View | Contents |
|------|----------|
| `pg_stat_activity` | One row per process: state, wait event, current query |
| `pg_stat_database` | Per database: commits, rollbacks, blocks read and hit, rows, temp files, deadlocks, session time (14+) |
| `pg_stat_user_tables` | Per table: sequential and index scans, rows read, inserts, updates, dead rows, last vacuum and analyze |
| `pg_stat_user_indexes` | Per index: scans and rows read; finds unused indexes |
| `pg_statio_user_tables` | Per table: heap, index and TOAST blocks read and hit |
| `pg_stat_io` (16+) | I/O by process type and context: reads, writes, extends, hits, evictions, fsyncs and their timings |
| `pg_stat_bgwriter`, `pg_stat_checkpointer` (17+) | Background writer and checkpoint activity |
| `pg_stat_wal` (14+) | WAL records, bytes and full-page images |
| `pg_locks` | Locks held and requested |
| `pg_stat_statements` | Per statement (extension; Section 4) |

All of these except `pg_stat_activity` and `pg_locks` are cumulative. `pg_stat_reset()` resets the current database's counters, and `pg_stat_reset_shared('io')` and similar reset the shared ones.

**Oracle**

| View | Contents |
|------|----------|
| `V$SESSION` | One row per session: status, current SQL, wait event, blocker |
| `V$SYS_TIME_MODEL` / `V$SESS_TIME_MODEL` | DB time, DB CPU, parse time and other time totals |
| `V$SYSTEM_EVENT` / `V$SESSION_EVENT` | Waits and time waited per event |
| `V$EVENT_HISTOGRAM` | Distribution of wait durations per event |
| `V$SYSSTAT` / `V$SESSTAT` | Hundreds of counters: logical and physical reads, commits, parses, redo size |
| `V$SYSMETRIC` | Rates and ratios computed over the last 60 seconds |
| `V$SQLSTATS`, `V$SQL` | Per statement (Section 4) |
| `V$SEGMENT_STATISTICS` | Per table or index: logical reads, physical reads, row lock waits |
| `V$ACTIVE_SESSION_HISTORY` | Sampled activity (Section 6) |
| `DBA_HIST_*` | AWR history of the above |

`V$SYSMETRIC` saves computing deltas by hand:

```sql
SELECT metric_name, ROUND(value, 1) AS value, metric_unit
FROM v$sysmetric
WHERE group_id = 2
  AND metric_name IN ('Average Active Sessions', 'Host CPU Utilization (%)',
                      'User Transaction Per Sec', 'Executions Per Sec',
                      'Logical Reads Per Sec', 'Physical Reads Per Sec',
                      'SQL Service Response Time');
```

`group_id = 2` selects the 60-second interval.

### Equivalents for readers coming from MySQL

| MySQL | Oracle | PostgreSQL |
|-------|--------|------------|
| Performance Schema | `V$` dynamic performance views, ASH | `pg_stat_*` views |
| sys schema (summary views over Performance Schema) | AWR and ASH reports, `DBA_HIST_*` | `pg_stat_statements`, monitoring dashboards |
| Slow query log | SQL Monitor, ASH, SQL trace | `log_min_duration_statement`, `auto_explain` |
| `EXPLAIN ANALYZE` (8.0.18+) | `DISPLAY_CURSOR(..., 'ALLSTATS LAST')` | `EXPLAIN ANALYZE` |

## 8. Latency

**Latency** is the time to complete one operation, usually one statement or one request. It is what users feel.

### Averages hide the problem

```
mean = 12 ms, but:

p50   ███                                          4 ms
p90   ██████                                       9 ms
p99   ████████████████████████████████████████   180 ms
```

A **percentile** p99 = 180 ms means 99% of executions finished within 180 ms and 1% took longer. A page that runs 20 statements hits the slowest 1% of statements far more often than 1% of the time. Track p50, p95 and p99, not only the mean.

### Where to measure

```
user ──► application ──► pool wait ──► network ──► database execution ──► network ──► application
         ├──────────────────────────── end-to-end latency ──────────────────────────────────┤
                                                    ├── database time ──┤
```

A query that takes 2 ms in the database can take 200 ms end to end if the application waits 198 ms for a free connection (Section 18). Measure at both ends: the application (or an APM tool) for end-to-end percentiles, the database for its share.

### In each database

Neither database stores per-statement percentiles. They provide the pieces:

| Need | PostgreSQL | Oracle |
|------|------------|--------|
| Average per statement | `mean_exec_time` | `ELAPSED_TIME / EXECUTIONS` in `V$SQLSTATS` |
| Spread per statement | `stddev_exec_time`, `max_exec_time` | ASH samples per `SQL_EXEC_ID`; SQL Monitor for long runs |
| Individual slow executions | `log_min_duration_statement`, `auto_explain` | SQL Monitor, SQL trace |
| Average for the whole database | Derived from `pg_stat_statements` | `SQL Service Response Time` in `V$SYSMETRIC` |
| Distribution of wait times | Not built in | `V$EVENT_HISTOGRAM` |

A large gap between `mean_exec_time` and `max_exec_time`, or a high `stddev_exec_time`, marks a statement whose latency varies. The usual causes are different parameter values needing different plans (Chapter 01, Section 13), lock waits, or cold cache reads.

## 9. Throughput

**Throughput** is work completed per unit of time: transactions per second (TPS), statements per second, or business operations per second, such as orders placed.

```sql
-- PostgreSQL: run twice, N seconds apart, and divide the difference by N
SELECT sum(xact_commit + xact_rollback) AS transactions,
       sum(tup_inserted + tup_updated + tup_deleted) AS rows_changed
FROM pg_stat_database;

-- Statements: sum(calls) from pg_stat_statements, sampled the same way
```

```sql
-- Oracle: rates over the last minute
SELECT metric_name, ROUND(value) AS per_sec
FROM v$sysmetric
WHERE group_id = 2
  AND metric_name IN ('User Transaction Per Sec', 'Executions Per Sec', 'User Calls Per Sec');
```

### Throughput, latency and concurrency are linked

**Little's law** relates the three:

```
concurrency = throughput × latency

2,000 statements/s  ×  0.005 s  =  10 statements in progress on average
```

This is useful in both directions:

- It predicts how many connections a workload needs (Section 18).
- When latency rises at the same throughput, concurrency rises with it. More sessions compete for CPU and locks, latency rises further, and the system can tip into overload quickly.

```
throughput
    │              ┌──────────── saturation: more load adds only latency
    │           ╱
    │        ╱
    │     ╱
    │  ╱
    └──────────────────────────► offered load
```

When throughput stops rising as load increases, a resource is saturated. Sections 12 to 18 identify which one.

## 10. Query Frequency

How often a statement runs matters as much as how long it takes. Total cost is:

```
total time = calls × mean time
```

| Statement | Calls per day | Mean | Total per day |
|-----------|---------------|------|---------------|
| Product lookup by ID | 9,000,000 | 0.3 ms | 45 min |
| Order history | 400,000 | 4.8 ms | 32 min |
| Daily sales report | 1 | 30 s | 0.5 min |

The 30-second report is the one people notice, but the 0.3 ms lookup costs 90 times more database time. Sort top-SQL lists by **total time** to find the load, and by **mean time** to find what users wait for. They are different lists, and both are useful.

### What high frequency reveals

| Pattern | What it usually means | Fix |
|---------|------------------------|-----|
| Same statement, `rows / calls` ≈ 1, calls ≫ requests | N+1 queries: a loop runs one query per row (Chapter 16, Section 6) | One query with a join, or one batch query |
| Same lookup by the same keys, all day | Data that rarely changes, read repeatedly | Cache it (Chapter 08) |
| `SELECT 1` or similar per request | Connection validation by the pool | Validate on borrow less often, or rely on the driver's check |
| Thousands of statement versions differing in literals | No bind variables | Use bind variables or prepared statements (Chapter 17, Section 7) |

```sql
-- PostgreSQL: frequent statements returning about one row per call
SELECT calls, rows, round(rows::numeric / calls, 1) AS rows_per_call, left(query, 60)
FROM pg_stat_statements
WHERE calls > 100000
ORDER BY calls DESC LIMIT 10;
```

```sql
-- Oracle: the same, plus parse calls
SELECT executions, rows_processed, parse_calls,
       ROUND(rows_processed / NULLIF(executions, 0), 1) AS rows_per_exec,
       SUBSTR(sql_text, 1, 60) AS sql_text
FROM v$sqlstats
WHERE executions > 100000
ORDER BY executions DESC FETCH FIRST 10 ROWS ONLY;
```

In Oracle, `PARSE_CALLS` close to `EXECUTIONS` means the application reparses each time instead of reusing the cursor. Client-side statement caching fixes it.

## 11. Rows Examined and Rows Returned

**Rows returned** is what the statement gives back. **Rows examined** is what it had to read to get there. Their ratio measures efficiency:

```
order history for one customer, returns 10 rows

with index on customer_id         examines 10 rows         ratio 1:1
without index                     examines 1,000,000 rows  ratio 100,000:1
```

A high ratio is the most common sign of a missing or unusable index, or of a predicate that cannot use one (Chapter 16, Section 4). Aggregations are the exception: a `SUM` over 1,000,000 rows legitimately returns one.

Neither database reports rows examined per statement directly. **Blocks read per row returned** is the practical substitute, and it is available in both:

```sql
-- PostgreSQL
SELECT calls, rows,
       round((shared_blks_hit + shared_blks_read)::numeric / nullif(rows, 0), 1) AS blocks_per_row,
       left(query, 60)
FROM pg_stat_statements
WHERE calls > 1000
ORDER BY (shared_blks_hit + shared_blks_read) DESC LIMIT 10;
```

```sql
-- Oracle
SELECT executions, rows_processed,
       ROUND(buffer_gets / NULLIF(executions, 0))     AS gets_per_exec,
       ROUND(buffer_gets / NULLIF(rows_processed, 0)) AS gets_per_row,
       SUBSTR(sql_text, 1, 60) AS sql_text
FROM v$sqlstats
ORDER BY buffer_gets DESC FETCH FIRST 10 ROWS ONLY;
```

| Blocks per row returned | Interpretation (row lookups, not aggregates) |
|-------------------------|-----------------------------------------------|
| Under 5 | Efficient index access |
| 5 to 50 | Acceptable; check for table lookups that a covering index could avoid |
| Hundreds or more | Scanning; find the scan in the plan |

### At table level

```sql
-- PostgreSQL: tables read mostly by sequential scans
SELECT relname, seq_scan, seq_tup_read,
       seq_tup_read / nullif(seq_scan, 0) AS rows_per_seq_scan,
       idx_scan, idx_tup_fetch
FROM pg_stat_user_tables
ORDER BY seq_tup_read DESC LIMIT 10;
```

A large table with many sequential scans of millions of rows each is being scanned by a frequent statement. In Oracle, `V$SEGMENT_STATISTICS` with `statistic_name = 'logical reads'` ranks tables and indexes by reads.

### In a plan

Inside one plan, rows examined appear directly: `Rows Removed by Filter` in PostgreSQL, and in Oracle a large `A-Rows` on a scan step feeding a `filter()` that leaves few rows.

## 12. CPU

When AAS is near the number of cores and sessions are mostly on CPU (Section 2), CPU is the constraint. Before adding cores, find what is using them.

### Measuring

| Level | PostgreSQL | Oracle |
|-------|------------|--------|
| Host | OS tools: `top`, `vmstat` (run queue `r`), `pidstat` | `Host CPU Utilization (%)` in `V$SYSMETRIC`; `V$OSSTAT` |
| Database share | Sessions `active` with no wait event in `pg_stat_activity` | `DB CPU` in `V$SYS_TIME_MODEL`; `ON CPU` in ASH |
| Per statement | Not in core; third-party `pg_stat_kcache`; or `top` on a backend PID, matched in `pg_stat_activity` | `CPU_TIME` in `V$SQLSTATS` |

Each PostgreSQL connection is an operating system process, so `top` sorted by CPU shows the busiest backends. Their PIDs lead to the query in `pg_stat_activity`.

A run queue (`vmstat` column `r`) consistently above the number of cores means processes are waiting for CPU. Their wait does not appear as a database wait event; it shows up only as longer elapsed time with no explanation inside the database.

### Common causes

| Cause | How it shows | Fix |
|-------|--------------|-----|
| Logical reads | High `buffer_gets` or shared hits per execution | Better plans and indexes; read fewer blocks (Section 11) |
| Hard parsing | Oracle: `parse time elapsed` and `hard parse elapsed time` high in `V$SYS_TIME_MODEL`; many literal versions | Bind variables; Oracle `CURSOR_SHARING = FORCE` as a stopgap |
| Planning | PostgreSQL: high `total_plan_time` (with `track_planning`) | Prepared statements; simpler queries over partitioned tables |
| Sorts and hashes | Large sorts and aggregates in top-CPU statements | Indexes that provide order; pre-aggregation (Chapter 07) |
| Too many active sessions | AAS far above cores; context switching | Smaller connection pool (Section 18) |
| Functions per row | PL/SQL or PL/pgSQL called in `WHERE` or `SELECT` for millions of rows | Set-based SQL, or move the call |

Most high CPU in databases is caused by reading too many blocks from memory. A faster plan usually removes more CPU load than faster hardware adds.

## 13. Memory

Database memory falls into two areas (Chapter 05, Section 3):

| Area | Oracle | PostgreSQL | Problem when too small |
|------|--------|------------|------------------------|
| Shared cache | SGA, mainly the buffer cache (`DB_CACHE_SIZE`, or `SGA_TARGET`) | `shared_buffers` plus the OS file cache | More physical reads |
| Per-operation memory | PGA (`PGA_AGGREGATE_TARGET`, hard cap `PGA_AGGREGATE_LIMIT` 12c+) | `work_mem` per sort or hash node, `maintenance_work_mem` | Sorts and hashes spill to temporary files |

Memory problems therefore show up as one of three symptoms: physical reads (Section 14), spills to temp, or the operating system swapping.

### Spills to disk

```sql
-- PostgreSQL: databases and statements writing temporary files
SELECT datname, temp_files, pg_size_pretty(temp_bytes) AS temp_size
FROM pg_stat_database;

SELECT calls, temp_blks_written, left(query, 60)
FROM pg_stat_statements
WHERE temp_blks_written > 0
ORDER BY temp_blks_written DESC LIMIT 10;
```

`log_temp_files = 0` logs every temporary file with its size and the statement that created it. In a plan, a spill shows as `Sort Method: external merge  Disk: 45120kB` or `Batches: 8` under a `Hash` node (Chapter 03, Section 5).

```sql
-- Oracle: how work areas executed
SELECT low_optimal_size / 1024 AS low_kb, (high_optimal_size + 1) / 1024 AS high_kb,
       optimal_executions, onepass_executions, multipasses_executions
FROM v$sql_workarea_histogram
WHERE total_executions > 0;

SELECT name, ROUND(value / 1048576) AS mb
FROM v$pgastat
WHERE name IN ('total PGA allocated', 'maximum PGA allocated', 'over allocation count');
```

| Execution type | Meaning |
|----------------|---------|
| Optimal | Entire sort or hash fitted in memory |
| One-pass | Data was written to temp once and read back once |
| Multi-pass | Written and read several times; very slow, investigate |

A non-zero `over allocation count` means `PGA_AGGREGATE_TARGET` is too small for the workload. `V$PGA_TARGET_ADVICE` and `V$SGA_TARGET_ADVICE` estimate the effect of resizing.

### Overcommitting memory

In PostgreSQL, `work_mem` is allowed **per operation**, and a query can have several sort and hash nodes, in each of several parallel workers, in each of many connections. A setting that looks small can exhaust RAM under load:

```
200 connections × 2 operations × 64 MB  =  25.6 GB  on top of shared_buffers
```

Watch the OS: any regular swapping (`vmstat` columns `si`/`so`) on a database server is a problem. Raise `work_mem` for specific sessions or roles that run large reports, not globally.

## 14. Disk I/O

Chapter 05, Section 4 covers device latencies, IOPS and the Oracle I/O wait events. Analysis needs three numbers from the storage: **how many** operations per second, **how much** data per second, and **how long** each one takes.

| Question | OS (`iostat -x`) | PostgreSQL | Oracle |
|----------|------------------|------------|--------|
| Operations per second | `r/s`, `w/s` | `pg_stat_io` reads and writes (16+) | `Physical Read Total IO Requests Per Sec` in `V$SYSMETRIC` |
| Bytes per second | `rkB/s`, `wkB/s` | `pg_stat_io` (byte columns in 18+) | `Physical Read Total Bytes Per Sec` |
| Time per operation | `r_await`, `w_await` (ms) | `read_time` / `reads` in `pg_stat_io`; `I/O Timings` in plans | Average wait of `db file sequential read`; `V$EVENT_HISTOGRAM` |
| Which statements | | `shared_blks_read`, `shared_blk_read_time` in `pg_stat_statements` | `DISK_READS`, `USER_IO_WAIT_TIME` in `V$SQLSTATS` |
| Which tables | | `heap_blks_read`, `idx_blks_read` in `pg_statio_user_tables` | `physical reads` in `V$SEGMENT_STATISTICS` |

```sql
-- Oracle: average single-block read latency
SELECT event, total_waits,
       ROUND(time_waited_micro / NULLIF(total_waits, 0) / 1000, 2) AS avg_ms
FROM v$system_event
WHERE event IN ('db file sequential read', 'db file scattered read', 'log file sync');
```

### Reading the numbers

| Observation | Likely meaning |
|-------------|----------------|
| Reads per second high, latency normal | The workload reads too much; fix plans or add memory |
| Latency high, utilisation near 100% or provisioned IOPS reached | Storage saturated |
| Latency high at low load | Slow or shared storage; check the volume and other tenants |
| Write latency on the WAL / redo device high | Commits are slow (Chapter 12, Section 7) |

Single-block reads on SSD should take well under 1 ms. If `db file sequential read` or `DataFileRead` averages several milliseconds, the storage is either slow or overloaded. Note that in PostgreSQL a "read" may be served by the OS cache, so `pg_stat_io` read times are often far below device latency.

## 15. Buffer-Cache Hit Ratio

The **buffer-cache hit ratio** is the share of block requests satisfied from memory:

```
hit ratio = logical reads that needed no disk read / all logical reads
```

Chapter 05, Section 3 shows how to compute it in both databases. Oracle also publishes it as `Buffer Cache Hit Ratio` in `V$SYSMETRIC`.

### Why it misleads

The ratio rises when the workload does **more** work from memory, not only when it does less from disk:

| | Logical reads | Physical reads | Hit ratio | Elapsed |
|---|---|---|---|---|
| Good plan | 20,000 | 2,000 | 90.0% | Fast |
| Bad plan, same query | 5,000,000 | 2,000 | 99.96% | Much slower, high CPU |

A bad plan that rereads cached blocks raises the ratio. A large one-off report that reads cold data lowers it, even though nothing is wrong. For this reason, a target hit ratio is not a useful tuning goal.

### How to use it

- **As a baseline.** A sudden drop from the usual value means the working set changed: a new query, data growth or a smaller cache.
- **Per table and per statement**, not per instance. `pg_statio_user_tables` and `shared_blks_hit` / `shared_blks_read` per statement in PostgreSQL; `logical reads` and `physical reads` per segment in Oracle.
- **Together with physical read latency.** A low ratio with fast reads costs little. A falling ratio with rising `db file sequential read` or `DataFileRead` time is worth acting on.

Reducing logical reads (Section 11) is almost always more valuable than raising the ratio.

## 16. Lock Waits

A **lock wait** is time a session spends blocked by another session's lock. Chapter 04, Section 12 shows how to find the current blocker. Analysis also needs the history: how much time is lost to locks, on which objects, and from which statements.

### PostgreSQL

PostgreSQL keeps no cumulative lock-wait time. Use three sources:

```
log_lock_waits = on            # off by default; logs waits longer than deadlock_timeout (1 s)
```

```
LOG:  process 41822 still waiting for ShareLock on transaction 9182736 after 1000.104 ms
DETAIL:  Process holding the lock: 41790. Wait queue: 41822.
CONTEXT:  while updating tuple (1204,7) in relation "products"
STATEMENT:  UPDATE products SET stock = stock - $1 WHERE product_id = $2
```

- The log shows which statement waited, on which table, and who held the lock.
- Sampling `pg_stat_activity` (Section 6) for `wait_event_type = 'Lock'` shows how often sessions are blocked.
- `pg_locks` shows the locks held and awaited right now.

| `wait_event` (type `Lock`) | Waiting for |
|----------------------------|-------------|
| `transactionid` | A row lock: another transaction updated or locked the row and has not committed |
| `tuple` | Queued behind another waiter for the same row |
| `relation` | A table lock, often from DDL such as `ALTER TABLE` |
| `advisory` | An advisory lock taken by the application |

### Oracle

```sql
-- Total time lost to row locks since startup
SELECT event, total_waits, ROUND(time_waited_micro / 1e6) AS seconds
FROM v$system_event
WHERE event LIKE 'enq: TX%' OR event LIKE 'enq: TM%';

-- Which objects have row lock waits
SELECT owner, object_name, value AS row_lock_waits
FROM v$segment_statistics
WHERE statistic_name = 'row lock waits' AND value > 0
ORDER BY value DESC;

-- Who blocked whom in the last hour (ASH)
SELECT sql_id, blocking_session, current_obj#, COUNT(*) AS seconds_waited
FROM v$active_session_history
WHERE event = 'enq: TX - row lock contention'
  AND sample_time > SYSTIMESTAMP - INTERVAL '1' HOUR
GROUP BY sql_id, blocking_session, current_obj#
ORDER BY seconds_waited DESC;
```

| Wait event | Waiting for |
|------------|-------------|
| `enq: TX - row lock contention` | A row locked by another transaction |
| `enq: TX - index contention` | Index block split under concurrent inserts (Chapter 04, Section 12) |
| `enq: TM - contention` | Table lock; often an unindexed foreign key during parent deletes or updates |

### Limiting the damage

| Setting | Oracle | PostgreSQL |
|---------|--------|------------|
| Fail instead of waiting | `SELECT ... FOR UPDATE WAIT n` / `NOWAIT` | `lock_timeout` |
| End idle transactions that hold locks | `MAX_IDLE_BLOCKER_TIME` (19c+, minutes) | `idle_in_transaction_session_timeout` (9.6+) |
| Cap a whole transaction | Resource Manager | `transaction_timeout` (17+) |

A blocker in state `idle in transaction` (PostgreSQL) or `INACTIVE` with an open transaction (Oracle) is not doing any work. The application opened a transaction and has not finished it. That is a code defect, not a database setting to tune.

## 17. Deadlocks

A **deadlock** is a cycle of lock waits that cannot resolve itself. The database detects it and cancels one statement (Chapter 04, Section 8). For analysis, you need to know how often deadlocks occur and which statements are involved.

### Counting

```sql
-- PostgreSQL
SELECT datname, deadlocks FROM pg_stat_database;

-- Oracle
SELECT name, value FROM v$sysstat WHERE name = 'enqueue deadlocks';
```

Any non-zero rate deserves investigation. Deadlocks are almost always caused by the application locking rows in different orders.

### Reading the details

**PostgreSQL** always logs a deadlock, with the statements of each process in the cycle:

```
ERROR:  deadlock detected
DETAIL:  Process 41822 waits for ShareLock on transaction 9182740; blocked by process 41790.
         Process 41790 waits for ShareLock on transaction 9182736; blocked by process 41822.
         Process 41822: UPDATE products SET stock = stock - 1 WHERE product_id = 17
         Process 41790: UPDATE products SET stock = stock - 1 WHERE product_id = 3
HINT:  See server log for query details.
```

**Oracle** raises `ORA-00060: deadlock detected while waiting for resource` in the session that is rolled back, writes a message to the alert log, and writes a **deadlock graph** to a trace file:

```
Deadlock graph:
                       ------------Blocker(s)-----------  ------------Waiter(s)------------
Resource Name          process session holds waits serial  process session holds waits serial
TX-000A0013-00004C2D        47     214     X        3391        52     188           X  1207
TX-00080021-00003A19        52     188     X        1207        47     214           X  3391
```

| Field | Meaning |
|-------|---------|
| `TX-...` | A row lock (transaction enqueue); each row is one resource in the cycle |
| `holds X` / `waits X` | Exclusive mode held and requested: the classic row-level deadlock |
| `holds X` / `waits S` on `TX` | Often an index-related wait, such as a unique key or bitmap index conflict |
| `TM-...` resource | A table lock; frequently an unindexed foreign key |

The trace file also lists the SQL each session was running and the `rowid` it waited for.

Both examples show the same defect: two checkouts updating products 3 and 17 in opposite orders. The fix is to update rows in a consistent order, such as by `product_id`.

## 18. Connection Utilisation

Each connection uses server memory and, in PostgreSQL, a whole process. The number of connections that are **busy** at once, not the number that exist, determines load.

### Measuring

```sql
-- PostgreSQL: connections by state
SELECT state, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state;

SHOW max_connections;   -- default 100
```

```
 state               | count
---------------------+-------
 idle                |   412
 active              |     9
 idle in transaction |    23
```

```sql
-- Oracle: current and peak use against limits
SELECT resource_name, current_utilization, max_utilization, limit_value
FROM v$resource_limit
WHERE resource_name IN ('processes', 'sessions');

SELECT status, COUNT(*) FROM v$session WHERE type = 'USER' GROUP BY status;
```

| Metric | Healthy | Problem |
|--------|---------|---------|
| Active connections | Around the number of CPU cores or fewer | Many times the core count: CPU and lock contention |
| Idle connections | Some, held by pools | Hundreds per server: memory per connection, PostgreSQL snapshot overhead |
| Idle in transaction | Near zero, briefly | Persistent: locks held, vacuum held back (Chapter 04, Section 12) |
| Peak vs limit | Peak well below `max_connections` / `PROCESSES` | Near the limit: new connections fail |
| New connections per second | Low; pools reuse connections | High: each connection costs a process start and authentication |

In the example, 412 idle connections serve 9 active ones. The application pools are much larger than the work requires.

Oracle's `logons cumulative` in `V$SYSSTAT` and PostgreSQL's `sessions` in `pg_stat_database` (14+) count new connections. A fast-rising count means the application connects per request instead of using a pool.

### From measurement to action

Little's law (Section 9) turns these measurements into a target: 2,000 statements per second at 5 ms each keeps about 10 connections busy on average. A pool somewhat above that absorbs bursts. Beyond the point where CPU or storage is saturated, more connections only add queueing inside the database. When the pool is too small, the application waits for a connection; that wait is invisible to the database and shows only in end-to-end latency (Section 8) and in the pool's own metrics.

Chapter 17 covers what to do with these numbers: pool types and PgBouncer modes (Section 3), pool sizing (Section 4), idle connections (Section 6) and saturation (Section 10).

## 19. A Systematic Approach to Performance Analysis

```
1. Define the symptom
   which request, since when, how slow (p50/p99), for whom
        │
        ▼
2. Is the time in the database?
   compare end-to-end latency with database time for that request
        │
        ├── No ──► application, network or pool wait            Section 18; Chapter 19
        │
        ▼
3. How busy is the database?
   AAS vs CPU cores; throughput vs normal
        │
        ▼
4. Where does database time go?
   Oracle:      ASH / AWR top events, ON CPU vs WAITING
   PostgreSQL:  sampled pg_stat_activity wait events
        │
        ├── CPU ────────────► top SQL by CPU / blocks              Sections 11, 12
        ├── I/O ────────────► top SQL by physical reads; latency   Sections 14, 15
        ├── Lock ───────────► blockers, objects, idle-in-txn       Sections 16, 17
        ├── Commit / WAL ───► commit rate, log device latency      Chapter 12
        └── Client ─────────► round trips, frequency               Section 10
        │
        ▼
5. Which statements?
   pg_stat_statements / V$SQLSTATS: by total time, then by mean time;
   check calls, rows per call, blocks per row, temp blocks
        │
        ▼
6. Why is that statement slow?
   actual plan: EXPLAIN (ANALYZE, BUFFERS), DISPLAY_CURSOR, SQL Monitor,
   auto_explain output for the slow executions                     Section 3
        │
        ▼
7. Fix at the right layer                                          Chapter 19
        │
        ▼
8. Measure again against the baseline: same metrics, same load
```

Steps 3 and 4 are the ones most often skipped. Going straight to the slowest query finds a slow query, but not necessarily the one that explains the symptom.

## 21. Short Summary

- Measure where database time goes before changing anything. Time on CPU and time in each wait event point to different fixes.
- Cumulative counters are meaningful only as deltas over a known interval; AWR does this for Oracle, a monitoring tool or saved snapshots for PostgreSQL.
- `pg_stat_statements` and `V$SQLSTATS` are the starting point for finding which statements matter. Rank by total time for load and by mean time for user-facing slowness.
- Statement averages hide outliers. Capture individual slow executions and their plans with `log_min_duration_statement`, `auto_explain`, SQL Monitor or SQL trace.
- ASH in Oracle, and sampled `pg_stat_activity` in PostgreSQL, explain what happened at a specific moment, including who blocked whom.
- Track latency as percentiles at both the application and the database. The gap between them is pool wait, network and application time.
- Little's law links throughput, latency and concurrency. It sizes connection pools and explains why latency rises sharply near saturation.
- Blocks read per row returned exposes inefficient statements better than the buffer-cache hit ratio, which can rise while performance gets worse.
- Lock waits and deadlocks are usually application defects: long or idle transactions and inconsistent locking order. Measure them, then fix the code path.
- Connection utilisation is about busy connections, not open ones. Hundreds of idle or idle-in-transaction sessions point to oversized pools or unfinished transactions, not to a need for more capacity.
