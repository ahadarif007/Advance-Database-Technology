# Chapter 19: End-to-End Performance Diagnosis

A database request passes through many layers before it touches a disk, and each layer can add time. The application decides how many statements to send. The ORM decides what SQL they contain. The optimizer chooses a plan, the plan chooses indexes, the indexes are read through a cache, the cache is filled by a storage engine, and the storage engine reads from a device. A slow request can be caused at any of these layers, and a fix at the wrong one changes nothing.

This chapter traces one slow application request, a customer's order history page, from the application through the ORM, connection pool, SQL statement, execution plan, indexes and cache down to storage. For each layer it shows what that layer decides, where delays typically arise, what evidence identifies them, and how to fix them in **Oracle** and **PostgreSQL**, with references to the chapters that cover each topic in depth.

## 1. The Layered Model

```
Application              how many requests, how many statements per request,
     ↓                   how long connections and transactions are held
ORM / SQL generation     which SQL text is produced, bind variables, fetch strategy
     ↓
SQL query                what is asked for, and whether it can be optimised
     ↓
Query optimizer          estimates rows, prices alternatives, picks a plan
     ↓
Execution plan           join methods, access paths, memory, parallelism
     ↓
Indexes                  how many blocks must be read to find the rows
     ↓
Buffer / cache           whether those blocks are already in memory
     ↓
Storage engine           row layout, MVCC versions, logging, bloat
     ↓
Disk / SSD               latency, IOPS and throughput of the device
```

Two properties of this stack shape every tuning decision:

- **Work multiplies downwards.** One extra statement per row in the application becomes thousands of plans, millions of block reads and many physical I/Os.
- **Fixes near the top remove work. Fixes near the bottom make the same work faster.** Removing a statement saves all the work below it. A faster disk speeds up only the part of the time spent on the disk.

That is why rewriting SQL syntax alone is often not enough. The SQL text is one layer of nine.

## 2. Sample Scenario: A Slow Page

The shop from Chapter 01 has an **order history page**: a customer's 20 most recent orders, each with its items and product names.

```
customers (1) ───< orders (N) ───< order_items (N) >─── (1) products
```

For most customers the page is fast. For business customers, who have tens of thousands of orders, it takes **1.8 seconds** at peak times. Measuring each layer (Chapter 18, Section 19) gives this breakdown:

```
Layer                         Time      Finding
────────────────────────────  ────────  ───────────────────────────────────────────────
Application: pool wait         700 ms   10 connections; each held during a 300 ms call
                                        to an external payment-status service
ORM: 82 statements             160 ms   lazy loading: 1 + 1 + 20 + 60 statements,
                                        about 2 ms per round trip
Orders query                   900 ms   index on customer_id only: reads all 50,000
                                        orders of the customer, sorts, keeps 20
Rendering and other             40 ms
                              ────────
                              1,800 ms
```

```
pool wait  ██████████████████████████████████████                    700 ms
ORM trips  █████████                                                 160 ms
orders     ██████████████████████████████████████████████████        900 ms
other      ██                                                         40 ms
```

Only one of the three causes is inside the database, and none of them would be fixed by rewriting the SQL text. Sections 3, 4 and 8 fix them, and the page drops to about 30 ms.

## 3. The Application Layer

The application decides **how often** the database is called and **how long** it holds resources. These decisions set an upper bound on performance before any SQL runs. Chapter 17 covers this layer in detail.

### Round trips

Every statement costs at least one network round trip, from about 0.1 ms within an availability zone to tens of milliseconds across regions (Chapter 17, Section 8). At 2 ms per round trip, the scenario's 82 statements cost 164 ms of waiting even if each one executes in no time. Reducing the number of statements usually helps more than speeding each one up.

| Problem | Fix | Covered in |
|---------|-----|------------|
| One statement per row in a loop | A join, a batch query, or batched writes | Chapter 16, Section 6; Chapter 12, Section 3 |
| Large results fetched in many small batches | Raise the fetch size (Oracle JDBC defaults to 10 rows) | Chapter 17, Section 8 |
| Same data read on every request | Cache it in the application or Redis | Chapter 08 |
| Counting or filtering in application code after fetching everything | Push the filter or aggregate into SQL | Chapter 15 |
| `OFFSET` pagination deep into a result | Keyset pagination | Chapter 01, Section 11 |

### Connections and transactions held too long

In the scenario, each request takes a connection at the start and returns it at the end, including during a 300 ms call to an external service. With 10 connections, at most about 30 requests per second can complete. Requests beyond that wait for a connection.

```
Before:  [get conn]─ query ─ HTTP call (300 ms) ─ query ─[release]     conn held ~320 ms
After:   [get conn]─ query ─[release]  HTTP call  [get conn]─ query ─[release]
                                                                        conn held ~20 ms
```

Moving the external call outside the transaction removes the pool wait entirely, without changing a single statement. Chapter 17, Section 9 covers the common causes of long transactions, and Section 4 of that chapter covers pool sizing.

### How to see it

| Signal | Oracle | PostgreSQL |
|--------|--------|------------|
| Many round trips | `SQL*Net roundtrips to/from client` in `V$SESSTAT` | `calls` per request in `pg_stat_statements` |
| Session waiting for the application | `SQL*Net message from client` in `V$SESSION` | `state = 'idle'` or `wait_event = 'ClientRead'` |
| Transaction left open | `INACTIVE` session with a row in `V$TRANSACTION` | `idle in transaction` |
| Requests waiting for a connection | Pool metrics in the application (not visible in the database) | As Oracle |

## 4. The ORM and SQL Generation Layer

An **ORM** (object-relational mapper, such as Hibernate, Entity Framework, Django ORM or Active Record) generates SQL from application objects. It saves code but hides the SQL, so its defaults decide the number and shape of statements.

### N+1 queries

The scenario's page code reads naturally:

```
customer = load customer 42
for order in customer.orders (latest 20):        ← 1 query for the orders
    for item in order.items:                     ← 1 query per order    (20)
        show item.product.name                   ← 1 query per item     (60)
```

With **lazy loading**, each related object is fetched the first time code accesses it, one statement at a time: 1 + 1 + 20 + 60 = 82 statements. This is the **N+1 problem** (Chapter 16, Section 6, which also lists the eager and batch loading options of each ORM). With batch fetching the page sends three statements, however many orders and items it shows:

```sql
SELECT ... FROM orders      WHERE customer_id = $1 ORDER BY order_date DESC LIMIT 20;
SELECT ... FROM order_items WHERE order_id   = ANY($1);   -- 20 ids
SELECT ... FROM products    WHERE product_id = ANY($1);   -- up to 60 ids
```

The page has two levels of one-to-many data (orders, then items), so a batch query per level is better than a single join, which would repeat each order's columns on every item row.

### Other ORM defaults that matter

| Default | Effect | Fix | Covered in |
|---------|--------|-----|------------|
| Loading whole entities | Wider rows, no index-only scans, more memory | Projections (DTO queries, `values()`) for read-only pages | Chapter 16, Section 3 |
| `IN` lists built from collections | A new statement text per list length; 1,000-item limit in Oracle (ORA-01795) | One array or collection parameter; Hibernate `in_clause_parameter_padding` | Chapter 16, Section 8 |
| Automatic count query for each page | A `COUNT(*)` over the whole result on every page | Skip the total, or fetch one extra row to detect a next page | |
| Bind type differs from column type | Conversion applied to the column; index not used | Map application types to column types exactly (below) | Chapter 16, Section 4 |
| Statement caching off | Parse on every execution | Driver statement cache; prepared statements | Chapter 17, Section 7 |

**Type mismatches** are easy to miss because the generated SQL looks correct. Two that come from driver and ORM mappings rather than from hand-written SQL:

| Database | Mismatch | What the plan shows |
|----------|----------|---------------------|
| Oracle | `VARCHAR2` column, driver sends strings as `NVARCHAR2` (for example with `oracle.jdbc.defaultNChar=true`) | `filter(SYS_OP_C2C("EMAIL")=:1)`, full scan |
| PostgreSQL | `bigint` column, `numeric` parameter (for example a Java `BigDecimal`) | `Filter: ((customer_id)::numeric = $1)`, sequential scan |

### Making generated SQL traceable

Tag each connection with the code that uses it, so statements seen in the database can be traced back to the application:

```sql
-- Oracle: appears in V$SESSION, ASH and V$SQL (MODULE, ACTION)
EXEC DBMS_APPLICATION_INFO.SET_MODULE(module_name => 'order-history', action_name => 'load');
```

```sql
-- PostgreSQL: appears in pg_stat_activity and the log (%a in log_line_prefix)
SET application_name = 'order-history';
```

Most drivers set these through connection properties, which avoids an extra statement per request. Turning on the ORM's SQL logging in development shows the statements each page sends, which is the simplest way to find N+1 before it reaches production.

## 5. The SQL Query Layer

Once the statement count is right, the content of each statement matters. Chapter 01 covers query optimisation in depth, and Chapter 16 the most common anti-patterns. The principles that resolve most cases:

| Principle | Example | Covered in |
|-----------|---------|------------|
| Keep indexed columns free of functions and conversions | Range on `order_date` instead of `EXTRACT(YEAR ...)` | Chapter 16, Section 4 |
| Ask only for what is needed | Named columns; `EXISTS` instead of `COUNT(*) > 0` | Chapter 16, Section 3; Chapter 01, Section 11 |
| Replace per-row subqueries with joins or window functions | One pass instead of a lookup per row | Chapter 16, Section 9 |
| Use set-based statements, not row-by-row loops | One `UPDATE ... FROM` instead of a cursor loop | Chapter 12, Section 6 |
| Use semi- and anti-joins correctly | `NOT EXISTS` instead of `NOT IN` | Chapter 03, Sections 8 – 9 |
| Let the optimizer see the whole query | Avoid materialised CTEs that block pushdown | Chapter 01, Section 10 |
| Paginate by key | `WHERE order_id > :last_id` | Chapter 01, Section 11 |

Row-by-row processing in stored code is the database-side form of N+1:

```sql
-- PL/pgSQL or PL/SQL loop: one UPDATE per row
FOR r IN (SELECT order_id FROM orders WHERE status = 'PENDING' AND order_date < DATE '2025-01-01') LOOP
    UPDATE orders SET status = 'CANCELLED' WHERE order_id = r.order_id;
END LOOP;

-- One statement does the same work
UPDATE orders SET status = 'CANCELLED'
WHERE status = 'PENDING' AND order_date < DATE '2025-01-01';
```

The rewrite is valuable only if the statement is one that matters. Find it first with statement statistics (Chapter 18, Section 4).

## 6. The Query Optimizer Layer

The optimizer turns the SQL into a plan. It does not see the data, only statistics about it (Chapter 01, Sections 12 – 13). Inaccurate row estimates are one of the most frequent sources of poor plans, which makes this layer a common place to look.

| Problem | Symptom | Fix |
|---------|---------|-----|
| Stale statistics after data changes | Estimates far below actual rows; plan change after a load | Gather statistics after bulk changes; tune automatic collection |
| Skewed values | Same plan for rare and common values | Histograms (Oracle `SIZE AUTO`; PostgreSQL MCV lists, `SET STATISTICS`) |
| Correlated columns | Underestimates with several predicates | Extended statistics (`CREATE_EXTENDED_STATS`, `CREATE STATISTICS`) |
| Bind-sensitive statements | Same SQL fast for some values, slow for others | Adaptive cursor sharing (Oracle); `plan_cache_mode` (PostgreSQL) |
| Plan changed for no visible reason | `PLAN_HASH_VALUE` change in AWR; regression after upgrade | Plan stability tools (below) |

The scenario shows the bind-sensitive case. The orders query is fast for a customer with 10 orders and slow for one with 50,000. A histogram on `customer_id` lets the optimizer know some customers are much larger than average, but here no plan with the existing index is good for the large customer. The fix belongs to the index layer (Section 8).

### Plan stability

| Need | Oracle | PostgreSQL |
|------|--------|------------|
| Keep a known good plan | SQL Plan Management: SQL plan baselines (`DBMS_SPM`) | Not built in; `pg_hint_plan` hint table |
| Correct estimates for one statement | SQL Profiles (SQL Tuning Advisor, Tuning Pack) | Extended statistics; rewrite |
| Add a hint without changing the code | SQL Patch (`DBMS_SQLDIAG.CREATE_SQL_PATCH`, 12.2+) | `pg_hint_plan` hint table |
| Keep old optimizer behaviour after upgrade | `OPTIMIZER_FEATURES_ENABLE` | Not available; test before upgrading |

Stabilise a plan only after statistics are right. A fixed plan does not adapt as data grows.

## 7. The Execution Plan Layer

The plan decides **how** the work runs: join methods, access paths, memory and parallelism. Chapters 03 and 13 cover joins and access paths. This layer also includes resources given to each operation.

| Decision | Problem | Signal | Fix |
|----------|---------|--------|-----|
| Join method | Nested loop with very high `loops` / `Starts` | Inner node executed thousands of times | Correct estimates; index on the inner join key (Chapter 03) |
| Access path | Full scan for few rows, or index scan for many | Rows examined far above rows returned | Chapter 13, Section 12 |
| Sort / hash memory | Spill to temp | `external merge`, `Batches > 1`, one-pass or multi-pass work areas | Raise `work_mem` per session; PGA size (Chapter 18, Section 13) |
| Parallelism | Large scan runs on one core, or OLTP query runs in parallel | `Gather` / `PX` nodes missing or unexpected | PostgreSQL `max_parallel_workers_per_gather` (default 2); Oracle `PARALLEL` hint or table degree |
| JIT compilation (PostgreSQL 11+, on by default from 12) | Short query spends more time compiling than executing | `JIT: ... Timing: ... Total` in `EXPLAIN ANALYZE` | Raise `jit_above_cost` (default 100000) or set `jit = off` for OLTP |

Oracle's `PARALLEL_DEGREE_POLICY` defaults to `MANUAL`, so statements run in parallel only when a hint or a table's degree asks for it. PostgreSQL decides automatically from table size (`min_parallel_table_scan_size`, default 8 MB).

## 8. The Index Layer

Indexes decide how many blocks must be read to find the rows. Chapter 02 covers index design, and Chapter 13 covers when an index is used.

In the scenario, the orders query is:

```sql
SELECT order_id, order_date, status, total_amount
FROM orders
WHERE customer_id = $1
ORDER BY order_date DESC
LIMIT 20;
```

With an index on `customer_id` only, the database finds all 50,000 orders of the business customer, reads 50,000 table rows scattered across the table, sorts them and keeps 20.

```
idx(customer_id)              idx(customer_id, order_date DESC)

find 50,000 entries           find the customer, walk 20 entries in date order
read 50,000 table rows        read 20 table rows
sort 50,000 rows              no sort
keep 20                       stop after 20
≈ 900 ms                      ≈ 1 ms
```

```sql
-- Both databases
CREATE INDEX idx_orders_cust_date ON orders (customer_id, order_date DESC);
```

The old single-column index is now redundant, because the new index starts with the same column. Dropping it saves write cost (Chapter 12, Section 9).

| Index decision | Effect | Covered in |
|----------------|--------|------------|
| Column order in composite indexes | Equality columns first, then range or sort columns | Chapter 02, Section 5 |
| Covering indexes | Index-only access, no table reads | Chapter 02, Section 6 |
| Expression and partial indexes | Support functions and frequent filters | Chapter 02, Sections 10 – 11 |
| Too many indexes | Every write updates every index | Chapter 12, Section 9 |

## 9. The Buffer and Cache Layer

Blocks are read through the buffer cache (Chapter 05, Section 3). Higher up, results can be cached by the database or the application (Chapter 08).

```
application cache (Redis, in-process)     avoids the database call entirely
        ↓ miss
database result cache (Oracle)            avoids executing the statement
        ↓ miss
buffer cache / shared_buffers             avoids a read from storage
        ↓ miss
OS file cache (PostgreSQL mainly)         avoids a read from the device
        ↓ miss
storage
```

| Problem | Signal | Fix |
|---------|--------|-----|
| Working set larger than the cache | Physical reads and read latency rising with data growth | Read fewer blocks first (Section 8); then more memory |
| One large scan evicts hot data | Hit ratio drops during reports | Both databases read large scans through a small ring or direct path, so this is uncommon; check for repeated scans |
| Same data read many times per second | High `calls` on a lookup of static data | Application cache (Chapter 08) |
| Cache sized without regard to the OS | PostgreSQL: `shared_buffers` set to most of RAM leaves little for the OS cache and `work_mem` | A starting point of about 25% of RAM for `shared_buffers` |
| Large memory areas paged in small pages | High system CPU, slow connections | Huge pages (`USE_LARGE_PAGES` in Oracle, `huge_pages` in PostgreSQL) |

A bigger cache helps only when the cause is physical reads of data that is reused. It does not help a query that reads too many blocks from memory (Chapter 18, Section 15).

## 10. The Storage Engine Layer

The storage engine decides how rows are laid out, how old versions are kept for MVCC, and how changes are logged (Chapters 04 and 05).

| Problem | Oracle | PostgreSQL | Covered in |
|---------|--------|------------|------------|
| Oversized types, wide rows, random keys | More blocks per row; random `SYS_GUID()` keys scatter index inserts | More blocks per row; random UUID keys scatter index inserts | Chapter 14 |
| Old row versions | Kept in undo; long queries can fail with `ORA-01555: snapshot too old` | Kept in the table as dead rows; tables bloat if vacuum falls behind | Chapter 04, Section 3 |
| Vacuum or undo pressure | `UNDO_RETENTION`, undo tablespace size | Autovacuum settings per table; long transactions block cleanup | Chapter 05 |
| Rows spread over too many blocks | Row migration and chaining; `PCTFREE` | Non-HOT updates; `fillfactor` | Chapter 05, Section 9; Chapter 12, Section 9 |
| Physical order unrelated to access | Clustering factor; index-organised tables | `correlation`; `CLUSTER` | Chapter 02, Section 13 |
| Huge tables, queries on recent data | Partitioning with pruning | Declarative partitioning | Chapter 06 |
| Analytic scans over row storage | Database In-Memory column store (option); Hybrid Columnar Compression on Exadata | No built-in column store; extensions | Chapter 05, Section 11 |
| Log volume on writes | `NOLOGGING`, direct path | `UNLOGGED`, fewer full-page images | Chapter 12, Section 7 |

```sql
-- PostgreSQL: tables with the most dead rows, and when they were last vacuumed
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 10;
```

Problems at this layer grow slowly. A table that bloats by 1% a day is fine in the first week and slow by the end of the year, so trends matter more than single readings.

## 11. The Disk and SSD Layer

The device sets the floor for any work that is not served from memory (Chapter 05, Sections 4 – 5).

| Problem | Signal | Fix |
|---------|--------|-----|
| Provisioned IOPS or throughput reached (cloud) | Latency rises at a fixed I/O rate; volume metrics at their cap | Larger or faster volume, or fewer reads (higher layers) |
| Slow commit log device | `log file sync` / `log file parallel write` (Oracle), `WALSync` / `WALWrite` (PostgreSQL) | Low-latency storage for redo or WAL, separate from data files (Chapter 12, Section 7) |
| Checkpoint spikes | Periodic latency peaks with write bursts | PostgreSQL: larger `max_wal_size` (default 1 GB), `checkpoint_completion_target` (0.9); Oracle: larger redo logs, fewer log switches |
| HDD-era cost settings on SSD | Full scans chosen where index access is faster | PostgreSQL `random_page_cost` about 1.1; Oracle system statistics (Chapter 13, Section 10) |

Faster storage helps a workload that is already efficient and still limited by I/O. For an inefficient workload, it gives a moderate gain at high cost, while a fix in a higher layer gives a large gain at low cost.

## 12. Beyond a Single Server

When one well-tuned server is not enough, the remaining options change the architecture rather than a layer:

```
Tune layers 3–11 on one server
        ↓ still not enough
Precompute expensive results        materialised views, summary tables    Chapter 07
        ↓
Cache in front of the database      Redis, application cache              Chapter 08
        ↓
Scale reads                          read replicas                         Chapter 09
        ↓
Scale writes and storage            sharding                              Chapter 10
        ↓
Accept distributed trade-offs       consistency, consensus, 2PC           Chapter 11
```

Each step adds operational cost and new failure modes, such as stale caches, replication lag and cross-shard queries. Each is justified only after the layers above have been addressed. A replica does not fix an N+1 problem. It runs the same 82 statements in a second place.

## 13. How the Layers Interact

### The size of the gain depends on the layer

| Fix | Layer | Typical effect |
|-----|-------|----------------|
| Remove N+1 statements | ORM | 10 – 100x fewer round trips |
| Release connections before external calls | Application | Removes pool waits entirely |
| Add the right composite index | Index | 100 – 10,000x fewer blocks for that query |
| Correct the statistics | Optimizer | From a pathological plan to a normal one |
| More memory | Cache | Fewer physical reads, if the data is reused |
| Faster storage | Disk | 2 – 5x on I/O time only |

The values are typical orders of magnitude, not guarantees. The pattern is consistent: the higher the layer, the more work a fix removes.

### Fixes at one layer can hide problems at another

| Masking fix | What it hides | When it fails |
|-------------|---------------|---------------|
| Application cache | A slow query | On a cache miss, expiry or stampede (Chapter 08, Section 12) |
| More buffer cache | A missing index | When data outgrows memory |
| Faster storage | Full scans that should be index reads | When load or data grows |
| Larger connection pool | Slow statements or held connections | At saturation, when more sessions add contention |
| Read replicas | Inefficient reads | When replicas saturate too, or lag grows |

### Fixes can move the problem

- Replacing 82 small statements with one join produces a larger statement that now needs good indexes on the join keys (Chapter 03, Section 4).
- An index that speeds up a read slows down every write to that table (Chapter 12, Section 9).
- Partitioning by date speeds up queries on recent data and slows down queries without a date filter, which must visit every partition (Chapter 06, Section 8).

After any fix, measure the whole request again, not just the part that was changed.

## 15. A Systematic Approach: Top-Down Diagnosis

```
1. Measure the request end to end; record p50 and p99            Chapter 18, Section 8
        │
        ▼
2. Split the time by layer
   pool wait, statement count × round trip, database time, other
        │
        ▼
3. Start at the highest layer with significant time
        │
        ├── Application ──► connections or transactions held during
        │                   external calls? fetch size? caching?            Section 3
        │
        ├── ORM ──────────► statements per request? N+1? type mismatches?
        │                   literals instead of binds?                       Section 4
        │
        └── Database ─────► which statement? (statement statistics)
                │
                ▼
4. For that statement, read the actual plan
        │
        ├── estimates wrong ─────────────► statistics, histograms          Section 6
        ├── wrong join / access path ────► estimates, then indexes         Sections 7, 8
        ├── spills, parallelism, JIT ────► memory and plan settings        Section 7
        └── plan fine, still slow ───────► waits: cache, storage engine,
                                           disk, locks                       Sections 9 – 11
        │
        ▼
5. Fix at the highest layer that removes the work
        │
        ▼
6. Re-measure the whole request; check for problems moved elsewhere   Section 13
        │
        ▼
7. Only when one tuned server is not enough: scale out                 Section 12
```

| Cache | Buffer cache | `DB_CACHE_SIZE`, `SGA_TARGET` | `shared_buffers`, `effective_cache_size` |
| Cache | Result cache | `RESULT_CACHE` hint, `RESULT_CACHE_MODE` | Not built in |
| Cache | Huge pages | `USE_LARGE_PAGES` | `huge_pages` |
| Storage engine | Old row versions | Undo (`UNDO_RETENTION`) | Dead rows, VACUUM |
| Storage engine | Free space per block | `PCTFREE` | `fillfactor` |
| Disk | Commit log waits | `log file sync`, `log file parallel write` | `WALSync`, `WALWrite` |
| Disk | Checkpoint sizing | Redo log file size | `max_wal_size`, `checkpoint_timeout` |
| Disk | I/O cost calibration | System statistics | `random_page_cost`, `effective_io_concurrency` |

## 17. Short Summary

- A request passes through nine layers, from the application to the disk. Each can add time, and a fix only helps at the layer where the time is spent.
- Work multiplies downward. Fixes at higher layers remove work; fixes at lower layers make the same work faster, usually by a smaller factor.
- The application layer sets the number of round trips and how long connections and transactions are held. Pool waits and round trips are invisible inside the database.
- ORMs decide the shape of the SQL. N+1 queries, type mismatches between binds and columns, and varying `IN` lists are the most common problems they introduce.
- Inside the database, wrong row estimates explain most bad plans. Fix statistics before indexes or hints, and stabilise plans only once estimates are right.
- An index that matches both the filter and the sort order can turn a query that reads thousands of blocks into one that reads a few.
- Memory, storage-engine settings and faster disks help efficient workloads that are still limited by resources. They mask inefficient ones until data or load grows.
- Every fix can move the problem: a join replacing N+1 needs indexes, an index slows writes, partitioning slows queries without the partition key. Measure the whole request again after each change.
- Scale out with caches, replicas or shards only after a single server is well tuned.
